<Warning>Ahead-of-time compilation is experimental.</Warning>

[`--aot`](/bundler/executables#ahead-of-time-compilation) does not erase your TypeScript types. It uses them to generate machine code, so it also holds your program to them:

- A value that does not match its type throws a `TypeError` at the first parameter, variable, property or return type that it reaches.
- A parameter that its function never reads is not checked: nothing depends on its type. The check is there as soon as the function reads the parameter or passes it on.
- `value as number` converts: if `value` is `"4"` when the program runs, the result is `4`. The same goes for `as string` and `as boolean`.
- The result of a call in tail position, `return f(x)` or `return f(x) as number` in a strict-mode function, is checked, and converted by the `as`, where it is received as a type, not in the function that returns it: that function's stack frame is gone by then. A caller that takes any value, such as `Array.prototype.map` or JavaScript code, gets what `f` returned, as without `--aot`.
- `{ name: "x" } as User` is not checked at the cast. If the literal lacks a property of `User`, the `TypeError` comes later, when your code reads a missing `number`, `boolean` or numeric enum property. Any other missing property reads `undefined`, as in JavaScript.
- Built-in objects are immutable.

Most programs have a few places where data from outside the type system, such as `JSON.parse`, `any` or an untyped package, is not what its type says. Four tools find them. Use them in this order:

| Step | Command                                                    | Where                 | Your program                           |
| ---- | ---------------------------------------------------------- | --------------------- | -------------------------------------- |
| 1    | `bun --aot-audit`, `bun test --aot-audit`                  | development, CI       | runs as usual, and logs                |
| 2    | `bun check --aot`, `bun check --aot --aot-explain=throws`  | CI, every build       | is not run                             |
| 3    | `bun build --compile --aot --aot-type-errors=log`          | production            | is compiled, logs, and keeps going where it can |
| 4    | `bun build --compile --aot`                                | production            | is compiled, and throws                |

Before you run anything, [`bun lint --aot`](/lint#before-you-compile-with-aot) reads your source and lists where data without a type enters your program, and where it reaches a type.

The examples use this program:

```ts app.ts icon="/icons/typescript.svg"
function double(n: number): number {
  return n * 2;
}

const body: any = JSON.parse('{"visits":"3"}');
console.log(double(body.visits));
console.log((body.visits as number) + 1);
```

```bash terminal icon="terminal"
bun app.ts
```

```txt
6
31
```

`bun run --aot` runs the program from its sources under the rules of `bun build --compile --aot`. It is the shortest way to see what changes:

```bash terminal icon="terminal"
bun run --aot app.ts
```

```txt
6 | console.log(double(body.visits));
                       ^
TypeError: expected number | undefined, got string "3" (bun --aot: https://bun.com/docs/bundler/executables#ahead-of-time-compilation)
      at /path/to/app.ts:6:20
```

`number | undefined` is what passes this check: `undefined` passes too, as a missing argument does in JavaScript.

It stops at the first error. The tools below show all of them, without stopping your program.

## 1. Audit while you develop

`--aot-audit` runs your program the way Bun always does, and writes a line to stderr at the places where it would behave differently under `--aot`.

```bash terminal icon="terminal"
bun --aot-audit app.ts
```

```txt
[aot] type-error 81eda900c1a1 read-property app.ts:6:20 (module): expected number | undefined, got string; would-throw; count 1; call 4d3156b73eaf
6
[aot] type-error 0d0dde539306 as-convert app.ts:7:14 (module): expected number, got string; would-convert; count 1
31
```

The output of your program does not change. Run your tests the same way, and keep it on while you edit:

```bash terminal icon="terminal"
bun test --aot-audit
bun --watch --aot-audit app.ts
bun --hot --aot-audit server.ts
```

Each line ends with what an `--aot` build would do:

| Action          | Under `--aot`                                                        |
| --------------- | -------------------------------------------------------------------- |
| `would-throw`   | a `TypeError` is thrown here                                         |
| `would-convert` | `as` converts the value, so the program goes on with another value   |
| `would-refuse`  | this write to a built-in object throws a `TypeError`                 |

An `--aot` build stops at the first `TypeError` that your program does not catch. The audit goes on, so a later line tells you what happens once the earlier ones are fixed.

Fix `would-convert` lines first. The audit does not convert, so the value continues unchanged. To avoid false lines, the audit does not report a value that `as` has converted when it fails a later check, nor an equal value from somewhere else.

Bun type checks and analyzes the whole program before it starts, so the first start takes longer. After you save a file, Bun analyzes that file alone before it reloads, and the rest in the background.

- Fix type errors first. `bun build --compile --aot` stops at a type error. The audit prints the errors and runs your program, but checks nothing until they are fixed.
- JavaScript files, such as most packages in `node_modules`, have no types to enforce. What they return is checked where it reaches your TypeScript code, against the declared type.
- There is no way to silence a line. If the value is right and the type is not, change the type.
- A file that calls `eval()` directly is not audited. Bun says so.
- Under `bun test`, when a test file or a preload can replace a module (`mock.module()`, `jest.mock()`, `vi.mock()`, `spyOn()` on a module namespace), arguments passed to imported functions are not checked in that run.
- Functions do not make tail calls while the audit is on, so stack traces have more frames and [very deep recursion](#common-fixes) overflows. An executable built with `--aot-type-errors=log` makes none either. The final executable makes them, as Bun does without `--aot`.
- Code with many type checks in hot loops runs 5% to 20% slower.

The exit code does not change either. To fail a CI job, write the lines to a file and test that it is empty. Bun appends to the file, so remove it first. The audit reads the [same two environment variables](#3-log-in-production) as the executable:

```bash terminal icon="terminal"
rm -f audit.jsonl
BUN_AOT_TYPE_ERROR_LOG=audit.jsonl bun test --aot-audit && test ! -s audit.jsonl
```

## 2. Report when you build

`bun check --aot` type checks your entry points and reports what can never work under `--aot`. Every error that `bun build --compile --aot` reports is one that `bun check --aot` reports too, and the build stops at it. The build does not report errors in code that it removes, such as the `process.platform === "win32"` branch in a build for Linux.

One group of type errors does not stop the build. When `@types/bun` is not installed, TypeScript does not know the names that Bun provides when your program runs. Errors about those names become warnings, Bun prints the first of them with a note to run `bun add -d @types/bun`, and the compiler treats each such name as `any`. The group is: `TS2580`, `TS2582`, `TS2584`, `TS2591`, `TS2593`, `TS2867` and `TS2868`, which TypeScript reports for names such as `console`, `process`, `require`, `describe` and `Bun`; `TS2304` and `TS2552` for the globals `AbortController`, `AbortSignal`, `Blob`, `BroadcastChannel`, `Buffer`, `Bun`, `ByteLengthQueuingStrategy`, `CloseEvent`, `CompressionStream`, `CountQueuingStrategy`, `Crypto`, `CryptoKey`, `CustomEvent`, `DOMException`, `DecompressionStream`, `ErrorEvent`, `Event`, `EventSource`, `EventTarget`, `File`, `FormData`, `HTMLRewriter`, `Headers`, `MessageChannel`, `MessageEvent`, `MessagePort`, `Performance`, `ReadableStream`, `Request`, `Response`, `SubtleCrypto`, `TextDecoder`, `TextDecoderStream`, `TextEncoder`, `TextEncoderStream`, `TransformStream`, `URL`, `URLSearchParams`, `WebAssembly`, `WebSocket`, `Worker`, `WritableStream`, `__dirname`, `__filename`, `addEventListener`, `alert`, `atob`, `btoa`, `clearImmediate`, `clearInterval`, `clearTimeout`, `confirm`, `console`, `crypto`, `exports`, `fetch`, `global`, `module`, `navigator`, `performance`, `postMessage`, `process`, `prompt`, `queueMicrotask`, `removeEventListener`, `reportError`, `require`, `self`, `setImmediate`, `setInterval`, `setTimeout` and `structuredClone`; `TS2307` for `bun`, any `bun:` or `node:` module, the Node.js modules `assert`, `async_hooks`, `buffer`, `child_process`, `cluster`, `console`, `constants`, `crypto`, `dgram`, `diagnostics_channel`, `dns`, `domain`, `events`, `fs`, `http`, `http2`, `https`, `inspector`, `module`, `net`, `os`, `path`, `perf_hooks`, `process`, `punycode`, `querystring`, `readline`, `repl`, `stream`, `string_decoder`, `timers`, `tls`, `tty`, `url`, `util`, `v8`, `vm`, `wasi`, `worker_threads` and `zlib` with their subpaths, and an import that ends in `.txt`, `.toml`, `.yaml`, `.yml`, `.jsonc`, `.json5`, `.xml`, `.html` or `/bun.lock`; and `TS2339` for a property of `import.meta`. With `@types/bun` installed, all of these are errors again and stop the build.

```ts wrong.ts icon="/icons/typescript.svg"
function double(n: number): number {
  return n * 2;
}

console.log(double("4" as any));
```

```bash terminal icon="terminal"
bun check --aot wrong.ts
```

```txt
wrong.ts(5,13): error TS100013: This always throws a TypeError under --aot: argument 1 of `double` expects 'number' and always gets "4".
Found 1 error in 1 file, checked 1 file
```

| Code       | What always fails                                              |
| ---------- | -------------------------------------------------------------- |
| `TS100013` | a value of the wrong type for a parameter, variable, field or result |
| `TS100014` | a write to a built-in object                                   |
| `TS100015` | a change to an object that its type does not allow             |
| `TS100017` | `as` on a value that is always of another primitive type       |

`TS100031` to `TS100034` are about [`int32`](/bundler/executables#32-bit-integers), which is never checked when the program runs: the build has to prove every value that is stored as one, and these are the places where it cannot.

In a JavaScript file, one of these inside a `try` block that has a `catch` is the warning `TS100020` and does not stop the build. That is how packages test for a feature: the write throws, and the `catch` falls back. In a TypeScript file it stays an error.

Most checks depend on data that only exists when the program runs. `--aot-explain=throws` lists them, with where the value comes from and how to fix it:

```bash terminal icon="terminal"
bun check --aot --aot-explain=throws app.ts
```

[aot] type-check c2be03ebd76c as-late-use app.ts:7:13 (module): a value that the cast let through is used as the type of the cast: expected number, may get object | number; warning; logged as 7e37ac7b188a; value from JSON.parse(..) at app.ts:5:24; fix: narrow instead of casting (typeof, a type guard), or write the conversion out
[aot] type-check 0d0dde539306 as-convert app.ts:7:14 (module): expected number, may get any; warning; value from JSON.parse(..) at app.ts:5:24; fix: narrow instead of casting (typeof, a type guard), or write the conversion out
[aot] type-check summary: 3 checks can fail when the program runs, 0 always fail

| Report            | Lists                                                                                     |
| ----------------- | ----------------------------------------------------------------------------------------- |
| `throws`          | every check that can fail because of `any`, JavaScript code, data from outside, or `as`   |
| `throws-all`      | also the checks that fail only if your TypeScript code itself produces a value of the wrong type |
| `throws-json`     | the same as `throws`, one JSON object per line, on stdout                                 |
| `throws-all-json` | the same as `throws-all`, one JSON object per line, on stdout                             |

The last line counts the checks that can fail by what causes them. Start with the causes that you wrote yourself: an `as`, a `!`, an `any`. In the JSON reports, each object has its cause as `cause`:

| `cause`             | The check is                                                              |
| ------------------- | ------------------------------------------------------------------------- |
| `as`                | at an `as`                                                                |
| `non-null`          | at a `!`                                                                  |
| `after-as`          | where a value that an `as` let through is used                            |
| `declared-only`     | on a value from code that has only a declaration: a package, a global     |
| `called-as-a-value` | on a parameter of a function that is called as a value or with `any`      |
| `any`               | on an `any`                                                               |
| `unknown-source`    | on a value whose source is not known                                      |
| `javascript`        | on a value from a JavaScript file of the program                          |
| `caught`            | on a caught exception                                                     |
| `builtin-write`     | at a write to a built-in object                                           |
| `rule`              | by another `--aot` rule                                                   |
| `narrowing`         | where a type is narrowed. Only in `throws-all`                            |
| `typed-code`        | within typed code. Only in `throws-all`                                   |

A line ends in `warning` if the check can fail, and in `error` if it always fails. `bun build --compile --aot` takes the same flag. `Bun.build` returns the lines in `logs`, at level `"verbose"`:

```ts build.ts icon="/icons/typescript.svg"
const result = await Bun.build({
  entrypoints: ["./app.ts"],
  compile: { outfile: "./app", aot: true, aotExplain: "throws-json" },
});
```

## 3. Log in production

Tests do not see all the data that production sees. Build with `--aot-type-errors=log`, and the executable writes a line where it would throw.

<Warning>
  A log build does not keep going everywhere yet. Where it does not, it writes its line and then throws, so that request fails as it does in step 4.
</Warning>

| What happens                                                                                                                                              | The line says            | Then                                                        |
| --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ | ----------------------------------------------------------- |
| A string, number or boolean is passed where the parameter has another type, also an interface or a type literal, to a function, an arrow function, an `async` function or a method of an object literal, such as a handler of `Bun.serve`: by name, or as a callback, a listener, a handler in a table or a `Map`, or a closure that another function returns, yields or stores | `continued`              | The call runs as plain JavaScript                           |
| The same is passed to a method of a class, a generator, a constructor, a `function` that uses `this`, or any function that uses `arguments`, a rest parameter, `super` or a private name, or that declares a class | `threw`                  | `TypeError`                                                 |
| A string, number, boolean, `null` or `undefined` of the wrong type reaches a variable, a property or a return type, or comes out of a call or an `await` | `threw`                  | `TypeError`                                                 |
| `as number`, `as string` or `as boolean` on a value of another of these types                                                                             | `converted`              | The value is converted, as in step 4                        |
| An object does not match its interface, type literal or class: parsed JSON without a property, an object from a package                                   | `continued` or `threw`   | It depends on the type. Where it goes on, a missing property reads `undefined` |
| Such an object has no value for a `number` or `boolean` property, and your code reads it                                                                  | `threw`                  | `TypeError`. If the object was passed to a function or an arrow function, that call runs as plain JavaScript instead, and the property reads `undefined` |
| Something else arrives where an array, a function or a built-in class such as `Map` is expected                                                           | `threw`                  | `TypeError`                                                 |
| A write to a built-in object                                                                                                                              | `threw`                  | `TypeError`                                                 |

To accept an object that does not match, the compiler has to discard what it knows about that type and about every type that can contain it. It does so for a type that data from outside the type system reaches, such as `any`, `unknown` or the result of an untyped function, unless too many other types would follow. Add `--aot-explain=throws` to the build to see what it decided. Each line says what this build does at that place, and the last line counts the places. A line of the log has the id of its line in the report:

[aot] type-check 4d3156b73eaf enter-argument app.ts:6:13 (module): argument 1 of `double`: expected number, may get any; warning; this log build continues here; value from JSON.parse(..) at app.ts:5:24; fix: validate the value once, where it enters the program, and build a typed value from it
[aot] type-check c2be03ebd76c as-late-use app.ts:7:13 (module): a value that the cast let through is used as the type of the cast: expected number, may get object | number; warning; this log build throws here; value from JSON.parse(..) at app.ts:5:24; fix: narrow instead of casting (typeof, a type guard), or write the conversion out

| Environment variable             | Value                                                        |

| Action      | What the executable did                                   |
| ----------- | --------------------------------------------------------- |
| `continued` | went on with the value, as plain JavaScript does          |
| `converted` | `as` converted the value, so the program goes on with another value than in plain JavaScript |

A write to a built-in object still throws.

## 4. Throw

When the log stays empty, drop `--aot-type-errors=log`. To go back, add it again, or drop `--aot`: your source does not change in any of the four steps.

```bash terminal icon="terminal"
bun build --compile --aot app.ts --outfile app
./app
```

```txt
6 | console.log(double(body.visits));
                       ^
TypeError: expected number | undefined, got string "3" (bun --aot: https://bun.com/docs/bundler/executables#ahead-of-time-compilation)
      at /$bunfs/root/app.ts:6:20
```

Unlike a line of the log, the message of the `TypeError` contains the value. If you send error messages to a service, it receives that data.

The default build writes no log. Set `BUN_AOT_TYPE_ERROR_LOG` to `stderr` or to a file, and it writes a line for each `TypeError` that `--aot` throws, also for one that your program catches. These lines have the action `threw`. Most have the kind `type-mismatch` and their own id. The report from step 2 prints that id on the line for the same location, as `logged as 19df4e0e09b7`. A wrong argument for a function that is called as a value or through `any` has the kind `enter-function`: the line names the function, not the call, and has the id of the function's line in the report. The call comes first after `from`. `bun run --aot` and `bun test --aot` write these lines too when the variable is set, with the kind and the id that `--aot-audit` prints for the same location.

## Common fixes

**`as` on data.** If `query.page` is `"2"`, then `page` is `2` under `--aot` and `"2"` without it. Convert, and both agree.

```ts
const page = query.page as number; // [!code --]
const page = Number(query.page); // [!code ++]
```

**A value of type `any` passed to a function.** Check it once, where it comes in. TypeScript does not narrow a property of `any`, so give the value a name of type `unknown` first. After the check it is a `number`, and the report has no line for it.

```ts
const body: any = JSON.parse(text);
double(body.visits); // [!code --]
const visits: unknown = body.visits; // [!code ++]
if (typeof visits !== "number") throw new Error("visits must be a number"); // [!code ++]
double(visits); // [!code ++]
```

**Very deep recursion.** A strict-mode function that ends in `return f(x)` gives its stack frame to `f`, with or without `--aot`. The audit and an executable built with `--aot-type-errors=log` keep a frame for every call, as Node.js does, so a tail-recursive `sum(1_000_000)` throws `RangeError: Maximum call stack size exceeded` in those two steps. If your program recurses that deeply, write a loop.

```ts
function sum(n: number, total = 0): number {
  if (n === 0) return total; // [!code --]
  return sum(n - 1, total + n); // [!code --]
  for (; n > 0; n--) total += n; // [!code ++]
  return total; // [!code ++]
}
```

**A declaration that says too little.** `expected string, got native Buffer` means that the value is fine and the type is not. Widen the parameter, or convert at the call.

```ts
function shout(text: string) { // [!code --]
function shout(text: string | Buffer) { // [!code ++]
```

## Packages that change built-in objects

Built-in objects are immutable in a compiled program. That is what lets the compiler turn `array.push(x)`, or a read of a property that an object does not have, into a few instructions, without first checking whether somebody has replaced `push` or added to `Object.prototype`. A few packages change built-ins, mostly to support old browsers or to offer a shorter syntax in tests. The `TypeError` names the object and the property, and its stack leads to the line of the package that tried:

```txt
TypeError: Cannot change 'call$0' of Function.prototype: built-ins are locked in a program compiled with --aot
      at dartProgram (node_modules/sass/sass.dart.js:125905:12)
```

| Package                             | What it does                                                                              | What you see                                                            | What works                                                                                                                                                                                                 |
| ----------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chai` 6, `vitest` 4 through it     | `chai.should()` defines `Object.prototype.should`                                         | `Cannot change 'should' of Object.prototype`, when `should()` is called | `expect` and `assert` of `chai`, `expect` of `vitest`                                                                                                                                                      |
| `sinon`                             | `useFakeTimers()` replaces `globalThis.Date`                                              | `Cannot change 'Date' of globalThis`, when `useFakeTimers()` is called  | Spies and stubs. In `sinon` 6, also `useFakeTimers({ toFake: ["setTimeout", "setInterval"] })`. In `sinon` 22, every form of `useFakeTimers()` throws                                                      |
| `@colors/colors` 1                  | Its default entry point adds getters such as `"text".red` to `String.prototype`           | `Cannot change 'strip' of String.prototype`, on import                  | `import colors from "@colors/colors/safe"`, then `colors.red("text")`                                                                                                                                      |
| `sass` 1                            | The Dart runtime inside it adds `call$0`, `call$1` and so on to `Function.prototype`      | `Cannot change 'call$0' of Function.prototype`, on import               | Compile your stylesheets before you build the executable. Or use `compileStringAsync()` of `sass-embedded`, with `node_modules` next to the executable: it starts a compiler that is a program of its own. Its `compileString()` hangs in any executable, with or without `--aot` |
| `core-js` 3                         | Every entry point, even `core-js/actual/array/at`, replaces `Function.prototype.toString` | `Cannot change 'toString' of Function.prototype`, on import             | Remove the import: Bun implements what it fills in. With Babel, set `useBuiltIns: false`. Or import one feature at a time from `core-js-pure`, such as `core-js-pure/actual/array/at`. `core-js-pure/stable` throws `Cannot change 'isError' of Error` |
| `envinfo` 7, `@webpack-cli/info`    | They contain `core-js` 2, which deletes `Function.prototype.toString`                     | `Cannot delete 'toString' of Function.prototype`, on import             | Nothing that we know of                                                                                                                                                                                    |

[`bun --aot-audit`](#1-audit-while-you-develop) reports these writes while your program still runs as usual, and the lint rule [`bun/aot-locked-builtin-write`](/lint/rules/bun/aot-locked-builtin-write) finds them in your own code. `Error.prototype` and the prototypes that inherit from it are not locked, and neither is what Bun or your program defines, such as `process`, `console` or `setTimeout`.

Seven prototypes that Bun defines are locked too: those of `Request`, `Response`, `Headers`, `Blob`, `URL` and `URLSearchParams`, and the one between `Request.prototype` and the requests that the `routes` of `Bun.serve` receive (`BunRequest`; it has no global name, `Object.getPrototypeOf(request)` is the way to it). The compiler relies on their getters and methods the way it relies on `Array.prototype.push`. The `TypeError` says what to do instead:

```txt
TypeError: Cannot change 'json' of Response.prototype: built-ins are locked in a program compiled with --aot. Use a subclass of Response or a wrapper function instead
```

Subclasses are not affected. `class NextRequest extends Request`, as in Next.js, has a prototype of its own: it can override getters and methods, add fields and call `super`. Compiled code checks the exact class of each object, so an instance of a subclass gets its overrides wherever a `Request` is expected. These also work as they do without `--aot`:

- a property on one instance: `Object.defineProperty(response, "url", { value })`
- another prototype for one instance: `Object.setPrototypeOf(request, other)`
- replacing a static function: `URL.createObjectURL = stub`
- replacing the global variable: `globalThis.Request = MyRequest`
- a polyfill that checks first: `Headers.prototype.getSetCookie ??= ...` assigns nothing, so nothing throws

## Frameworks that load your pages by path

`bun build` compiles what the entry point reaches through string literals. Next.js and Angular load the pages and routes of your application by paths that they put together while the server runs, so this command leaves them out:

```bash terminal icon="terminal"
cd .next/standalone
bun build --compile --aot --compile-in-place ./server.js --outfile server
```

The server starts and every response is correct, because it finds those files on disk and Bun interprets them. Nothing tells you, and a request takes about a quarter more instructions. Name the files as additional entry points:

```bash terminal icon="terminal"
# Next.js, in .next/standalone
bun build --compile --aot --compile-in-place ./server.js $(find .next/server -name '*.js') --asset .next --asset public --outfile server
```

For Angular the files are `$(find dist/site/server -name '*.mjs' -not -name server.mjs)`. Nuxt, SvelteKit, Astro and React Router need no additional entry points.

To check, start the server once with `BUN_JSC_crashIfInterpreterIsUsed=1` in its environment and request every route. It stops at the first function that is interpreted and names the file.

## Syntax the compiler refuses

The build stops and names the file and the line.

| You wrote                       | The build says                                                  | Write instead                                                                        |
| ------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `with (options) { run(name); }` | ``--aot does not support a `with` statement``                   | `run(options.name);`                                                                 |
| `eval(...parts)`                | ``--aot does not support a direct `eval` with spread arguments`` | `eval(parts[0])`, or `(0, eval)(...parts)` if the code does not read local variables |

`with` is only valid in files that are not modules and not in strict mode. Code that a template engine generates when the program runs and passes to `new Function` may use it.

## Reading a line

```txt
[aot] type-error 81eda900c1a1 read-property app.ts:6:20 (module): expected number | undefined, got string; would-throw; count 1; call 4d3156b73eaf; from server.ts:41 < router.ts:12
```

| Part                       | Meaning                                                                                                   |
| -------------------------- | --------------------------------------------------------------------------------------------------------- |
| `81eda900c1a1`             | The id of this location. It is the same in the audit, in the report and in the executable, and from run to run, until the line moves. For an argument of a call, the executable uses the id after `call`. |
| `read-property`            | What happens there: `enter-argument`, `enter-function`, `enter-variable`, `enter-field`, `enter-return`, `read-property`, `read-element`, `call-result`, `as-convert`, `non-null`, and others. `as-late-use` is the use of a value that `as` could not check, because it is an object. |
| `app.ts:6:20 (module)`     | File, line, column, and the function. `module` is code outside of any function.                           |
| `expected ..., got ...`    | What passes this check, and the kind of value that did not. A check can let more pass than the type says: here `undefined` passes too, as a missing argument does in JavaScript. |
| `count 1`                  | How often this location has failed with this kind of value.                                               |
| `reason ...`               | For an object: which property does not match, such as `property 'id' is missing in untyped object but required in User`. Only the executable writes it. |
| `call 4d3156b73eaf`        | The value is an argument of a call. An executable built with `--aot-type-errors=log` reports it under this id, at the position of the call. |
| `from ...`                 | The callers, nearest first.                                                                               |
