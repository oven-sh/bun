<Warning>Ahead-of-time compilation is experimental.</Warning>

An executable built with [`bun compile`](/bundler/aot) runs the same language and the same APIs as `bun run`. This page lists what differs.

A value that doesn't match its declared type isn't on the list. It [falls back to the slow path](/bundler/aot-types#when-a-value-doesnt-match-its-type), and the program behaves as it does under `bun run`.

## What works the same

- npm packages, with or without types
- ES modules, CommonJS, `require()`, `import()` of a string literal, top-level `await`
- every `node:` and `bun:` module
- [Workers](#workers) and [native addons](#native-addons)
- [`eval` and `new Function`](#code-from-strings), in the interpreter
- [macros](/bundler/macros)
- [plugins of `Bun.build`](#plugins-and-build-options), `files`, `define`, `loader` and the other build options
- proxies, getters and setters, generators, symbols, `Reflect`, private members, `delete`, BigInt, regular expressions

Some of these take a slow path: a `Proxy` used as an array, and an array with holes, with getters for elements or with inherited elements. They behave as under `bun run`.

## Type errors are TypeScript 7's

The build reports the errors that `tsc` from TypeScript 7 reports, like [`bun check`](/runtime/check), whichever version of `typescript` your project has installed. A project that passes TypeScript 5 or 6 can still have errors. [Coming from TypeScript 5](/runtime/check#coming-from-typescript-5) lists the options and defaults that changed.

TypeScript 7 also stopped reading four older patterns in JavaScript files. They still run. But when a TypeScript file imports one of your own `.js` files that uses them, it no longer sees what TypeScript 6 saw, and the build stops at the TypeScript file.

| In the `.js` file                                                             | The error in the TypeScript file                                       | Write instead                                           |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------- |
| `function f() { return arguments.length }`, called with arguments             | `TS2554: Expected 0 arguments, but got 3.`                             | A rest parameter: `function f(...values) {}`            |
| A constructor function: `function Old(v) { this.value = v }` and `new Old(3)` | `TS7009: 'new' expression, whose target lacks a construct signature`   | A `class` with a `constructor`                          |
| A method added later: `Grown.prototype.extra = function () {}`                | `TS2339: Property 'extra' does not exist on type 'Grown'.`             | A method in the body of the class                       |
| `/** @enum {number} */ const Level = { Low: 1 }`, with `Level` used as a type | `TS2749: 'Level' refers to a value, but is being used as a type here.` | `/** @typedef {number} Level */` above the object       |
| `module.exports = Main` followed by `module.exports.helper = ...`             | `TS2339: Property 'helper' does not exist on type 'typeof Main'.`      | `Main.helper = ...` first, then `module.exports = Main` |

The build doesn't report type errors inside a `.js` file, so only the TypeScript files that use it are affected.

## Built-in objects are read-only

The compiler turns `array.push(x)` into a few instructions without first checking whether somebody has replaced `push`. So nobody can. Replacing an existing member of a built-in object isn't supported. Adding a new one is fine, with the exceptions in the table.

```ts builtins.ts icon="/icons/typescript.svg"
function attempt(change: () => unknown): void {
  try {
    console.log(change());
  } catch (error) {
    console.log((error as Error).name);
  }
}

attempt(() => ((Array.prototype as any).last = 1));
attempt(() => ((Array.prototype as any).push = 1));
attempt(() => delete (String.prototype as any).slice);
attempt(() => Reflect.set(Array.prototype, "push", 1));
attempt(() => ((Object.prototype as any).extra = 1));
attempt(() => ((Date as any).tomorrow = 1));
```

```bash terminal icon="terminal"
bun compile ./builtins.ts && ./builtins
```

```txt
1
TypeError
TypeError
false
TypeError
1
```

| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Object.prototype`, `RegExp.prototype`, `Promise.prototype`, the prototypes of generators                                                                                                                                                                                | Every change                                                                                                                                                                                                                                      | The same on your own object or subclass                                                                                                                                   |
| `Function.prototype`                                                                                                                                                                                                                                                     | Every change but the ones on the right                                                                                                                                                                                                            | Replacing `toString`. Changing the object's prototype | Adding a property under a new name: `Array.prototype.last`, `"text".red`, `BigInt.prototype.toJSON`                                                                       |
| `Math`, `JSON`, `Reflect`, `Atomics`. The constructors `Array`, `Object`, `String`, `Number`, `Boolean`, `BigInt`, `Symbol`, `Map`, `Set`, `WeakMap`, `WeakSet`, `Promise`, `Proxy`, `RegExp`, `Date`, `ArrayBuffer`, `SharedArrayBuffer`, the typed arrays and `Buffer` | Replacing, redefining or deleting a member. Adding a well-known symbol or a name that the object inherits, such as `call` or `toString`. Changing the object's prototype                                                                          | Adding a property under a new name, a number or a symbol that you made: `Math.tau`, `Object.myHelper`, `Array[1]`, `Symbol.observable`. Changing it and deleting it again |
| The built-in functions themselves, constructors too: `Math.max`, `Array.prototype.map`, `Object.prototype.hasOwnProperty`, `parseInt`, `console.log`, `Error`                                                                                                            | Giving the function a `call`, `apply`, `bind` or `Symbol.hasInstance` of its own: `Math.max.call = f`. Changing its prototype                                                                                                                     | Adding a property under any other name. All of it on your own functions, classes and bound functions                                                                      |
| Everything else: `Error` and the other error constructors, `Function`, `Intl`, `Temporal`, `WebAssembly`, `console`, `process`, `fetch`                                                                                                                                  | An assignment from [code in a string](#code-from-strings) or a [module loaded at run time](#dynamic-imports) to a member that your compiled code never assigns                                                                                    | Every assignment in the code that you compile                                                                                                                             |

A few members of the third and fourth groups can be replaced, because well-known packages do: `String.prototype.at`, `trim`, `trimStart` and `trimEnd` of strings, the HTML methods of strings such as `bold` and `link`, the methods of `Set` that take another set, such as `union`, `Math.random`, `Math.sign`, `Math.sinh`, `Math.sumPrecise`, `JSON.parse`, `JSON.stringify`, `Date.now`, `Date.parse`, `Date.prototype.toString`, `toLocaleString`, `toLocaleDateString` and `toLocaleTimeString` of dates, `Number.parseFloat`, `Number.parseInt`, `Map.groupBy`, `Promise.try`, `RegExp.escape`, `Uint8Array.fromBase64`, `Uint8Array.fromHex` and `Buffer.poolSize`. They follow the rule of the last group. `toJSON` can be added to `Map.prototype` and `Set.prototype`, and `toLocaleString` to a typed array constructor. The `Reflect` functions return `false` where an assignment would throw. An assignment or a `delete` throws in sloppy-mode code too, which is what most CommonJS packages are. A package always finds out that it didn't replace the member.

In the last group, an assignment counts when the compiler can tell which object it goes to: `console.log = f`, `const con = console; con[name] = f`. If your code gets hold of `console` in a way that the compiler can't follow, such as out of a `JSON.parse` reviver, an assignment through that value to a member that nothing else assigns throws the same `TypeError`, with the member's name. Assign through the global name instead.

The same goes for the global object as `this`. A constructor function that starts with `if (!(this instanceof F)) return new F(...)` can be called without `new`, and behind that test the compiler takes `this` for an instance of `F`. The global object passes the test only if you set `F.prototype = Object.prototype`. Then an assignment such as `this[key] = value` in that function goes to the global object in a way that the compiler didn't follow: it throws the same `TypeError`.

`Object.freeze()`, `Object.seal()` and `Object.preventExtensions()` work on all of these objects as they do under `bun run`, so a server can freeze `Object.prototype` when it starts, to guard against prototype pollution. So does an `Object.defineProperty()` that repeats what a member already is, or that only makes it read-only or non-configurable.

The build reports each such assignment that it can see as `TS100014`. It's an error if the assignment always runs, and a warning if it only might. The built-in objects of a `node:vm` context or a `ShadowRealm` that your program creates can be changed: each has its own.

A global that can't be replaced can't be shadowed either. A script that you run with `vm.runInThisContext()` or `new vm.Script()` shares its top-level `let`, `const` and `class` declarations with the whole program, so `let Math = ...` at the top of such a script throws a `SyntaxError`. Use another name, move the declaration into a function or a block, or run the script with `vm.runInNewContext()`.

### New properties on built-in prototypes

You can add a new property to the objects of the third group and to `Error.prototype`. It doesn't matter who adds it: your compiled code, [code in a string](#code-from-strings) or an `--external` package. Compiled code finds the property as it does under `bun run`. `list.last` finds an `Array.prototype.last`, and `this.node = node` in a class that extends `Error` runs a setter called `node` on `Error.prototype`.

The exceptions are the names that the language looks up by itself. A prototype of the third group that doesn't have such a name never gets it:

| Name                      | Looked up by                                                                                      | Can't be added to                                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `then`                    | `await`, and a promise that is resolved with the object                                           | The prototypes whose instances are objects: the third group without `String`, `Number`, `Boolean`, `BigInt` and `Symbol` |
| `toJSON`                  | `JSON.stringify`                                                                                  | The same prototypes, except `Map.prototype` and `Set.prototype`                                                          |
| `next`, `return`, `throw` | `for...of`, spread, destructuring and `yield*`, on the object that `[Symbol.iterator]()` returned | Every prototype of the third group, but `next` on `Date.prototype`                                                       |

```txt
TypeError: Cannot assign to Array.prototype.next because built-in objects are read-only in a compiled executable (bun compile differs from bun run here: https://bun.com/docs/bundler/aot-compatibility)
```

Put the method on your own object or class instead. A class that extends `Array` can have a `then`, a `toJSON` or a `next`.

### Request, Response and five other classes

The prototypes of `Request`, `Response`, `Headers`, `Blob`, `URL` and `URLSearchParams` are read-only too. So is the prototype of the request objects that `Bun.serve` passes to your `routes` handlers. `File.prototype` is the same object as `Blob.prototype`.

Use a subclass. It has a prototype of its own.

```ts response.ts icon="/icons/typescript.svg"
try {
  (Response.prototype as any).text = async () => "patched";
} catch (error) {
  console.log(String(error));
}

class Upper extends Response {
  override async text(): Promise<string> {
    return (await super.text()).toUpperCase();
  }
}

console.log(await new Upper("hello").text());
```

```bash terminal icon="terminal"
bun compile ./response.ts && ./response
```

```txt
TypeError: Cannot assign to Response.prototype.text because built-in objects are read-only in a compiled executable (bun compile differs from bun run here: https://bun.com/docs/bundler/aot-compatibility)
HELLO
```

A subclass can override methods and getters such as `text()` and `ok`, add fields and call `super`.

These also work as usual:

- a property on one instance: `Object.defineProperty(response, "url", { value })`
- replacing a static function: `URL.createObjectURL = stub`
- replacing the global: `globalThis.Response = Upper`
- a polyfill that checks first: `Headers.prototype.getSetCookie ??= ...` assigns nothing, so nothing throws

## Code from strings

`eval`, `new Function` and `node:vm` work. The build can't see their code, and the executable has no JIT, so Bun interprets it.

```ts strings.ts icon="/icons/typescript.svg"
const add = new Function("a", "b", "return a + b");
const local = 5;
console.log(add(2, 3), eval("local * 2"), (0, eval)("typeof Bun"));
```

```bash terminal icon="terminal"
bun compile ./strings.ts && ./strings
```

```txt
5 10 object
```

That's fine for a template or a configuration file. It matters when a library generates its hot code that way: zod 4, ajv, fast-json-stringify and Elysia do. If the library has a mode without generated code, measure both: `z.config({ jitless: true })` makes `parse` in zod 4 about 2.5 times cheaper, while `new Elysia({ aot: false })` makes a request slower.

If your program never calls `eval` or `new Function`, the compiler assumes it has seen all the code that will ever run (a closed-world assumption, like GraalVM Native Image) and optimizes accordingly.

It finds these calls by tracking the functions as values, so `const run = eval`, `Reflect.construct(Function, [code])`, `(() => {}).constructor(code)` and `new Proxy(Function, {})(code)` all count.

A direct `eval` in strict code doesn't count if its string is known at build time and is only the name of a variable, as in `eval("require")`, or `eval("quire".replace(/^/, "re"))` in the `@protobufjs/inquire` package. It's compiled as a read of that variable.

Only a call counts. Naming `eval` or `Function`, storing one in an object or passing one to another function costs nothing by itself. Neither does a call to a function that the compiler knows nothing about: it doesn't assume that such a call might be `eval`.

What it doesn't track is an `eval` or a `Function` that your program reads under a computed key, as in `object[name](code)` or `globalThis[name](code)`. That holds for your own objects too. A table such as `{ "%eval%": eval, "%parse%": parse }`, like the one in the `get-intrinsic` package, costs nothing however it's read, and `table["%eval%"](code)` counts as a call while `table[name](code)` doesn't. In a program with no other such call, that one throws:

```txt
EvalError: Code generation from strings disallowed for this context: the compiler couldn't tell at build time that this call reaches eval() or the Function constructor. Call eval() or new Function() directly.
```

A few other ways to load code follow the same rule. They work where the compiler finds the call, and throw where it doesn't.

- `Bun.plugin`
- `require` and `process.getBuiltinModule` used as values, in a program where every import path is a constant

Code in a string can use any API, with one exception. Some of `process`, `console` and `Bun` is written in JavaScript, and the executable only contains the APIs that your program uses. If a string is the only thing that uses one of the others, that use throws:

```ts stream.ts icon="/icons/typescript.svg"
const text = process.argv[2] ?? "process.stdout.write('hi\\n')";
try {
  new Function(text)();
} catch (error) {
  console.log(String(error));
}
```

```txt
Error: None of console._stderr, console._stdout, process.stderr or process.stdout was compiled into this executable because your code never uses them. To keep them, use one of them somewhere in your code. (bun compile differs from bun run here: https://bun.com/docs/bundler/aot-compatibility)
```

The error is catchable. Using `process.stdout` anywhere in your own code fixes it.

This affects `process.stdout`, `stderr`, `stdin`, `openStdin()`, `finalization`, `allowedNodeEnvironmentFlags` and `loadEnvFile()`, `console.Console` and `console.write()`, and `Bun.$`, `Bun.sql`, `Bun.SQL` and `Bun.peek()`.

A function of a `node:` module that your program imports and never calls isn't compiled either. A string rarely finds one, but it can: on an object such as `process` that inherits from `EventEmitter`, or by loading the module itself, as in `process.getBuiltinModule("node:http").request(url)` in a program that only has `import { createServer } from "node:http"`. The call then throws `'...' was not compiled into this executable because your code never calls it`, with the function's name.

`process.mainModule` is `undefined` in a string unless [a file of your program names it](#module-objects), as it is in every executable built without `--aot`. It's the only path from a string to your CommonJS modules, so without it the compiler knows every caller of what they export. `require.cache` is no such path: [it lists none of them](#the-module-cache).

Everything that belongs to the language always works in a string: `Array`, `Map`, `Promise`, `JSON`, regular expressions, generators. So does everything that Bun implements natively, such as `fetch`, `Bun.file` and `Bun.serve`.

It's always the call that throws. Importing `node:vm`, `node:worker_threads`, `node:repl` or `bun:ffi` costs nothing and never fails. `inspector.open()` from `node:inspector` starts no debugger and doesn't throw, unless you build with [`--compile-inspector`](#options-that-load-code).

If your program needs none of it, [`--disallow-code-generation-from-strings`](/runtime/code-generation-from-strings) turns it off in the executable, like the Node.js flag of the same name.

```bash terminal icon="terminal"
bun compile --disallow-code-generation-from-strings ./strings.ts && ./strings
```

```txt
EvalError: Code generation from strings disallowed for this context
      at /$bunfs/root/strings.ts:1:17
```

With the flag, a call to `eval` or `new Function` can only throw, so the compiler treats your program as if the call ran nothing. It knows every caller of your functions again, which means less code to compile and more that it can optimize, and [`--trim`](/bundler/aot-size#turn-off-code-from-strings) can remove the interpreter. A library that tries `new Function` inside a `try`, such as zod 4, falls back to plain code. A library that can't work without generated code, such as Elysia, throws the `EvalError` when it starts.

**With `=strict`, code from the disk fails with the flag's error too.** `require()` and `import()` of a file that isn't in the executable throw `EvalError: Code generation from strings disallowed for this context`. `--preload`, `-r`, `--require`, `--import` and `BUN_INSPECT_PRELOAD` end the process with that error and exit code `1`. An executable built without `--aot` does the same. Without the flag, you get [the messages that say what to do](#code-that-isnt-in-the-executable).

**Pass the flag when you build.** `BUN_OPTIONS` can turn it on too, but that's too late for a string that's a constant. The compiler has compiled `(0, eval)("1 + 1")` and `new Function("return 2")` like the rest of your program, so they still run. A string that's put together at run time throws.

## WebAssembly

A `.wasm` file that your program imports is compiled at build time.

```ts
import path from "./add.wasm";

const bytes = await Bun.file(path).arrayBuffer();
const { instance } = await WebAssembly.instantiate(bytes);
```

The executable recognizes the module by its bytes. So it makes no difference how your program reads the file, or which function of `WebAssembly` it passes the bytes to.

Bun interprets every other module: bytes that your program downloads, decodes from a string or assembles itself. The executable has no JIT, so a tight loop runs about 20 times slower there.

On some machines, and with some memories, the executable can't use the compiled code of a module. [The run-time log says so](/bundler/aot-debugging#webassembly-that-falls-back-to-the-interpreter).

## Dynamic imports

`bun compile` compiles every module that the entry point reaches through an `import` or `require`. When an import path isn't a constant, the compiler uses the parts of it that are.

```ts app.ts icon="/icons/typescript.svg"
const wanted = process.argv[2] ?? "csv";
const plugin = await import("./plugins/" + wanted + ".ts");
console.log(plugin.name);
```

```ts plugins/csv.ts icon="/icons/typescript.svg"
export const name: string = "csv";
```

```ts plugins/json.ts icon="/icons/typescript.svg"
export const name: string = "json";
```

Every path here starts with `./plugins/` and ends with `.ts`, so the compiler includes every such file below `plugins/`. The executable contains both plugins and runs without your source files.

```bash terminal icon="terminal"
bun compile ./app.ts --outfile elsewhere/app && cd elsewhere && ./app json
```

```txt
json
```

A path with no constant start, like `require(name)`, adds nothing to the executable. Of your own files it finds the entry points, by the path the file had at build time, as in an executable built without `--aot`. A file that's only in the executable because another file imports it isn't found, even after it has run.

```txt
error: Cannot load '/$bunfs/root/inside.ts': this executable can't load a module from a dynamic path. Pass the file to bun compile as another entry point.
```

To load a file by a dynamic path, pass it as an additional entry point. An entry point can be a glob pattern.

```bash terminal icon="terminal"
bun compile ./app.ts './extra/*.ts' --outfile app
```

A package that's loaded by a dynamic name, like the database driver of an ORM, works the same way. Pass the file that the package's `main` or `exports` points to. `require(name)` and `import(name)` then find it by the name of the package, from every file that sees the package in its `node_modules`, and the executable doesn't need `node_modules` on disk.

```bash terminal icon="terminal"
bun compile ./app.ts ./node_modules/pg/lib/index.js --outfile app
```

A package with `exports` is found by the names it exports, patterns like `"./features/*"` included. A package without `exports` is also found by the paths of its files, like `pg/lib/client`.

### Paths that start at the file's folder

The compiler knows that `__dirname`, `import.meta.dir` and `import.meta.dirname` name the folder of the file, and it follows `path.join` and `path.resolve` when their first argument is one of them. `require(path.join(__dirname, "..", "package.json"))` is compiled like `require("../package.json")`.

Two things turn such a path into a dynamic path:

- **The file changes `__dirname`, `__filename` or `import.meta`.** That includes handing `import.meta` to a function. Files that only read them aren't affected.
- **The program replaces `path.join` or `path.resolve`.** The executable compares the path that the call returned with the path that Bun's own function returns. If they differ, `require` throws and `import()` rejects. `bun run` would load whatever file the replacement named.

```txt
error: Cannot load './plugin.js': path.join or path.resolve was replaced and returned a different path. This executable can't load a module from a dynamic path.
```

### Built-in modules

The same rule applies to `node:` and `bun:` modules. The executable contains the ones that your program, a package or another built-in module imports by a constant name. A `require(name)` doesn't add the rest, so one such call in a package doesn't put `node:repl` and `node:dgram` into your server.

```ts load.ts icon="/icons/typescript.svg"
import "node:path";

const name = process.argv[2] ?? "node:path";
console.log(Object.keys(require(name)).length > 0);
```

```bash terminal icon="terminal"
bun compile ./load.ts && ./load node:path && ./load node:dgram
```

```txt
true
error: Cannot load 'node:dgram': it isn't in this executable. Import it by name somewhere in your program to keep it. (bun compile differs from bun run here: https://bun.com/docs/bundler/aot-compatibility)
```

A built-in module that a dynamic name finds works like one that you import, even if it's only in the executable because another built-in module imports it.

To keep a built-in module that your program only loads by a dynamic name, import it once by its name. The import costs nothing until the module is used.

```ts load.ts icon="/icons/typescript.svg"
import "node:dgram";
```

The same goes for `node:cluster`. `server.listen()` in a cluster worker asks the primary for its socket, and that code is in the executable only if your program imports `node:cluster`, itself or through a package. A program that forks itself does. If another program starts your executable as a worker, with `cluster.setupPrimary({ exec })`, and your program never imports `node:cluster`, `listen()` fails with `Cannot load 'node:cluster': it isn't in this executable` instead of listening on its own. `import "node:cluster"` fixes it.

Some properties of `process`, `Bun` and `console` are written in JavaScript too: `process.stdout` needs `node:tty`, and `Bun.sql` needs `bun:sql`. The executable contains the ones your program can reach. Reading `process[name]` with a dynamic name, or storing `process` where the compiler can't follow it, keeps all of them.

The compiler follows a built-in module through variables, parameters, return values and properties of objects that your own code creates, so `fs[name]()` with a dynamic name keeps every function of `node:fs` wherever `fs` got there that way. It can't follow a module through an object that came from outside your code: after `const box = event.detail; box.url = require("node:url")`, `box.url[name]()` throws `'...' was not compiled into this executable because your code never calls it`, unless your program also calls that function by name or reads `url[name]` somewhere the compiler can follow.

The code behind the IPC channel is kept for `process.on("message", ...)` only when the compiler can see that the call is on `process`: called on `process` itself, or on a variable or parameter that holds it. If `process` got there through a value the compiler can't follow, like `error.cause`, a message that carries a `Buffer` or a handle throws an error that names what's missing. Using `process.send` anywhere in your code keeps it.

### Code that isn't in the executable

A dynamic `import()` or `require()` can only load code that's in the executable. Anything else throws: JavaScript, TypeScript, WebAssembly or a native addon. So does everything that Bun would read as JavaScript: a file with no extension, a file with an extension that Bun doesn't know, and a `data:` or `blob:` URL.

```txt
error: Cannot load '/home/me/plugins/late.ts': it isn't in this executable. Pass it to bun compile as another entry point, or mark it --external.
```

The error has the code `MODULE_NOT_FOUND` from `require()` and `ERR_MODULE_NOT_FOUND` from `import()`, like a file that doesn't exist. The build warns at each import where this can happen.

```txt
warn: TS100064: this import path isn't a constant. If it resolves to code that isn't in the executable, the import throws at run time (data files still load). Add the file as an entry point, or mark it --external
```

| You want                     | Do this                                                                                                                           |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| The file compiled            | Pass it as an additional entry point                                                                                              |
| One package loaded from disk | `--external <package>`. Bun interprets it, and everything it loads                                                                |
| Data                         | Nothing. JSON, JSON5, TOML, YAML, XML, text, Markdown and CSS files run no code, so they load from disk as usual                  |
| A database or an HTML page   | Import it by a constant path. `import(name, { with: { type: "sqlite" } })` and `require(name)` of an `.html` file throw like code |

An `--external` package has `require`, `module`, `require.cache` and every built-in module, whole: the compiler can't see what the package calls, so a build with `--external` compiles every function of the built-in modules in the executable, not only the ones that your program calls. That makes the executable a few megabytes larger. The package doesn't see the modules of your program, as in an executable built without `--aot`: its `module.parent` has the path of the file that required it and empty `exports`, and `require.cache` lists the files that were loaded from disk. If a file of your program [names a way between module objects](#module-objects), the package finds your modules through `process.mainModule` too. [Built-in objects are read-only](#built-in-objects-are-read-only) for it too: it can add a global or a property, and it can't replace one that your compiled code uses. `globalThis.fetch = polyfill` in such a package throws a `TypeError` if your program calls `fetch`.

`createRequire()`, `import.meta.require()` and `module.require()` follow the same rules. So does a [macro](/bundler/macros) in text that you hand to `new Bun.Transpiler()` at run time: the file of the macro has to be in the executable.

The compiler also follows `require` under another name, as long as it can see that the name holds `require`. Where it can't, every path is a dynamic path, a string literal too.

| Call                                                                        | Compiled like                              |
| --------------------------------------------------------------------------- | ------------------------------------------ |
| `const load = require; load("./inside.js")`                                 | `require("./inside.js")`                   |
| `require.call(this, "./inside.js")`, `require.apply(this, ["./inside.js"])` | `require("./inside.js")`                   |
| `const load = require; load("./plugins/" + wanted + ".js")`                 | `require("./plugins/" + wanted + ".js")`   |
| `(r => r("./inside.js"))(require)`                                          | `require(name)`: it finds the entry points |
| `({ load: require }).load("./inside.js")`                                   | `require(name)`: it finds the entry points |
| `require.bind(null)("./inside.js")`                                         | `require(name)`: it finds the entry points |
| `let load = require; load = other; load("./inside.js")`                     | `require(name)`: it finds the entry points |

A function that's called where it's written and returns `require` counts as another name too. That's the `__require` helper that esbuild puts into ES module bundles.

| Call                                                                                               | Compiled like            |
| -------------------------------------------------------------------------------------------------- | ------------------------ |
| `var __require = (x => typeof require !== "undefined" ? require : x)(f); __require("./inside.js")` | `require("./inside.js")` |
| `const load = (() => require)(); load("./inside.js")`                                              | `require("./inside.js")` |

With code splitting, esbuild and `bun build` export the helper from a shared chunk. The compiler follows `require`, `import.meta.require` and `createRequire()` from an `export` to an `import` for built-in modules, whose names mean the same in every file. Any other path is still a dynamic path there.

| Call                                                               | Compiled like                              |
| ------------------------------------------------------------------ | ------------------------------------------ |
| `import { __require } from "./chunk.js"; __require("node:zlib")`   | `require("node:zlib")`                     |
| `import { __require } from "./chunk.js"; __require("./inside.js")` | `require(name)`: it finds the entry points |

`process.getBuiltinModule("node:fs")` with a string literal is compiled like `require("node:fs")`. If your program assigns a function of its own to `process.getBuiltinModule`, such a call still gets the built-in module. A call with a dynamic name runs the replacement. The compiler follows `process.getBuiltinModule` under another name like `require`. It can't see the function behind a computed key (`process[key](name)`): such a call throws `Cannot load '...': this executable can't load a module from a dynamic path`.

`require()` can't wait. If it reaches an ES module outside of the executable that has a top-level `await`, it throws a `TypeError` that tells you to use `await import()`.

### Frameworks that load your pages by path

Next.js and Angular load your application's pages and routes from paths that they build while the server runs, so the compiler doesn't find them. Pass the pages as additional entry points, and they are compiled. Pass the rest of the build output with [`--asset`](/bundler/executables#embed-directories), and the server reads it out of the executable.

```bash terminal icon="terminal"
# Next.js with `output: "standalone"`, in .next/standalone
bun compile ./server.js ".next/server/**/*.js" --asset .next --asset public --asset node_modules/@img --outfile server
```

The result is one file that needs nothing else on the machine that runs it. Bun expands the quoted pattern itself. `node_modules/@img` holds `sharp`, which resizes the images of `next/image`; without it Next.js serves them at their original size. Next.js can't write its page cache into the executable, so it keeps the cache in memory. It can't store the images it has resized either, and logs `Failed to write image to cache` for each of them.

`--compile-in-place` builds an executable that only runs on the machine that built it: modules keep their paths on disk, and whatever wasn't compiled or embedded is read from there.

```bash terminal icon="terminal"
bun compile --compile-in-place ./server.js $(find .next/server -name '*.js') --outfile server
```

For Angular the files are `$(find dist/site/server -name '*.mjs' -not -name server.mjs)`. Nuxt, SvelteKit, Astro and React Router need no additional entry points. Pass what the server reads from disk with `--asset`:

```bash terminal icon="terminal"
bun compile ./.output/server/index.mjs --asset .output/public --outfile server # Nuxt
bun compile ./dist/server/entry.mjs --asset dist/client --outfile server # Astro
bun compile ./build/index.js --asset build/client --asset build/prerendered --outfile server # SvelteKit
bun compile ./server.ts --asset build/client --outfile server # React Router, with a server of your own
```

Without the entry points, the first request fails with the error above.

## Options that load code

`--preload` and a few other options load code that the compiler never saw. What the compiler proved about your program only holds while nothing else runs, so an executable rejects them.

```ts greeting.ts icon="/icons/typescript.svg"
console.log("hello");
```

```ts before.ts icon="/icons/typescript.svg"
console.log("before");
```

```bash terminal icon="terminal"
bun compile ./greeting.ts && BUN_OPTIONS="--preload ./before.ts" ./greeting
```

```txt
error: --preload can't be used with this executable because it only runs code that was compiled into it. Rebuild it with --compile-inspector to load other code
```

The executable exits with code `1`, before any of your code runs. To run `before.ts` first, import it at the top of `greeting.ts`.

| A default build | Options                                                                                                                                                          |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Rejects         | `--preload`, `-r`, `--require`, `--import`, `--eval`, `-e`, `--print`, `-p`, `--hot` and `--watch` in `BUN_OPTIONS`, and `BUN_INSPECT_PRELOAD`                   |
| Rejects         | `BUN_INSPECT`, and `--inspect`, `--inspect-wait` and `--inspect-brk` in `BUN_OPTIONS`                                                                            |
| Ignores         | `--trace-exit`, `--trace-env`, `--trace-env-js-stack` and the three `--trace-event` options in `BUN_OPTIONS` and in the `execArgv` of a `Worker`, with a warning |
| Ignores         | `preload` and `[serve.static] plugins` in a `bunfig.toml`                                                                                                        |

An executable reads the `bunfig.toml` of the directory it's started in. That file may be there for `bun run`, so what it would load is ignored and isn't an error. The build has bundled your pages, so no server needs the plugins.

A module of Bun's own library carries out the `--trace` options of the third row, and an executable has only the modules that your program uses. They print or write something for you to look at, and your program does the same without them. So the executable prints one line for each and runs your program. `--stack-trace-limit` works like in `bun run`.

```txt
warn: --trace-exit is ignored by this executable because it only runs code that was compiled into it. Rebuild it with --compile-inspector to load other code
```

In `--compile-exec-argv`, the options of the first and the third row fail the build.

Two build flags change that.

| Flag                           | In `Bun.build`                       | The executable                                                                            |
| ------------------------------ | ------------------------------------ | ----------------------------------------------------------------------------------------- |
| `--compile-inspector`          | `compile: { inspector: true }`       | Accepts all of the above, so that a debugger can attach. Bun interprets the code it loads |
| `--no-compile-function-source` | `compile: { functionSource: false }` | Rejects the options in the first row, with `--compile-inspector` too                      |

- **`--compile-inspector` has a price.** A debugger can run any code in any scope, so the compiler can prove less about the program. The executable is larger and slower, and [`--trim`](/bundler/aot-size) removes no features.
- **An option in `--compile-exec-argv` is part of the build.** `--inspect` there needs no `--compile-inspector`.
- **Editors set `BUN_INSPECT_CONNECT_TO`** for every process that you start from their terminals. An executable built without `--compile-inspector` ignores it and runs.

## The module cache

A module of the executable runs at most once. `require.cache` and `Module._cache` don't list it, and `delete require.cache[path]` does nothing to it. That goes for CommonJS modules, ES modules and JSON files. An executable built without `--aot` does the same.

```js counter.cjs icon="/icons/javascript.svg"
globalThis.runs = (globalThis.runs ?? 0) + 1;
exports.runs = globalThis.runs;
```

```js again.cjs icon="/icons/javascript.svg"
const path = require.resolve("./counter.cjs");
console.log(require("./counter.cjs").runs, path in require.cache);
delete require.cache[path];
console.log(require("./counter.cjs").runs);
```

```bash terminal icon="terminal"
bun run ./again.cjs && bun compile ./again.cjs && ./again
```

```txt
1 true
2
1 false
1
```

**Circular requires work as under `bun run`.** A module that is required again while it's still running doesn't start over. The second `require()` returns its `module.exports` as it is at that moment, with the names that have been assigned so far. The rest show up as the module keeps running.

One case differs. A callback that you handed to other code may call `require()` on an ES module while that module is still running, without any `import` or `require()` leading from the module back to the file of the callback. The call then returns the module's namespace object, and reading an export that isn't initialized yet throws a `ReferenceError`. Under `bun run` that's what happens if an `import` started the module; if a `require()` started it, the call returns an empty object.

**A CommonJS module that throws isn't tried again.** The `require()` that started it throws. Every later `require()` of that module throws the same error, as it does for an ES module. Under `bun run` the CommonJS module would run again, so a program that repeats a `require()` until something outside of it has changed keeps getting the first error.

**A file that your program loads from disk at run time isn't part of the executable**: an `--external` package, or a config file that a package reads with `require()`. It's in `require.cache`, `delete` takes it out, and it runs again at the next `require()`, as under `bun run`.

**A module of the executable can't be loaded a second time in another form.** `new Bun.ModuleGraph().import(url)` of one rejects with `ERR_MODULE_NOT_FOUND`: a second graph would have to run the module again from its file. `require(path, { type: "text" })` with a path that is put together at run time throws as well, because the file isn't there to be read. Use `import(path, { with: { type: "text" } })` with a constant path: the text is then included at build time.

```txt
error: Cannot load '/$bunfs/root/app.ts': it's compiled into this executable, and a compiled module can't be loaded a second time (for example into a Bun.ModuleGraph).
```

## Loader hooks

The compiler resolves every `import` and every `require()` of a constant path at build time, and compiles it to a call of the module. Nothing in `node:module` is asked on the way, so a hook doesn't see those.

| Hook                                                                                     | The assignment    | Bun calls it for                                                             |
| ---------------------------------------------------------------------------------------- | ----------------- | ---------------------------------------------------------------------------- |
| `Module._resolveFilename`, `Module.prototype.require`                                    | Works             | A `require()` of a [dynamic path](#dynamic-imports), and `require.resolve()` |
| `Module._load`, `Module.wrap`                                                            | Works             | Nothing. `bun run` doesn't call `Module._load` either                        |
| `Module._extensions[".js"]`, and every other extension that a file in the executable has | Throws an `Error` |                                                                              |

Frameworks such as Next.js install the first two when they are loaded, to point a few names at their own copies of a package. In an executable the names that are constants already point where the build found them.

A loader for an extension that no file in the executable has is stored as under `bun run`. Packages such as `handlebars` register one for their own kind of file (`require.extensions[".hbs"]`) when they are required, and it changes nothing that was compiled.

```txt
Cannot replace a loader in Module._extensions: imports in this executable were resolved at build time, so the module loader can't be patched.
```

Packages that patch the loader to transpile, trace or mock what a program requires don't see the modules of an executable. Run such a program with `bun run`, or build it with `--no-aot`.

## Module objects

`module`, `require.main` and `process.mainModule` work as under `bun run`, and so do `children` and `parent` of the objects they give you.

```js
console.log(require.main === module, module.parent?.filename);
for (const child of module.children) console.log(child.id, Object.keys(child.exports));
```

`require.main`, `process.mainModule`, `module.children` and `module.parent` are the only ways from the object of one module to the object of another. The compiler looks for them in the text of your program: `module.children`, `const m = module; m.parent`, `show(require.main)`. What it can answer at build time doesn't count: `require.main === module`, `require.main.filename`, and `!module.parent` in most files.

- **If any file names one of the four, all four work everywhere**, also in a [string that you `eval`](#code-from-strings) and in an `--external` package. It doesn't matter whether the code that names it ever runs.
- **If no file does, all four are `undefined` for everybody**, as in an executable built without `--aot`. That only shows where your code gets to them in a roundabout way: `module[key]` with a computed key, or a `module` that came out of an array or back from native code. The rest of such an object works: `module.exports`, `module.id`, `module.filename`, `require.resolve()`, and `require(path)`, which [finds the entry points](#dynamic-imports).

On an object that the compiler didn't expect anybody to reach, `children` is `undefined` if it would have to list a module for which the compiler keeps no exports object, and `parent` likewise.

If the four always worked, one `require` that a package stores in a table would make the compiler keep an exports object for every CommonJS module of your program. Most need none.

## Re-exports of CommonJS modules

The names that a CommonJS module exports are only known once it has run. The same goes for a JSON file, a built-in module and a module outside of the executable. When an ES module re-exports one of these with `export *`, two rare cases differ from `bun run`. Both are about the namespace object that `import * as ns` gives you. Named imports work the same.

- `b.js` has two or more such `export *` lines, and gets `x` from one of them. `a.js` has `export { x as y } from "./b.js"`. Then `import { y } from "./a.js"` works, but the namespace object of `a.js` has no `y`.
- A file has `export *` for two ES modules that both export `x`. That makes `x` ambiguous, so the namespace object of the file has no `x`. If a third `export *` of that file re-exports a CommonJS module that exports `x` as well, the compiled namespace object has the CommonJS value.

## Workers

Pass the worker as an additional entry point, like in [any executable](/bundler/executables#worker). It's compiled with the rest.

```ts worker.ts icon="/icons/typescript.svg"
declare var self: Worker;
self.onmessage = event => self.postMessage(event.data * 2);
```

```ts spawn.ts icon="/icons/typescript.svg"
const worker = new Worker("./worker.ts");
worker.onmessage = event => {
  console.log(event.data);
  worker.terminate();
};
worker.postMessage(21);
```

```bash terminal icon="terminal"
bun compile ./spawn.ts ./worker.ts --outfile spawn && rm worker.ts && ./spawn
```

```txt
42
```

A Worker that you create from a `blob:` or `data:` URL runs [code that isn't in the executable](#code-that-isnt-in-the-executable), so it fails to load. Put the code in a file and pass it as an entry point.

A file can start itself as a Worker. To tell the two threads apart, use `Bun.isMainThread`, not `import.meta.main`. In an executable with a single entry point, `import.meta.main` is decided at build time, like in any executable: it's `true` in that file on every thread. Under `bun run` it's `false` in the Worker.

## Native addons

`require("./addon.node")` embeds the addon in the executable, like in [any executable](/bundler/executables#embed-n-api-addons). `process.dlopen(module, path)` loads one from disk, and its path can be computed. Calls into either work the same. A `require()` with a computed path doesn't load an addon, because it [only finds code that's in the executable](#code-that-isnt-in-the-executable).

An addon is native code. It can keep, call and change whatever your program hands it, right away or later, and it can read, call and change globals by name. [Built-in objects are read-only](#built-in-objects-are-read-only) for it too. `napi_run_script` runs [code from a string](#code-from-strings), so it throws the same `EvalError` as `eval` unless the compiler found a call to `eval` or `Function` in your program.

## Plugins and build options

[Plugins](/bundler/plugins) of `Bun.build` work with `compile: { aot: true }`. The compiler is handed what your plugins resolve and load, never what's on disk. Which names a CommonJS file exports, in which order modules run and what types a TypeScript module has all come from the text that `onLoad` returns.

```ts build.ts icon="/icons/typescript.svg"
await Bun.build({
  entrypoints: ["./app.ts"],
  compile: { outfile: "./app", aot: true },
  plugins: [
    {
      name: "settings",
      setup(build) {
        build.onResolve({ filter: /^settings:/ }, args => ({ path: args.path.slice(9), namespace: "settings" }));
        build.onLoad({ filter: /.*/, namespace: "settings" }, async args => ({
          contents: `export default ${JSON.stringify(await readSettings(args.path))};`,
          loader: "js",
        }));
      },
    },
  ],
});
```

All of this behaves as in a build without `aot`, and each hook gets the same arguments:

- `onStart`, `onResolve`, `onLoad`, `onEnd`, `defer()`, and `onBeforeParse` with a native plugin
- several plugins, which are asked in order until one answers
- filters, namespaces, modules that are in no file, and what such a module imports
- `external: true`
- every loader, `contents` as a string or as bytes, and answers that come late
- a plugin that throws or rejects: the build fails with its message
- answers for the entry point, for a package in `node_modules`, for a CommonJS file, for a file of a page
- `files`, macros, `define`, `loader`, `env`, `conditions`, `external`, `packages`, `drop`, `features`, `jsx`, `tsconfig`, `root`, `minify` and `sourcemap`

This differs:

|                                                                               | `bun build --compile`                  | `bun compile`                                                              |
| ----------------------------------------------------------------------------- | -------------------------------------- | -------------------------------------------------------------------------- |
| Files that a [computed path](#dynamic-imports) or `import.meta.resolve` names | Not in the executable, so no hook runs | In the executable, so the hooks run for them                               |
| One import that a file has twice                                              | `onResolve` runs twice                 | `onResolve` runs once                                                      |
| One path in two namespaces                                                    | One module                             | Two modules                                                                |
| `minify`                                                                      | Renames functions and classes          | `name` is what you wrote                                                   |
| `sourcemap`                                                                   | A map is one of the outputs            | There's no map. Stack traces have the positions of your sources either way |
| `metafile`                                                                    | One output for each entry point        | [One output, the executable](#metafile)                                    |
| `format`, `bytecode`, `--bytecode-depth`, `--bytecode-order`                  | Change what's in the executable        | No effect. Nothing is bundled, and the executable has no bytecode          |
| `banner` or `footer` with code                                                | Work                                   | The build fails. A `banner` or `footer` that's only comments is fine       |

The text that `onLoad` returns is type checked like a file. `onResolve` doesn't change what the type checker reads: it resolves an import as TypeScript does. So a module that's in no file needs a declaration, like in your editor.

```ts settings.d.ts icon="/icons/typescript.svg"
declare module "settings:*" {
  const settings: { port: number };
  export default settings;
}
```

If the module doesn't match its declaration, the program [behaves as under `bun run`](/bundler/aot-types#when-a-value-doesnt-match-its-type).

### Metafile

`--metafile`, `--metafile-md` and `metafile` in `Bun.build` write [the same format](/bundler#metafile) as without `--aot`. `inputs` lists every file of yours and of your packages that's in the executable, with its imports. Nothing is bundled, so a few things differ:

- `outputs` has one entry, the executable, whatever the number of entry points. Its `entryPoint` is the first one.
- `bytes` of the output is the size of your compiled program inside of the executable. That includes the parts of Bun's own modules, like `node:fs`, that are compiled with it. It doesn't include the Bun runtime.
- `bytesInOutput` is the machine code of the functions in that file. A function that's inlined counts for the file that calls it.
- Files that a [computed path](#dynamic-imports) or `import.meta.resolve` names are inputs, and imports of the file that names them.
- An import that's only types, or that nothing uses, isn't listed. When a file that only re-exports is left out of the executable, its importer lists the files behind it instead, without `original`.

The executable is the same with and without a metafile.

`bun build` on the command line has no plugins, with or without `--aot`. [`Bun.plugin`](/runtime/plugins) in your program is about [code that isn't in the executable](#code-from-strings): a plugin can't replace a module that was compiled.

## `Function.prototype.toString()`

The executable includes the source code of your functions, with the types removed, and `toString()` returns it. It's the text of your file. `bun run` returns what its transpiler printed, so line breaks, indentation and quotes can differ.

`--no-compile-function-source` removes the text. The executable is smaller and doesn't contain your source code. It also [only runs code that was compiled into it](#options-that-load-code). In `Bun.build`, the option is `compile: { functionSource: false }`.

```ts text.ts icon="/icons/typescript.svg"
function add(a: number, b: number): number {
  return a + b;
}
console.log(String(add), add.name, add.length);
```

```bash terminal icon="terminal"
bun compile --no-compile-function-source ./text.ts && ./text
```

```txt
function add() { [native code] } add 2
```

Code that reads parameter names out of that string, as some dependency injection libraries do, finds none.

## Error messages

The class of an error, its line and its stack are the same as under `bun run`. Where `bun run` quotes your source in a message, an executable quotes less of it.

```ts messages.ts icon="/icons/typescript.svg"
const o: any = { a: null };
try {
  o.b();
} catch (error) {
  console.log(String(error));
}
try {
  o.b(1, 2);
} catch (error) {
  console.log(String(error));
}
try {
  new o.b();
} catch (error) {
  console.log(String(error));
}
try {
  o.a.c;
} catch (error) {
  console.log(String(error));
}
try {
  o.a.c = 1;
} catch (error) {
  console.log(String(error));
}
```

```bash terminal icon="terminal"
bun messages.ts
```

```txt
TypeError: o.b is not a function. (In 'o.b()', 'o.b' is undefined)
TypeError: o.b is not a function. (In 'o.b(1, 2)', 'o.b' is undefined)
TypeError: undefined is not a constructor (evaluating 'new o.b')
TypeError: null is not an object (evaluating 'o.a.c')
TypeError: null is not an object (evaluating 'o.a.c = 1')
```

```bash terminal icon="terminal"
bun compile ./messages.ts && ./messages
```

```txt
TypeError: o.b is not a function. (In 'o.b()', 'o.b' is undefined)
TypeError: o.b is not a function. (In 'o.b()', 'o.b' is undefined)
TypeError: undefined is not a constructor (evaluating 'new o.b')
TypeError: null is not an object (evaluating 'null.c')
TypeError: null is not an object (evaluating 'null.c')
```

| The message                    | What an executable quotes                                                                                                                                     |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `… is not a function`          | What you called, as you wrote it: `o.b`, `this.client.send`, `handlers[name]`. Not the arguments                                                              |
| `… is not a constructor`       | The same, behind `new`                                                                                                                                        |
| `… is not an object`           | The value that was `null` or `undefined`, then the name of the property: `null.c`, `undefined["key"]`, `null[0]`. Not the expression that gave you the `null` |
| `… is not an Object.`, of `in` | Nothing: `5 is not an Object.`, where `bun run` adds `(evaluating '"x" in five')`                                                                             |

An executable doesn't hold the text of each expression. It keeps what you called where that consists of names, `this`, `super` and keys in brackets, up to 80 characters. A callee that's more than that has no name in the message: `f()()` says `5 is not a function`, and so does a call with spread arguments.

One more message differs, although `bun run` quotes nothing in it. An update through a computed key, `o[k] += 1`, `o[k]++`, `--o[k]` or `o[k] &&= 1`, throws `undefined is not an object` when `o` is `undefined` and `null is not an object` when it's `null`. `bun run` says `Cannot access property of undefined or null` for both.

When a function of Bun or Node rejects an argument, the end of the message describes what it got, as in `Received an instance of Foo` or `Received { a: 1 }`. An executable writes that description without running your code. It doesn't call a custom inspect function, a getter or a proxy trap. A `Map`, a `Date`, a `Buffer` or any other object that isn't a plain object or an array is shown by its class, as in `Received [Map]`. A `Proxy` whose handler has a `get` trap is `[Object]`. One without is described by its target.

The class of the error is the same, so test `error instanceof TypeError` or `error.name`, not `error.message`. A service that groups errors by message, such as Sentry, sees new groups.

When `bun run` prints an error, it prints the lines of your file around it first, with a caret under the place. An executable prints the message and the stack trace without those lines. It doesn't hold the text of your files, and it never opens a file to show you one: what lies on the disk under that name may not be what was compiled. The stack trace has the lines and columns of your sources. [`bun run --aot`](/bundler/aot-debugging) runs your files where they are, so it prints the lines.

## Class names from computed keys

A class without a name takes the name of the property that it's assigned to. With a computed key, `bun run` sets that name after the static fields of the class have run, and not at all if one of them has read `name`. An executable sets it first, as the ECMAScript specification says.

```ts names.ts icon="/icons/typescript.svg"
function create(key: string) {
  return {
    [key]: class {
      static label = this.name;
    },
  }[key]!;
}

const Shape = create("Shape");
console.log([Shape.label, Shape.name]);
```

```bash terminal icon="terminal"
bun compile ./names.ts && ./names
```

```txt
[ "Shape", "Shape" ]
```

`bun names.ts` prints `[ "", "" ]`.

## Function names from local variables

A function or a class without a name takes the name of the variable that it's assigned to. Inside a function or a block, Bun's transpiler replaces a `let` or `const` that is used once, in the next statement, with its value. Under `bun run` the function then never reaches a variable, so it has no name. An executable gives it the name, as the ECMAScript specification says.

```ts locals.ts icon="/icons/typescript.svg"
function create() {
  const double = (x: number) => x * 2;
  return double;
}

console.log([create().name]);
```

```bash terminal icon="terminal"
bun compile ./locals.ts && ./locals
```

```txt
[ "double" ]
```

`bun locals.ts` prints `[ "" ]`. A `var`, and a variable at the top level of a file, give the name in both.

## Raw strings of tagged templates

`String.raw`, and `strings.raw` in a tag function, give you the text of a template as you wrote it.

```ts raw.ts icon="/icons/typescript.svg"
console.log(String.raw`é`, String.raw`é`.length);
```

```bash terminal icon="terminal"
bun compile ./raw.ts && ./raw
```

```txt
é 1
```

That's what the ECMAScript specification says. `bun raw.ts` prints `é 6`, because Bun's transpiler rewrites every character above U+007F in a tagged template to an escape before the file runs. The cooked strings, `strings[0]` in a tag function, are the same in both.

## Sloppy-mode code

This section applies to CommonJS files without `"use strict"` at the top. ES modules and TypeScript files with `import` or `export` are always strict.

| You write                                  | Compiled                                                                                                                                                  |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `f.caller`, `f.arguments`                  | `null`. The build warns where it can see that `f` is a function                                                                                           |
| `"use strict"` at the top of a function    | The function runs in sloppy mode, as under `bun run`: Bun's transpiler removes the directive. A function declared in a block inside it stays in its block |
| A decorator, with `experimentalDecorators` | The decorator expression runs in strict mode, like the class body. Under `bun run` it runs after the class, in sloppy mode                                |
| A `.cjs` file loaded with `import`         | Sloppy mode, as in Node.js. `bun run` has it strict if it never names `require`, `module` or `exports` and no `package.json` says `"type": "commonjs"`    |

`with` statements work, and so does a direct `eval` that declares variables.

## Flags on process

Bun itself looks at five properties of `process`: `noDeprecation`, `throwDeprecation`, `traceDeprecation`, `traceProcessWarnings` and `domain`. In a compiled executable, Bun only reads them as own properties of `process`. `process.noDeprecation = true` and `BUN_OPTIONS="--no-deprecation"` work as before. `EventEmitter.prototype.noDeprecation = true` doesn't: Bun ignores it, and still warns. `util.inspect` reads its `styles` the same way: only the object's own keys count.

## Memory

- **Each thread can have 32 GB of objects.** References between objects take 32 bits. Objects and small arrays count toward the limit. The characters of strings, large arrays, `ArrayBuffer`s and typed arrays don't. Each `Worker` has a limit of its own. Where the address space of the process is limited (`ulimit -v`), objects take address space as they need it and share the limit with everything else in the process. Address space that objects have taken stays reserved for objects until the process exits. A thread that goes over it gets a `RangeError` whose message starts with "Out of memory" and names the limit and the option that removes it. Your code can catch it. It is thrown where it allocates, in `JSON.parse` and `structuredClone`, or at the next function call that checks the stack. One case is left: a loop that allocates inside a `try` of its own function, or that the compiler has inlined into one, and that calls no function gets no error there, and ends the process with an out-of-memory error once memory is used up. In a `Worker` it ends that Worker alone: its parent gets an `error` event with the `RangeError`, and the exit code is 1. Move the loop into a function of its own. `bun compile --aot-huge-heap` compiles with 64-bit references, which removes the limit. The executable then uses more memory and runs slower.
- **A local variable stops keeping its value alive after its last use,** even if the function is still waiting at an `await`. Under `bun run`, a local variable that a closure captures lives as long as the function's other variables. So if a `FinalizationRegistry` is in a local variable that you never touch again, it can be collected while the function waits, and its callback never runs. Keep the registry at module level.
- **A variable or property that nothing reads doesn't keep its value alive.** The compiler removes it along with the stores into it. If you park an object in a module-level variable only so that a `WeakRef` to it keeps answering, or so that its `FinalizationRegistry` callback doesn't run yet, read that variable somewhere.
