<Warning>Ahead-of-time compilation is experimental.</Warning>

An executable built with [`--aot`](/bundler/executables#ahead-of-time-compilation) has no bytecode and no JIT. Most tools work as they do for any other executable. The debugger does not. This page lists what to expect from each.

Every runtime flag below can be passed to an executable that is already built, through [`BUN_OPTIONS`](/bundler/executables#runtime-arguments-via-bun_options).

## Stack traces

Stack traces have the file, line and column of your sources. You do not need a source map.

```ts app.ts icon="/icons/typescript.svg"
class Repo {
  find(id: number): string {
    if (id < 0) throw new RangeError("bad id " + id);
    return "x";
  }
}
new Repo().find(-1);
```

```bash terminal icon="terminal"
bun build --compile --aot ./app.ts --outfile app && ./app
```

```txt
1 | class Repo {
2 |   find(id: number): string {
3 |     if (id < 0) throw new RangeError("bad id " + id);
                              ^
RangeError: bad id -1
      at find (/$bunfs/root/app.ts:3:27)
      at /$bunfs/root/app.ts:7:12
```

- **`--minify` shortens names and paths**, as it does without `--aot`. See [Minified executables](#minified-executables).
- **Without `--minify`, `--sourcemap` adds nothing.** `bun build` prints a note, and any map that it writes is empty.
- **The path in a frame starts with `/$bunfs/root/`.** What follows is the path of the source file from the directory where you ran `bun build`. A file above that directory has `_.._/` for each `../`. The executable does not contain the path of that directory.
- **The source excerpt is read from disk.** Bun prints it when the file lies at the path that follows `/$bunfs/root/` in the frame, relative to the working directory. On a machine without your sources you get the frames alone.
- **Inlined functions keep their frames.** A strict-mode function that ends in `return f(x)` makes a tail call, so it has no frame while `f` runs, with or without `--aot`.
- `Error.captureStackTrace`, `Error.prepareStackTrace`, `Error.stackTraceLimit`, `console.trace`, async frames, `process.on("uncaughtException")` and `process.on("unhandledRejection")` work as they do without `--aot`.

What differs:

| | without `--aot` | with `--aot` |
| --- | --- | --- |
| Reading a property of `null` | `null is not an object (evaluating 'a.b')` | `Cannot read properties of null (reading 'b')` |
| Calling a value that is not a function | `a.b is not a function. (In 'a.b()', 'a.b' is undefined)` | `b is not a function, it is undefined` |
| Frames of `eval` and `new Function` | `file:///$bunfs/root/app:1:35` | `unknown:1:35` |

If you group errors by message, in Sentry for example, expect new groups for the first two.

### Minified executables

With `--minify`, the names of functions, classes, variables and private members, the names of types in error messages and the paths of your source files become short tokens. The executable does not contain the originals. A name that a property or a string of your program also spells stays, as in any minified bundle, so a method keeps its name. Lines and columns stay those of your sources. `--keep-names` keeps everything.

Code that `--define` or a feature flag removes leaves no text behind, even if your types still mention it:

```ts
type Mode = "plain" | "debug";
interface Options {
  mode: Mode;
  trace?: boolean;
}
```

If the build removes every expression that produces `"debug"` or compares with it, and everything that touches `trace`, the executable contains neither word. For `"debug"` it keeps a hash, so that `JSON.parse('{"mode":"debug"}') as Options` is still recognized as an `Options`. A hash cannot be read or searched for, but someone who guesses the string can confirm the guess. The same goes for the source of a regular expression that your program assembles at run time.

```txt
RangeError: bad id -1
      at find (/$bunfs/root/bA:3:27)
      at /$bunfs/root/bA:7:12
```

To read such a trace, build with `--sourcemap=external`, or `sourcemap: "external"` in `Bun.build`. Bun writes `app.map` next to the executable. The executable contains nothing of that file, and your program does not read it. It is a source map without mappings, because the positions are already the original ones. Its `x_bun_aot.tokens` says what each token stands for:

```json app.map icon="file-json"
{
  "version": 3,
  "sources": [],
  "mappings": "",
  "names": [],
  "x_bun_aot": {
    "positions": "original",
    "tokens": {
      "aA": "Repo",
      "bA": "app.ts"
    },
    "types": [{ "name": "aA", "at": "app.ts:1", "members": { "cache": "Map<number, string> | undefined" } }]
  }
}
```

A token is a lowercase letter followed by letters and digits, at least one of which is a capital. It never has four letters in a row, so it does not spell a word, and it is never a name that your program also uses. So you can replace every token in a text, whether the text is a stack trace or an error message:

```ts restore.ts icon="/icons/typescript.svg"
const { tokens } = (await Bun.file(process.argv[2]).json()).x_bun_aot;
const restore = (text: string) => text.replace(/[a-z][A-Za-z0-9]*/g, word => (Object.hasOwn(tokens, word) ? tokens[word] : word));
console.log(restore(await Bun.stdin.text()));
```

```bash terminal icon="terminal"
./app 2>&1 | bun restore.ts app.map
```

The `TypeError` for a value that does not match its type names the type by its token and describes the types of its members by their structure. `x_bun_aot.types` has what the executable no longer holds: where each type is declared, and each member's type as your source spells it. `name` is what the message prints.

Sentry finds the function names of minified JavaScript by parsing the minified file. An `--aot` executable has no such file, so uploading `app.map` as a source map does not restore them. Apply `restore` to `exception.values[].value` and to the `function`, `filename` and `abs_path` of each frame instead. Do that where you receive or forward the events, not in the program that you ship: the file holds the names that `--minify` took out.

## Crashes

When the process crashes, Bun prints its crash report. With `--aot`, the report ends with the functions of your program that were on the stack:

```txt
panic(main thread): Segmentation fault at address 0x8
oh no: Bun has crashed. This indicates a bug in Bun, not your code.

To send a redacted crash report to Bun's team,
please file a GitHub issue using the link below:

 https://bun.report/1.4.4/M_24eaedc6E…CGaotmh6QCGaot+kmTCGaot+7iT…

Compiled JavaScript on the stack:
    at peek (/$bunfs/root/app.ts:6:17)
    at sum (/$bunfs/root/app.ts:11:47)
    at start (/$bunfs/root/app.ts:15:17)
    at /$bunfs/root/app.ts:19:13
```

These lines go to stderr only. The link holds offsets into your executable, and none of your names or paths.

A function whose last act is a call, as in `return f(x)`, is not in these lines while `f` runs. It is not in a stack trace either, with or without `--aot`.

If all you have is the link, give it back to the same executable. It prints the lines and exits without running your program:

```bash terminal icon="terminal"
BUN_OPTIONS='--aot-decode-crash-report=https://bun.report/1.4.4/M_24eaedc6E…' ./app
```

Keep each executable that you deploy. A link can only be read by the build that produced it.

Infinite recursion is not a crash. It throws a `RangeError` that you can catch.

## CPU profiles

```bash terminal icon="terminal"
BUN_OPTIONS="--cpu-prof" ./app      # a .cpuprofile for Chrome DevTools or VS Code
BUN_OPTIONS="--cpu-prof-md" ./app   # the same as Markdown
```

Profiles name your functions and your source files. `Profiler.start` and `Profiler.stop` of `node:inspector`, and `profile()` of `bun:jsc`, do the same from inside the program.

Time spent in a function that the compiler inlined is counted for its caller.

### perf and gdb

On Linux, the executable has a symbol table and unwind information for your functions, as a C or Go program does, and compiled code keeps frame pointers. `perf` and `gdb` show your functions by name:

```bash terminal icon="terminal"
perf record -g ./app
perf report
```

```bash terminal icon="terminal"
gdb ./app -ex 'break fibonacci' -ex run
```

None of it is loaded when the program runs. `strip ./app` removes it, and the executable still works.

On macOS, native tools such as Instruments, `sample` and `lldb` walk through compiled frames and show addresses, not names. Use `--cpu-prof`.

## Memory

`Bun.generateHeapSnapshot()`, `v8.getHeapSnapshot()`, `v8.writeHeapSnapshot()`, `--heap-prof` and `--heap-prof-md` work. Objects appear under the names of their classes, with the names of their properties.

```bash terminal icon="terminal"
BUN_OPTIONS="--heap-prof" ./app
```

- The variables that a function captures appear by number, `[0]`, `[1]`, not by name.
- A function that your program only ever calls has no object, so it is not in the snapshot.
- `process.memoryUsage()`, `heapStats()` of `bun:jsc`, `v8.getHeapStatistics()` and `node:perf_hooks` work as they do without `--aot`.

## The inspector

`--inspect`, `--inspect-wait` and `--inspect-brk` start the inspector, and VS Code and `debug.bun.sh` connect to it.

| Works | Does not work |
| --- | --- |
| The console, with objects you can open | Breakpoints |
| Evaluating expressions, calling your functions, reading your objects | Stepping and pausing |
| Heap snapshots and garbage collection | `debugger` statements |
| The CPU timeline | The list of sources |

The console shows a warning that says so when a debugger attaches. Code that the build did not compile, such as `eval` and files loaded from disk at run time, can be debugged. The part of Bun that serves the inspector is not compiled into your executable either: it loads only when the inspector starts, and Bun interprets it.

To use breakpoints, run your program from its sources:

```bash terminal icon="terminal"
bun --inspect-brk ./app.ts
```

To find out whether a bug only shows with `--aot`, compare that with `bun run --aot ./app.ts`.

## Instrumentation

`AsyncLocalStorage`, `AsyncResource`, `node:diagnostics_channel` and tracing channels work as they do without `--aot`.

Libraries that trace by replacing functions, such as OpenTelemetry's instrumentations, can replace some things and not others:

| | |
| --- | --- |
| What Bun and Node.js provide: `fetch`, `setTimeout`, `console.*`, `process.*`, `Bun.serve`, `fs.readFileSync`, `http.request`, `EventEmitter.prototype.emit` | can be replaced |
| Classes and exports of JavaScript packages: `pg.Client.prototype.query` | can be replaced |
| Objects of the language: `Promise.prototype.then`, `JSON.parse`, `Date.now`, `Array.prototype.push` | throws a `TypeError` |
| The prototypes of `Request`, `Response`, `Headers`, `Blob`, `URL`, `URLSearchParams` and `BunRequest`: `Response.prototype.json` | throws a `TypeError`. Replace the global with a subclass instead: `globalThis.Response = class extends Response { .. }` |
| Classes written in TypeScript, in your program or in a [typed version of a package](/bundler/executables#typed-versions-of-packages) | throws a `TypeError`, unless TypeScript code of your program assigns to that method |

To wrap a method of one of your own classes, use a subclass or a `Proxy`, or assign to the method in TypeScript: `Db.prototype.query = traced(Db.prototype.query)`.

In an executable, as in any bundle, the modules of your program are resolved when you build. `Module._load`, `Module.prototype.require` and `module.register` are not asked for them. They are asked for built-in modules such as `node:os`. A CommonJS module that throws while it loads is not evaluated again: the next `require()` returns what it had exported by then, as in an executable built without `--aot`.

[`bun run --aot` and `bun test --aot`](/bundler/executables#try-your-code-without-building-an-executable) load your modules from their source files, as `bun run` does, so all of these hooks are asked for your own modules too.

## Code that loses its types

`--aot` is fast where the compiler can use your types. Where it cannot, it does not stop. It compiles that part like plain JavaScript, which behaves the same and runs slower. A class can lose its layout because of one line, and nothing in the program's behavior tells you.

The last line of a build, and of `bun check --aot`, says how much of the program is affected:

```txt
aot: 75.0% of reads typed, 2 of 3 types open, 0 classes without a layout, 0 packages and 0 files untyped (--aot-warn=all lists them)
```

A read is typed if the compiler knows the type of the value that a property or element access produces.

### Rules

A rule reports one kind of loss, where it happens and why. Each rule is off, a warning, or an error that fails the build:

```bash terminal icon="terminal"
bun check --aot ./app.ts --aot-warn=all
bun build --compile --aot ./app.ts --outfile app --aot-deny=untyped-file,lost-layout
```

| Rule              | Reports                                                                                                                        | Default |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------- |
| `untyped-file`    | A TypeScript file or package has type errors that do not stop the build, so it is compiled without its types                   | warning |
| `untyped-package` | A dependency is JavaScript, so it is compiled without types. Says how much of the program it is                                | off     |
| `lost-layout`     | A class has no fixed layout, or leaves declared fields out of it. Its instances or those fields are accessed by name           | off     |
| `untyped-base`    | A class has no fixed layout because it extends a built-in class, such as `Error`, or a JavaScript class                        | off     |
| `open-layout`     | A declared type can also hold objects that typed code did not create, so every property access through it checks first         | off     |
| `external-type`   | A declared type describes data from outside the type system, such as the result of `JSON.parse`, so its shape is not relied on | off     |
| `by-name`         | Typed code reads a property or calls a method of an object whose layout is not known: an `any`, external data, a dictionary    | off     |
| `can-throw`       | A value is checked against its type when the program runs, and the check can fail. The findings of `--aot-explain=throws`      | off     |
| `interpreted`     | `eval`, `new Function` or `node:vm` evaluates source text when the program runs. That code runs in the interpreter             | off     |
| `reshaped-layout` | `Object.freeze`, `seal`, `preventExtensions` or `setPrototypeOf` gets a value of unknown type, so it could reach any object      | off     |

`--aot-deny`, `--aot-warn` and `--aot-allow` take a list of rules, or `all`. If two flags name the same rule, the later one counts. An error from a rule is like a type error: nothing is written and the exit code is 1.

Every finding has its reasons under it, each with a position:

```ts app.ts icon="/icons/typescript.svg"
interface Point {
  x: number;
  y: number;
}
function fromAnywhere(value: any): Point {
  return value;
}
const made: Point = { x: 1, y: 2 };
console.log(made.x + fromAnywhere({ x: 3, y: 4 }).y);
```

```txt
app.ts(1,11): error TS100022: 'Point' can hold objects that typed code did not create, so every property access through it checks the object first. [open-layout]
  app.ts(6,10): A value of type 'any' or 'unknown' is assigned to it here.
```

```ts fiber.ts icon="/icons/typescript.svg"
class Fiber {
  declare id: number;
  declare steps: number;
  [nameFromConfig()]() {}
}
```

```txt
fiber.ts(1,7): error TS100024: Class 'Fiber' leaves declared fields out of its layout, so every access to them is a lookup by name: id, steps. [lost-layout]
  fiber.ts(4,4): The name of this member is computed and is not a constant, so it could be the name of any field.
```

One unchecked `JSON.parse` can take the types away from much more than the line it is on. The type it is cast to, the types inside that type, and the types its values are assigned to all become data that the compiler cannot rely on. `external-type` reports each of them, and its reasons lead back to the place where the data enters:

```ts config.ts icon="/icons/typescript.svg"
interface Server {
  port: number;
}
interface Config {
  server: Server;
}
export const config = JSON.parse(text) as Config;
```

```txt
config.ts(1,11): error TS100029: 'Server' describes data from outside the type system, so the compiler cannot rely on its shape: every property access through it is looked up by name or checked when the program runs. [external-type]
  config.ts(1,11): 'Server' is part of 'Config'.
  config.ts(7,23): A value from outside the type system is used as 'Config' here.
```

Validate the value where it enters the program and build a typed object from it. Then the types stay typed.

`by-name` works on accesses, not on types. It is meant for the code that has to be fast, so limit it to a folder or put `// @aot-strict` on a function. It reports the first access of a chain (`raw.items`, not `raw.items.length`) and only where it can say why. It leaves out built-ins and objects of the runtime, such as `process` or a `Response`.

```txt
app.ts(12,16): error TS100030: 'name' is looked up by name when the program runs: the compiler does not know the layout of the object. [by-name]
  app.ts(11,19): The object is declared here, and its type is 'any'.
```

A build reports only what is in the executable. Code that `--define` or a feature flag removes is not reported. `bun check --aot` has no bundler, so it does not load the JavaScript of a package that ships declaration files. `untyped-package`, and `interpreted` inside such a package, are reported by a build only.

### Some files only

Put a pattern after the rule. It has the syntax of `exclude` in `tsconfig.json` and is relative to the working directory:

```bash terminal icon="terminal"
bun build --compile --aot ./app.ts --outfile app --aot-deny=open-layout:src/server/** --aot-allow=all:node_modules
```

### In the source

`// @aot-strict` makes every rule an error for the declaration that follows it. Before the first statement of a file, it does so for the whole file. Use it on the types and classes that must stay fast:

```ts
// @aot-strict
export class Fiber {
  // ...
}
```

`// @aot-allow` turns rules off for one declaration:

```ts
// @aot-allow untyped-base
export class TimeoutError extends Error {}
```

A comment in the source wins over flags and over `bunfig.toml`.

### bunfig.toml

```toml bunfig.toml icon="settings"
[aot]
deny = ["untyped-file", "lost-layout"]
warn = ["open-layout"]

[[aot.overrides]]
files = ["src/server/**"]
deny = ["open-layout", "interpreted"]
```

`bun build --compile --aot` and `bun check --aot` both read it. Overrides apply in order, after the lists above them. Flags on the command line apply last.

### Only what got worse

A large program has thousands of findings on the day you turn a rule on. A baseline accepts them and fails the build when there are more:

```bash terminal icon="terminal"
bun build --compile --aot ./app.ts --outfile app --aot-deny=all --aot-baseline=aot-baseline.json --aot-update-baseline
git add aot-baseline.json
```

```json aot-baseline.json icon="file-json"
{
  "version": 1,
  "files": {
    "src/db.ts": { "open-layout": 12 },
    "src/server.ts": { "lost-layout": 1, "open-layout": 3 }
  }
}
```

From then on, build without `--aot-update-baseline`:

- While a file has no more findings of a rule than the baseline says, they are not reported.
- Once it has more, all of that rule's findings in that file are reported, each with a line such as `The baseline allows 3 of these in this file, and there are 4.` The baseline holds counts, so it cannot say which one is new.
- A file that is not in the baseline accepts nothing. New files have to be clean.
- When counts fall, a note says so. Run with `--aot-update-baseline` again to lower them in the file.

Paths are relative to the working directory. A package that `untyped-file` reports is counted under its name. In `bunfig.toml`:

```toml bunfig.toml icon="settings"
[aot]
deny = ["all"]
baseline = "aot-baseline.json"
```

### JSON

`--aot-explain=rules-json` prints one object per finding on stdout:

```json
{"rule":"open-layout","severity":"deny","code":100022,"file":"app.ts","line":1,"column":11,"message":"'Point' can hold objects that typed code did not create, so every property access through it checks the object first.","because":[{"code":100040,"file":"app.ts","line":6,"column":10,"message":"A value of type 'any' or 'unknown' is assigned to it here."}]}
```

### What costs the most

A large program has thousands of findings, and most of them go back to a few lines. `--aot-explain` leads every finding of every rule back to the place that causes it, counts what each place costs, and prints the most expensive places first. It needs no `--aot-warn`, and it fails no build:

```bash terminal icon="terminal"
bun check --aot ./config.ts --aot-explain
bun build --compile --aot ./config.ts --outfile app --aot-explain
```

```ts config.ts icon="/icons/typescript.svg"
interface Server {
  port: number;
  host: string;
}
interface Config {
  server: Server;
  names: string[];
}
export const config = JSON.parse(process.argv[2]) as Config;

export function address(config: Config): string {
  return config.server.host + ":" + config.server.port;
}
```

```txt
aot: 1 place where the compiler gives something up, 1 with a cost that can be counted. The most expensive first:

  1. config.ts:9:23 [external-type]
     | export const config = JSON.parse(process.argv[2]) as Config;
     A value from outside the type system is used as 'Config' here.
     cost: 4 reads by name, 1 check of a type in 1 function
     types: 'Server', 'Config'
     for example at config.ts:12:17, config.ts:12:44, config.ts:12:10
     config.ts:1:11: 'Server' is part of 'Config'.
     fix: check the value where it enters the program and build a new object from it in typed code, instead of asserting its type

 In all, by rule:
     external-type: 1 place: 4 reads by name, 1 check of a type
```

- The first line is the cause and the rule it belongs to. That rule, with `--aot-deny`, a pattern or a baseline, keeps it from coming back.
- `cost` counts places in the compiled code, not how often they run: reads, stores and calls that look a property up by name, type checks, checks that may copy an object into another layout, functions that check their parameters when they are entered, field accesses that test the object first, and calls of built-ins such as `JSON.stringify` that are not specialized for the type of their argument.
- `types` are the declared types that the cause takes away from the compiler.
- `for example at` names up to three of the places that pay.
- The lines with a position lead from the cause to the types.
- `fix` says what to change at the cause.

Costs do not add up. If data from outside reaches the same types at several places, or several places can freeze any object, they are one row. It lists the other places (`otherCauses` in the JSON), and the cost stays until all of them are fixed: fixing all but one buys nothing. Fixing one cause can also uncover another behind it, so run the report again after each fix.

The order is an estimate. A place in a loop counts eight times, in a nested loop sixty-four times. Code that only runs while the program starts counts for a sixty-fourth.

`--aot-explain=costs-json` prints every row on stdout, one object per line, for a script or a coding agent:

```json
{"rank":1,"rule":"external-type","file":"config.ts","line":9,"column":23,"inDependency":false,"source":"export const config = JSON.parse(process.argv[2]) as Config;","message":"A value from outside the type system is used as 'Config' here.","because":[{"file":"config.ts","line":1,"column":11,"message":"'Server' is part of 'Config'."}],"types":["Server","Config"],"examples":[{"file":"config.ts","line":12,"column":17},{"file":"config.ts","line":12,"column":44},{"file":"config.ts","line":12,"column":10}],"otherCauses":[],"cost":{"score":45,"readsByName":4,"storesByName":0,"callsByName":0,"checks":1,"checksThatMayCopy":0,"checksOfParameters":0,"guardedAccesses":0,"unspecializedCalls":0,"functions":1,"functionsAfterStart":1},"fix":"check the value where it enters the program and build a new object from it in typed code, instead of asserting its type"}
```

To work through the report, take the first row whose `inDependency` is `false`, read `source`, `because` and `otherCauses`, apply `fix`, and run the report again. Then `--aot-deny` with the row's rule, or a baseline, keeps it from coming back.

## `Function.prototype.toString()`

By default the executable keeps the text of your functions, after TypeScript's types are removed, and `toString()` returns it. The functions of a file that calls `eval()` directly at its top level are the exception: they have no text.

`--no-compile-function-source` leaves the text out, which makes the executable smaller and keeps your code out of it:

```ts
String(function add(a, b) { return a + b; }); // "function add() { [native code] }"
String(class Point {});                       // "class Point { [native code] }"
String(async () => {});                       // "async () => { [native code] }"
```

`name` and `length` stay as they are. Code that reads parameter names out of the text, as some dependency injection libraries do, finds none.
