<Warning>Ahead-of-time compilation is experimental.</Warning>

Without `--aot`, Bun removes your TypeScript types before it runs your program. With [`--aot`](/bundler/aot), the compiler reads them first and generates machine code that depends on them.

## What a type buys

```ts account.ts icon="/icons/typescript.svg"
class Account {
  constructor(
    public id: number,
    public balance: number,
  ) {}
}

function total(accounts: Account[]): number {
  let sum = 0;
  for (const account of accounts) sum += account.balance;
  return sum;
}

const accounts: Account[] = [];
for (let id = 0; id < 1000; id++) accounts.push(new Account(id, id % 100));
console.log(total(accounts));
```

```bash terminal icon="terminal"
bun check --aot ./account.ts --aot-explain
```

```txt
aot: there is no place where the compiler gives something up
```

- **A fixed layout.** Every `Account` has the same two fields at the same offsets. `account.balance` is a load from a known offset, with no lookup and no cache to check.
- **Unboxed numbers.** `balance` is stored as a raw 64-bit number, not as a boxed value.
- **Direct calls.** The compiler knows which function `total(accounts)` calls, so it can call that function directly or inline it.

Here is the same program as JavaScript.

```js account.js icon="/icons/javascript.svg"
class Account {
  constructor(id, balance) {
    this.id = id;
    this.balance = balance;
  }
}

function total(accounts) {
  let sum = 0;
  for (const account of accounts) sum += account.balance;
  return sum;
}

const accounts = [];
for (let id = 0; id < 1000; id++) accounts.push(new Account(id, id % 100));
console.log(total(accounts));
```

```bash terminal icon="terminal"
bun check --aot ./account.js --aot-explain
```

```txt
aot: 1 place where the compiler gives something up, 1 with a cost that can be counted. The most expensive first:

  1. account.js:1:1 [untyped-package]
     'account.js' is JavaScript, so it is compiled without types.
     cost: 3 reads by name, 2 stores by name, 3 calls by name in 3 functions (2 run only while the program starts)
     fix: turn the file into TypeScript
```

Both programs compile, and both print `49500`. In the second one, the compiled code looks up `balance` by name on every iteration of the loop.

## Where untyped values meet typed code

TypeScript lets you call a value a `number` when it isn't one: through `any`, `as`, `!`, `JSON.parse` and declaration files. Without `--aot` nothing happens, because the types are gone when the program runs. With `--aot`, what happens depends on how the value got its type.

| You write                                                                                                      | If the value doesn't match                                    |
| -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| An `any` where a type is declared: `double(anyValue)`, `const n: number = anyValue`, `return anyValue`         | [A `TypeError`](#an-any-that-reaches-a-declared-type)          |
| `anyValue as number`, `as string`, `as boolean`                                                                | [The value is converted](#as-converts-between-primitives)      |
| A type for data from outside: `JSON.parse(text) as User`, `const user: User = JSON.parse(text)`                | [Nothing. The code is slower](#data-from-outside-keeps-its-shape) |
| An object literal that's missing properties of the type you cast it to: `{ name: "x" } as Options`                               | [A `TypeError` where a missing number is used](#an-object-literal-with-missing-properties) |
| `value!`                                                                                                       | [Nothing](#the-non-null-assertion-checks-nothing)              |
| `Bun.validate<User>(value)`                                                                                    | [A `TypeError` that lists every mismatch](#check-data-with-bunvalidate) |

A [type error](/bundler/aot#type-errors-stop-the-build) stops the build, so the table only covers code that TypeScript accepts.

### An `any` that reaches a declared type

```ts visits.ts icon="/icons/typescript.svg"
function double(n: number): number {
  return n * 2;
}

const body: any = JSON.parse('{"visits":"3"}');
console.log(double(body.visits));
```

```bash terminal icon="terminal"
bun visits.ts
```

```txt
6
```

```bash terminal icon="terminal"
bun compile ./visits.ts && ./visits
```

```txt
6 | console.log(double(body.visits));
                       ^
TypeError: expected number | undefined, got string "3" (bun --aot: https://bun.com/docs/bundler/executables#ahead-of-time-compilation)
      at /$bunfs/root/visits.ts:6:20
```

The compiled `double` takes a raw number, so it can't accept a string. The executable checks an `any` at the first declared type that the value reaches: a parameter, a variable, a property or a return type. If the value doesn't match, the check throws a `TypeError`.

The message says `number | undefined` because `undefined` passes this check too, as a missing argument does in JavaScript. `double(undefined)` returns `NaN`, with and without `--aot`. `null` doesn't pass.

When the `any` holds an object, the check at the parameter lets it through. The executable checks each property later, when your code reads it.

```ts label.ts icon="/icons/typescript.svg"
interface User {
  id: number;
  name: string;
}

function label(user: User): string {
  return user.name + " #" + user.id;
}

const body: any = JSON.parse('{"id":"7","name":"Ada"}');
console.log(label(body));
```

```bash terminal icon="terminal"
bun compile ./label.ts && ./label
```

```txt
TypeError: expected number, got string "7" (bun --aot: https://bun.com/docs/bundler/executables#ahead-of-time-compilation)
      at label (/$bunfs/root/label.ts:7:29)
      at /$bunfs/root/label.ts:11:13
```

| The property                                | Reading it                   |
| ------------------------------------------- | ---------------------------- |
| has a value of another type                 | throws a `TypeError`         |
| is a `number` or a `boolean`, and is missing | throws a `TypeError`         |
| is a `string` or an object, and is missing  | gives `undefined`            |
| isn't declared in the type                 | works as in plain JavaScript |

To fix it, narrow the value before it reaches the type. TypeScript doesn't narrow a property of an `any`, so copy the value into a variable of type `unknown` first.

```ts
const body: any = JSON.parse('{"visits":"3"}');
console.log(double(body.visits)); // [!code --]
const visits: unknown = body.visits; // [!code ++]
if (typeof visits !== "number") throw new Error("visits must be a number"); // [!code ++]
console.log(double(visits)); // [!code ++]
```

For a whole object, such as `body` in `label.ts`, use [`Bun.validate`](#check-data-with-bunvalidate).

A check like this can sit on a path that runs once a month. Three tools find them before your users do. [Adopting `--aot`](/bundler/aot-adoption) walks through them in this order:

1. [`bun --aot-audit`](/bundler/aot-reports#run-with-your-own-data) runs your program as usual and logs the checks that would fail.
2. [`bun check --aot --aot-explain=throws`](/bundler/aot-reports#checks-that-can-fail) lists every check like this in your program.
3. `bun compile --aot-type-errors=log` builds an executable that [logs and keeps going where it can](/bundler/aot-adoption#3-log-in-production).

### `as` converts between primitives

```ts page.ts icon="/icons/typescript.svg"
const query: any = { page: "2" };
const page = query.page as number;
console.log(typeof page, page + 1);
```

```bash terminal icon="terminal"
bun page.ts
```

```txt
string 21
```

```bash terminal icon="terminal"
bun compile ./page.ts && ./page
```

```txt
number 3
```

After the cast, the value is what the cast says.

| Cast         | Converts like    | Examples                                      |
| ------------ | ---------------- | --------------------------------------------- |
| `as number`  | `Number(value)`  | `"12"` to `12`, `""` to `0`, `"twelve"` to `NaN` |
| `as string`  | `String(value)`  | `7` to `"7"`                                  |
| `as boolean` | `Boolean(value)` | `"yes"` to `true`, `0` to `false`             |

A cast converts whenever its target is made of primitive types only.

| Cast                                                         | Converts like                                                  |
| ------------------------------------------------------------ | -------------------------------------------------------------- |
| `as UserId`, where `UserId` is `number & { __brand: "UserId" }` | `as number`                                                 |
| `as "asc" \| "desc"`, or a string enum                        | `as string`. `5` becomes `"5"`, which is neither of the two    |
| A numeric enum                                               | `as number`                                                    |
| `as number \| undefined`                                      | `as number`                                                    |
| `as bigint`                                                  | `BigInt(value)`                                                |
| `as unknown as number`, `<number>value`                      | `as number`                                                    |

`null`, `undefined`, objects and arrays pass through every cast unchanged. If typed code then uses such an object as a number, as in `({} as number) + 1`, that throws a `TypeError`.

Nothing tells you when a cast converts. [`bun check --aot --aot-explain=throws`](/bundler/aot-adoption#2-report-when-you-build) lists every cast that can, as `as-convert`. [`bun --aot-audit`](/bundler/aot-adoption#1-audit-while-you-develop) logs each cast that does, as `would-convert`.

Write the conversion out, and the program behaves the same with and without `--aot`.

```ts
const page = query.page as number; // [!code --]
const page = Number(query.page); // [!code ++]
```

### Data from outside keeps its shape

`JSON.parse`, `response.json()` and `structuredClone` return data that the compiler has never seen. So does any function you import from a JavaScript package that only has a declaration file (`.d.ts`). When you give the result a type, with `as` or with an annotation, the compiler treats the type as a prediction. If an object doesn't match, nothing throws and the object isn't changed.

```ts user.ts icon="/icons/typescript.svg"
interface User {
  id: number;
  name: string;
}

const user = JSON.parse('{"id":"7"}') as User;
console.log(typeof user.id, user.id, user.name);
```

```bash terminal icon="terminal"
bun compile ./user.ts && ./user
```

```txt
string 7 undefined
```

`bun user.ts` prints the same output.

The compiler follows the data until somebody writes `any`.

| You write                                                              | If the data doesn't match                                                                       |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `JSON.parse(text) as User`, or `const user: User = JSON.parse(text)`   | Nothing throws                                                                                  |
| `label(JSON.parse(text))`, or `return JSON.parse(text)` in a function that returns a `User` | Nothing throws                                                             |
| `const data = JSON.parse(text)`, and later `label(data)` or `data as User` | Nothing throws                                                                              |
| `const body: any = JSON.parse(text)`, and later `label(body)`          | `body` is an `any` like any other, so [the check](#an-any-that-reaches-a-declared-type) can throw |

Nothing checks the object, and reading `user.id` gives the string. The string can still fail a check later, when it reaches typed code that needs a `number`.

```ts late.ts icon="/icons/typescript.svg"
interface User {
  id: number;
  name: string;
}

function double(n: number): number {
  return n * 2;
}

const user = JSON.parse('{"id":"7"}') as User;
console.log(user.id + 1);
console.log(double(user.id));
```

```bash terminal icon="terminal"
bun compile ./late.ts && ./late
```

```txt
71
TypeError: expected number | undefined, got string "7" (bun --aot: https://bun.com/docs/bundler/executables#ahead-of-time-compilation)
```

You pay for the prediction in speed. Anywhere in your program, the compiler can no longer rely on the shape of a `User`, or of any type inside `User`.

```bash terminal icon="terminal"
bun check --aot ./user.ts --aot-warn=external-type
```

```txt
user.ts(1,11): warning TS100029: 'User' describes data from outside the type system, so the compiler cannot rely on its shape: every property access through it is looked up by name or checked when the program runs. [external-type]
  user.ts(6,14): A value from outside the type system is used as 'User' here.
```

To keep `User` typed, check the data where it enters your program.

### Check data with `Bun.validate`

`Bun.validate<T>(value)` checks a value against a type you've already written. There's no separate schema to keep in sync with it.

```json user.json icon="file-json"
{ "id": 7, "name": "Ada", "role": "admin" }
```

```ts checked.ts icon="/icons/typescript.svg"
import type { Schema } from "bun";

interface User {
  id: number;
  name: string;
}

const user = Bun.validate<User>(await Bun.file("user.json").json());
console.log(typeof user.id, user.name, Object.keys(user));

try {
  Bun.validate<User>({ id: "7", name: "Ada" });
} catch (error) {
  console.log(String(error));
  console.log((error as Schema.Error).issues);
}
```

```bash terminal icon="terminal"
bun compile ./checked.ts && ./checked
```

```txt
number Ada [ "id", "name", "role" ]
TypeError: id: Invalid input: expected number, received string
[
  {
    path: [ "id" ],
    code: "invalid_type",
    expected: "number",
    received: "string",
    message: "Invalid input: expected number, received string",
  }
]
```

If the value matches, `Bun.validate` returns a copy of it, nested objects included. It never changes the value you passed in. The copy keeps properties that `User` doesn't declare, such as `role`. To reject them, validate against `User & Schema.Strict`.

If the value doesn't match, `Bun.validate` throws a `TypeError`. Its `issues` property lists every mismatch, not only the first. `Schema` only exists in types, so there's no class to test with `instanceof`. Test for the property.

```ts
async POST(request) {
  try {
    const user = Bun.validate<User>(await request.json());
    return Response.json({ created: user.id });
  } catch (error) {
    if (error instanceof TypeError && "issues" in error) return Response.json({ issues: error.issues }, { status: 400 });
    throw error;
  }
}
```

`Bun.validate` can't check a type that holds a function, a class such as `Date`, or a type parameter. The build stops with an error that names the property.

```ts job.ts icon="/icons/typescript.svg"
interface Job {
  at: Date;
}

console.log(Bun.validate<Job>({ at: "2026-01-01" }));
```

```bash terminal icon="terminal"
bun compile ./job.ts
```

```txt
error: /path/to/job.ts:5: --aot does not support a type that cannot be validated: Job.at: Date
```

Declare what the data holds. JSON has no dates, so a date arrives as a `string`.

`Bun.validate` needs `--aot`. Plain `bun run` removes your types before the program starts, so `Bun.validate` has nothing to check against and throws a `TypeError` that says so. That error has no `issues`. The same goes for `bun test`, `bun build` and `bun compile --no-aot`. While you develop, use `bun run --aot` and `bun test --aot`. `bun --aot --watch` and `bun --aot --hot` work too.

[Validate data by its type](/bundler/executables#validate-data-by-its-type) lists the types that `Bun.validate` can check. It also lists the `Schema` types for rules that TypeScript can't express, such as a whole number or a minimum length.

You can also write the check yourself and build a new object from the data. [See what the compiler did](/bundler/aot-reports#fix-it) has a worked example.

### An object literal with missing properties

```ts options.ts icon="/icons/typescript.svg"
interface Options {
  name: string;
  times: number;
}

function twice(options: Options): number {
  return options.times * 2;
}

console.log(twice({ name: "x" } as Options));
```

```bash terminal icon="terminal"
bun compile ./options.ts && ./options
```

```txt
TypeError: expected number, got undefined (bun --aot: https://bun.com/docs/bundler/executables#ahead-of-time-compilation)
      at twice (/$bunfs/root/options.ts:7:10)
```

`bun options.ts` prints `NaN`. The cast itself doesn't throw. The executable throws later, where typed code uses a `number` or a `boolean` that the literal left out. A missing `string` or object reads as `undefined`.

Tests often build partial objects this way. Give the literal every property, or make the property optional in the type. The lint rule [`bun/aot-cast-lacks-member`](/lint/rules/bun/aot-cast-lacks-member) finds such casts.

### The non-null assertion checks nothing

```ts port.ts icon="/icons/typescript.svg"
const ports = new Map<string, number>();
const port: number = ports.get("http")!;
console.log(port);
```

```bash terminal icon="terminal"
bun compile ./port.ts && ./port
```

```txt
undefined
```

`bun port.ts` prints the same output. `port` holds `undefined`, whatever its type says, and nothing checks it later either. If you store it in a `number` field of a class, the field reads `undefined`, as it does without `--aot`.

## Patterns that lose types

When the compiler can't use a type, it doesn't stop. It compiles that part like plain JavaScript. Each of these patterns has a [rule](/bundler/aot-debugging#rules) that reports it. `bun check --aot --aot-warn=all` turns on every rule.

| Pattern                                                             | What it costs                                                          | Rule              |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------- | ----------------- |
| `JSON.parse(text) as Config`                                        | Properties of `Config` and of every type inside it are looked up by name                | `external-type`   |
| An `any` that is returned or passed as a declared type              | Every access through that type tests the object first                  | `open-layout`     |
| `class HttpError extends Error`, or a base class from JavaScript    | The class has no fixed layout                                          | `untyped-base`    |
| A member whose name is computed: `[hook]() {}`                      | Declared fields of the class are looked up by name                     | `lost-layout`     |
| `Object.freeze(value)` where `value` is an `any`                    | Every store to a field, in the whole program, tests for a frozen object | `reshaped-layout` |
| A `.js` file or a JavaScript package                                | All of its code is compiled without types                              | `untyped-package` |
| `eval`, `new Function`, `node:vm`                                   | Bun interprets that code                                               | `interpreted`     |

### Build the object in typed code

```ts point.ts icon="/icons/typescript.svg"
interface Point {
  x: number;
  y: number;
}

function fromPlugin(value: any): Point {
  return value;
}

const origin: Point = { x: 0, y: 0 };
console.log(origin.x + fromPlugin({ x: 3, y: 4 }).y);
```

```bash terminal icon="terminal"
bun check --aot ./point.ts --aot-warn=open-layout
```

```txt
point.ts(1,11): warning TS100022: 'Point' can hold objects that typed code did not create, so every property access through it checks the object first. [open-layout]
  point.ts(7,10): A value of type 'any' or 'unknown' is assigned to it here.
```

Even `origin.x` pays, though `origin` never comes near the `any`. Return a new object literal instead, and typed code creates every `Point`.

```ts
function fromPlugin(value: any): Point {
  return value; // [!code --]
  return { x: Number(value.x), y: Number(value.y) }; // [!code ++]
}
```

### Say what you freeze

```ts settings.ts icon="/icons/typescript.svg"
class Settings {
  retries = 3;
}

function lock(value: any): void {
  Object.freeze(value);
}

const settings = new Settings();
lock(settings);
console.log(settings.retries);
```

```bash terminal icon="terminal"
bun check --aot ./settings.ts --aot-warn=reshaped-layout
```

```txt
settings.ts(6,17): warning TS100080: This can freeze any object of the program, because the compiler does not know what it is applied to: every store to a field first tests whether the object is frozen. [reshaped-layout]
```

The same goes for `Object.seal`, `Object.preventExtensions` and `Object.setPrototypeOf`. Give the parameter a type.

```ts
function lock(value: any): void { // [!code --]
function lock(value: Settings): void { // [!code ++]
```

### Subclasses of built-in classes

```ts http-error.ts icon="/icons/typescript.svg"
class HttpError extends Error {
  status: number;
  constructor(status: number, message: string) {
    super(message);
    this.status = status;
  }
}

console.log(new HttpError(404, "Not found").status);
```

```bash terminal icon="terminal"
bun check --aot ./http-error.ts --aot-warn=untyped-base
```

```txt
http-error.ts(1,7): warning TS100027: Class 'HttpError' extends a class from outside typed code, so it has no fixed layout and its instances are compiled as untyped objects. [untyped-base]
  http-error.ts(1,25): This base class is a built-in or comes from JavaScript.
```

An error class is rarely in a hot loop, so leave it as it is. `// @aot-allow untyped-base` above the class turns the rule off for it. For a class that you create by the million, hold the built-in object in a field instead of extending it.

## What else types can do

- [`int32`](/bundler/executables#32-bit-integers) is a 32-bit integer. The build proves that every value stored in one fits, so the executable never checks. It halves the size of a number field.
- [Typed versions of packages](/bundler/executables#typed-versions-of-packages) give a JavaScript package its types back, without changing its code.
- An array type such as `number[]` means an ordinary array. [Compatibility with `--aot`](/bundler/aot-compatibility#an-array-type-means-an-ordinary-array) shows the arrays that this rules out.
