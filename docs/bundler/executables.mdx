---

Bun's bundler implements a `--compile` flag for generating a standalone binary from a TypeScript or JavaScript file.

<Tabs>
  <Tab title="CLI">
    ```bash terminal icon="terminal"
    bun build ./cli.ts --compile --outfile mycli
    ```
  </Tab>
  <Tab title="JavaScript">
    ```ts build.ts icon="/icons/typescript.svg"
    await Bun.build({
      entrypoints: ["./cli.ts"],
      compile: {
        outfile: "./mycli",
      },
    });
    ```
  </Tab>
</Tabs>

```ts cli.ts icon="/icons/typescript.svg"
console.log("Hello world!");
```

Bun bundles `cli.ts` into an executable you can run directly:

```bash terminal icon="terminal"
./mycli
```

```txt
Hello world!
```

Bun bundles all imported files and packages into the executable, along with a copy of the Bun runtime. All built-in Bun and Node.js APIs are supported.

Use the `--target` flag to compile your standalone executable for a different operating system, architecture, or version of Bun than the machine you're running `bun build` on.

### Supported targets

The segments of the `--target` value can appear in any order, as long as they're delimited by `-`.

| --target             | Operating System | Architecture | Libc  |
| -------------------- | ---------------- | ------------ | ----- |
| bun-linux-x64        | Linux            | x64          | glibc |
| bun-linux-arm64      | Linux            | arm64        | glibc |
| bun-windows-x64      | Windows          | x64          | -     |
| bun-windows-arm64    | Windows          | arm64        | -     |
| bun-darwin-x64       | macOS            | x64          | -     |
| bun-darwin-arm64     | macOS            | arm64        | -     |
| bun-linux-x64-musl   | Linux            | x64          | musl  |
| bun-linux-arm64-musl | Linux            | arm64        | musl  |

<Note>
  On x64, Bun ships a single binary that targets Nehalem (SSE4.2) and selects AVX2/AVX-512 code paths at runtime. The
  `-baseline` and `-modern` target suffixes are still accepted for backward compatibility and resolve to the same
  binary; you do not need to pick one based on the destination CPU.
</Note>

## Build-time constants

Use the `--define` flag to inject build-time constants into your executable, such as version numbers, build timestamps, or configuration values:

<Tabs>
  <Tab title="CLI">
    ```bash icon="terminal" terminal
    bun build --compile --define BUILD_VERSION='"1.2.3"' --define BUILD_TIME='"2024-01-15T10:30:00Z"' src/cli.ts --outfile mycli
    ```
  </Tab>
  <Tab title="JavaScript">
    ```ts build.ts icon="/icons/typescript.svg"
    await Bun.build({
      entrypoints: ["./src/cli.ts"],
      compile: {
        outfile: "./mycli",
      },
      define: {
        BUILD_VERSION: JSON.stringify("1.2.3"),
        BUILD_TIME: JSON.stringify("2024-01-15T10:30:00Z"),
      },
    });
    ```
  </Tab>
</Tabs>

Bun inlines these constants into the binary at build time, so they cost nothing at runtime and enable dead code elimination.

<Note>For more examples and patterns, see the [Build-time constants guide](/guides/runtime/build-time-constants).</Note>

## Deploying to production

Compiled executables reduce memory usage and improve Bun's start time.

Normally, Bun reads and transpiles JavaScript and TypeScript files on `import` and `require`. This is part of what makes so much of Bun "just work", but it's not free: reading files from disk, resolving paths, parsing, transpiling, and printing source code costs time and memory.

Compiled executables move that cost from runtime to build time.

When deploying to production, we recommend the following:

<Tabs>
  <Tab title="CLI">
    ```bash icon="terminal" terminal
    bun build --compile --minify --sourcemap ./path/to/my/app.ts --outfile myapp
    ```
  </Tab>
  <Tab title="JavaScript">
    ```ts build.ts icon="/icons/typescript.svg"
    await Bun.build({
      entrypoints: ["./path/to/my/app.ts"],
      compile: {
        outfile: "./myapp",
      },
      minify: true,
      sourcemap: "linked",
    });
    ```
  </Tab>
</Tabs>

### Bytecode compilation

To improve startup time, enable bytecode compilation:

<Tabs>
  <Tab title="CLI">
    ```bash icon="terminal" terminal
    bun build --compile --minify --sourcemap --bytecode ./path/to/my/app.ts --outfile myapp
    ```
  </Tab>
  <Tab title="JavaScript">
    ```ts build.ts icon="/icons/typescript.svg"
    await Bun.build({
      entrypoints: ["./path/to/my/app.ts"],
      compile: {
        outfile: "./myapp",
      },
      minify: true,
      sourcemap: "linked",
      bytecode: true,
    });
    ```
  </Tab>
</Tabs>

Using bytecode compilation, `tsc` starts 2x faster:

<Frame>
  ![Bytecode performance comparison](https://github.com/user-attachments/assets/dc8913db-01d2-48f8-a8ef-ac4e984f9763)
</Frame>

Bytecode compilation moves parsing overhead for large input files from runtime to bundle time. Your app starts faster, in exchange for making the `bun build` command a little slower. Bytecode compilation doesn't obscure source code.

<Note>Bytecode compilation supports both `cjs` and `esm` formats when used with `--compile`.</Note>

### What do these flags do?

The `--minify` argument reduces the size of the transpiled output code. For a large application, this can save megabytes of space. For smaller applications, it might still improve start time a little.

The `--sourcemap` argument embeds a sourcemap compressed with zstd, so that errors & stacktraces point to their original locations instead of the transpiled location. Bun decompresses & resolves the sourcemap automatically when an error occurs.

The `--bytecode` argument enables bytecode compilation. Every time you run JavaScript code in Bun, JavaScriptCore (the engine) compiles your source code into bytecode. `--bytecode` moves that parsing work from runtime to bundle time, which shortens startup.

With `--bytecode`, JavaScriptCore's build-time optimization passes also run over the generated bytecode; `--no-optimize-bytecode` (`optimize: { bytecode: false }` in `Bun.build`) skips them.

### Profile-guided bytecode layout

`--bytecode-order` is profile-guided optimization (PGO) for `--bytecode`. Run your executable once to record which functions it uses, then build again with that profile. Bun places the bytecode the run used together at the front of the file, so the executable reads and decodes less of itself: it starts faster and uses less memory.

In one large CLI application, cold start went from 1.0s to 0.53s and memory at startup dropped by 40 MB.

```sh
# 1. Build
bun build --compile --bytecode ./cli.ts --outfile myapp

# 2. Run it the way your users do. The profile is written on exit.
BUN_BYTECODE_ORDER_OUT=myapp.order ./myapp --help

# 3. Build again with the profile
bun build --compile --bytecode --bytecode-order=myapp.order ./cli.ts --outfile myapp
```

In CI, record the profile and use it in the same job:

```yaml .github/workflows/release.yml icon="file-code"
name: Release
on:
  push:
    tags: ["v*"]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
      - run: bun install

      - name: Build
        run: bun build --compile --bytecode ./cli.ts --outfile myapp

      - name: Record a profile
        run: ./myapp --help
        env:
          BUN_BYTECODE_ORDER_OUT: myapp.order

      - name: Build with the profile
        run: bun build --compile --bytecode --bytecode-order=myapp.order ./cli.ts --outfile myapp

      - uses: actions/upload-artifact@v4
        with:
          name: myapp
          path: myapp
```

With `Bun.build`:

```ts build.ts icon="/icons/typescript.svg"
await Bun.build({
  entrypoints: ["./cli.ts"],
  bytecode: true,
  compile: { outfile: "./myapp", bytecodeOrder: "./myapp.order" },
});
```

- **Profiles keep working as your code changes.** Functions are matched by a hash of their syntax, not by name or position, so a profile from last week's build still applies. Commit it or cache it if recording on every build is inconvenient. Functions that changed since the recording are placed right after the recorded ones.
- **One profile works for every `--target`.**
- **Several profiles** cover several ways of starting the app: `--bytecode-order=interactive.order,oneshot.order`. List the most common one first.
- **Only the layout changes.** The program behaves the same, and builds stay reproducible. The profile contains hashes, not source code.
- `%p` in `BUN_BYTECODE_ORDER_OUT` becomes the process id. `Worker` threads are recorded too.
- `bytecodeOrderStats()` from `bun:jsc` reports how many loaded functions the profile covered (`hot`) or missed (`cold`). A growing share of `cold` means it is time to record again.

### JIT policy

Code that only runs during startup rarely pays back the time the JIT spends compiling it. `--compile-jit-policy <n>` (`compile: { jitPolicy: n }` in `Bun.build`) starts the executable with JavaScriptCore's tier-up thresholds multiplied by `n`, so startup code stays in the interpreter longer. The default, `1`, is the normal JIT policy. The scale stays in effect until the program calls `Bun.unsafe.setJITPolicy(1)`, which it should do once it is interactive:

```ts build.ts icon="/icons/typescript.svg"
await Bun.build({
  entrypoints: ["./app.ts"],
  compile: { outfile: "./myapp", jitPolicy: 8 },
  bytecode: true,
});
```

```ts app.ts icon="/icons/typescript.svg"
await renderFirstScreen();
Bun.unsafe.setJITPolicy(1); // back to the normal JIT policy
```

### Ahead-of-time compilation

<Warning>Ahead-of-time compilation is experimental.</Warning>

`--aot` compiles your JavaScript to machine code when you build the executable. Without it, JavaScriptCore compiles the functions that run often while your program runs.

<Tabs>
  <Tab title="CLI">
    ```bash icon="terminal" terminal
    bun build --compile --aot ./app.ts --outfile myapp
    ```
  </Tab>
  <Tab title="JavaScript">
    ```ts build.ts icon="/icons/typescript.svg"
    await Bun.build({
      entrypoints: ["./app.ts"],
      compile: { outfile: "./myapp", aot: true },
    });
    ```
  </Tab>
</Tabs>

`--aot` implies `--bytecode` and `--format=esm`. `--bytecode-depth` and `--bytecode-order` have nothing to act on, because the executable contains machine code instead of bytecode, so `bun build` reports an error for them. CommonJS files in your program work as they do in any other bundle.

The compiler sees your whole program at once, and the executable differs from one built without `--aot` in these ways:

- **Types are enforced.** The compiler relies on your TypeScript types, so a value that does not match its type throws a `TypeError`, and `as` between primitive types converts. [Adopting `--aot`](/bundler/aot-adoption) shows how to find the places this affects before you ship.
- **`int32` is a 32-bit integer.** `import type { int32 } from "bun"` names a whole number from -2147483648 to 2147483647. To TypeScript it is `number`. With `--aot`, a field, variable, parameter or result of that type takes four bytes, a value that is not such a number throws a `TypeError` where it enters, and a constant that is not stops the build. Only the type that `"bun"` declares has this meaning, under whatever name you import or alias it. A `type int32 = number` of your own is a `number`.
- **Data can be validated by its TypeScript type.** `Bun.validate<T>(value)` and `Bun.parse<T>(text)` check what comes from outside against the type `T` that you have already written. See [Validate data by its type](#validate-data-by-its-type).
- **An array type means an ordinary array.** When the TypeScript type of a value is an array or a tuple, such as `number[]`, reading an element that is defined as a getter throws a `TypeError` instead of calling the getter. The same applies to an element that the array would inherit from a getter or a `Proxy` on its prototype chain. `a[i]`, `for...of` and destructuring are affected. `for...of` and destructuring also throw for an array, or an instance of a subclass of `Array`, that has its own `[Symbol.iterator]` method, instead of calling that method. The same goes for typed arrays such as `Uint8Array`. Declare the value as `Iterable<T>` if you want the method to be called. Assignments still call setters, methods such as `map` and `join` and the spread syntax still call getters, and arrays that typed code never sees behave as usual.
- **The JIT is off.** Bun interprets code that the build cannot see: `eval`, `new Function`, `import()` of a `data:` or `blob:` URL that your program puts together when it runs, files that your program loads from disk when it runs, and Workers created from a blob URL. Some libraries generate their hot code with `new Function` when they start, among them zod 4, ajv, fast-json-stringify and Elysia, and that code stays interpreted for as long as your program runs. If a library has an option to work without generated code, measure both ways: `z.config({ jitless: true })` makes `parse` in zod 4 about 2.5 times cheaper, while `new Elysia({ aot: false })` makes a request slower.
- **A file that your program names in two ways can run twice.** `require(name)` and `import(name)` look for the file on disk when your program puts the name together as it runs. If the executable already contains that file, because other code names it with a string literal, the copy on disk runs as a second module with its own state, and Bun interprets it. If the file is not on disk, the call throws. Use a string literal where you can, or pass the file to `bun build` as another entry point. An executable built with `--compile-in-place` loads the compiled module both ways.
- **Additional entry points are found by their paths.** Files that your program only loads by a name it puts together as it runs, such as a folder of plugins or a worker, are not part of the executable unless you pass them as additional entry points. An entry point can be a glob pattern: `bun build --compile --aot ./app.ts './plugins/*.ts' ./worker.ts`. The executable finds each of them by the path it had when you built it. `require(path.join(__dirname, "plugins", name))`, `require("./plugins/" + name)`, `import()` and `new Worker()` load the compiled code, `require(name)` finds a package whose main file is one of them (`'./node_modules/pg/lib/**/*.js'`), and `fs.existsSync()`, `fs.statSync()` and `fs.readdirSync()` report the files, on a machine that does not have your sources. Reading the text of such a file still fails there.
- **Built-in objects are immutable.** Assigning to, redefining or deleting a property of a built-in object, such as `Array.prototype.push` or `Math.random`, throws a `TypeError` in both strict and sloppy mode. So does adding a property to a built-in prototype such as `Object.prototype`, changing the prototype of a built-in object, or replacing a global variable that names one, such as `Promise`. You can add new properties to a constructor or a namespace such as `Date` or `Math`, unless the new property would hide one that it inherits from another built-in object: `Date.toString = f` throws because it would hide `Function.prototype.toString`. The `Reflect` functions return `false` instead of throwing. `bun build` reports a write that always runs as error `TS100014`, and the lint rule [`bun/aot-locked-builtin-write`](/lint/rules/bun/aot-locked-builtin-write) finds the others. Objects that Bun or your program defines, such as `console` and `process`, stay mutable, with one exception: the prototypes of `Request`, `Response`, `Headers`, `Blob`, `URL` and `URLSearchParams` are immutable too (`File.prototype` is the same object as `Blob.prototype`). Nothing can be added to `Response.prototype`, replaced on it or deleted from it, and its own prototype cannot be changed. Subclasses are not affected: `class MyRequest extends Request` has a prototype of its own and can override any getter or method. Instances can get properties of their own, the static functions such as `Response.json` can be replaced, and so can the global variables, as in `globalThis.Request = MyRequest`. The built-in objects of a context that your program creates with `node:vm`, and of a `ShadowRealm`, stay mutable as well: each has its own.
- **A few things that only sloppy-mode code can do are unavailable.** They concern CommonJS files without `"use strict"`. A `with` statement stops the build. A direct `eval` whose code declares a `var` or a function in the function that calls it throws a `SyntaxError`. `let` and `const` in that code are fine, and so is `(0, eval)(code)`, which declares globals. `f.caller` and `f.arguments` are `null` while `f` runs. `arguments.callee`, `arguments[0]` as another name for the first parameter, `this` as the global object, and writes to read-only properties that do nothing all work as they do without `--aot`.
- **`bun:ffi` callbacks are unavailable.** `dlopen` and calls into native code work. `JSCallback` needs the JIT, and throws a `TypeError` that says so.
- **Breakpoints are unavailable.** The inspector connects, and its console, heap snapshots and CPU profiles work. Breakpoints, stepping and `debugger` statements do not. [Debugging and profiling with `--aot`](/bundler/aot-debugging) lists what each tool shows.
- **[Macros](/bundler/macros) are unavailable**, and so are `bun --aot -e` and `bun --aot -p`.
- **`Bun.build` cannot compile with `aot`** from inside an executable that was compiled with `--aot`: it throws. A build script that you run with `bun run --aot` can.
- **`Bun.ModuleGraph` runs the compiled code.** Each graph gets its own copy of the module state, as without `--aot`. The `globals` option can add names, but it cannot replace a global that already exists, such as `console` or `Math`: importing a compiled module into such a graph throws a `TypeError`.
- **An HTML file is imported with `import page from "./page.html"`**, as in a [full-stack executable](#full-stack-executables). `import()`, `require()` and `import * as` of an HTML file are errors at build time.
- **The executable has no bytecode.** It keeps the text of your functions for `Function.prototype.toString()`. With `--no-compile-function-source` it does not, and `toString()` returns `function name() { [native code] }`. Stack traces have the files, lines and columns of your sources either way.
- **`--minify` shortens names and the paths of your sources in stack traces**, as it does without `--aot`. With `--sourcemap=external`, `bun build` writes a file that turns them back: see [Minified executables](/bundler/aot-debugging#minified-executables).
- **Each thread can hold 32 GB of objects.** References between objects take 32 bits, so the objects of the main thread live in a 32 GB range of address space, and each `Worker` gets a range of its own. Objects and small arrays count toward the limit. The characters of strings, large arrays, `ArrayBuffer`s and typed arrays do not. A thread that fills its range ends the process with an out-of-memory error. `--aot-huge-heap` compiles with 64-bit references, which removes the limit. The executable then uses more memory and runs slower, so only reach for it if you hit the limit. It is a flag of `bun build`, `bun run --aot` and `bun test --aot`; `Bun.build` does not have it.
- **A variable that is not used again keeps nothing alive.** That also holds across an `await`. A `FinalizationRegistry` that nothing refers to any more is collected, and its callback never runs, in every JavaScript engine. Without `--aot`, a local variable that a closure mentions lives as long as the other variables of its function. With `--aot` it ends with its last use, so a registry in such a variable can be collected while the function waits. Keep the registry at module level, or use it after the wait.
- **Some error messages differ.** `null is not an object (evaluating 'o.a.c')` becomes `Cannot read properties of null (reading 'c')`, and `o.b is not a function` becomes `b is not a function, it is undefined`. A service that groups errors by message sees new groups.

The build target must be the platform and the version of Bun that runs the build. `bun build` reports an error for any other `--target`.

#### Validate data by its type

With `--aot` the compiler knows your types, so it can write the code that checks a value against one. There is no schema to keep in step with the type.

```ts server.ts icon="/icons/typescript.svg"
import type { Int, Min, Max, MinLength, MaxLength, MinItems, Format } from "bun";

interface Order {
  customer: { id: number & Int & Min<1>; email: string & Format<"email"> };
  items: { sku: string & MinLength<1> & MaxLength<32>; quantity: number & Int & Min<1> & Max<1000> }[] & MinItems<1>;
  coupon?: string & MaxLength<16>;
}

Bun.serve({
  routes: {
    "/orders": {
      async POST(request) {
        const result = Bun.safeValidate<Order>(await request.json());
        if (!result.success) return Response.json({ issues: result.issues }, { status: 400 });
        return Response.json({ items: result.data.items.length });
      },
    },
  },
});
```

| Call                         | A value that is a `T`         | A value that is not                            |
| ---------------------------- | ----------------------------- | ---------------------------------------------- |
| `Bun.validate<T>(value)`     | returns a copy that is a `T`  | throws a `TypeError` with an `issues` property |
| `Bun.safeValidate<T>(value)` | `{ success: true, data }`     | `{ success: false, issues }`                   |
| `Bun.parse<T>(text)`         | returns a `T`                 | throws a `TypeError` with an `issues` property |
| `Bun.schema<T>()`            | a [Standard Schema](https://standardschema.dev) for libraries that take one |          |

- Each issue has a `path`, a `code`, `expected`, `received` and a `message`.
- Properties that `T` does not declare are left out of the result. A type with an index signature, such as `{ id: number; [key: string]: unknown }`, keeps them. `T & Strict` makes them an issue.
- The required properties of the result come first, in the order in which `T` declares them, then the optional ones, then the ones that an index signature keeps.
- `number` means a finite number: `NaN` and `Infinity` are issues.
- A branded primitive, such as `string & { readonly __brand: "UserId" }`, is checked as the primitive.
- `Bun.parse<T>(text)` parses JSON. It leaves out an optional property whose value does not match its type. A required property that is missing or does not match is an issue, and text that is not JSON throws a `SyntaxError`.
- Without `--aot` TypeScript's types are gone when the program runs, so these functions throw a `TypeError` that says so.
- Objects, optional properties, arrays, tuples, unions, literal types, template literal types such as `` `user-${number}` ``, enums, `null`, `undefined`, `bigint`, `Record<string, T>`, and types that refer to themselves can be checked. A type that holds a function, a symbol, a class such as `Date`, or a type parameter cannot, and `bun build` reports an error that names the property.

The types `Int`, `Min`, `Max`, `Above`, `Below`, `MultipleOf`, `MinLength`, `MaxLength`, `MinItems`, `MaxItems`, `Pattern`, `Format`, `Message`, `Default`, `Strict` and `DeepStrict` from `"bun"` say what a plain type cannot. To TypeScript, `number & Min<1>` is a `number`.

#### Try your code without building an executable

`bun run --aot` and `bun test --aot` run your program from its sources, with the interpreter and the JIT, under the rules of `--aot`. Nothing is compiled ahead of time. Use them while you develop and in CI, and build the executable for production.

```bash icon="terminal" terminal
bun run --aot ./app.ts
bun test --aot
```

Before the first line of your program runs, Bun type checks it together with everything it imports. A type error, or anything else that stops `bun build --compile --aot`, ends the process with exit code 1. While the program runs:

- A value that does not match its declared type throws the `TypeError` that the executable throws, at the same place.
- `as` converts between `string`, `number` and `boolean`, and `x!` throws for `null` and `undefined`.
- Built-in objects are immutable, and objects of a declared type keep their shape.

The check takes a fraction of a second for a small program and seconds for a large one. Bun keeps its result. If no file that the check read has changed since, the next start skips it and is almost as fast as `bun run`. After an edit a small program is checked again as a whole. In a program with 1 MiB or more of TypeScript of its own, if you have only edited your own TypeScript files, and in a way that no other file can see (inside a function, say, without changing what it takes or returns), only those files are checked before your program starts, and the check of the whole program runs beside it. A problem that only the whole-program check can find is then reported late: your program, or your tests, have already begun when Bun prints it and exits with code 1. The result is kept beside the transpiler's cache, so `BUN_RUNTIME_TRANSPILER_CACHE_PATH=0` turns this off, and deleting that folder is always safe. Kept results take at most 1 GiB together: the oldest are deleted first.

With `--watch`, every restart checks again. A type error does not end the process: Bun prints it, runs nothing, and waits for the next save.

In `bun test --aot`, `mock.module()`, `spyOn()`, mock functions and fake timers work as they do in `bun test`. The test runner can also spy on built-in objects, as in `spyOn(Date, "now")` or `spyOn(Array.prototype, "push")`, which your own code cannot change. What a mock returns is held to its type like any other value. The globals `describe`, `it`, `test`, `expect`, `vi`, `jest` and the hooks have the types that your program declares for them, for example through `"types": ["vitest/globals"]`. If nothing declares them, they have the types of the `vitest` that is installed, else of `@jest/globals`, else of `bun:test`, as an import from `"vitest"` or `"@jest/globals"` does. They are always the functions of `bun:test`: one that it does not have, such as `vi.stubGlobal()`, fails the test that calls it. A type error does not stop the whole run: the test files that import the file with the error, directly or through other files, fail without running, and the other test files run. An error in a `--preload` script stops the run.

This mode finds most of what changes under `--aot`, but it does not match the executable in everything yet:

- `bun build` reports some errors that have nothing to do with types, such as an assignment to a `const` or to an import. Here they show when that line runs.
- A type error in code that only the bundler removes, such as the last arm of `table ? a : b` where `table` is a `const` that holds an object, stops `bun run --aot` but not the build.
- When untyped code stores into an object of a declared type, the value is held to the type of the field, with two gaps. An object of the wrong class is not noticed where the field's type is a class or a union of object types. And an object that came from outside, such as the result of `JSON.parse`, is not protected from untyped code after typed code has taken it as a declared type. An executable throws in both cases.
- When untyped code calls a typed function, primitives, arrays, functions and built-in classes are checked against the parameter's type. An object of the wrong class or shape is not noticed at the call if the parameter's type is a class or an object type. An executable throws there.
- A stack trace can show one frame more: the first of a chain of tail calls whose result is checked.

`--aot` applies to a file. For a `package.json` script, a shell script, or an executable in `node_modules/.bin`, `bun run --aot` exits with an error: put `--aot` in the script's own command instead.

A `--preload` script is compiled with your program.

Every file is type-checked with the `tsconfig.json` nearest to it, the same one Bun uses for that file's `paths`, JSX and decorators. This holds for `bun build --compile --aot`, `bun run --aot`, `bun test --aot` and `bun check --aot`. In a monorepo each package keeps its own compiler options, also when another package or a test imports it, and neither the order nor the names of your entry points or test files change what is reported.

- `include` and `exclude` do not decide which `tsconfig.json` applies. A test file that a package's `tsconfig.json` excludes from its build is still checked with that file's options.
- If the nearest `tsconfig.json` has `references`, a file that it does not include itself uses the first referenced project that includes it.
- A file with no `tsconfig.json` above it uses the one of the working directory, or Bun's defaults if there is none.
- Files in `node_modules` use the options of the entry points.
- `--tsconfig-override` applies one file to everything.

Some options cannot differ between the files of one program:

| Options | What the program uses |
| --- | --- |
| `strictNullChecks`, `exactOptionalPropertyTypes`, `strictFunctionTypes`, `strictBindCallApply`, `strictBuiltinIteratorReturn` | On if the `tsconfig.json` of any of your TypeScript files turns it on. If a file whose own `tsconfig.json` leaves one off has type errors, they do not stop the build: Bun prints a warning and compiles that file without its types, which is slower but behaves the same. |
| `lib`, `types`, global declarations in files that a `tsconfig.json` includes, `module`, `moduleResolution`, `jsx`, `skipLibCheck` and the rest | The `tsconfig.json` of the entry points. If they have different ones, the one nearest to the folder that contains all of them, or else Bun's defaults. |

To list every place where your program would behave differently, without stopping at the first one, use [`bun --aot-audit`](/bundler/aot-adoption).

#### Typed versions of packages

`--aot` generates faster code for TypeScript than for JavaScript, because the types tell it how your objects are laid out. Most packages on npm ship JavaScript. A typed version of a package is the package's own code with types added and nothing else changed. When your project has one for the exact files that are installed, `--aot` compiles it in place of the JavaScript. Nothing in `node_modules` is modified, and builds without `--aot` ignore typed versions.

Install the typed version of a package the way you install its `@types` package:

```bash icon="terminal" terminal
bun add -d @sound/react-dom
```

For a package named `pkg`, Bun looks in two places:

1. `.sound/pkg/` in the directory you run the build from. Use it for a package that you have patched.
2. `node_modules/@sound/pkg` (`@sound/scope__pkg` for `@scope/pkg`), if your own `package.json` lists it in `dependencies` or `devDependencies`. Bun ignores a typed version that only one of your dependencies depends on. Your own `package.json` is the nearest one at or above the directory you run the build from.

Either one has a `sound.json` and a `lay` directory:

```json sound.json icon="file-json"
{
  "sound": 1,
  "name": "react-reconciler",
  "version": "0.33.0",
  "when": { "process.env.NODE_ENV": "production" },
  "basis": { "cjs/react-reconciler.production.js": "9eab580c..." },
  "lay": {
    "cjs/react-reconciler.production.ts": "new",
    "index.js": "fc1202d3..."
  },
  "needs": []
}
```

| Field             | Meaning                                                                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `name`, `version` | The installed package they are for.                                                                                                                    |
| `when`            | What the build must [`define`](/bundler#define), as strings.                                                                                           |
| `basis`           | Installed files that the types were written for and that are not replaced, each with its SHA-256.                                                      |
| `lay`             | Paths in the package that `lay/<path>` takes the place of, each with the SHA-256 of the installed file, or `"new"` for a file the package doesn't have. |
| `needs`           | Other packages whose typed versions must be in use too.                                                                                                |

Bun uses a typed version only if everything matches, and says so:

```txt
note: "react-reconciler" 0.33.0 is compiled from its typed version in node_modules/@sound/react-reconciler
```

Otherwise it compiles the package as installed and prints a warning that names the first mismatch, such as after you upgrade the package:

```txt
warn: the typed version of "react-reconciler" in node_modules/@sound/react-reconciler is not used: it is for version 0.33.0, and 0.33.1 is installed (install the typed version for 0.33.1, or remove this one): the package is compiled untyped
```

`Bun.build` returns both in `logs`. `bun run --aot` and `bun test --aot` print neither.

Bun type checks a typed version when you build. What your `tsconfig.json` asks for beyond `strict`, such as `noUncheckedIndexedAccess`, and its `lib`, `target` and `types` do not apply to it. If it has a type error, the build stops with that error, as it does for a type error in your own files:

```txt
error: TS100021: The typed version of 'react-reconciler' in .sound/react-reconciler has type errors (1), the first at /app/node_modules/react-reconciler/cjs/react-reconciler.production.ts:12354:35. Fix it, or remove it to compile 'react-reconciler' untyped.

12354 |   export type ReactElement = $jsx.ReactElement;
                                          ^
note: TS2694: Namespace '"/app/node_modules/react/cjs/react-jsx-runtime.production"' has no exported member 'ReactElement'.
   at /app/node_modules/react-reconciler/cjs/react-reconciler.production.ts:12354:35
```

A package that ships its own TypeScript and has no typed version is compiled without its types instead, with a warning that shows the error, and the `compile` line counts it.

## Automatic config loading

Standalone executables can automatically load configuration files from the directory where they are run. By default:

- **`tsconfig.json`** and **`package.json`** loading is **disabled** — these are typically only needed at development time, and the bundler already uses them when compiling
- **`.env`** and **`bunfig.toml`** loading is **enabled** — these often contain runtime configuration that may vary per deployment

<Note>
  In a future version of Bun, `.env` and `bunfig.toml` may also be disabled by default for more deterministic behavior.
</Note>

### Enabling config loading at runtime

If your executable needs to read `tsconfig.json` or `package.json` at runtime, opt in with these flags:

```bash icon="terminal" terminal
# Enable runtime loading of tsconfig.json
bun build --compile --compile-autoload-tsconfig ./app.ts --outfile myapp

# Enable runtime loading of package.json
bun build --compile --compile-autoload-package-json ./app.ts --outfile myapp

# Enable both
bun build --compile --compile-autoload-tsconfig --compile-autoload-package-json ./app.ts --outfile myapp
```

### Disabling config loading at runtime

To disable `.env` or `bunfig.toml` loading for deterministic execution:

<Tabs>
  <Tab title="CLI">
    ```bash icon="terminal" terminal
    # Disable .env loading
    bun build --compile --no-compile-autoload-dotenv ./app.ts --outfile myapp

    # Disable bunfig.toml loading
    bun build --compile --no-compile-autoload-bunfig ./app.ts --outfile myapp

    # Disable all config loading
    bun build --compile --no-compile-autoload-dotenv --no-compile-autoload-bunfig ./app.ts --outfile myapp
    ```

  </Tab>
  <Tab title="JavaScript">
    ```ts build.ts icon="/icons/typescript.svg"
    await Bun.build({
      entrypoints: ["./app.ts"],
      compile: {
        // tsconfig.json and package.json are disabled by default
        autoloadTsconfig: true, // Enable tsconfig.json loading
        autoloadPackageJson: true, // Enable package.json loading

        // .env and bunfig.toml are enabled by default
        autoloadDotenv: false, // Disable .env loading
        autoloadBunfig: false, // Disable bunfig.toml loading
        outfile: "./myapp",
      },
    });
    ```

  </Tab>
</Tabs>

## Act as the Bun CLI

<Note>New in Bun v1.2.16</Note>

Set the `BUN_BE_BUN=1` environment variable to run a standalone executable as if it were the `bun` CLI itself. The executable ignores its bundled entrypoint and exposes the full `bun` CLI instead.

For example, consider an executable compiled from this script:

```bash icon="terminal" terminal
echo "console.log(\"you shouldn't see this\");" > such-bun.js
bun build --compile ./such-bun.js
```

```txt
[3ms] bundle 1 modules
[89ms] compile such-bun
```

Normally, running `./such-bun` with arguments executes the script.

```bash icon="terminal" terminal
# Executable runs its own entrypoint by default
./such-bun install
```

```txt
you shouldn't see this
```

However, with the `BUN_BE_BUN=1` environment variable, the executable acts like the `bun` binary:

```bash icon="terminal" terminal
# With the env var, the executable acts like the `bun` CLI
BUN_BE_BUN=1 ./such-bun install
```

```txt
bun install v1.2.16-canary.1 (1d1db811)
Checked 63 installs across 64 packages (no changes) [5.00ms]
```

CLI tools built on top of Bun can use this to install packages, bundle dependencies, or run other files without downloading a separate binary or installing Bun.

## Full-stack executables

<Note>New in Bun v1.2.17</Note>

The `--compile` flag can create a standalone executable that contains both server and client code, which suits full-stack applications. When you import an HTML file in your server code, Bun bundles the frontend assets (JavaScript, CSS, and so on) and embeds them into the executable.

<CodeGroup>

```ts server.ts icon="/icons/typescript.svg"
import { serve } from "bun";
import index from "./index.html";

const server = serve({
  routes: {
    "/": index,
    "/api/hello": { GET: () => Response.json({ message: "Hello from API" }) },
  },
});

console.log(`Server running at http://localhost:${server.port}`);
```

```html index.html icon="file-code"
<!DOCTYPE html>
<html>
  <head>
    <title>My App</title>
    <link rel="stylesheet" href="./styles.css" />
  </head>
  <body>
    <h1>Hello World</h1>
    <script src="./app.ts"></script>
  </body>
</html>
```

```ts app.ts icon="file-code"
console.log("Hello from the client!");
```

```css styles.css icon="file-code"
body {
  background-color: #f0f0f0;
}
```

</CodeGroup>

To build this into a single executable:

<Tabs>
  <Tab title="CLI">
    ```bash terminal icon="terminal"
    bun build --compile ./server.ts --outfile myapp
    ```
  </Tab>
  <Tab title="JavaScript">
    ```ts build.ts icon="/icons/typescript.svg"
    await Bun.build({
      entrypoints: ["./server.ts"],
      compile: {
        outfile: "./myapp",
      },
    });
    ```
  </Tab>
</Tabs>

This creates a self-contained binary that includes:

- Your server code
- The Bun runtime
- All frontend assets (HTML, CSS, JavaScript)
- Any npm packages used by your server

The result is a single file you can deploy anywhere without installing Node.js, Bun, or any dependencies:

```bash terminal icon="terminal"
./myapp
```

Bun serves the frontend assets with the correct MIME types and cache headers. Bun replaces the HTML import with a manifest object that `Bun.serve` uses to serve the pre-bundled assets.

For more on building full-stack applications, see the [full-stack guide](/bundler/fullstack).

## Embed assets & files

Standalone executables can embed files directly into the binary, so a single executable can ship images, JSON configs, templates, or any other assets your application needs.

### How it works

Use the `with { type: "file" }` [import attribute](https://github.com/tc39/proposal-import-attributes) to embed a file:

```ts index.ts icon="/icons/typescript.svg"
import icon from "./icon.png" with { type: "file" };

console.log(icon);
// During development: "./icon.png"
// After compilation: "/$bunfs/root/icon-a1b2c3d4.png" (internal path)
```

The import returns a **path string** that points to the embedded file. At build time, Bun:

1. Reads the file contents
2. Embeds the data into the executable
3. Replaces the import with an internal path (prefixed with `/$bunfs/`)

You can then read this embedded file using `Bun.file()` or Node.js `fs` APIs.

### Reading embedded files with Bun.file()

`Bun.file()` is the recommended way to read embedded files:

```ts index.ts icon="/icons/typescript.svg"
import icon from "./icon.png" with { type: "file" };
import { file } from "bun";

// Get file contents as different types
const bytes = await file(icon).arrayBuffer(); // ArrayBuffer
const text = await file(icon).text(); // string (for text files)
const blob = file(icon); // Blob

// Stream the file in a response
export default {
  fetch(req) {
    return new Response(file(icon), {
      headers: { "Content-Type": "image/png" },
    });
  },
};
```

### Reading embedded files with Node.js fs

Embedded files work with the Node.js file system APIs:

```ts index.ts icon="/icons/typescript.svg"
import icon from "./icon.png" with { type: "file" };
import config from "./config.json" with { type: "file" };
import { readFileSync, promises as fs } from "node:fs";

// Synchronous read
const iconBuffer = readFileSync(icon);

// Async read
const configData = await fs.readFile(config, "utf-8");
const parsed = JSON.parse(configData);

// Check file stats
const stats = await fs.stat(icon);
console.log(`Icon size: ${stats.size} bytes`);
```

### Practical examples

#### Embedding a JSON config file

```ts index.ts icon="/icons/typescript.svg"
import configPath from "./default-config.json" with { type: "file" };
import { file } from "bun";

// Load the embedded default configuration
const defaultConfig = await file(configPath).json();

// Merge with user config if it exists
const userConfig = await file("./user-config.json")
  .json()
  .catch(() => ({}));
const config = { ...defaultConfig, ...userConfig };
```

#### Serving static assets in an HTTP server

Use static routes in `Bun.serve()` for efficient static file serving:

```ts server.ts icon="/icons/typescript.svg"
import favicon from "./favicon.ico" with { type: "file" };
import logo from "./logo.png" with { type: "file" };
import styles from "./styles.css" with { type: "file" };
import { file, serve } from "bun";

serve({
  // Inside the compiled executable, file() on an embedded path returns an
  // in-memory Blob, which routes only accepts wrapped in a Response.
  routes: {
    "/favicon.ico": new Response(file(favicon)),
    "/logo.png": new Response(file(logo)),
    "/styles.css": new Response(file(styles)),
  },
  fetch(req) {
    return new Response("Not found", { status: 404 });
  },
});
```

Bun automatically handles Content-Type headers and caching for static routes.

#### Embedding templates

```ts index.ts icon="/icons/typescript.svg"
import templatePath from "./email-template.html" with { type: "file" };
import { file } from "bun";

async function sendWelcomeEmail(user: { name: string; email: string }) {
  const template = await file(templatePath).text();
  const html = template.replace("{{name}}", user.name).replace("{{email}}", user.email);

  // Send email with the rendered template...
}
```

#### Embedding binary files

```ts index.ts icon="/icons/typescript.svg"
import wasmPath from "./processor.wasm" with { type: "file" };
import fontPath from "./font.ttf" with { type: "file" };
import { file } from "bun";

// Load a WebAssembly module
const wasmBytes = await file(wasmPath).arrayBuffer();
const wasmModule = await WebAssembly.instantiate(wasmBytes);

// Read binary font data
const fontData = await file(fontPath).bytes();
```

### Embed text as a string

Use the `text` loader when you want the contents of a file as a string. `.txt` files use it by default. For other extensions, add `with { type: "text" }` or pass `--loader .md:text`.

```ts index.ts icon="/icons/typescript.svg"
import notes from "./notes.txt";
import readme from "./README.md" with { type: "text" };

console.log(notes); // the contents of notes.txt
```

In a compiled executable the text is stored once, in the form the JavaScript engine uses for strings (one byte per character for ASCII text, UTF-16 otherwise). The runtime hands the string back without a copy, so a large text import costs its size in the binary and no extra copy on the heap. A text import is a module, not a file: `Bun.embeddedFiles` does not list it. Use `with { type: "file" }` when you need a file path instead.

### Embed SQLite databases

To embed a SQLite database into the compiled executable, set `type: "sqlite"` in the import attribute and the `embed` attribute to `"true"`.

The database file must already exist on disk. Then, import it in your code:

```ts index.ts icon="/icons/typescript.svg"
import myEmbeddedDb from "./my.db" with { type: "sqlite", embed: "true" };

console.log(myEmbeddedDb.query("select * from users LIMIT 1").get());
```

Finally, compile it into a standalone executable:

```bash terminal icon="terminal"
bun build --compile ./index.ts --outfile mycli
```

<Note>
  The database file must exist on disk when you run `bun build --compile`. The `embed: "true"` attribute tells the
  bundler to include the database contents inside the compiled executable. When running normally with `bun run`, Bun
  loads the database file from disk like a regular SQLite import.
</Note>

In the compiled executable, the embedded database is read-write. Because the database is stored in memory, all changes are lost when the executable exits.

### Embed N-API Addons

You can embed `.node` files into executables.

```ts index.ts icon="/icons/typescript.svg"
const addon = require("./addon.node");

console.log(addon.hello());
```

If you're using `@mapbox/node-pre-gyp` or similar tools, require the `.node` file directly, or it won't bundle correctly.

### Embed directories

Use `--asset` (or `compile.assets` in the JavaScript API) to embed a file or directory tree into the executable under its original relative path. The embedded files live under `import.meta.dir` at runtime and are reachable via `node:fs` (`existsSync`, `statSync`, `readdirSync`, `readFileSync`) and `Bun.file()`.

<Tabs>
  <Tab title="CLI">
    ```bash terminal icon="terminal"
    bun build --compile ./index.ts --asset ./public --outfile myapp
    ```
  </Tab>
  <Tab title="JavaScript">
    ```ts build.ts icon="/icons/typescript.svg"
    await Bun.build({
      entrypoints: ["./index.ts"],
      compile: {
        outfile: "./myapp",
        assets: ["./public"],
      },
    });
    ```
  </Tab>
</Tabs>

```ts index.ts icon="/icons/typescript.svg"
import fs from "node:fs";
import path from "node:path";

const publicDir = path.join(import.meta.dir, "public");

for (const entry of fs.readdirSync(publicDir, { withFileTypes: true })) {
  console.log(entry.name, entry.isDirectory() ? "(dir)" : fs.statSync(path.join(publicDir, entry.name)).size);
}

const html = await Bun.file(path.join(publicDir, "index.html")).text();
```

Pass `--asset` multiple times to embed several directories (for example `--asset ./client --asset ./prerendered` for a SvelteKit build). Bun embeds only regular files; it skips symlinks and empty subdirectories inside the tree.

You can also embed individual files via the `with { type: "file" }` import attribute or, for files that use the `file` loader (images, fonts, and so on) as well as `.wasm` and `.node` files, by adding them as extra entry points. Bun renames imported assets according to `--asset-naming` (default `[name]-[hash].[ext]`):

```ts
import icon from "./public/assets/icon.png" with { type: "file" };
```

### Detecting standalone mode at runtime

Use `Bun.isStandaloneExecutable` to check whether the current process is running from a compiled binary:

```ts index.ts icon="/icons/typescript.svg"
if (Bun.isStandaloneExecutable) {
  // Running from `bun build --compile` output
} else {
  // Running via `bun <file>` or as a library
}
```

Unlike `Bun.embeddedFiles.length > 0`, this check does not allocate `Blob` objects for each embedded file, so it is safe to call at startup in binaries that embed large assets.

### Listing embedded files

`Bun.embeddedFiles` exposes all embedded files as `Blob` objects:

```ts index.ts icon="/icons/typescript.svg"
import "./icon.png" with { type: "file" };
import "./data.json" with { type: "file" };
import "./template.html" with { type: "file" };
import { embeddedFiles } from "bun";

// List all embedded files
for (const blob of embeddedFiles) {
  console.log(`${blob.name} - ${blob.size} bytes`);
}
// Output:
//   icon-a1b2c3d4.png - 4096 bytes
//   data-e5f6g7h8.json - 256 bytes
//   template-i9j0k1l2.html - 1024 bytes
```

Each item in `Bun.embeddedFiles` is a `Blob` with a `name` property:

```ts
embeddedFiles: ReadonlyArray<Blob>;
```

Use it to serve every embedded asset through static routes:

```ts server.ts icon="/icons/typescript.svg"
import "./public/favicon.ico" with { type: "file" };
import "./public/logo.png" with { type: "file" };
import "./public/styles.css" with { type: "file" };
import { embeddedFiles, serve } from "bun";

// Build static routes from all embedded files
const staticRoutes: Record<string, Response> = {};
for (const blob of embeddedFiles) {
  // Remove hash from filename: "icon-a1b2c3d4.png" -> "icon.png"
  const name = blob.name.replace(/-[a-z0-9]+\./, ".");
  // embeddedFiles are plain Blobs, which routes does not accept directly
  staticRoutes[`/${name}`] = new Response(blob);
}

serve({
  routes: staticRoutes,
  fetch(req) {
    return new Response("Not found", { status: 404 });
  },
});
```

<Note>
  `Bun.embeddedFiles` excludes bundled source code (`.ts`, `.js`, etc.) to help protect your application's source.
</Note>

#### Content hash

By default, Bun appends a content hash to the name of each embedded file, which helps with cache invalidation when you serve the files from a URL or CDN. To keep the original name instead, configure asset naming:

<Tabs>
  <Tab title="CLI">
    ```bash terminal icon="terminal"
    bun build --compile --asset-naming="[name].[ext]" ./index.ts
    ```
  </Tab>
  <Tab title="JavaScript">
    ```ts build.ts icon="/icons/typescript.svg"
    await Bun.build({
      entrypoints: ["./index.ts"],
      compile: {
        outfile: "./myapp",
      },
      naming: {
        asset: "[name].[ext]",
      },
    });
    ```
  </Tab>
</Tabs>

## Windows-specific flags

When compiling a standalone executable on Windows, platform-specific options customize metadata on the generated `.exe` file:

<Tabs>
  <Tab title="CLI">
    ```bash terminal icon="terminal"
    # Custom icon
    bun build --compile --windows-icon=path/to/icon.ico ./app.ts --outfile myapp

    # Hide console window (for GUI apps)
    bun build --compile --windows-hide-console ./app.ts --outfile myapp
    ```

  </Tab>
  <Tab title="JavaScript">
    ```ts build.ts icon="/icons/typescript.svg"
    await Bun.build({
      entrypoints: ["./app.ts"],
      compile: {
        outfile: "./myapp",
        windows: {
          icon: "./path/to/icon.ico",
          hideConsole: true,
          // Additional Windows metadata:
          title: "My Application",
          publisher: "My Company",
          version: "1.0.0",
          description: "A standalone Windows application",
          copyright: "Copyright 2024",
        },
      },
    });
    ```
  </Tab>
</Tabs>

Available Windows options:

- `icon` - Path to `.ico` file for the executable icon
- `hideConsole` - Disable the background terminal (for GUI apps)
- `title` - Application title in file properties
- `publisher` - Publisher name in file properties
- `version` - Version string in file properties
- `description` - Description in file properties
- `copyright` - Copyright notice in file properties

<Warning>
  Except for `hideConsole`, you can't use these flags when cross-compiling because they depend on Windows APIs.
</Warning>

## Code signing on macOS

To codesign a standalone executable on macOS (which fixes Gatekeeper warnings), use the `codesign` command.

```bash terminal icon="terminal"
codesign --deep --force -vvvv --sign "XXXXXXXXXX" ./myapp
```

We recommend including an `entitlements.plist` file with JIT permissions.

```xml icon="xml" title="entitlements.plist"
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>com.apple.security.cs.allow-jit</key>
    <true/>
    <key>com.apple.security.cs.allow-unsigned-executable-memory</key>
    <true/>
    <key>com.apple.security.cs.disable-executable-page-protection</key>
    <true/>
    <key>com.apple.security.cs.allow-dyld-environment-variables</key>
    <true/>
    <key>com.apple.security.cs.disable-library-validation</key>
    <true/>
</dict>
</plist>
```

To codesign with JIT support, pass the `--entitlements` flag to `codesign`.

```bash terminal icon="terminal"
codesign --deep --force -vvvv --sign "XXXXXXXXXX" --entitlements entitlements.plist ./myapp
```

After codesigning, verify the executable:

```bash terminal icon="terminal"
codesign -vvv --verify ./myapp
./myapp: valid on disk
./myapp: satisfies its Designated Requirement
```

<Warning>Codesign support requires Bun v1.2.4 or newer.</Warning>

## Using plugins

Plugins work with standalone executables; use them to transform files during the build:

```ts build.ts icon="/icons/typescript.svg"
import type { BunPlugin } from "bun";

const envPlugin: BunPlugin = {
  name: "env-loader",
  setup(build) {
    build.onLoad({ filter: /\.env\.json$/ }, async args => {
      // Transform .env.json files into validated config objects
      const env = await Bun.file(args.path).json();

      return {
        contents: `export default ${JSON.stringify(env)};`,
        loader: "js",
      };
    });
  },
};

await Bun.build({
  entrypoints: ["./cli.ts"],
  compile: {
    outfile: "./mycli",
  },
  plugins: [envPlugin],
});
```

Example use case - embedding environment config at build time:

```ts cli.ts icon="/icons/typescript.svg"
import config from "./config.env.json";

console.log(`Running in ${config.environment} mode`);
console.log(`API endpoint: ${config.apiUrl}`);
```

Plugins can perform any transformation: compile YAML/TOML configs, inline SQL queries, generate type-safe API clients, or preprocess templates. See the [plugin documentation](/bundler/plugins).

## Unsupported CLI arguments

The `--compile` flag does not support the following flags:

- `--outdir` — use `outfile` instead.
- `--public-path`
- `--target=node`
- `--target=browser` (without HTML entrypoints — see [Standalone HTML](/bundler/standalone-html) for `--compile --target=browser` with `.html` files)
- `--no-bundle` - Bun always bundles everything into the executable.

## API reference

The `compile` option in `Bun.build()` accepts three forms:

```ts title="types" icon="/icons/typescript.svg"
interface BuildConfig {
  entrypoints: string[];
  compile: boolean | Bun.Build.CompileTarget | CompileBuildOptions;
  // ... other BuildConfig options (minify, sourcemap, define, plugins, etc.)
}

interface CompileBuildOptions {
  target?: Bun.Build.CompileTarget; // Cross-compilation target
  outfile?: string; // Output executable path
  assets?: string[]; // Files/directories to embed under import.meta.dir
  execArgv?: string[]; // Runtime arguments (process.execArgv)
  executablePath?: string; // Bun executable to use instead of downloading one for target
  autoloadTsconfig?: boolean; // Load tsconfig.json (default: false)
  autoloadPackageJson?: boolean; // Load package.json (default: false)
  autoloadDotenv?: boolean; // Load .env files (default: true)
  autoloadBunfig?: boolean; // Load bunfig.toml (default: true)
  bytecodeOrder?: string | string[] | false | null; // Order file(s) to lay the bytecode out by (requires bytecode: true)
  jitPolicy?: number; // JIT tier-up threshold scale at startup (default: 1 = normal)
  windows?: {
    icon?: string; // Path to .ico file
    hideConsole?: boolean; // Hide console window
    title?: string; // Application title
    publisher?: string; // Publisher name
    version?: string; // Version string
    description?: string; // Description
    copyright?: string; // Copyright notice
  };
}
```

Usage forms:

```ts icon="/icons/typescript.svg"
// Simple boolean - compile for current platform (uses entrypoint name as output)
compile: true

// Target string - cross-compile (uses entrypoint name as output)
compile: "bun-linux-x64"

// Full options object - specify outfile and other options
compile: {
  target: "bun-linux-x64",
  outfile: "./myapp",
}
```

Without `outfile`, the executable is named after the entrypoint and written to `outdir`, or to the current working directory when there is no `outdir`. This matches `bun build --compile`.

### Supported targets

```ts title="Bun.Build.CompileTarget" icon="/icons/typescript.svg"
type CompileTarget =
  | "bun-darwin-x64"
  | "bun-darwin-arm64"
  | "bun-linux-x64"
  | "bun-linux-arm64"
  | "bun-linux-x64-musl"
  | "bun-linux-x64-baseline-musl"
  | "bun-linux-arm64-musl"
  | "bun-windows-x64"
  | "bun-windows-arm64";
// The "-baseline" and "-modern" suffixes are accepted for backward
// compatibility and resolve to the same x64 binary.
```

### Complete example

```ts build.ts icon="/icons/typescript.svg"
import type { BunPlugin } from "bun";

const myPlugin: BunPlugin = {
  name: "my-plugin",
  setup(build) {
    // Plugin implementation
  },
};

const result = await Bun.build({
  entrypoints: ["./src/cli.ts"],
  compile: {
    target: "bun-linux-x64",
    outfile: "./dist/mycli",
    execArgv: ["--smol"],
    autoloadDotenv: false,
    autoloadBunfig: false,
  },
  minify: true,
  sourcemap: "linked",
  bytecode: true,
  define: {
    "process.env.NODE_ENV": JSON.stringify("production"),
    VERSION: JSON.stringify("1.0.0"),
  },
  plugins: [myPlugin],
});

if (result.success) {
  console.log("Build successful:", result.outputs[0].path);
}
```
