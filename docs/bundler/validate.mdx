<Warning>`JSON.parse<T>()` and `validate<T>()` are experimental.</Warning>

```ts
const user = JSON.parse<User>(text);
```

TypeScript takes your word for the type of parsed JSON. `JSON.parse(text) as User` compiles whether or not the text is a `User`, and the mistake shows up later, somewhere else.

`JSON.parse<User>(text)` checks. Bun reads the type argument when it compiles the file and generates the check from it, so there's no schema to write and keep in sync with the type. If the data doesn't match, the call throws.

It works under [`bun compile`](/bundler/aot), `bun run --aot` and `bun test --aot`. See [Where it works](#where-it-works).

## Parse JSON

Pass the type of the data as the type argument.

```ts user.ts icon="/icons/typescript.svg"
import type { Schema } from "bun";

interface User {
  id: number;
  name: string;
  tags?: string[];
}

const user = JSON.parse<User>('{"id":7,"name":"Ada","role":"admin"}');
console.log(user.id, user.name, Object.keys(user));

try {
  JSON.parse<User>('{"id":"7","tags":["a",1]}');
} catch (error) {
  console.log(String(error));
  for (const issue of (error as Schema.Error).issues) console.log(issue.path, issue.code, issue.message);
}
```

```bash terminal icon="terminal"
bun run --aot user.ts
```

```txt
7 Ada [ "id", "name", "role" ]
TypeError: id: expected number, received string (and 2 more)
[ "id" ] invalid_type Invalid input: expected number, received string
[ "name" ] invalid_type Invalid input: expected string, received undefined
[ "tags", 1 ] invalid_type Invalid input: expected string, received number
```

| Call                    | The text is a `T` | The text is JSON, but not a `T`                | The text isn't JSON    |
| ----------------------- | ----------------- | ---------------------------------------------- | ---------------------- |
| `JSON.parse<T>(text)`   | Returns the value | Throws a `TypeError` with an `issues` property | Throws a `SyntaxError` |
| `JSON.parse<any>(text)` | Returns the value | Returns the value                              | Throws a `SyntaxError` |

- **The result is what `JSON.parse(text)` returns.** Properties that `T` doesn't declare, such as `role`, are still there. To reject them, use [`T & Schema.Strict`](#rules-that-a-type-cant-express).
- **`import { JSON } from "bun"` is the global `JSON`, typed with the type argument.** It's the same object. See [Types in your editor](#types-in-your-editor) for the global name.
- **Only a call with a type argument checks.** `JSON.parse(text)` is the ordinary call and returns `any`. `JSON.parse(text) as User`, `const user: User = ...` and `.then(JSON.parse)` check nothing.
- **Bun goes by what the name refers to, not by how the call is spelled.** `const { parse } = JSON; parse<User>(text)` checks too.
- **The reviver runs first.** `JSON.parse<T>(text, reviver)` checks what the reviver returns and hands it to you as it is: an object that the reviver returned is that same object in the result. So `Schema.Default` fills nothing in when you pass a reviver.
- **`T` can come from anywhere.** Bun's type checker resolves it, so you can import it from another file or from a package, and it can be `Partial<User>`, `Omit<User, "id">` or `Page<User>`.

### Types in your editor

A build knows the type argument by itself. Your editor and `tsc` learn it from `@types/bun`, in one of two ways.

Import `JSON` from `"bun"`. Nothing else changes.

```ts
import { JSON } from "bun";

const user = JSON.parse<User>(text);
```

Or add the type argument to the global `JSON`, with one line in any file of the project:

```ts
/// <reference types="bun-types/aot" />
```

The second way gives the global `JSON.parse` a second signature for the whole project. You can see that in two places, even in a file that never passes a type argument. That's why you have to ask for it.

- A function expression that you type as `typeof JSON.parse` needs types on its parameters, because TypeScript doesn't infer them from an overloaded type. So does a `parse` method in an object that you type as `JSON`.
- A call with a wrong argument, such as `JSON.parse(buffer)`, is error TS2769 ("No overload matches this call") and no longer TS2345.

## Validate a value

`validate<T>(value)` does the same for a value that isn't text: the fields of a form, a message from a Worker, a row from a database.

```ts login.ts icon="/icons/typescript.svg"
import { validate } from "bun:bundle";
import type { Schema } from "bun";

interface Login {
  name: string & Schema.MinLength<1>;
  password: string & Schema.MinLength<8>;
}

const form = new FormData();
form.set("name", "ada");
form.set("password", "hunter2");

try {
  validate<Login>({ name: form.get("name"), password: form.get("password") });
} catch (error) {
  console.log(String(error));
}
```

```bash terminal icon="terminal"
bun run --aot login.ts
```

```txt
TypeError: password: expected string to have >=8 characters
```

`validate` throws the same `TypeError` as `JSON.parse<T>`. If the value matches, it returns a copy. Bun copies the objects and arrays that `T` describes, with all of their keys in the same order, and never changes the value you passed in.

For JSON text, prefer `JSON.parse<T>(await request.text())` to `validate<T>(await request.json())`. It makes no copy.

`validate` comes from `"bun:bundle"`, like [`feature`](/bundler#features), because it only exists while Bun compiles the file. Import it by name and call it with a type argument. You can't assign it, pass it as an argument or export it.

## Handle the error

The `TypeError` has an `issues` array. To TypeScript, that error is a `Schema.Error`. `Schema` only exists in types, so there's no class to test with `instanceof`. Test for `issues` instead.

```ts server.ts icon="/icons/typescript.svg"
interface Order {
  sku: string;
  quantity: number;
}

Bun.serve({
  routes: {
    "/orders": {
      async POST(request) {
        try {
          const order = JSON.parse<Order>(await request.text());
          return Response.json({ sku: order.sku });
        } catch (error) {
          if (error instanceof SyntaxError) return Response.json({ error: "The body isn't JSON" }, { status: 400 });
          if (error instanceof TypeError && "issues" in error)
            return Response.json({ issues: error.issues }, { status: 400 });
          throw error;
        }
      },
    },
  },
});
```

| Property of an issue   | Example                                                                                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `path`                 | `["items", 0, "sku"]`                                                                                                                                |
| `code`                 | `"invalid_type"`, `"invalid_value"`, `"invalid_union"`, `"too_small"`, `"too_big"`, `"not_multiple_of"`, `"invalid_format"` or `"unrecognized_keys"` |
| `expected`, `received` | `"number"`, `"string"`                                                                                                                               |
| `message`              | `"Invalid input: expected number, received string"`                                                                                                  |

The codes and messages are worded like those of zod 4. The message of the `TypeError` describes the first mismatch and counts the rest. `issues` lists them, up to the first 100.

## Rules that a type can't express

The types in `Schema` add rules to a type. They have no run-time value, so import them with `import type`. To TypeScript, `number & Schema.Min<1>` is a `number`, and you can assign a plain `5` to it.

```ts
import type { Schema } from "bun";

interface Order {
  email: string & Schema.Format<"email">;
  quantity: number & Schema.Int & Schema.Min<1> & Schema.Max<1000>;
  coupon?: string & Schema.MaxLength<16>;
  items: string[] & Schema.MinItems<1>;
}
```

| Type                                                    | The value                                                                         |
| ------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `number & Schema.Int`                                   | is a whole number                                                                 |
| `Schema.Min<1>`, `Schema.Max<100>`                      | is at least 1, at most 100                                                        |
| `Schema.Above<0>`, `Schema.Below<1>`                    | is more than 0, less than 1                                                       |
| `Schema.MultipleOf<5>`                                  | is a multiple of 5                                                                |
| `string & Schema.MinLength<1>`, `Schema.MaxLength<100>` | has that many characters                                                          |
| `string & Schema.Pattern<"^[a-z]+$">`                   | matches the regular expression                                                    |
| `string & Schema.Format<"email">`                       | is an `"email"`, `"uuid"`, `"ipv4"`, `"ipv6"`, `"date"`, `"date-time"` or `"url"` |
| `string[] & Schema.MinItems<1>`, `Schema.MaxItems<10>`  | has that many elements                                                            |
| `number & Schema.Default<8080>`                         | is `8080` in the result when the property is missing. The property needs no `?`   |
| `Schema.Message<"Order at least one">`                  | fails with this message                                                           |
| `{ id: number } & Schema.Strict`                        | has no property that the type doesn't declare                                     |
| `Schema.DeepStrict`                                     | the same, for every object type inside the type too                               |

`MinLength` and `MaxLength` count Unicode code points, like JSON Schema and zod. `"🍞".length` is 2, but it's one character here. Half of a surrogate pair on its own counts as one.

## What a type means

The check is a little stricter than TypeScript. Some values that you can assign to `T` don't pass.

- A property without `?` has to be there, even if its type is `unknown` or includes `undefined`.
- `number` means a finite number. `1e400` parses to `Infinity`, so it fails the check.
- An object type only matches plain objects. `{ p: {} }` rejects `{"p": 1}` and `{"p": []}`, though TypeScript accepts a number or an array as `{}`. `{ length: number }` rejects a string and an array.
- `object` matches objects and arrays. `Record<string, any>` matches objects.
- `any` and `unknown` inside `T` accept whatever is there.
- A branded primitive, such as `string & { readonly __brand: "UserId" }`, is checked as the primitive.
- Bun tries the members of a union in the order you declared them, and builds the value as the first member that accepts it. `{ port: number & Schema.Default<80> } | Record<string, number>` fills in `port`. `Record<string, number> | { port: number & Schema.Default<80> }` doesn't. Members that a literal property tells apart, such as `kind: "circle"` and `kind: "square"`, are picked by that property before any other member is tried. If no member accepts the value, the error points to the value that failed.

Bun can check primitives, objects, optional properties, arrays, tuples, unions, intersections, literal types, template literal types such as `` `user-${number}` ``, enums, `null`, `Record<string, T>` and types that refer to themselves.

Bun can't check a type that contains one of these. The error says which property it is.

- a function or a symbol
- a class, such as `Date`
- a type parameter
- a tuple with an optional or a rest element, such as `[string, number?]`
- an index signature whose key isn't `string`, such as `{ [key: number]: string }`, or more than one index signature

```ts job.ts icon="/icons/typescript.svg"
import { validate } from "bun:bundle";

interface Job {
  at: Date;
}

console.log(validate<Job>({ at: "2026-01-01" }));
```

```bash terminal icon="terminal"
bun run --aot job.ts
```

```txt
error: TS100107: validate<Job>() cannot validate 'at: Date'. Only types that JSON can represent can be validated.
```

Declare what the data contains. JSON has no dates, so a date arrives as a `string`.

A type parameter rules out a generic wrapper such as `function load<T>(text: string) { return JSON.parse<T>(text); }`. Bun generates the check at the call site, and `T` isn't known there. Pass a concrete type at each call site.

If `T` refers to itself and the JSON is nested thousands of levels deep, the call throws a `RangeError`. You can catch it.

## Where it works

| Command                                                                       | `JSON.parse<T>(text)`           | `validate<T>(value)`   |
| ----------------------------------------------------------------------------- | ------------------------------- | ---------------------- |
| `bun compile`, `bun build --compile --aot`, `bun run --aot`, `bun test --aot` | Validates                       | Validates              |
| `bun run`, `bun test`, `bun build`, `Bun.Transpiler`                          | Is `JSON.parse(text)`: no check | The import is an error |

**Without `--aot`, the type argument is erased.** Bun removes it like any other type, and so do `tsc`, esbuild, swc and Vite. `JSON.parse<User>(text)` then parses and checks nothing, and nothing says so. If your program relies on the check, run its tests with `bun test --aot`. `validate` can't be skipped that way, because it only exists while Bun compiles the file.

**A file that an executable loads at run time isn't compiled.** Calls that Bun compiled into the executable validate. In a TypeScript file that the executable loads from disk, `JSON.parse<T>(text)` is `JSON.parse(text)`.

## In a compiled executable

[`bun compile`](/bundler/aot) uses your types to generate machine code, and unchecked data is what most often gets in its way. One `JSON.parse(text) as User` slows down every read that the object can reach. The compiler trusts a value that was validated, so those reads are as fast as they are for an object that your own code created. See [Unchecked data keeps its shape](/bundler/aot-types#unchecked-data-keeps-its-shape).
