<Warning>Ahead-of-time compilation is experimental.</Warning>

`bun compile` compiles your program to machine code at build time and writes one executable. It runs on machines that don't have Bun installed.

```bash terminal icon="terminal"
bun compile ./server.ts
./server
```

There's no new syntax and nothing to annotate. TypeScript, JavaScript and npm packages all compile. Where your code has types, the compiler [uses them](/compiler/types) to generate faster code.

## What to expect

Under `bun run`, and in an executable from [`bun build --compile`](/compiler/executables), your code starts in an interpreter and a JIT compiles the hot functions while the program runs. `bun compile` does that work at build time, and the executable has no JIT.

What you get:

- Your program starts faster. There's no source to parse and nothing to warm up.
- It uses less memory. The process has no bytecode, no JIT-compiled code and no profiling data.
- Typed code runs faster. A property access is one load from a fixed offset, like a struct field in Go or Rust.
- A small program's file is smaller, because it leaves out the `bun` command line and the JIT. In a large program, the machine code can outweigh that. [`--trim`](/compiler/size) removes the Bun APIs you don't use.

What it costs:

- The build takes longer. Bun type checks and compiles every function that the program can reach, and nothing is cached between builds.
- Untyped code can run slower than under the JIT. A JIT watches the program run and learns which objects show up at each property access. The compiler has to prove that at build time. Where it can't, the code looks the property up at run time.
- [A few things differ from `bun run`](/compiler/compatibility). Built-in objects such as `Array.prototype` are read-only, and code from a string (`eval`, `new Function`) runs in an interpreter.

[`bun compile --explain`](/compiler/explain) lists the code that compiled to a slow path, worst first, with a fix for each.

## When to stay with the JIT

- Peak throughput matters most, and your hot code is untyped JavaScript from npm.
- You build on one platform and deploy to another. `bun compile` only builds for the platform it runs on, so run it in CI or in a container.
- A library generates its hot code with `new Function`, as some validators and serializers do. [That code is interpreted](/compiler/compatibility#code-from-strings).
- A dependency changes [built-in objects](/compiler/compatibility#built-in-objects-are-read-only). Assigning to `Array.prototype.push` throws a `TypeError`.
- Your program spends its time in [WebAssembly](/compiler/compatibility#webassembly) that it downloads or decodes at run time. Only a `.wasm` file that you import is compiled.
- You need breakpoints in the executable. [The inspector](/compiler/debugging#the-inspector) connects, but it can't pause compiled code.

If you aren't sure, build the same entry point both ways and measure. With `--no-aot`, the executable holds your JavaScript and runs it with the JIT.

```bash terminal icon="terminal"
bun compile --no-aot ./server.ts --outfile server-jit
bun compile ./server.ts --outfile server-aot
```

Put both under the same load, on routes that do what your application does in production. Run the load twice and keep the second result, so the JIT has warmed up. [Benchmarking](/project/benchmarking) covers the tools.

`bun compile` is short for `bun build --compile --aot` and takes the same flags. Without an entry point, it builds the file that `"bin"` in `package.json` points to, then `"module"`, then `"main"`, then `index.ts`.

### Type errors stop the build

```ts wrong.ts icon="/icons/typescript.svg"
const port: number = "3000";
console.log(port);
```

```bash terminal icon="terminal"
bun compile ./wrong.ts
```

```txt
1 | const port: number = "3000";
          ^
error: TS2322: Type 'string' is not assignable to type 'number'.
    at /path/to/wrong.ts:1:7
```

`bun run` removes your types and never checks them. `bun compile` relies on them, so it type checks the program first. If there's a type error, it writes no executable and exits with code `1`. It doesn't check code that the executable leaves out: a type error inside a function that nothing calls doesn't stop the build. `bun compile --check` and `bun check --aot` check that function too.

`bun compile --check` and `bun check --aot` don't type check [a branch that the build removes](/runtime/check#bun-compile), such as `if (process.platform === "win32")` on Linux. In that branch, they report only the few errors that also stop the build there, such as a `let` declared twice or a store to a constant or an import. They report no type errors in a file that the build doesn't compile, such as one that you import only with `import type`. Run `bun check` without `--aot` to see the type errors in both.

JavaScript files aren't type checked, even with `checkJs` or `// @ts-check`. A syntax error in one still stops the build.

One error is different. TypeScript gives up on a type after 100 nested steps and reports `TS2589` ("Type instantiation is excessively deep and possibly infinite"). The compiler works such a type out in parts instead, so `TS2589` only stops the build when the type really has no end. `bun check` still reports it wherever `tsc` does.

[`bun check --aot`](/runtime/check) reports every error that stops the build, and also the type errors in functions that nothing calls. It builds nothing. Bun checks each file with the nearest `tsconfig.json`, and reads that config's `files` and `include` for the globals they declare, even if nothing imports them. If you can't fix an error yet, you can [suppress it](/compiler/troubleshooting#the-build-stops-at-a-type-error).

The build only stops where `tsc` reports an error under your own `tsconfig.json`:

- `"noCheck": true` turns type errors off for the build too. Syntax errors still stop it.
- An entry point that `exclude` rules out isn't type checked, and neither are the files that only it imports. An example is a worker that has a `tsconfig.json` of its own.
- If `@types/bun` is installed but `types` doesn't name it, the build still reads it, and an error that only comes from its declarations doesn't stop the build.
- Without a `tsconfig.json`, the build uses [the options of `bun check`](/runtime/check#without-a-tsconfigjson) with TypeScript's default `lib`, which declares the DOM. `typeof window` and `HTMLElement` are not errors.

A few options can't change from one file to the next, because a build has one type checker and the entry point's `tsconfig.json` sets it up: `strictNullChecks`, `strictFunctionTypes`, `strictBindCallApply`, `strictBuiltinIteratorReturn`, `exactOptionalPropertyTypes`, `lib` (or the `target` it defaults from), `allowJs`, `maxNodeModuleJsDepth`, `resolveJsonModule` and `allowArbitraryExtensions`. If a folder's `tsconfig.json` sets one of them differently, the build doesn't type check the files in that folder, and its last line counts them as compiled without types. It still reads their types, but takes each one as a [guess](/compiler/internals#what-types-are-used-for) that the compiled code checks. They behave the same. Run `bun check` in that folder to see their type errors. A package that [publishes its types](/compiler/libraries#publish-a-package-with-its-types) is the exception: it keeps them whatever your `tsconfig.json` says.

During development, [`bun run --aot`](/compiler/debugging#run-under-the-compilers-rules) runs the same checks and then runs your program from its source. [`bun test --aot`](/compiler/debugging#run-your-tests-compiled) compiles your tests and runs the compiled code.

### Harden the compiled code

The compiler leaves out every test that it can prove is not needed. If such a proof were wrong, which would be a bug in Bun, the program could read or write memory that it shouldn't. Every build keeps one guard against that. Where a value enters a place whose type the compiler has proven, it tests the type, unless the code there has already seen it: at a parameter, the result of a call, a store to a field, a variable or a captured variable, and a read of an element. `--aot-harden` puts more tests back, for programs that handle input from people you don't trust and can spare some speed.

```bash terminal icon="terminal"
bun compile ./server.ts --outfile server --aot-harden=proof-checks,ignore-told-ranges
```

| Name                 | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `proof-checks`       | Tests those types again where the value is read. Also tests what a branch has narrowed, what the compiler remembers of a field or an element across other code, and that nothing is used after the compiler has ended its life. Objects and closures that would have lived on the stack, or been reused once dead, stay on the heap. Every read or write of an element looks up, at that moment, where the array or typed array keeps its elements, how many there are and how they are stored, and stops the process if the compiler expected something else. |
| `ignore-told-ranges` | Stops the compiler from telling any read or write that its index is in range. Each one tests its index where it is used, against the length that the array, typed array or string has at that moment, whatever an earlier test or the head of a loop has shown.                                                                                                                                                                                                                                                                                                |

A test that fails, in any build, prints a line that starts with `AOT:` and ends with `This is a bug in Bun.`, and aborts the process. The program can't catch it. Neither name is on by default, and neither changes what a correct program does. In `Bun.build`, pass `compile: { aot: true, aotHarden: ["proof-checks", "ignore-told-ranges"] }`. A name that Bun doesn't know is an error.
