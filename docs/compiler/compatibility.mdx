<Warning>Ahead-of-time compilation is experimental.</Warning>

Most programs behave the same under [`bun compile`](/compiler/aot) as under `bun run`. The language, every `node:` and `bun:` module, Workers, native addons, `Bun.build` plugins and nearly all npm packages work. A value that doesn't match its TypeScript type [is slower, not wrong](/compiler/types#when-a-value-doesnt-match-its-type).

What differs: [built-in objects are read-only](#built-in-objects-are-read-only), [code from a string is interpreted](#code-from-strings), [a dynamic import only finds what the build found](#dynamic-imports), [nothing can hook the module loader](#loader-hooks-and-the-module-cache), [a file that your code reads has to be embedded](#files-beside-your-code), [packages are bundled](#packages), and [a store to `undefined` or `null` throws before its key is converted](#a-store-to-undefined-or-null). The build also checks your types, and [a type error stops it](/compiler/aot#type-errors-stop-the-build).

## Built-in objects are read-only

```js patch.js icon="/icons/javascript.svg"
Array.prototype.last = last; // works: a new method
Array.prototype.push = push; // TypeError: replaces a built-in method
Object.prototype.extra = 1; // TypeError: nothing can be added here
```

```txt
TypeError: Cannot assign to Array.prototype.push because built-in objects
are read-only in a compiled executable
```

Compiled code calls `push` directly. It doesn't check first whether something replaced it, so nothing can.

`Reflect.set`, `Reflect.defineProperty` and `Reflect.deleteProperty` answer `false` for such a member, as they do for any read-only property, and don't throw. The build may warn with `TS100014`.

- You can't replace, redefine or delete an existing member of the language's own objects: `Object`, `Array`, `String`, `Number`, `Boolean`, `BigInt`, `Symbol`, `Map`, `Set`, `WeakMap`, `WeakSet`, `Promise`, `RegExp`, `Date`, `Math`, `JSON`, `Reflect`, `Proxy`, `Atomics`, `ArrayBuffer`, `SharedArrayBuffer`, `DataView`, `Buffer`, the typed arrays, and their prototypes. The same goes for `Function.prototype`, `Iterator.prototype`, `Intl.DateTimeFormat.prototype` and `Intl.NumberFormat.prototype`. The store throws a `TypeError` in code that isn't in strict mode too. The members that packages replace are the exception: the table below lists them.
- You can't replace most of those objects themselves either. `Object = Other`, `globalThis.Array = List`, `Object.defineProperty(globalThis, "Math", d)` and `delete globalThis.JSON` throw. That goes for `Object`, `Array`, `String`, `Number`, `Boolean`, `BigInt`, `Symbol`, `Map`, `Set`, `WeakSet`, `RegExp`, `Math`, `JSON`, `Reflect`, `Proxy`, `Atomics`, `ArrayBuffer`, the typed arrays, `globalThis` and `process`. The descriptor of such a global still says `writable: true`. A variable of your own with one of these names is an ordinary variable: `const Map = require("./map")`. You can replace every other global where the build sees the assignment: `fetch = fake`, `globalThis.Promise = Bluebird`, `eval = run`.
- You can add a new member to most of them: `Array.prototype.last`, `Math.tau`, `BigInt.prototype.toJSON`.
- You can't add what the language looks up by itself to a prototype that doesn't have it yet. None of them takes a well-known symbol: `Symbol.toPrimitive`, `Symbol.toStringTag`, `Symbol.isConcatSpreadable`, `Symbol.iterator`, `Symbol.asyncIterator`, `Symbol.hasInstance`, `Symbol.species`, `Symbol.unscopables`, `Symbol.dispose`. One that inherits `valueOf`, `toString` or `toLocaleString` can't get its own. The prototypes of `Array`, `Map`, `Set`, `WeakMap`, `RegExp`, `Date`, `ArrayBuffer` and the typed arrays don't take a `then`, and those of `Array`, `WeakMap`, `Promise`, `RegExp`, `ArrayBuffer` and the typed arrays don't take a `toJSON`. `Map.prototype.toJSON` and `Set.prototype.toJSON` work. So does a symbol of your own, or `Symbol.for("nodejs.util.inspect.custom")`, on all of them. The prototype that the iterators of a built-in share doesn't take a `return`, because a `for...of` that ends early doesn't look for one: that goes for arrays, strings, `Map`, `Set`, `matchAll()`, `Headers`, `URLSearchParams`, `FormData` and `Bun.CookieMap`, and for `Iterator.prototype`.
- `Function.prototype` takes a new member too, with two exceptions. The first is a name that your compiled code reads off a function, as in `handler.once`, while the build sees nobody put it on `Function.prototype`. Compiled code has taken that name for absent and doesn't look, so adding it throws. It works where the build sees the name at the assignment: `Function.prototype.once = once`, in your code and in a package. So do `Function.prototype.once ??= once`, `Object.defineProperty(Function.prototype, "once", d)`, `Object.assign(Function.prototype, { once })`, with the object in a `const` too, `Object.defineProperties(Function.prototype, Object.getOwnPropertyDescriptors({ once }))` and a loop over `Object.entries({ once })`. `Function.prototype[name] = f`, where the build can't read `name`, works for every name that no compiled code reads off a function. The second is `prototype`: `Function.prototype.prototype = {}` always throws, and so does `Object.defineProperty(Function.prototype, "prototype", d)`. A function without a `prototype` of its own, like an arrow function, doesn't inherit one.
- You can't add anything to `Object.prototype`, and it says so: `Object.isExtensible(Object.prototype)` is `false`. The language holds a `Proxy` around it to that: its `isExtensible` trap can't answer `true`, its `getPrototypeOf` trap can't answer another object, its `ownKeys` trap can't add a key and its `has` trap can't hide one. Each throws a `TypeError`. Every other built-in object is extensible, as under `bun run`.
- You can't put anything on `Array.prototype` under a name that is a number: an index, such as a setter at `Array.prototype[0]`, or `-1`, `1.5`, `NaN`, `Infinity`. You can't change what `Array.prototype` inherits from either. A store to `list[0]` never looks for one. A subclass can have one: `class List extends Array {}`. No other read-only prototype takes such a name either: `Map.prototype[0] = 1` throws.
- What the prototypes of `Request`, `Response`, `Headers`, `Blob`, `URL`, `URLSearchParams` and `Bun.CookieMap` already have is read-only too, and so is `next` of the iterators of `Headers`, `URLSearchParams`, `FormData` and `Bun.CookieMap`. You can add to them, or write a subclass: `class Upper extends Response {}`.
- What a program reads to find out which runtime it is on is read-only: `process.isBun`, `process.versions`, `process.release`, `process.versions.node`, `process.versions.bun` and `process.release.name`. The build replaces those reads with their values, so a branch for another runtime is not compiled. Under `bun test --aot` they are read when the code runs, and a test can replace each of them.

What tests usually mock still works: `Date.now`, `Math.random`, `JSON.parse`, `JSON.stringify`, `fetch`, the timers, and everything on `console`. Under [`bun test --aot`](/compiler/debugging#run-your-tests-compiled) a test can replace most other methods too, [but not all](#what-a-test-cant-replace). So does `Object.freeze(Object.prototype)`, and a polyfill that checks first, like `Array.prototype.at ??= at`.

These members of read-only objects can be replaced, redefined and deleted too, because packages replace them:

The build has to see the code that replaces them. It can't see [code from a string](#code-from-strings), so `eval("Date.now = () => 5")` throws the same `TypeError` unless compiled code assigns to `Date.now` too.

The build reports the assignments it can see as `TS100014`. It's an error if every run reaches the assignment, and a warning if the program might exit, throw or still be waiting before it gets there. It's only a warning inside a function too, even one that is called at once, and in a CommonJS file that isn't in strict mode: there `Array.prototype.push = push` as the first statement builds, and throws when the program starts. `Object.defineProperty(Array.prototype, "push", d)` is an error there as well. Where it can see the object but can't read the name, as in `Array.prototype[name] = method`, it says that too. It doesn't follow an object into a function of Bun's own that writes to it, as in `mock.method(Date.prototype, "getTime", fake)` of `node:test`. The others throw when they run, and the stack trace points at the line. If that line is in a package, look it up in [Packages that don't work](/compiler/libraries#packages-that-dont-work).

### What a test can't replace

[`bun test --aot`](/compiler/debugging#run-your-tests-compiled) lets a test replace most built-in methods. What the language looks up by itself stays read-only there too.

```js patched.test.js icon="/icons/javascript.svg"
Array.prototype.values = fake; // works
spyOn(String.prototype, "split"); // works
spyOn(Uint8Array.prototype, "set"); // works, though a Uint8Array inherits `set` from the prototype above
Array.prototype[Symbol.iterator] = fake; // TypeError
Object.prototype[0] = "polluted"; // TypeError
```

In a test run, compiled code checks for a replacement before it calls a method that your tests replace. It has no such check for what it never calls by name: it doesn't ask an array for its `Symbol.iterator` before a `for...of`, or for its `constructor` before `map()`.

A `return` added to the array iterator. | `Symbol.iterator` of `Map` and `Set`. The methods that return an iterator: `values`, `keys`, `entries`.                                     |
| Closing iterators   | `return` and `throw` of a generator. `Symbol.dispose` of `Iterator.prototype`.                                                                                                                                                                               | `return` and `throw` of an iterator that you wrote yourself.                                                                                |
| What a method makes | `Symbol.species` of `Array`, `Promise`, `RegExp`, `ArrayBuffer` and the typed arrays. `constructor` on their prototypes and on `Object.prototype`.                                                                                                           | The methods themselves: `map`, `slice`, `concat`, `Array.from`, `then`, `catch`, `finally`, `Promise.resolve`.                              |
| Regular expressions | `Symbol.match`, `matchAll`, `replace`, `search` and `split` of `RegExp.prototype`, or one of them added to `String.prototype` or `Object.prototype`.                                                                                                         | `exec`, `test`, `toString`, `source`, `flags` and the getter of each flag. `match`, `replace`, `split` and `indexOf` of `String.prototype`. |

| Symbols             | A symbol of your own added to `Object.prototype`, also one from `Symbol.for()`: `Object.prototype[Symbol("mark")] = 1`.                                                                                                                                      | A symbol of your own on any other built-in prototype: `Array.prototype[mark] = 1`.                                                          |
| Conversions         | `Symbol.toStringTag`, `Symbol.toPrimitive` and `Symbol.isConcatSpreadable` on a built-in prototype, changed or added. `Array[Symbol.hasInstance]`.                                                                                                           | `toString` and `valueOf`, on `Object.prototype` too. `Error.prototype.name`. A `toJSON` added to `Object.prototype`.                        |

| Prototype chains    | The prototype of a built-in function, prototype or namespace object, such as `Array`, `Date`, `Array.prototype`, `Uint8Array.prototype` or `Math`: `Object.setPrototypeOf()`, `Reflect.setPrototypeOf()` and `__proto__ =` all throw.                        | A subclass: `class List extends Array {}`.                                                                                                  |

It makes no difference how the test does it: an assignment, a helper that takes the object and the key, `Object.defineProperty()` or `Reflect.defineProperty()`. The write throws, and the run lists it again when it ends, with the test file that was running.

A helper that only your tests import, like `test-utils/patch.ts`, is one of their files wherever it lies. If your program imports it too, assigning to a built-in there throws, unless it's an `index` file imported as `./index.js`. Import from `bun:test` in it, or name it as a preload.

A helper also has to be compiled with your tests, because the build reads what a run replaces in the files that it compiles. It follows `import("./rows/" + name)`, `import(import.meta.dir + "/rows/" + name)` and `import(new URL("./rows/" + name, import.meta.url).href)`, and compiles every file that they can name. It doesn't follow a folder that's taken out of a URL first, as in `const folder = fileURLToPath(new URL("./rows/", import.meta.url)); await import(folder + name)`. Those files are loaded when the tests run, and a `spyOn(namespace, "name")` or `vi.doMock()` in one of them throws a `TypeError` that names the file.

A few more methods are read-only only in a run whose build has skipped the call. Code that TypeScript compiled for an older target keeps `#count` in a `WeakMap`. The build turns it into a field of the object, so nothing calls `WeakMap.prototype.get` for it. A test that replaces `get` where the build can read the name works, because the build then keeps the `WeakMap`: `WeakMap.prototype.get = fake` or `spyOn(WeakMap.prototype, "get")`. One that reaches the prototype another way, like `globalThis[name].prototype.get = fake`, throws a `TypeError` that names the method and says what to write instead.

A name on `Object.prototype` isn't a way to name a file either. The build reads which files `require(table[key])` and `import(table[key])` can load off the object that's written in your code. After `Object.prototype.extra = "./two.cjs"`, `require(table.extra)` throws an error that names the file instead of loading it.

The same goes for a global below which the build has put in a constant. Where a compiled file says `Symbol.iterator` or `Intl.DateTimeFormat`, the build puts in the value itself, as it does in the executable. `globalThis.Symbol = Fake` in a test works: the build reads it and looks `Symbol.iterator` up instead. `root.Symbol = Fake`, with a `root` that the build can't follow to `globalThis`, throws the same `TypeError`. Writing `globalThis.Symbol = Fake` anywhere in the tests, even in a function that nobody calls, is enough. A constructor's `prototype` is looked up with the constructor: `root.Map = Fake` works, and `Map.prototype` is `Fake.prototype` then.

A test of how your code copes with one of these, such as a patched array iterator or an index on `Object.prototype`, has to run under `bun test`.

## Code from strings

```ts strings.ts icon="/icons/typescript.svg"
const add = new Function("a", "b", "return a + b");
const local = 5;
console.log(add(2, 3), eval("local * 2"), (0, eval)("typeof Bun"));
```

```bash terminal icon="terminal"
bun compile ./strings.ts && ./strings
```

```txt
5 10 object
```

`eval`, `new Function` and `node:vm` work, also when your code gets to them by a computed name, like `globalThis[name](code)`. The build can't see that code and the executable has no JIT, so Bun interprets it.

`globalThis[name](code)` finds `eval` and `Function` whatever the name is and however your code makes it. So do `global[name]`, `self[name]`, `Reflect.get(globalThis, name)` and a variable that your code sets to `globalThis`, `global` or `self`.

Where your code has the global object without writing its name, such as the `this` of a function that isn't in strict mode, a computed name finds them when the build finds that name in your code: as a string (`"eval"`, also in `case "eval":`), as a key of an object or an enum whose keys your code lists with `Object.keys()` or `Object.entries()` or looks up with a computed key (`name in { eval: 1 }`), or as the name of a function whose `.name` your code reads. The build doesn't find a name that only a regular expression matches, a key that only a `for...in` loop lists, the name of a static member of a class, or a name that your code assembles at run time with `slice()`, `startsWith()` or `String.fromCharCode()`. There the call throws an `EvalError`, so call `eval` or `new Function` directly. The same goes for `"constructor"` in `fn[name](code)`, where a key or a static member of that name counts as well.

Code from a string can call `import()`, but the build can't see which file it names. `eval("import(path)")` finds your entry points. It finds data files, and other compiled files if your own code has a computed `import()` or `require()` too. Otherwise it throws `Cannot load`. `bun test --aot` refuses it as the executable does, and lists it at the end of the run. Import the file by a constant path and hand the module to that code. Code that only runs through `fn.constructor(code)` sees no `process.mainModule.children`: write `void Function;` once.

A namespace object hands out the exports that the build saw somebody read from it. If code the build didn't follow gets hold of the object some other way, for example a run-time plugin whose `onResolve` answers for an `--external` package with the path of a compiled file, reading any other export throws the same `Cannot load`. `in`, `Object.keys()` and `for...in` list it. A data file just lacks it: use its `default`.

A script from a string can't declare a built-in global again at its top level. `vm.runInThisContext("let Array = 5")` throws a `SyntaxError` and `(0, eval)("function parseInt() {}")` throws a `TypeError`, because compiled code reads `Array` and `parseInt` as constants. Declare them inside a function or a block, or run the script in a `node:vm` context of its own.

`ShadowRealm` isn't supported. An executable has no such global, so code that uses it throws a `ReferenceError` when it runs, and the build warns. Use a `node:vm` context.

Interpreted code is fine for a template or a config file. It costs you when a library generates its hot code this way, as zod 4, ajv, fast-json-stringify and Elysia do.

- zod 4: call `z.config({ jitless: true })` before you create a schema.
- Fastify: call `app.setSerializerCompiler(() => JSON.stringify)`, and write the validators to files with the standalone mode of `@fastify/ajv-compiler`.

If your program needs no code from strings, build with [`--disallow-code-generation-from-strings`](/runtime/code-generation-from-strings). `eval` then throws an `EvalError`, and the compiler can optimize more.

## WebAssembly

A `.wasm` file that you import is compiled at build time, and so is a module that sits in your source as a base64 string. Bytes that your program downloads or assembles at run time are interpreted, and a tight loop in them runs much slower than under `bun run`.

## Dynamic imports

```ts app.ts icon="/icons/typescript.svg"
await import("./plugins/" + name + ".ts"); // finds plugins/*.ts
await import(new URL(`./plugins/${name}.ts`, import.meta.url)); // same
await import(`@/plugins/${name}.ts`); // same, with "paths": { "@/*": ["./*"] } in tsconfig.json
await import(`locales/data/${name}.js`); // finds node_modules/locales/data/*.js
await import(process.env.PLUGIN || "./plugins/a.ts"); // compiles plugins/a.ts
await import(name); // finds the entry points, and files whose path is a string in your code
```

The build compiles every file it can reach from your entry point. Where a path isn't a constant, it uses the parts that are. A path that starts with a folder or with the start of a file's name, like `"./locales/" + lang` or `"./lang-" + code`, embeds every file it may name, code and data, and the build lists the ones that aren't code (`TS100088`). A path that starts with nothing but `./` or `../` embeds code only (JavaScript, TypeScript, WebAssembly and native addons, going by the loader of each file), and any other file, like a `.json`, `.txt`, `.md` or `.html` file, only if the path ends in its extension, as in `"./" + name + ".json"`, or the import says its type: `import("./" + name, { with: { type: "json" } })` takes `.json`, `.jsonc` and `.json5` files, and `type: "text"` takes `.txt` files and files whose extension Bun has no loader for, like `.sql`. A file or folder whose name begins with a dot is never found that way. The build warns (`TS100089`) where it leaves out a file that such a path may name, and lists the first few. A package in `node_modules` is exempt: a path written there embeds code and data of that package alike. To embed any other file, write its path out, `import data from "./data.json"`, name it in an `import.meta.glob()`, or pass it to [`--asset`](/compiler/executables#embed-directories). `__dirname`, `import.meta.dir`, `import.meta.url`, `path.join()`, `new URL()`, `require.resolve()`, `process.platform` and `process.arch` count as constants, so the usual loader of a native addon works.

`import.meta.glob()` is expanded at build time, as in `bun build`, and every file that matches is compiled. A call that can't be expanded, like one whose pattern isn't a string literal, gets a warning from the build and throws a `TypeError` when your program reaches it.

A file that only a non-constant path can reach doesn't stop the build if it has a syntax error, like a `.json` file with comments or a broken fixture in a package. Importing it throws when your program runs. A file of code that you import by a constant path still stops the build, and so does a data file that an `import` statement names. A data file that `require()` or `import()` names only gets a warning. A `.json` file throws the same `SyntaxError` as under `bun run`. Import a file under one type: two can mix up.

For a mistake that JavaScript finds only when it reads the file, like an invalid regular expression, the message also ends with the line and column: `Invalid regular expression: missing ) (1:16)`. None of the files that are imported together with such a file run, as under `bun run`. `bun run` reports a mistake that its transpiler finds, like a name that is declared twice, as a `BuildMessage`. Compiled code throws a `SyntaxError` for it, in the compiler's words.

With a `baseUrl` in `tsconfig.json`, or a key like `"*"` in its `paths`, a name like the last one can also mean one of your own files. An executable then holds your files that match and leaves the package's files on disk, as `bun build --compile` does without `--aot`. `bun test --aot` compiles both.

A file that the build compiled is also found by a relative path that's written out as a string somewhere in your code, like `"./plugins/a.ts"` or the `"/plugins/a.ts"` in `import.meta.dir + "/plugins/a.ts"`, however that string and the loader meet: through a variable, a function, or a `require` that's stored in an object.

The build has to see the name `require` too. Reading it off `module` or `import.meta` with a computed key works if the string `"require"` is written somewhere in that file, as in React's `module[("require" + Math.random()).slice(0, 7)]`. Without that string, calling what you read throws an error that says the module loader wasn't compiled into the executable.

The build also has to know which folder a `createRequire()` looks from. `createRequire(import.meta.url)` and `createRequire(__dirname + "/plugins/")` work, and so does a URL object or a path made from the file's own, as in `createRequire(new URL(import.meta.url))`. A folder doesn't work with `--aot-allow-code-from-disk`. If that value names another folder by the time `createRequire()` gets it, say because the URL's `pathname` was changed, what it returns still loads built-in modules, and anything else throws the error below. `createRequire("/")` and `createRequire("/start.cjs")` find none of the executable's files by a relative name: they don't lie in the root of the file system, and `bun run` only finds one there because it looks in the working directory. If one call gets a different folder each time it runs, as in `createRequire(__dirname + folder)("./part.cjs")`, it throws the error below. Give `require()` the whole path instead: `require(__dirname + folder + "part.cjs")`.

`fs.readdirSync()`, `existsSync()` and `statSync()` see the compiled files, so a loader that lists a folder works too. Their source text isn't in the executable, so `readFileSync()` doesn't find them.

```ts app.ts icon="/icons/typescript.svg"
const folder = path.join(import.meta.dir, "commands");
for (const file of fs.readdirSync(folder)) require(path.join(folder, file));
```

This also works for a folder above your entry point: through `__dirname` however far up it is, and through `import.meta.dir` or `import.meta.url` one folder up, if the file that loads the path lies in your entry point's folder or below it. A file above it, like a package in a `node_modules` beside `src`, doesn't find such a path: hand it one made from `__dirname`. Two folders up, `path.join(import.meta.dir, "../../commands")` is `/commands` in an executable, which `fs` can't tell from a path on disk. Use `__dirname` there.

`require.resolve()` and `import.meta.resolve()` return a path and nothing more. A file that's only named that way isn't embedded, and an HTML page isn't bundled. `require.resolve()` returns where the file was when you ran the build, if the build can read the path. Reading it fails with `ENOENT` on another machine. To embed a file, import it: `import icon from "./icon.png" with { type: "file" }`.

Anything else isn't in the executable:

```txt
error: Cannot load '/home/me/late.ts': it isn't in this executable ...
```

| You want to load                     | Do this                              |
| ------------------------------------ | ------------------------------------ |
| One of your files                    | Pass it as another entry point       |
| A package with a dynamic name        | Pass its main file as an entry point |
| A `node:` module with a dynamic name | `import "node:dgram"` somewhere      |
| JSON, TOML, YAML or text from disk   | Give an absolute path                |
| One package from disk                | `--external <package>`               |
| Any file from disk                   | `--aot-allow-code-from-disk`         |

```bash terminal icon="terminal"
bun compile ./app.ts './extra/*.ts' ./node_modules/pg/lib/index.js
```

A dynamic name finds the file that `bun run` would have found when you built. If that file isn't in the executable, the name can find another file that the executable holds. So if your tree has two copies of a package, pass the copy that the file which asks for it would get: for `node_modules/orm`, that's `node_modules/orm/node_modules/pg` if it exists, not `node_modules/pg`. And if `lib.js` lies beside `lib/index.js`, `"./lib"` means `lib.js`. A relative path is never looked up on disk, unless you build with `--aot-allow-code-from-disk`: `bun run` looks beside the file that asks, and that folder exists only in the executable.

An absolute path finds a compiled file only if it's the path the file had when you built it, which is what you get from `import.meta.dir` and `__dirname`. A path made from the working directory, like `path.resolve("lib/a.js")` or `process.cwd() + "/lib/a.js"`, names the file on disk, as in `bun build --compile`: it may belong to the project your program was started in. Data there is read from disk. Code there is loaded with `--aot-allow-code-from-disk` and refused without it, also if you passed your own `lib/a.js` as an entry point. What's loaded that way is a second module with its own state, even if the file is the very source that was compiled.

Express loads a view engine that way, by the extension of the view's file, so `res.render("index")` answers 500. Register the engine yourself and it is compiled in: `app.engine("ejs", require("ejs").__express)`.

Code that's loaded from disk is interpreted, and both flags make the executable larger. A file that's loaded from disk can use globals, built-in modules, files and packages on disk, and whatever your program hands it, such as an argument or your own `require`. It can't load the files that were compiled into the executable: `import`, `require()`, `import.meta.require()` and a function made by `createRequire()` throw `Cannot load '/$bunfs/root/..': code that this executable loads from disk can't load the files that were compiled into it`, whether the path is the one in the executable or one made from `__dirname`. A package name is looked up on disk from the folder of the file that asks, as under `bun run`: if the same package was compiled in, the file from disk gets a second instance, and if the disk doesn't hold it, the package isn't found. In such an executable a `Worker` starts only at a file where the build saw a `Worker` start, or that you passed as an entry point. What such a file imports from disk is found as under `bun run`: the `package.json` and `tsconfig.json` files on disk are read, as with `--compile-autoload-package-json` and `--compile-autoload-tsconfig`.

In such a file `module.parent` says which file loaded it (`id`, `filename`, `paths`) and nothing else. It has no `exports` and no `require`, and its `loaded` is `false`, as with `--no-aot`.

Code from disk can't change a built-in either, and neither can a `node:` module that only code from disk loads. `mock.timers.enable()` of `node:test` replaces the timers and `Date`, so there it throws a `TypeError` such as `Cannot assign to Date`. Import the module in one of your own files, `import "node:test"`, and the build leaves writable what the module replaces.

Workers follow the same rule. The build finds `new Worker("./worker.ts")`, `new Worker(new URL("./worker.ts", import.meta.url))` and `new Worker("./jobs/" + name + ".ts")`. If the build can't tell which file a `new Worker(x)` starts, as in a function that takes `x` from another file, it also compiles every code file whose full path your own files write out and pass along: a `new URL()` or a `path.join()` from the file's own folder, `require.resolve("./worker.js")`, `"./worker.ts"`, an import with `{ type: "file" }`, and `import.meta.url` or `__filename` for the file itself. Such a file never stops the build: if it can't be compiled, it fails when a Worker loads it. It doesn't follow a path that a package in `node_modules` passes along. Pass any other worker as an entry point.

A query on an import path, like `import("./a.ts?v=2")`, loads one more copy of the file, as in `bun run`. Of Vite's suffixes, `?worker` and `?sharedworker` work as in `bun run`: the default export is a function that starts the file as a worker, and the build compiles the file as a worker's entry point. `?raw`, `?url`, a query on a data file and any query in a `require()` stop the build with `TS100159`. With `--aot-allow-code-from-disk` the build leaves them to the loader. `bun run --aot` then loads them as `bun run` does. An executable looks on disk when it runs, and a relative path or a package name starts from the working directory. A load that finds nothing throws an error you can catch, and so does a query on a file that's also compiled into the executable.

Next.js and Angular load your pages by dynamic paths. [Frameworks](/compiler/libraries#frameworks) shows what to pass.

### Under `bun test --aot`

Your tests see the same rule as your executable. A `require()` or `import()` with a computed path can load a file that wasn't compiled only if the call is written in a test file, a preload, a file that only your preloads import, a file in a test file's folder or below it, a file of your project that imports from `bun:test`, a file of your project that nothing but those files imports, or a package that nothing but your test files and files that import from `bun:test` reaches, such as `webpack` or `@babel/core` in the tests of a plugin. Written anywhere else, in your source, in a package that another file of your project imports or in one that your `package.json` lists under `dependencies`, `peerDependencies` or `optionalDependencies`, it finds compiled files only. For a helper beside your tests, like `support/load.ts`, Bun also reads the files below the folder where `bun test` runs that the run doesn't reach, outside `node_modules`: if one of them that isn't a file of your tests imports the helper, be it a script or an example that nothing imports, the helper is part of your program, and so is what `main`, `module`, `bin` or `exports` in your `package.json` names, whether the run loads it or not. The list at the end of the run names the file that imports it:

```txt
error: Cannot load '/home/me/plugins/late.ts': it wasn't compiled with the program, and --aot only runs code that was.
Import the file by a constant path, or add --aot-allow-code-from-disk.
```

So a test that passes doesn't hide a plugin that the executable can't load. A test can still write a module and import it. A package may catch that error and carry on without a word, so the run ends with a list of every load that was refused, and where. A test that fails in a file where a load was refused says so under its own line.

A native addon, a `.node` file, loads from disk wherever the call is written: whether your executable holds it depends on how you build it, which a test run can't know. The run lists each addon that the build didn't find. Pass it as an entry point when you build the executable.

If you build with `--aot-allow-code-from-disk`, test with it: `bun test --aot --aot-allow-code-from-disk` loads files from disk wherever the call is written.

`bun test` doesn't wait for a promise that a test never awaits: the run fails only if the promise has rejected by the time the file's last test ends. A compiled test is faster, so such a promise has less time, and a run that fails without `--aot` can pass with it. Given the same time, both see the same errors. Await the promise.

`import()` calls in a test run and settle in the order they do in your executable, which is Node's order. `bun test` reads a file on another thread when a call asks for it, so the two can differ where nothing waits for a call. If `a.ts` calls `import("./b.ts")` in its body, `import("./a.ts").then(done)` runs `b.ts` before `done` with `--aot` and after it without.

`vi.resetModules()`, `jest.resetModules()` and `delete require.cache[path]` work as in `bun test`: the next load runs the file again, unless it's still at a top-level `await`. That second copy runs from source, not compiled, and it stays: whatever imports the file from then on, in that test file or in a later one, gets the copy and doesn't test the code your executable runs. What a preload had loaded is the exception, as in `bun test`: after a `resetModules()` in a test file, the next test file gets the preload's own instances back, compiled. `--isolate` starts each test file from compiled code, except what a test wrote over. The build points at each `resetModules` with `TS100078`.

`require.cache[path]` and `Module._cache[path]` give you the entry of a compiled file, as in `bun test`, if a file that was compiled names the cache, or if the build saw an `import()` or `require()` of a computed path that can reach the file. Code from a string doesn't count: the build can't read what goes to `eval()` or `new Function()`, or the text of a `data:` URL. What a file exports is compiled for the code that imports it, as in your executable, so such code gets an error where `bun test` hands it the entry:

```txt
error: Cannot read the entry of '/home/me/src/lib.ts' in require.cache: the build found nothing that reads the cache, so the module was compiled for the code that imports it. Spell the read in a file that the tests import: require.cache[require.resolve("./module")]
```

Once a test file or a helper says `require.cache`, every reader in the run gets the entries.

A plugin that a test or a preload registers with `Bun.plugin()` is asked as in `bun test`, also about a package or a file that exists. `import()` and `require()` ask it where they stand. An `import` statement was linked when its file was compiled, so a file that hasn't run yet and imports a name that `build.module()` was given, or that an `onResolve()` callback answers for, runs from source, and so does whatever imports that file.

The build has to see the plugin coming. Some file that it compiles has to say `Bun.plugin` or import `plugin` from `"bun"`, and then the whole run is compiled so that a plugin can answer. If your tests only get to the function some other way, as in `register(Bun)` with `bun.plugin(options)` inside, `Bun["plu" + "gin"](options)`, or a file that `require(path)` loads from disk with a path the build can't work out, the call throws as soon as `setup()` registers something with `onResolve()`, `onLoad()` or `module()`:

```txt
error: Cannot use Bun.plugin: no file that was compiled names it, so the program's imports were linked as if no plugin could answer for them. Write Bun.plugin(...) or import { plugin } from "bun" in a file that the build compiles.
```

A file that's imported under a query, like `import("./a.js?" + Date.now())`, is one more instance of the file, and it runs from source too. So does what a `Bun.ModuleGraph` imports. The run ends with a list of these, not of files a test reset or wrote over.

A module mock that has ended is gone, but some of what it did can stay:

- A file that read the mock while it ran doesn't run again for the next test file, so a value that it took stays. With `--isolate` it does.
- A package that had the real module reads the mock from then on.
- `vi.doUnmock()` alone doesn't run the file's importers again.
- A name that the mock didn't have can stay `undefined`, and the error of its original can come back.
- The mock of a preload can come back in the next test file, or stay away.
- `require.cache` still lists a file that never ran.

If two files both say `export * as ns from "./h.ts"` and a test mocks both, the later mock's `ns` answers for both files while it stands, as in `bun test`. Once both have ended, `ns` is the real namespace again. Without `--aot`, `bun test` leaves the first mock's `ns` in place, also for the next test file unless you run with `--isolate`.

`vi.doMock()` and `jest.doMock()` of a file that's already loaded reach the same importers as in `bun test`, and that depends on which test file loaded it. If this test file did, whatever imports the file already keeps the real one, and a later `import()` of such an importer returns the same module. A barrel with `export *` of it can lose names or throw, and a package that had the real file beside an earlier mock can get this one. If an earlier test file did, the next `import()` that reaches an importer loads it again, linked to the mock, while a binding that your test already holds keeps the real file, and so can a namespace that it read in a loop. `mock.module()` patches the loaded file in place, so every importer sees it at once, and the file still counts as loaded by whoever loaded it. Once a `doMock()` that was loaded has ended, the next load of the file makes it this test file's. Another difference: if a test holds an importer and also imports it again after the mock, `bun test` has two instances of that importer and compiled code has one, so with `--aot` both see the mock.

`vi.importActual()`, `vi.importMock()`, `jest.requireActual()`, `jest.requireMock()` and `jest.createMockFromModule()` load the compiled file. It can run twice if it has a top-level `await`, and lack names behind a barrel. The build follows their path as it follows that of an `import()`: it compiles a file that's named by a constant path even if nothing else imports it, and a computed path finds the compiled files that it can name. `__mocks__` files that only `vi.importMock()` names aren't compiled.

A module that some `mock.module()` names doesn't count as loaded by the `import` above the call. After `import { name } from "./middle.mjs"; mock.module("./middle.mjs", ...)` in one test file, a `.cjs` file that `middle.mjs` imports and that [doesn't say what it is](#loader-hooks-and-the-module-cache) runs as CommonJS, ahead of the ES modules. `bun test` has loaded it as an ES module by then, so there it runs in strict mode and in its turn.

Inside `namespace Box { ... }`, the name `Box` is the variable, as in an executable. If your code assigns to it, `Box = {}`, a function of the namespace that returns `Box` returns the new object. Under `bun test` it still returns the namespace's own. `tsc` refuses the assignment with `TS2631`.

## Loader hooks and the module cache

Every `import`, and every `require()` of a constant path, is resolved at build time. An absolute path that doesn't exist yet, such as `/etc/app/config.json`, is looked up when the program runs. Nothing in `node:module` runs on the way. If your program depends on a hook, build it with `--no-aot`.

- `Module._resolveFilename` and `Module.prototype.require` can be replaced, but Bun only calls them for dynamic paths. A path that's written out in the call isn't dynamic, also where it's one of two, as in `require(flag ? "./a.js" : "./b.js")`. If the other one is an `--external` package or a URL, the file isn't found. The build points at each place that replaces one with `TS100080`. For aliases, use `paths` in `tsconfig.json` or `imports` in `package.json`.
- `Module._extensions[".js"] = loader` is stored, and Bun only calls it for dynamic paths. That's the same with `--no-aot`. Your loader can set `module.exports` itself, or call the loader that it replaced, which runs the compiled file. If it does both, the file still starts with an `exports` object of its own: what your loader had put in or on `module.exports`, or on another module object that it hands on, is replaced, even if it made the property read-only. A `require("./file.js")` with the path written out, called inside your loader, runs the file right there, where `bun run` hands out its `exports` while they are still empty. It can't change the source text, because the text isn't in the executable: if it replaces `module._compile`, the loader that it calls throws. You don't need `@babel/register` or anything like it, because the build compiles TypeScript and JSX.
- A tracer that patches modules as they load, like OpenTelemetry's auto-instrumentation, sees none of them.
- A plugin that your program registers with `Bun.plugin()` answers for code that's loaded at run time, so `build.module("lodash", ...)` doesn't replace a `lodash` that was compiled into the executable. That's the same with `--no-aot`. A plugin isn't asked about `import("./a.ts")` or `require("./a.ts")`, where the path is written out in the call. It's asked first where the call takes the path from a variable or puts it together, as in `const path = "./a.ts"; await import(path)` or `await import("./" + name + ".ts")`, and the compiled file answers if no plugin does. The build sends those calls to the plugins only if some compiled file says `Bun.plugin` or imports `plugin` from `"bun"`. If the program only gets to the function some other way, as in `register(Bun)`, `Bun["plu" + "gin"](options)`, code from a string, or an `--external` package, the call throws `Cannot use Bun.plugin: no file that was compiled names it` as soon as `setup()` registers something. With `--aot-allow-code-from-disk` it doesn't throw, because a file from disk may register a plugin for what it loads itself. The calls in your compiled files aren't sent to that plugin.
- A module that has run doesn't run again. `require.cache` doesn't list compiled modules, and `delete require.cache[path]` does nothing. An entry that your program stores there under the path of one of its own files, `require.cache[require.resolve("./dep.js")] = { exports: fake }`, is kept and can be read back, but `require()` doesn't look at it: the file runs and answers, where `bun run` answers `fake`. No error tells you. That's the same with `--no-aot` for a `require()` with the path written out.
- A CommonJS file that throws while it loads hasn't run. The next `require()` that the build can see runs it again, with a new `module` and `exports`, as in `bun run` and Node.js. With `--no-aot`, the next `require()` returns what the file had exported before it threw. That also holds where a loader that your program stored in `Module._extensions` catches the error and goes on: a later `require("./file.js")` with the path written out runs the file again from the top, where `bun run` returns what the file had exported before it threw.
- A CommonJS file that an ES module imports runs while the modules are being loaded, before the body of any of them, as in `bun run`. After `import "./a.mjs"; import b from "./b.cjs"`, `b.cjs` runs first. In Node.js and with `--no-aot` it runs at its place, after `a.mjs`. Every such file runs, even after one of them has thrown: if `one.cjs` throws, `two.cjs` below it still runs, and then the error of `one.cjs` comes out. A file that threw this way isn't run again. The next `require()` or `import` of it throws the same error, as in `bun run`. Node.js runs it again, and with `--no-aot` the next `require()` returns what it had exported.
- A `.cjs` file with no `require`, `module`, `exports`, `import` or `export` in it doesn't say what it is. Under `bun run`, whoever gets to it first decides: `import "./setup.cjs"` makes it an ES module, which runs in strict mode and in its turn, and `require("./setup.cjs")` makes it CommonJS. The build decides once, from the order in which your files load. After `import lib from "./lib.cjs"; import "./setup.cjs"`, where `lib.cjs` has `exports.load = () => require("./setup.cjs")`, it takes `setup.cjs` for CommonJS, because `lib.cjs` runs before `setup.cjs` is loaded and the build doesn't know when `load()` is called. `bun run` has loaded `setup.cjs` as an ES module by the time your code calls `load()`. If the `require()` runs while the files are still loading, `bun run` itself goes either way from one run to the next. A `require(name)` whose name the build can't work out isn't taken to come first. Write `export {}` or `module.exports = {}` in the file and it's the same everywhere.
- An `import()` of a CommonJS file that's still running, called from a module that the file has loaded with `require()`, waits until the file has ended and gets what the file exports then, as in Node.js and with `--no-aot`. `bun run` settles the call inside the `require()`, with what the file had exported by then, and an error that the file throws afterwards is lost.
- An `import()` that's called while a `require()` loads an ES module isn't part of what the `require()` loads. The file that it names runs after the `require()` has returned, as in Node.js. `bun run` runs it inside the `require()`, where it can find the module that called `import()` half done: `require()` of that module answers `undefined` for a name that the module exports further down. The file also runs behind the jobs that are already waiting, as in Node.js: if `a.mjs` is loaded with `require()` and says `import("./b.mjs"); Promise.resolve().then(job)`, then `job` runs before the body of `b.mjs`, and doesn't see what that body sets. In `bun run` and with `--no-aot`, the body of `b.mjs` runs first.
- An `import()` of an ES module that's still running, called from a file that the module has loaded with `require()`, settles when the module has run, as in Node.js and with `--no-aot`. In `bun run` and `bun test`, the promise stays pending forever unless the module is the one that was asked for first. `bun test --aot` settles it, like your executable.
- An executable has the text of every module at hand, with or without `--aot`, so an `import()` of a module that hasn't loaded yet is answered within the same turn of the event loop, after a few jobs. `bun run` reads the file on another thread, and the module runs in a later turn, behind every job that's waiting and behind a `setImmediate()` callback. Nothing in the language says how long an `import()` takes. If one module says `await import("./part.ts")` while another is in the middle of a chain of `await`s, don't rely on which of the two goes on first.
- `require.cache["fs"] = { exports: fake }` makes `require("fs")` answer with `fake`, as in `bun run`, if the build can read the key. In an ES module that another file imports, `require("fs")` answers `fake` too, where `bun run` answers the module itself. Under a computed key that turns out to be `"fs"`, the store throws.
- `Bun.main = path` changes what `require.main`, `require.main === module` and `import.meta.main` answer, as in `bun run`, if the build sees that your code may store there: it writes `Bun.main = path`, stores or reads `Bun[key]` with a computed key, or hands `Bun` on as a value. Without one of those the store throws a `TypeError`, as `Bun.main = path` in [code from a string](#code-from-strings) does.

## Paths of the running file

Every compiled file keeps a path of its own under `/$bunfs/root`, laid out like your sources, so what a file asks about itself answers as in Node.js. An executable built with `--no-aot` is one bundle, and there every file gets the bundle's answer.

`/$bunfs/root` is the folder of your entry point. A file that lies above it, like a package in a `node_modules` beside `src`, is under `/$bunfs/_.._` instead: `/$bunfs/_.._/_.._/node_modules/ms/index.js`. Each `_.._` stands for a folder on the way down to your entry point, and the executable doesn't tell their names. In such a file a `..` leads where it leads on disk: `path.join(import.meta.dirname, "../../locales")` names the same folder as under `bun run`. In a file in or below the folder of your entry point, one `..` past that folder works as well. A second one leaves `/$bunfs`, see [Dynamic imports](#dynamic-imports): use `__dirname` there.

| In `lib/inner.js`                               | `bun compile`                                   | With `--no-aot`                                  |
| ----------------------------------------------- | ----------------------------------------------- | ------------------------------------------------ |
| `import.meta.url`                               | `file:///$bunfs/root/lib/inner.js`              | The executable's own, the same in every file     |
| `import.meta.dirname`, `import.meta.dir`        | `/$bunfs/root/lib`                              | `/$bunfs/root` in every file                     |
| `import.meta.filename`, `import.meta.path`      | `/$bunfs/root/lib/inner.js`                     | `/$bunfs/root/` and the executable's name        |
| `import.meta.file`                              | `inner.js`                                      | The executable's name in every file              |
| `process.argv[1]`, `Bun.main`                   | `/$bunfs/root/cli.js`, your entry point         | `/$bunfs/root/` and the executable's name        |
| `createRequire(import.meta.url)("./data.json")` | Works, also for a package and with `.resolve()` | `MODULE_NOT_FOUND`                               |
| `require.main`, `process.mainModule`            | The module of your entry point                  | `undefined`, so `require.main.filename` throws   |
| `module.paths`, `module.parent`                 | As in Node.js                                   | `undefined`                                      |
| `module.filename`, `module.path`, `module.id`   | As in Node.js, under `/$bunfs/root`             | `"inner.js"`, `"lib/inner.js"`, `"lib/inner.js"` |
| `require.main === module`, `import.meta.main`   | `true` in your entry point                      | The same                                         |
| `__dirname`, `__filename`                       | Where the file was when you built               | The same                                         |

Packages rely on the first column. `@babel/core`, `@nestjs/common` and `@nuxt/kit` load files with `createRequire(import.meta.url)`, `sass` finds your project through `require.main.filename`, and `dd-trace` walks `module.paths`.

A usage line made from `path.basename(process.argv[1])` names your entry point's file, as it does under `bun run`. For the name of the executable use `process.argv0` or `process.execPath`.

An executable runs your entry point by itself, so a program that starts a copy of itself must not pass the file. After `fork(__filename, ["child"])` or `spawn(process.execPath, [process.argv[1], "child"])` the child finds the path in `process.argv[2]` and `"child"` in `process.argv[3]`, takes itself for the parent and starts another copy, with `--no-aot` too: write `spawn(process.execPath, ["child"])`.

### Files beside your code

```js render.js icon="/icons/javascript.svg"
const template = fs.readFileSync(new URL("./template.html", import.meta.url));
const { version } = JSON.parse(fs.readFileSync(path.join(import.meta.dirname, "../package.json")));
```

These paths are inside the executable, so the read only finds a file that's in there too. The build embeds what you `import` or `require()`, not what you read. That's the same with `--no-aot`.

Your own code is in there as machine code, not as text. `fs.existsSync()` and `fs.statSync()` find a compiled file, so a check in front of a `require()` passes as it does under `bun run`, but its size is `0`, and opening or reading it fails with `ENOENT`.

Embed the file with [`--asset`](/compiler/executables#embed-directories). It keeps its relative path, so the same line finds it, in a package too:

```bash terminal icon="terminal"
bun compile ./app.ts --asset ./template.html --asset ./package.json
```

`__dirname` and `__filename` are [the paths on the machine that built the executable](/compiler/executables#embed-directories). A read through them finds the file there, and the embedded one anywhere else.

Some packages load their own code that way, by a name they put together when the program runs. The build can't see those files either:

| Package             | In an executable                                                               | Do this                                                              |
| ------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| `moment`            | `moment.locale("fr")` stays `"en"`, with no error                              | `import "moment/locale/fr"`                                          |
| `express`           | `app.set("view engine", "ejs")` throws `Cannot find package 'ejs'` on a render | `app.engine("ejs", require("ejs").__express)`, and `--asset ./views` |
| `require-directory` | Throws `ENOENT`                                                                | Pass the folder's files as entry points                              |
| `pino`              | `pino.transport()` fails to start its worker                                   | Pass the three files below as entry points, or log without a worker  |

```bash terminal icon="terminal"
bun compile ./app.ts './routes/*.js'
bun compile ./app.ts ./node_modules/thread-stream/lib/worker.js ./node_modules/pino/lib/worker.js ./node_modules/pino/file.js
```

`pino(pino.destination(1))` writes the same lines without a worker. For another transport, pass its main file in place of `pino/file.js`.

With `--no-aot` these four fail too. The changes to your code fix them there, and the extra entry points don't.

## Packages

An executable is a bundle, so two fields of a `package.json` mean what they mean to `bun build`. `bun run` treats them differently. That's the same with `--no-aot`.

### `"main"` and `"module"`

```json node_modules/both/package.json icon="file-json"
{ "name": "both", "main": "./main.js", "module": "./module.mjs" }
```

```ts app.ts icon="/icons/typescript.svg"
import { which } from "both"; // bun run loads main.js. An executable loads module.mjs.
```

| Your program loads the package with     | `bun run` | An executable |
| --------------------------------------- | --------- | ------------- |
| `import`, `import()`, `export ... from` | `"main"`  | `"module"`    |
| `require()`                             | `"main"`  | `"main"`      |
| Both                                    | `"main"`  | `"main"`      |

One `require()` of the package is enough for the last row, in any file or package that the build compiles. Every import of it then loads `"main"` too, so an executable never holds both files.

- If a package has `"module"`, an `index.js` and no `"main"`, the `index.js` counts as its `"main"`.
- A folder of your own with a `package.json` follows the same rules: `import "./lib"`.
- `"exports"` wins over both fields, in an executable and under `bun run`.
- [`bun test --aot`](/compiler/debugging#what-differs-from-an-executable) loads `"main"`, as `bun test` does.

The two files of a package usually export the same things, so this rarely shows. If it does, put `"main"` first:

```bash terminal icon="terminal"
bun compile ./app.ts --main-fields main --main-fields module
```

### `"sideEffects": false`

```json node_modules/pure/package.json icon="file-json"
{ "name": "pure", "main": "./index.js", "sideEffects": false }
```

```ts app.ts icon="/icons/typescript.svg"
import "pure"; // bun run runs index.js. An executable doesn't.
```

With that field, a package says that loading its files does nothing except define their exports. The build takes it at its word: if your program uses nothing from an import, the import is removed. The file never runs, and neither does a file that only it imports. `bun run` doesn't read the field.

| In your program                                         | In an executable |
| ------------------------------------------------------- | ---------------- |
| `import "pure"`                                         | Removed          |
| `import { x } from "pure"`, and nothing uses `x`        | Removed          |
| `import * as pure from "pure"`, and nothing uses `pure` | Removed          |
| `import { x } from "pure"`, and `x` is used             | The file runs    |
| `require("pure")`, `await import("pure")`               | The file runs    |

- A use counts only where it can run. If `x` appears only in a function that nothing calls, nothing uses `x`. With `--no-aot`, a use in a function nested in code that runs counts even if nothing calls that function.
- With a list, as in `"sideEffects": ["./setup.js"]`, an import of a file on the list stays. The field covers the package's other files.
- In a TypeScript file, `import { x } from "pure"` and `import * as pure from "pure"` need type declarations for the package where `noImplicitAny` is on, as it is by default. Without them, `tsc` and `bun check` report `TS7016`. The build [stops with it](/compiler/aot#type-errors-stop-the-build) in a project that has `@types/bun` installed and names `"bun"`, `"bun-types"` or `"*"` under `"types"` in `tsconfig.json`, as `bun init` sets it up. In any other project the build stops only if the file uses the name nowhere as a value: a use in a function that nothing calls is enough to build. `import "pure"` builds.
- The field in your own `package.json` covers your own files, so `import "./setup.ts"` is removed too.
- `bun test --aot` removes the same imports, except in a test file or a preload itself. No executable holds those two, so an import that one of them writes runs its file wherever `bun test` runs it. In a TypeScript file, `bun test` and `bun test --aot` both leave out an import whose names nothing uses as a value.
- A removed import is still checked. If a file behind it imports a name that doesn't exist, the build stops with `No matching export` (`TS100200`), with `--no-aot` too. `bun run` stops with a `SyntaxError` before the first line.
- A file that re-exports other files and also does something when it loads is skipped too. `zod@3.25.76` sets its English error messages in such a file, so after `import * as z from "zod/v4"` every message is `Invalid input` in an executable and under `bun test --aot`. `bun run` and `bun test` print the real one. zod 4 lists that file in the field.

If you import such a package for what it does when it loads, like a polyfill or a plugin that registers itself, its field is wrong. Build with `--ignore-dce-annotations`. The build then keeps those imports, and ignores `/* @__PURE__ */` comments too. An index file that only re-exports from other files still [loads only the files you import a name from](/bundler#optimizeimports).

## A store to `undefined` or `null`

Assigning to a computed property of `undefined` or `null` throws before the key is converted, as in Node. `bun run` converts the key first, so a key's `toString` runs there and doesn't run in an executable.

```js store.js icon="/icons/javascript.svg"
const key = {
  toString() {
    console.log("converted");
    return "name";
  },
};
undefined[key] = 1; // bun run prints "converted" and throws. An executable only throws.
```

## A function declared in a block

In a CommonJS file that isn't in strict mode, a function declared inside a block is also visible in the rest of the enclosing function once the declaration is reached, as in Node, but not under `bun run`. Don't name it like an import or an index variable.

```js block.cjs icon="/icons/javascript.svg"
{
  function inner() {}
}
console.log(typeof inner); // bun run prints "undefined". An executable prints "function".
```

## `"use strict"` in a function

In a CommonJS file that isn't in strict mode, a function that starts with `"use strict"` runs in strict mode, and so do the functions inside it, as in Node. `bun run` drops the directive, so there the function runs like the rest of the file. `bun test --aot` does the same as an executable.

```js strict.cjs icon="/icons/javascript.svg"
const point = Object.freeze({ x: 0 });
function move() {
  "use strict";
  point.x = 1; // An executable throws a TypeError. Under bun run nothing happens.
}
move();
```

## A class used above its declaration

A class declared at the top level of a file can be used above its declaration, as under `bun run`, which moves such a class to the start of the file. Node throws a `ReferenceError` there, and so does an executable built with `--no-aot`.

```js early.js icon="/icons/javascript.svg"
console.log(new Point().x); // bun run and an executable print 1. Node and --no-aot throw a ReferenceError.
class Point {
  x = 1;
}
```

That goes for a class without `extends`, decorators, computed member names or static blocks, whose static fields hold only literals, functions or such classes. Any other class throws when it's used early, and so does a class declared inside a function or a block. `bun test --aot` does the same as `bun test`.

## A constant read above its declaration

A `const` that is read before its declaration has run throws a `ReferenceError`, as the language says and as in Node. It takes a function that is called early, or a file that calls back into the one that imports it.

```js early.js icon="/icons/javascript.svg"
const first = read(),
  limit = 5;
function read() {
  return limit; // An executable throws a ReferenceError. bun run returns 5. With --no-aot it returns undefined.
}
```

`bun run` writes the value in place of the name if the constant is a number, a string, a boolean, `null` or `undefined` and only such declarations stand above it, so nothing is left to throw. With `--no-aot`, a `const` at the top level of a file becomes a `var`, which reads as `undefined` until it's set. Inside a function it throws there too.

A read that computes nothing is left out, as under `bun run` and with `--no-aot`, so it doesn't throw: `limit;` as a statement, or `void limit`. Three places keep such a read: the initializer of a class field, the default of a parameter and the head of a loop, as in `field = (limit, 1)`. There it throws, with `--no-aot` too, where `bun run` leaves it out.

`--minify-syntax`, which `--minify` includes, makes `bun build` write those values in place like `bun run`, and an executable does the same: `read()` returns 5.

## Members of a TypeScript enum

An executable has the value of an enum member in place of `Color.Red` and `Color["Red"]` wherever `bun build` has it, with and without `--aot`. That includes the files that import the enum, where `bun run` reads the object. A program only sees the difference if it stores to the enum's object, or reads a member before the enum has run.

```ts colors.ts icon="/icons/typescript.svg"
export enum Color {
  Red = 1,
  Size = "red".length,
}
```

```ts app.ts icon="/icons/typescript.svg"
import { Color } from "./colors";
const colors: any = Color;
colors.Red = 2;
console.log(Color.Red); // An executable prints 1. bun run prints 2.
```

A member has such a value if its initializer is made of numbers, strings, other such members and operators. `bun run` also works out `"red".length`, and so does an executable: `Color.Size` is `3` in `colors.ts` itself, and a member after it without an initializer counts on from it. TypeScript wants an initializer for that member (`TS1061`), so it needs a `// @ts-ignore` above it to build. Both also work out a `const` from outside the enum's own block. If `enum Code { Ok = BASE, Fail }` stands in a function, a namespace or a block, and `const BASE = 100` is declared above that function, namespace or block, `Fail` is `BASE + 1` where `bun run` [writes the `const` in place](#a-constant-read-above-its-declaration). `bun run` doesn't if a line such as `import { a } from "./a"`, a function or a class stands above the `const` in its own file, function, namespace or block. Then `Fail` is `undefined` in both. If the `const` has a type annotation, TypeScript wants an initializer for `Fail` too. Other files read `Color.Size` from the object, as under `bun run`. With `--no-aot`, `bun build` works neither out unless you pass `--minify-syntax`: `Color.Size` is read from the object everywhere, and the member after it is `undefined`. `Color["é"]`, `Color?.Red` and `Color[key]` always read the object.

## Where `--no-aot` goes another way

An executable usually behaves like one built with `--no-aot` where that differs from `bun run`. In these places it follows the language instead.

| In your program                                                                            | `bun compile`                      | With `--no-aot`                                                                            |
| ------------------------------------------------------------------------------------------ | ---------------------------------- | ------------------------------------------------------------------------------------------ |
| A `const` at the top level of a file, [read early](#a-constant-read-above-its-declaration) | Throws a `ReferenceError`          | `undefined`                                                                                |
| `(Color as any).Red = 9`, where `Color` is an enum of another file                         | Stores to the enum's object        | Doesn't start: `SyntaxError: Left side of assignment is not a reference`                   |
| `Depth.Low ** 2`, where `Low = -5`                                                         | `25`                               | Doesn't start: `SyntaxError: Unexpected token '**'`                                        |
| `enum Code { Ok = BASE, Fail }` where `bun run` works out the `const BASE`                 | `Fail` is `BASE + 1`, as `bun run` | `Fail` is `undefined`. `BASE + 1` with `--minify-syntax`                                   |
| `function f(first, this: any) {}`, where `this` isn't the first parameter                  | Stops the build with `TS2680`      | Drops the parameter, under `bun run` too                                                   |
| An accessor without a body in a class: `get size(): number;`                               | Stops the build with `TS1005`      | Drops the accessor, under `bun run` too                                                    |
| `enum Header { "content-type" = 1, "content-type" = 2 }`                                   | Stops the build with `TS2300`      | `Header["content-type"]` is `2`, under `bun run` too                                       |
| `function f(a = 1) { "use strict"; }`, also with a pattern or a rest parameter             | Stops the build with `TS1346`      | Drops the directive, under `bun run` too                                                   |
| `await` as a name in a TypeScript file: `import await = shelf.await`                       | Stops the build with `TS1262`      | Runs, under `bun run` too                                                                  |
| A CommonJS file without `"use strict"`                                                     | Runs in sloppy mode, as in Node    | Runs in strict mode: `this` is `undefined` in a plain call, and a store to a string throws |
| A file whose only `require()` is behind `const debug = false; if (debug)`                  | An ES module, as under `bun run`   | CommonJS, so its namespace has a `default`. An ES module with `--minify-syntax`            |
| What `require()` returns for an ES module                                                  | Its namespace, as under `bun run`  | A plain object with the same names                                                         |
| `require.resolve("node:" + "path")`                                                        | `"node:path"`                      | Throws `Cannot find package 'node:'`, under `bun run` too                                  |

With `--no-aot` and under `bun run`, `require.resolve("node:" + "path")` asks for `node:` alone. The error prints as `Cannot find package 'node:'`, and its `message` reads `Cannot find module 'node:'`.

`// @ts-nocheck` doesn't turn off the rows that stop the build. `TS2680`, `TS1005` and `TS2300` are errors for `tsc` too. Under `bun test --aot`, a file with one of those three fails to load with a `SyntaxError` that has the same message, and the other files run. `TS1346` is an early error of JavaScript itself, which `tsc` lets pass only for a `target` below ES2016. `tsc` reports `TS1262` only in a file with an `import` or an `export`, and Bun takes every TypeScript file for a module. It goes for a declaration inside a namespace too: `namespace shelf { export const await = 1 }`.

`const arguments = 1` or `const eval = 1` in a function of a TypeScript file stops the build with `TS1215`. `--no-aot` stops at it as well, with `Declarations with the name "arguments" cannot be used with the ESM output format due to strict mode`, so only `bun run` runs it. In a CommonJS file that isn't in strict mode, `const arguments = 1` is an ordinary declaration and works.

A store to an import, like `limit = 1` after `import { limit } from "./limits"`, stops the build with `TS2632`, in a JavaScript file too. So does a store to a member of `import * as limits` (`TS2540`), and a `delete` of one (`TS2704`). `--no-aot` stops at all three as well, with `Cannot assign to import "limit"`, so only `bun run` runs such a file: it throws a `TypeError` when it gets to that line.

## `fn.caller` and `fn.arguments`

These two properties of a function that isn't in strict mode are always `null`, also while the function runs. Under `bun run` they hold the calling function and the arguments of the running call. They aren't part of the language, and strict mode and ES modules never had them. The `arguments` object inside a function works as usual.

```js caller.cjs icon="/icons/javascript.svg"
function inner() {
  return [inner.caller === outer, inner.arguments, arguments.length];
}
function outer() {
  return inner(1, 2, 3);
}
console.log(outer()); // bun run prints [ true, [ 1, 2, 3 ], 3 ]. An executable prints [ false, null, 3 ].
```

The call sites that `Error.prepareStackTrace` gets are the same: `getFunction()` returns `undefined` for every frame, as it does under `bun run` for a function in strict mode. `getFunctionName()` still gives its name.

## Error messages

The class of an error, its line and its stack trace are the same, except for some errors of a load or a mock, for the frames of some built-ins and for what [Smaller differences](#smaller-differences) lists. The functions of `Math`, `regexp.exec()`, `regexp.test()` and `array.pop()`, among others, are compiled into the function that calls them and have no frame of their own. When `Math.max(value)` calls `value.valueOf()`, a trace taken there has your function right below `valueOf`, where `bun run` has a frame for `max`.

Where `bun run` quotes your source in the message, an executable quotes it from the text of your functions, which it also keeps for `fn.toString()`, and of the statements at the top level of your files. With [`--no-compile-function-source`](/compiler/size) it has no text and quotes less. [`bun test --aot`](/compiler/debugging#run-your-tests-compiled) has your files beside it and reads the line from there.

A function of Bun or of a `node:` module has no text: `http.IncomingMessage.toString()` is `function IncomingMessage() { [native code] }`, where `bun run` prints its source.

```txt
bun run      TypeError: null is not an object (evaluating 'o.a.c')
bun compile  TypeError: null is not an object (evaluating 'o.a.c')
bun compile  TypeError: null is not an object (evaluating 'null.c')  without the text
```

A message quotes the expression that failed as Bun prints your source, so spaces, quotes and parentheses are the printer's. An executable quotes what `bun build --compile` prints. `bun run`, `bun test` and `--minify-syntax` rewrite the source before they print it, and `bun test --aot` or an executable built with `--minify-syntax` follows part of that: `o["name"]` reads `o.name`, `` `text` `` reads `"text"` and `(0, f())` reads `f()`. The rest stays as you wrote it: `const r = f(x); return r.y` reads `r.y` where `bun test` says `f(x).y`, and `const x = o.x; const y = o.y`, which `bun test` joins into one pattern, fails on a null `o` with `null is not an object (evaluating 'o.x')` where `bun test` says `Cannot destructure property 'x' from null or undefined value`. `bun test --aot` also keeps `f(1 + 2)` and the name of a constant where `bun test` says `f(3)` and shows the value. `fn.toString()` in an executable still returns your source, without its types and mostly without what `bun build` removes: a branch that never runs, such as `if (false)`, is empty, and a name that `--define` replaces reads as its value. What TypeScript turns into code is there as code: a constructor parameter like `public x` reads as the field `x` and `this.x = x`, an enum member like `Color.Green` reads as its value, an enum declared inside the function reads as the code that builds its object, and a variable that `namespace Box` exports reads as `Box.side`. Decorators, `accessor` fields and JSX stay as you wrote them, so that text can't be evaluated again. Class fields stay fields under `useDefineForClassFields: false` too. It keeps your line breaks, spaces and parentheses, and isn't laid out as the bundler prints it. An executable doesn't keep the source of Bun's built-in modules, so when an error is thrown inside one, for example after your code replaces `Object.keys`, the quoted expression can differ too.

Neither quotes one kind of text whole: a function or an arrow with statements in its body, a class, a method, getter or setter in an object literal, and an array or object literal written on several lines. A failed call with one of these among its arguments reads `list.forEech()`, a failed call on one of them reads `nope()`, and a failed read off one names the value, as in `undefined.b`.

A member of an enum is quoted as you wrote it, `table[Kind.Closed].title`. `bun run` quotes the value that its transpiler put there, `table[1 /* Closed */].title`.

Where a function of Bun or of a `node:` module refuses an argument or its `this` for its type, the message describes an object without a constructor as Node does: `[Object: null prototype]`, or `[Object]` if it has a prototype. `bun run` prints what the object holds.

Check `error.name` or use `instanceof`, not `error.message`. A service that groups errors by message, such as Sentry, shows new groups. An uncaught error prints [without the source excerpt](/compiler/debugging#stack-traces) that `bun run` shows above it.

## Garbage collection

At an `await`, a local variable that isn't read again stops keeping its value alive. A class declared in a function keeps what its constructor captures, and a CommonJS file keeps its first `exports` object, until the program ends. Under `bun run`, a variable that a closure captures lives as long as the function's other variables. An executable may collect a value earlier than `bun run` does, for example one that only a branch that can never run still reads, and only a `WeakRef` or a `FinalizationRegistry` can tell.

```ts watch.ts icon="/icons/typescript.svg"
async function watch(target: object) {
  const registry = new FinalizationRegistry(() => console.log("collected"));
  registry.register(target, 0);
  await finished; // the registry can be collected here, and then its callback never runs
}
```

Keep a `FinalizationRegistry` at module level, or somewhere your program reads it again later.

A variable that nothing in your program can read is removed. So is an object that only that variable held, unless your program could notice that it's gone, for example through a `WeakRef`. A [heap snapshot](/compiler/debugging#profiles) doesn't list what was removed.

## Smaller differences

Few programs notice these.

| What you read                                                                     | `bun run`                                                                    | An executable                                    |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------ |
| `fn.caller` and `fn.arguments` while `fn` runs, outside strict mode               | The calling function and the arguments                                       | `null`                                           |
| `callSite.getFunction()` in `Error.prepareStackTrace`, outside strict mode        | The function of the frame                                                    | `undefined`, as in strict mode                   |
| `error.originalLine` and `error.originalColumn`                                   | The position in the text that the transpiler printed                         | The same as `error.line` and `error.column`      |
| `socket.map`, `.filter`, `.toArray` and the like, without importing `node:stream` | There once anything has touched `process.stdout` or `process.stderr`         | There once `node:stream` is imported             |
| `Bun.deepMatch()`, `toMatchObject()` of two classes: a `static #private` field    | It is compared                                                               | It isn't                                         |
| `toMatchObject()` of what the build can't follow: an object in a `#private` field | It is compared                                                               | An `Error` says how to write the comparison      |
| `heapStats().objectTypeCounts.Structure` of `bun:jsc`                             | Grows with each property name that an object gets                            | Doesn't grow for a name that is added only once  |
| `typeof name;` in a function or a block, where `name` is a getter on `globalThis` | The transpiler drops the statement, so the getter isn't called               | The getter is called, as the language says       |
| `f.name` after `const f = 1 + 1 === 2 ? () => 3 : null`                           | `"f"`: the transpiler drops the test, so the engine sees `const f = () => 3` | `""`, as the language says                       |
| `error.stack` after `fn.displayName = "x"` or `defineProperty(fn, "name", ..)`    | The name that you set                                                        | The name that you wrote                          |
| In `error.stack`, the frame around a `using` whose `[Symbol.dispose]()` throws    | A place near the end of the scope, and sometimes one after it                | The name that the `using` declares               |
| `fn.name` and `Class.name`, built with `--obfuscate`                              | The name that you wrote                                                      | `""`, which is what the flag is for              |
| `new Below()` after `Object.setPrototypeOf(Below, CString)`, of `bun:ffi`         | The string that `new CString()` returns                                      | Throws a `TypeError`: `this` has to be an object |
| A name imported from a CommonJS file that was still running, after a later import | What the file had exported when that import was linked                       | What the file had exported when it ended         |
| `res.write()` after `req.socket._writableState = copy`, in `node:http`            | Goes by the `highWaterMark` of the copy                                      | Goes by the one that the socket had              |
| `require("node:http")` after `stream.Stream = Mine` or `stream.Duplex = Mine`     | Its classes extend yours                                                     | A `TypeError`: add to its `prototype` instead    |
| `{ [key]: value }`, where `key` has a `toString()` that you can watch             | The value is evaluated, then the key is converted                            | The key is converted first, as the language says |
| `using x = value`, where a getter for `Symbol.dispose` reads `x`                  | `x` already holds the value                                                  | A `ReferenceError`, as the language says         |
| `let [a = late] = iterator; let late`, which throws a `ReferenceError`            | The iterator's `return()` isn't called                                       | It is called first, as the language says         |
| `for (name of list)` or `for (name in object)`, above `let name`                  | Stores into `name` and runs the loop                                         | A `ReferenceError`, as the language says         |
| `Object.keys({ get a() {}, set a(v) {}, b: 1, get a() {} })`, or of such a class  | `b`, `a`                                                                     | `a`, `b`, as the language says                   |
| A function declared in a later `case`, called while an earlier `case` runs        | A `ReferenceError`                                                           | It is called, as the language says               |
| `typeof Later` above a `class Later {}` that stands behind a `return`             | `"undefined"`: the transpiler drops the class                                | A `ReferenceError`, as the language says         |
| `typeof w` after `class C { [eval("var w = 1")]() {} }`, outside strict mode      | `"number"`: the text runs as the code around the class does                  | `"undefined"`: a class is strict code            |

`Bun.$` is compiled into an executable if your code can reach it: it writes `Bun.$`, reads `Bun[name]`, hands `Bun` on as a value, or reads `globalThis` under a key that is put together while it runs. Asking whether the name is there counts too: `"$" in Bun` counts as writing `Bun.$`, and `Object.hasOwn(Bun, "$")` hands `Bun` on as a value. Only a list of the names, as in `Object.keys(Bun).includes("$")`, answers `true` and keeps nothing. Text that the compiler never saw, such as a string handed to `eval`, can still ask for the shell in a program that doesn't use it. Reading `Bun.$` then throws `Bun.$ was not compiled into this executable`. Write `Bun.$` once anywhere in your program to keep it.

Text that the compiler never saw, such as a string handed to `eval`, can reach a built-in function or object that your program doesn't use. Whoever then reads it, as in `typeof process.finalization`, gets an error that says `was not compiled into this executable`, and can catch it. A program that can't run such text never sees that error. If it needs a function that isn't there, the compiler has made a mistake: the executable prints `was left out of the executable` with the name of the function and stops. No `catch` takes that, so a wrong build can't go unnoticed. Please report it.

Some roads to the global object get past the compiler. `addEventListener` and `dispatchEvent` of `EventTarget.prototype` work on the global object when they are called without a receiver, and the event then answers it as its `target`. The compiler follows that wherever your code writes the name of the method, at the read itself or anywhere else as a string: `const send = signal.dispatchEvent`, a pattern, `Reflect.get(signal, "dispatchEvent")`, `signal[Name.Send]` for a member `Send = "dispatchEvent"` of an `enum`, a name out of a JSON file that you import. It doesn't follow a name that is put together while the program runs, as in `const send = signal[["dispatch", "Event"].join("")]; send(event)`, or that comes out of `for...in`, `Object.keys()` or the `name` of a function. It doesn't follow the method either where your code finds it without any name, as in `Object.values(Object.getPrototypeOf(Object.getPrototypeOf(signal)))`. What `event.target` leads to from there, such as `event.target.process.finalization`, may have been left out, and the executable then stops with `was left out of the executable`. Write `void dispatchEvent` once anywhere in your program to keep everything that the global object leads to. It also stops if `require` or `process` meets your own `Symbol.hasInstance`, or if `Bun.inspect()` prints the `this` of a call without a receiver.

`process.stdout.write()` and `process.stderr.write()` don't load `node:stream` in an executable, which is why the stream helpers aren't on a `net.Socket` until you import it.

In a package, `./x.mjs` also finds `x.mts` and `./x.cjs` also finds `x.cts`, so that a package can [publish its TypeScript](/compiler/libraries#publish-a-package-with-its-types). `bun run` and an executable built with `--no-aot` look for those only outside `node_modules`.

With `"useDefineForClassFields": false` in `tsconfig.json`, the fields of a class are assigned, unless one of them stands under a key that has to be computed: then all of them are defined. What has to be computed is what `bun build` computes, as with `--no-aot`. Without `--minify-syntax` that includes `[KEY]` for a constant that `bun run` [writes in place](#a-constant-read-above-its-declaration), `["a" + "b"]`, `[1 + 2]`, ``[`a${1}`]`` and `["abc".length]`, whose values `bun run` has: there `bun run` assigns the fields and an executable defines them. `[-1]`, ``[`a`]`` and `[1 < 2 ? "a" : "b"]` are computed by neither. Of these keys TypeScript takes only `[KEY]`, `[-1]` and ``[`a`]``: each of the others stops the build with `TS1166` unless `// @ts-ignore` stands above the field. Below an `import()` in the same file, `bun build` has the values of `["a" + "b"]`, `[1 + 2]` and ``[`a${1}`]`` too, and an executable assigns the fields there.

`process.env.NODE_ENV`, `process.platform` and `process.arch`, written out like that, are replaced by their values when you build, as with `--no-aot`: `NODE_ENV=production ./app` still reads `"development"` unless you built with `NODE_ENV=production` or `--production`.

If `NODE_UNIQUE_ID` is set in the environment and no `node:cluster` primary started the process, an executable that never imports `node:cluster` listens as usual with `node:http`, `node:net` and `node:dgram`, and leaves the variable in `process.env`. `bun run` listens with `node:http` and deletes the variable, but with `node:net` and `node:dgram` it waits for a primary and never listens. Node.js never listens with any of the three.

A `NaN` that you write to a typed array or a `DataView` can have other bytes than under `bun run`, which the language leaves to the implementation: on x64, when a loop adds up a `Float64Array` that holds `Infinity` and `-Infinity`, the sum is stored as `7ff8000000000000`, where `bun run` stores `fff8000000000000` while it interprets the loop, and either of the two once its JIT has compiled it. `a[0] + a[1]` stored at once is `fff8000000000000` in both.

An executable keeps 256 KB of the stack of every thread for the runtime's own code. Deep recursion throws `RangeError: Maximum call stack size exceeded` at least that much sooner than `bun run`, and with a very small stack (`ulimit -s`) the program throws it at the start: it needs about 512 KB where `bun run` needs about 192 KB. `bun test --aot` is the same.

`CString` of `bun:ffi` answers `new` with a string, not an object. A class that gets it as its parent from `Object.setPrototypeOf()`, `Reflect.setPrototypeOf()` or `__proto__` throws `TypeError: The constructor did not return an object` at `super()`. `new CString(ptr)` itself returns the string as under `bun run`.

A CommonJS file can be imported while it's still running: it calls `require()` on an ES module, and that module imports the file back. The module gets what the file has exported so far. If an `import()` of the same file was under way at that moment, whoever imports the file afterwards gets what it has exported when it ended. `bun run` keeps the two apart for good, so the first module goes on reading the early values. In an executable all importers of a file read the same variables: once a later module has been linked, the first module reads the later values too, and its `import * as file` is the later namespace object, with the names that the file added in between.

## Not supported

| Feature                                     | Instead                                                        |
| ------------------------------------------- | -------------------------------------------------------------- |
| `--target` for another platform             | Build on that platform, or pass `--no-aot`                     |
| `--preload`, `--import` in `BUN_OPTIONS`    | Import the file from your entry point                          |
| `preload` in `bunfig.toml`                  | Import the file from your entry point                          |
| `--inspect` in `BUN_OPTIONS`, `BUN_INSPECT` | Build with `--compile-inspector`                               |
| `--unhandled-rejections` in `BUN_OPTIONS`   | Build with `--compile-exec-argv=--unhandled-rejections=<mode>` |
| `--sql-preconnect` in `BUN_OPTIONS`         | Build with `--compile-exec-argv=--sql-preconnect`              |
| Breakpoints and `debugger`                  | `bun --inspect-brk ./app.ts`                                   |
| `cc()` from `bun:ffi`, on Linux             | Compile the C file first, then `dlopen()`                      |
| Over 256 open `JSCallback`s, see below      | Let the executable read its own file, or `close()` some        |
| Over 32 GB of objects in a thread           | `--aot-huge-heap`                                              |
| `with { type: "macro" }` on an import       | Pass `--no-aot`                                                |
| A plugin that gives an asset another loader | `--loader .ext:ts`, for that extension                         |

`--unhandled-rejections` prints its warnings with Bun's own JavaScript, which is compiled in when the option is written into the executable. `--sql-preconnect` connects with `Bun.sql`, which is compiled in when the program uses it or the option is written into the executable. Otherwise the executable prints, for example, `--unhandled-rejections can't be used with this executable`, and exits before the program starts.

An executable holds the entry points for 256 `JSCallback`s of `bun:ffi`. It gets more by mapping that part of its own file again. On Linux 6.7 and later that is the only way, because the executable gives up the right to make memory executable when it starts. So if it can't open its file, because the file's mode is execute-only or no file descriptor is free, the 257th open `JSCallback` throws a `RangeError`.

An import of a [macro](/bundler/macros) stops the build with `TS100053: Macros are disabled`. Nothing of the program is compiled with the call left in.

The build decides what a file is, code, data or an asset, from its extension and from `with { type }` before it asks a plugin for the file. If `onLoad` then answers for `late.bin` with `loader: "ts"`, or for an asset with `"js"` or `"text"`, the build stops with `TS100050` and names the `--loader` flag that says the same up front. A plugin can still change the contents of an asset.

A `bunfig.toml` in the working directory never stops the executable, since it may be there for `bun`: the executable prints a warning for its `preload` and runs without it. Build with `--no-compile-autoload-bunfig` to leave the file unread. A `preload` in a file that `--config` names is an error, like `--preload`.
