<Warning>Ahead-of-time compilation is experimental.</Warning>

Stack traces, crash reports and profilers work on an executable built with [`bun compile`](/compiler/aot). Breakpoints don't. To use them, run your program from its source with `bun --inspect-brk ./app.ts`. If the problem only shows up in the executable, check [Compatibility](/compiler/compatibility).

## Stack traces

```ts repo.ts icon="/icons/typescript.svg"
class Repo {
  find(id: number): string {
    if (id < 0) throw new RangeError("bad id " + id);
    return "x";
  }
}
new Repo().find(-1);
```

```bash terminal icon="terminal"
bun compile ./repo.ts && ./repo
```

```txt
RangeError: bad id -1
      at find (/$bunfs/root/repo.ts:3:27)
      at /$bunfs/root/repo.ts:7:12
```

Stack traces have the file, line and column of your source code. You don't need a source map. The part after `/$bunfs/root/` is the path of the source file, relative to the directory where you ran the build. The executable doesn't hold the text of your files, so it prints no source excerpt above the message.

### Minified executables and external source maps

```bash terminal icon="terminal"
bun compile --minify --sourcemap=external ./repo.ts
```

`--minify` shortens the names of functions, classes and variables. `--sourcemap=external` moves what stack traces show (function names, paths, lines and columns) out of the executable and into `repo.map`, next to it. Every frame then points into `compiled.js`, as in `compiled.js:4:2`. That file doesn't exist. The line and column are a position in the map, and any source map library turns them back into your names, files and lines.

Your program reads the names it read before: `--sourcemap=external` doesn't change `handler.name` or `error.constructor.name`. With `--minify` they are short, as in any minified build, and the map has them as you wrote them. The source text of functions moves out too, as with [`--no-compile-function-source`](/compiler/size): `handler.toString()` returns `function handler() { [native code] }`.

Keep the map of every build you deploy, and don't ship it.

### Keep every name out of the executable

```bash terminal icon="terminal"
bun compile --obfuscate ./repo.ts
```

`--obfuscate` does what `--sourcemap=external` does, and the `name` of every function and class is `""`. That includes built-in functions that are written in JavaScript, such as `Array.prototype.map`. An error message names a variable by a single letter. Code that reads a name behaves differently: `this.name = new.target.name` sets an empty name, and a table keyed by `constructor.name` puts every class under one key. Property names, strings and the descriptions of symbols stay in the executable, because your program finds and prints them when it runs.

### List the strings in an executable

```bash terminal icon="terminal"
bun build --aot-stored-strings ./dist/app > strings.bin
```

Before you ship, you may want to check that a name didn't end up in the executable. `strings` and `grep` are a poor fit for that. Compiled code stores its strings back to back and shares bytes between them, so two neighbors can spell a word that isn't in your program. This command prints every string that the compiled code stores, whole, as UTF-8, each followed by a zero byte. It reads an executable built for any platform, builds nothing, and takes no other flag.

Standard error gets one line for each place in the file that holds such bytes: the strings, the source text that error messages quote, and the source text of functions.

```txt
image 0 | Text | offset 94617600 | length 18883161 | 1 bytes that no string covers
image 0 | quoted text | offset 201326848 | length 412007 | 0 bytes that no string covers
image 0 | function text | offset 201738855 | length 96110 | 0 bytes that no string covers
```

The exit code is 0 when the bytes that no string covers are all zero, 1 when one of them isn't, and 2 when the file holds no compiled code or comes from a Bun with another image format.

### Use with Sentry

```bash terminal icon="terminal"
bun compile --minify --sourcemap=external ./src/index.ts --outfile dist/app
sentry-cli sourcemaps upload --org my-org --project my-project dist
```

`@sentry/bun` and `@sentry/node` work as they are. Sentry finds the map of an event by its debug ID, so you don't set a release or a URL prefix, and you don't run `sentry-cli sourcemaps inject`. Deploy `dist/app` without `app.map` and `app.map.js`.

## Crash reports

If the process crashes, Bun prints a report to stderr. It ends with the functions of your program that were running, innermost first, with file, line and column. The `Build ID:` line matches the ID that `bun compile` printed when you built it. Please [open an issue](https://github.com/oven-sh/bun/issues) with the report.

## Run your tests compiled

```bash terminal icon="terminal"
bun test --aot
```

`bun test --aot` compiles your test files, your preloads and everything they import the way `bun compile` does, and runs the compiled code. The type checker, the optimizer's settings, the object model and the run time are those of an executable, so every [difference from `bun run`](/compiler/compatibility) shows up in your tests as it would there.

`--isolate`, `--parallel`, `--rerun-each` and `--coverage` work as in `bun test`. `--watch`, `--hot` and `--inspect` exit with an error.

`--shard=i/n` still runs every test file in exactly one shard, but splits the files differently from `bun test`. A compiled run builds everything its test files import before the first test starts. So test files that import the same code go into the same shard, and each part of your project is compiled on one machine instead of on all of them. What your preloads import is compiled in every shard. With `--timings` written by a compiled `--parallel` run, a shard that has more to compile gets fewer test files. Each machine works out the split for itself, from the files on disk and the timings and from nothing else, so every machine needs the same checkout and the same timings, and `--parallel` may differ between them. Each shard prints a hash of the whole split. It's the same on every shard. Where no other split is faster, you get the split of `bun test`.

The build also has to see whether your tests take a file out of `require.cache`, because only then is the run compiled for modules that can load twice: a test file calls what it imports like code that wasn't compiled, and the call isn't inlined. One `delete require.cache[path]` anywhere in the run, also in a package, counts for every file, whatever the path is, and your tests run slower. `Reflect.deleteProperty(require.cache, path)`, a store to an entry, `require.cache` passed to a function and `jest.resetModules()` count the same. A `delete` that the build never saw, in a file that a test writes and then loads, throws an error that names the file.

A file that was compiled runs as it was compiled, also where a test writes, moves or removes it before it's first loaded. `bun test` reads what's on disk by then. To import what a test generates, write it to a path where there's no file when the run starts.

An entry that a test stores under the name of a Node.js module, `require.cache["fs"] = { exports: fake }`, doesn't reach compiled code. `require("fs")` answers the module itself there, where `bun test` answers `fake`, and no error tells you. Use `mock.module("fs", () => fake)`.

A spy or a mock of `export const value = 1` reaches the file's own reads of `value`, as the language says. `bun test` has copied the constant into those reads by then, so `() => value` in that file still answers `1` there.

A store to a member of a TypeScript enum, `(Color as any).Red = 9`, or a spy on it doesn't reach `Color.Red` in the files that import the enum, and no error tells you. [The member's value stands in place of the read](/compiler/compatibility#members-of-a-typescript-enum), as in an executable, where `bun test` reads the object.

The build also has to see which exports your tests replace, because only those are read from a variable. It reads `spyOn(namespace, "name")`, `jest.spyOn()` and `vi.spyOn()` where they're called, also where the spy function is kept in a variable, and `mock.module()` the same way. Where the name isn't a constant, every export of that module can be replaced. Where the object isn't the namespace import itself, as in `spyOn(holder.module, "read")`, the build opens the exports called `read` of every module whose namespace object is passed around as a value. A name there that isn't a constant is read where the file writes out everything it can be: a list that a loop or a callback walks, a column of the rows of `test.each()`, the pieces of `"open read".split(" ")`, what the calls of a function of the file pass. Each spy is read by itself. Where one of its names is made, as by `Object.keys()` or `join()`, or its list is changed after it's written, or the spy function itself is handed to a helper or taken from `Bun.jest()`, every export of those modules can be replaced. In a test run that loads a module under a name only known at run time, as in `await import(name)`, every module counts as passed around. A spy that the build never saw, in text that a test evaluates or in a file that it writes and then loads, throws a `TypeError` that names the export. So does a spy on a namespace object that only such a file passes around, as in `spyOn((await import("./generated.js")).held, "read")`: the build follows a namespace object only through code that it has read.

The build finds what a run replaces on built-in objects in your tests: the test files, your preloads, the files that only they import and the packages that only they need. Code that a test holds as a string isn't read. A file of your program, or a package that your program needs, opens nothing, and its assignment to a built-in method throws the `TypeError` of the executable, whatever your tests replace and whichever test files run. The end of the run lists it. That also goes for an assignment whose object the build can't follow, as in `for (const holder of [Array.prototype, Object]) holder[name] = patch`, which `bun test` stores. Your program is what `package.json` names (`main`, `module`, `bin`, `exports`), what a file of your project that the run doesn't load and that isn't a test imports, and everything those import, whichever test files run. A file that only your tests come to isn't part of it, however deep it lies. A store that stands in a file of your program is refused also where a test calls that function to patch a built-in, as in `patch(Array.prototype, "push", fake)`: do the store, or call `spyOn()`, in a file of your tests. Where your tests replace the same method, a store of your program is still taken if nothing of your program is running when it happens: a built-in function that it hands to a timer or a promise, as in `setTimeout(Object.assign, 0, Math, patch)`, or that it holds in a variable and calls as the last thing it does, as in `return set(fake)` with `const set = Reflect.set.bind(null, Math, "floor")`. So is a store in a text that it hands to `node:vm`. The other way round, a test's `run(() => set(fake))` is refused where `run` is a function of your program, because the arrow function is gone when `set` stores: write `run(() => { set(fake); })`. A method that an executable can replace too, like `Function.prototype.toString`, and a new name on `Function.prototype` are open to your program as well once a test replaces or adds them. Where the build sees the object, `bun compile` reports the line as `TS100014`. With `--aot-allow-code-from-disk` every file counts as a test's. The build follows a built-in out of Bun's own modules, as in `require("node:console")` or `import { performance } from "node:perf_hooks"`. Where the name is only known when the test runs, as in `spyOn(Date, name)`, or the object goes where the build doesn't follow it, as in `module.exports = { holder: Object }` or `helper(Date)`, every method of that object can be replaced. On the global object that goes only for what an executable can replace too, like `fetch` and the timers. `mockRestore()` and `mock.restore()` put the original back. If the build can't tell which object a test writes to, as in `Object.getPrototypeOf([]).join = fake`, the replacement throws a `TypeError` that names the method and shows how to spell it out. What the language calls by itself (`next`, `constructor`, `Symbol.iterator`) and an index like `Array.prototype[0]` can't be replaced, and the `TypeError` says so: [the whole list](/compiler/compatibility#what-a-test-cant-replace). An existing `toString`, `valueOf`, `toJSON` or `then` can be replaced, and so can the `Symbol.iterator` of `Map`, `Set`, `Headers` and `URLSearchParams`. A `toJSON` can also be added to `Object.prototype`; a `then` can't.

## Run under the compiler's rules

```bash terminal icon="terminal"
bun run --aot ./app.ts
```

`bun run --aot` checks your program the way `bun compile` does, and exits with code `1` on anything in it that would stop the build. It generates no code, so it can't reach the limits on generated code: `bun compile` and `bun check --aot` can still refuse a function that needs too large a stack frame, or a program over another limit of the compiler (`TS100057`). Then it runs the program from its source files with the JIT, with [built-in objects read-only](/compiler/compatibility#built-in-objects-are-read-only) as in an executable. `--watch` and `--inspect` work. The other [differences from `bun run`](/compiler/compatibility) don't show up, because the code that runs isn't compiled. To see those, run your tests with `bun test --aot`, or build the executable and run it.

## Find the guards that fail

```bash terminal icon="terminal"
bun check --aot --explain=guards ./app.ts
```

A [guard](/compiler/types#when-a-value-doesnt-match-its-type) that fails doesn't change what your program does. It sends the rest of the call to the function's slow version, or slows down one operation, so look here when a hot function is slower than you expected.

The command reads your source and lists each guard that the compiler couldn't remove, with the reason, what happens when it fails and a fix.

## Profiles

```bash terminal icon="terminal"
BUN_OPTIONS="--cpu-prof" ./app    # a .cpuprofile for Chrome DevTools or VS Code
BUN_OPTIONS="--heap-prof" ./app   # a heap profile
```

Both show your functions, classes and files by their names. `perf`, `gdb` and Instruments show addresses where your compiled code runs. On Linux, build with `--aot-symbols` to see function names there too.

A heap snapshot (`Bun.generateHeapSnapshot()`, `v8.writeHeapSnapshot()`) lists what the top-level variables of each module and the variables that closures capture hold, under the variables' names, as it does under `bun run`. A captured variable is listed on the closure that holds it, or with its module's variables if its function runs only once. It shows the heap of the compiled program, which can hold less. The compiler removes a variable that nothing in your program can read, along with an object that only that variable held, and it creates some objects when they're first read instead of when the module loads. Those aren't in the heap, so they aren't in the snapshot. Build with [`--compile-inspector`](#the-inspector) to see every variable that `bun run` shows.

## The inspector

```bash terminal icon="terminal"
bun compile --compile-inspector ./app.ts
BUN_INSPECT="ws://127.0.0.1:6499/app" ./app
```

The console, heap snapshots and CPU profiles work. Breakpoints, stepping and `debugger` statements don't. The flag makes the executable larger and slower, so leave it out of production builds.

Code you run in the console can call any function and change any object it gets hold of, including one you pick out of a heap snapshot, and compiled code sees the change. That's where the slowdown comes from: the compiler can no longer assume it has read every caller and every write.

Some variables are the exception. The inspector can read the locals of a compiled function but can't assign to them. The same goes for any variable that your program never assigns to after declaring it, like a `const` or a function declaration.
