<Warning>Ahead-of-time compilation is experimental.</Warning>

Stack traces, crash reports and profilers work on an executable built with [`bun compile`](/compiler/aot). Breakpoints don't. To use them, run your program from its source with `bun --inspect-brk ./app.ts`. If the problem only shows up in the executable, check [Compatibility](/compiler/compatibility).

## Stack traces

```ts repo.ts icon="/icons/typescript.svg"
class Repo {
  find(id: number): string {
    if (id < 0) throw new RangeError("bad id " + id);
    return "x";
  }
}
new Repo().find(-1);
```

```bash terminal icon="terminal"
bun compile ./repo.ts && ./repo
```

```txt
RangeError: bad id -1
      at find (/$bunfs/root/repo.ts:3:23)
      at /$bunfs/root/repo.ts:7:12
```

Stack traces have the file, line and column of your source code. You don't need a source map. The part after `/$bunfs/root/` is the path of the source file, relative to the directory where you ran the build. The executable doesn't hold the text of your files, so it prints no source excerpt above the message.

### Minified executables and external source maps

```bash terminal icon="terminal"
bun compile --minify --sourcemap=external ./repo.ts
```

`--minify` shortens the names of functions, classes and variables. `--sourcemap=external` moves names, paths, lines and columns out of the executable and into `repo.map`, next to it. Every frame then points into `compiled.js`, as in `compiled.js:4:2`. That file doesn't exist. The line and column are a position in the map, and any source map library turns them back into your names, files and lines.

Keep the map of every build you deploy, and don't ship it.

### Use with Sentry

```bash terminal icon="terminal"
bun compile --minify --sourcemap=external ./src/index.ts --outfile dist/app
sentry-cli sourcemaps upload --org my-org --project my-project dist
```

`@sentry/bun` and `@sentry/node` work as they are. Sentry finds the map of an event by its debug ID, so you don't set a release or a URL prefix, and you don't run `sentry-cli sourcemaps inject`. Deploy `dist/app` without `app.map` and `app.map.js`.

## Crash reports

If the process crashes, Bun prints a report to stderr. It ends with the functions of your program that were running, innermost first, with file, line and column. The `Build ID:` line matches the ID that `bun compile` printed when you built it. Please [open an issue](https://github.com/oven-sh/bun/issues) with the report.

## Run your tests compiled

```bash terminal icon="terminal"
bun test --aot
```

`bun test --aot` compiles your test files, your preloads and everything they import the way `bun compile` does, and runs the compiled code. The type checker, the optimizer's settings, the object model and the run time are those of an executable, so every [difference from `bun run`](/compiler/compatibility) shows up in your tests as it would there.

`--isolate`, `--parallel` and `--rerun-each` work as in `bun test`, but for one thing: if a worker process crashes in a run that is compiled as several programs, the test file it was running fails and the run goes on, where `bun test --parallel` stops the run. `--watch`, `--hot` and `--inspect` exit with an error. `--coverage` is ignored, with a warning.

The build also has to see which files your tests take out of `require.cache`, because only the code that imports those is compiled for a module that can load twice: a test file calls what it imports from such a file like code that wasn't compiled, and the call isn't inlined. It follows `delete require.cache[require.resolve("./config")]`, a path kept in a `const`, and `Reflect.deleteProperty()`. Where it can't tell the path, as in a loop over `Object.keys(require.cache)` or a helper that takes the path as a parameter, every file can be taken out, and your tests run slower. A `delete` that the build never saw, in a file that a test writes and then loads, throws an error that names the file.

The build also has to see which files your tests write, because only those are compared with the disk, and the new text can import anything, so every export of the run is kept and can be called from it. It follows the functions of `node:fs`, `node:fs/promises` and `Bun` that write, move or remove a file, and a path that the file spells: `join(import.meta.dir, "state.js")`, `new URL("./state.js", import.meta.url)`, `require.resolve("./state.js")`, a path from the working directory, a path kept in a `const`, the names of a list. Where it can't tell the path, as in a helper that takes the path as a parameter, or where another process writes the file, the compiled file runs.

An entry that a test stores under the name of a Node.js module, `require.cache["fs"] = { exports: fake }`, answers `require("fs")`, as in `bun test`. The build reads the key the same way. Where it can't tell the key, or `require.cache` is passed to a function, every `require()` of a module that the key could name looks in `require.cache` first, and a call of what it answers isn't inlined. A key that ends like the path of a file, as in `path.join(dir, "addon.node")`, names none. A store that the build never saw throws an error that names the module.

The build also has to see which exports your tests replace, because only those are read from a variable. It follows `spyOn(namespace, "name")`, `jest.spyOn()` and `vi.spyOn()`, also where the spy function is kept in a variable, handed to a helper or taken from `Bun.jest()`, and the same for `mock.module()`. Where the name is only known when the test runs, every export of that module can be replaced. Where the object isn't the namespace import itself, as in `spyOn(holder.module, "read")`, the build opens the exports called `read` of every module whose namespace object is passed around as a value. It finds the name in a constant, in the list or the pairs that a loop walks, and in what your tests pass to a helper that takes it. Where it can't find the name, every export of those modules can be replaced. Where a test evaluates text that's made at run time, with `eval()`, `new Function()` or `node:vm`, every export of every module whose namespace object that text can get hold of can be replaced. That doesn't hold in a test run that also passes around a module it loaded under a name only known at run time, as in `loaded.push(await import(name))`: every namespace object is within reach there, so the build follows only the spies it sees. A file that a test writes and then loads under a path that the build can't tell is read from the string the test writes it from: the exports it spies on by name can be replaced in every module that has that name, and a module it spies on under a name it's told, in every file whose path ends the way it writes it. A spy that the build never saw, in text like that or in a file the test doesn't hold as a string, throws a `TypeError` that names the export.

The build finds what your tests replace on built-in objects in your tests, your preloads and what they import, also in code that a test holds as a string. `mockRestore()` and `mock.restore()` put the original back. If the build can't tell which method a test replaces, for example because the name is only known when the test runs, the replacement throws a `TypeError` that names the method and shows how to spell it out. What the language calls by itself (`next`, `constructor`, `Symbol.iterator`) and an index like `Array.prototype[0]` can't be replaced, and the `TypeError` says so. An existing `toString`, `valueOf`, `toJSON` or `then` can be replaced, and so can the `Symbol.iterator` of `Map`, `Set`, `Headers` and `URLSearchParams`. A `toJSON` can also be added to `Object.prototype`; a `then` can't.

## Run under the compiler's rules

```bash terminal icon="terminal"
bun run --aot ./app.ts
```

`bun run --aot` checks your program the way `bun compile` does, and exits with code `1` on anything that would stop the build. Then it runs the program from its source files with the JIT, with [built-in objects read-only](/compiler/compatibility#built-in-objects-are-read-only) as in an executable. `--watch` and `--inspect` work. The other [differences from `bun run`](/compiler/compatibility) don't show up, because the code that runs isn't compiled. To see those, run your tests with `bun test --aot`, or build the executable and run it.

## Find the guards that fail

```bash terminal icon="terminal"
bun check --aot --explain=guards ./app.ts   # guards that can fail
bun --aot-log-type-mismatches ./app.ts      # guards that do fail
```

A [guard](/compiler/types#when-a-value-doesnt-match-its-type) that fails doesn't change what your program does. It sends the function to its slow version, so look here when a hot function is slower than you expected.

The first command reads your source and lists each guard that the compiler couldn't remove, with the reason and a fix. The second compiles your program and runs it. When a value doesn't match its declared type, it writes a line to stderr with the location, the declared type and the kind of value that arrived. `bun test` and `bun compile` take the flag too. A build that logs is slower, so don't benchmark it.

## Profiles

```bash terminal icon="terminal"
BUN_OPTIONS="--cpu-prof" ./app    # a .cpuprofile for Chrome DevTools or VS Code
BUN_OPTIONS="--heap-prof" ./app   # a heap profile
```

Both show your functions, classes and files by their names. `perf`, `gdb` and Instruments show addresses where your compiled code runs. On Linux, build with `--aot-symbols` to see function names there too.

A heap snapshot (`Bun.generateHeapSnapshot()`, `v8.writeHeapSnapshot()`) lists what the top-level variables of each module and the variables that closures capture hold, under the variables' names, as it does under `bun run`. A captured variable is listed on the closure that holds it, or with its module's variables if its function runs only once. It shows the heap of the compiled program, which can hold less. The compiler removes a variable that nothing in your program can read, along with an object that only that variable held, and it creates some objects when they're first read instead of when the module loads. Those aren't in the heap, so they aren't in the snapshot. Build with [`--compile-inspector`](#the-inspector) to see every variable that `bun run` shows.

## The inspector

```bash terminal icon="terminal"
bun compile --compile-inspector ./app.ts
BUN_INSPECT="ws://127.0.0.1:6499/app" ./app
```

The console, heap snapshots and CPU profiles work. Breakpoints, stepping and `debugger` statements don't. The flag makes the executable larger and slower, so leave it out of production builds.
