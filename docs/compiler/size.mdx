title: "Smaller executables"
description: "Why an executable is as big as it is, and how to make it smaller with bun compile --trim"

<Warning>`--trim` and ahead-of-time compilation are experimental.</Warning>

An executable is a copy of the Bun runtime with your program attached. For a small program, almost all of the file is Bun, which is why ten lines of code make tens of megabytes. `--trim` removes the Bun and Node.js APIs that your program never uses.

```bash terminal icon="terminal"
bun compile --trim ./server.ts
```

The build prints the size of the executable and how much it removed. `bun compile` always leaves out the `bun` command line and the JIT compilers. `bun build --compile` keeps both, and `--trim` only removes the command line there. In `Bun.build`, the option is `compile: { trim: true }`.

A trimmed executable doesn't read `bunfig.toml` at startup unless you pass `--compile-autoload-bunfig`. Otherwise your program behaves the same, as long as it doesn't reach [a removed feature](#using-a-removed-feature).

## See what the compiler found

`--trim` only removes what the compiler can prove you don't use. `--explain=trim` lists what it keeps and why. With `bun check --aot`, it builds nothing.

```ts server.ts icon="/icons/typescript.svg"
Bun.serve({
  port: 3000,
  routes: { "/": () => new Response("hello") },
});
console.log("listening");
```

```bash terminal icon="terminal"
bun check --aot --explain=trim ./server.ts
```

```txt
aot: trim: the compiler can see every API this program uses
aot: trim: kept Bun.serve (serve): used (Bun.serve) at server.ts:1:1
aot: trim: removed bun:sqlite and node:sqlite (sqlite): unused
```

## What blocks `--trim`

If the report starts with `blocked by`, your program or a dependency could reach APIs that the compiler can't see, so `--trim` keeps more. The line says where. With the first three reasons, unused Bun and Node.js APIs are still removed. With the last three, `--trim` keeps every API.

| `blocked by`      | Your program                                              |
| ----------------- | --------------------------------------------------------- |
| `eval`            | Calls `eval` or `new Function` on a computed string       |
| `runtime-code`    | Uses `node:vm`, `bun:ffi`, a native addon or `Bun.plugin` |
| `dynamic-import`  | Imports a computed path, or starts a `Worker`             |
| `external-import` | Imports an `--external` package or a URL                  |
| `build-option`    | Is built with `--compile-inspector`                       |
| `no-aot`          | Is built without `--aot`                                  |

## Make it smaller

- `--disallow-code-generation-from-strings` removes the parser and the interpreter. `eval` and `new Function` then throw.
- `--trim-locales en,de` removes the `Intl` data for every other locale. Using another locale exits the process.
- `--no-compile-function-source` removes the source text of functions. `fn.toString()` then returns `[native code]`.

Without `--trim-locales`, Bun keeps the locales that your code passes as constants, as in `toLocaleString("de")`. One call with a computed locale, or with none, keeps them all. The flag has no effect on macOS, where Bun uses the system's ICU library.

### Turn off code from strings

A dependency that calls `new Function` is the most common reason `--trim` is blocked. With [`--disallow-code-generation-from-strings`](/runtime/code-generation-from-strings), those calls throw an `EvalError`, so they block nothing. A library that tries `new Function` in a `try` block falls back to plain code, and one that needs generated code throws at startup. `bun` takes the flag too, so you can find out which before you build.

## Using a removed feature

Bun removes code, not names. `typeof HTMLRewriter` and `typeof Bun.sql` give the same result as before. A call throws an `Error` with the code `ERR_FEATURE_REMOVED` and a message that says how to keep the feature.

Your own code only runs into this through a name that isn't known until run time. Members of `Bun`, `Intl`, `Temporal` and `WebAssembly` count as used where your code names them, as in `Bun.file(path)` or `value.toLocaleString()`. `Bun[name]()` doesn't count. `bun test` runs your source files, so it can't find these errors. Test the executable itself.

In `Bun.build`, `trim: { allow: ["color"] }` keeps a feature that only a string passed to `eval`, a computed name or a native addon uses. `trim: { remove: ["sqlite"] }` takes a feature out even if your code uses it. Neither has a command-line flag.

### Feature names

`allow` and `remove` take these names. Your editor completes them from the type `Bun.Build.TrimFeature`, and `--explain=trim` prints them in parentheses. Each size is roughly what the feature adds to a trimmed executable.
