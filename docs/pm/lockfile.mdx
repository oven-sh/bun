`bun install` creates a lockfile called `bun.lock`.

#### Should it be committed to git?

Yes

#### Generate a lockfile without installing?

To generate a lockfile without installing to `node_modules`, use the `--lockfile-only` flag. Bun always saves the lockfile to disk, even if it is already up to date with your project's `package.json`(s). The exceptions are `--frozen-lockfile` (or `--production`), `--dry-run`, and `--no-save`, which save nothing.

```bash terminal icon="terminal"
bun install --lockfile-only
```

`bun add`, `bun remove`, and `bun update` also accept `--lockfile-only`.

<Note>
  `--lockfile-only` still populates the global install cache with registry metadata and git/tarball dependencies.
</Note>

#### Can I opt out?

To install without creating a lockfile:

```bash terminal icon="terminal"
bun install --no-save
```

To write a Yarn lockfile _in addition_ to `bun.lock`:

<CodeGroup>

```bash terminal icon="terminal"
bun install --yarn
```

```toml bunfig.toml icon="settings"
[install.lockfile]
# whether to save a non-Bun lockfile alongside bun.lock
# only "yarn" is supported
print = "yarn"
```

</CodeGroup>

#### Text-based lockfile

Bun v1.2 changed the default lockfile format to the text-based `bun.lock`. To migrate an existing binary `bun.lockb`, run `bun install --save-text-lockfile --frozen-lockfile --lockfile-only` and delete `bun.lockb`.

For more on the format, see [the blog post](https://bun.com/blog/bun-lock-text-lockfile).

#### Lockfile version

The `lockfileVersion` field at the top of `bun.lock` is the version of the format.

| `lockfileVersion` | Change                                                                                               | Minimum Bun version |
| ----------------- | ---------------------------------------------------------------------------------------------------- | ------------------- |
| `0`               | The first version of the text lockfile.                                                              | v1.1.39             |
| `1`               | The entry of a workspace package in `packages` no longer lists its dependencies.                     | v1.2.0              |
| `2`               | The same content as `1`. Bun applies stricter checks when it reads the lockfile.                     | v1.4.0              |
| `3`               | [`overrides`](/pm/overrides) has a nested or version-scoped rule, so a value there can be an object. | v1.4.0              |

At `lockfileVersion` 2 and later, Bun rejects a lockfile that has:

- an integrity hash that Bun does not support
- an npm package with no integrity hash, from a tarball URL outside both the configured registry and the default registry
- a `.bun-tag` on a `git` dependency that is not a safe path component

At `lockfileVersion` 0 and 1, Bun still reads such a lockfile. Two checks apply at every version. Bun rejects a `.bun-tag` longer than 256 bytes, and a `.bun-tag` on a `github` dependency that is not a safe path component.

Bun picks the version when it saves the lockfile:

- A new lockfile gets `2`.
- An existing lockfile keeps its version. The exception is `0`, which becomes `1`.
- A lockfile gets `3` while `overrides` has a nested or version-scoped rule. When you remove the last such rule, a lockfile at `3` goes back to `2`.

Before Bun writes `3`, or a `2` that the lockfile did not have before, it checks the packages. Bun writes `1` instead when it finds one of these:

- an npm package with no supported integrity hash, from a tarball URL outside the default registry
- a `.bun-tag` on a `git` dependency that is not a safe path component

This check ignores the registries in your configuration, so the result is the same on every machine. Such a lockfile stays at `1`, also with object values in `overrides`. Bun v1.4.0 and later reads object values at every `lockfileVersion`.

If the `lockfileVersion` is not a whole number from 0 to 4294967295, Bun stops with `Invalid lockfile version`. If the value is in that range and your version of Bun does not support it, Bun stops with `Unsupported lockfile version`. Run `bun upgrade` for the second error only.

#### Automatic lockfile migration

When you run `bun install` in a project without a `bun.lock`, Bun automatically migrates existing lockfiles:

- `yarn.lock` (Yarn v1, and Yarn 2+ "Berry")
- `npm-shrinkwrap.json` and `package-lock.json` (npm, `lockfileVersion` 2, 3 or 4)
- `pnpm-lock.yaml` (pnpm)

When a project has both npm lockfiles, Bun reads `npm-shrinkwrap.json` and ignores `package-lock.json`, as npm does.

When a project has lockfiles of several package managers, Bun migrates the first one it can, in this order: `npm-shrinkwrap.json`, `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`. It prints a warning for each one it had to skip.

Bun does not migrate an npm lockfile from npm 6 or older (`lockfileVersion` 1); it prints a warning and, when there is no other lockfile, resolves from `package.json` instead.

Bun preserves the original lockfile. You can remove it manually after verification.

Bun writes the migrated `bun.lock` only when the command saves a lockfile. `bun install --frozen-lockfile` (and `bun ci`), `--dry-run`, `--no-save`, and read-only commands such as `bun outdated` use the migrated lockfile in memory and write nothing. Under `--frozen-lockfile`, Bun prints a `note:` asking you to run `bun install` and commit the result. To migrate without installing, run `bun pm migrate` or `bun install --lockfile-only`.
