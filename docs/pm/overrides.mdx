---
title: "Overrides and resolutions"
description: "Control metadependency versions with npm overrides and Yarn resolutions"
---

Bun supports npm's `"overrides"` and Yarn's `"resolutions"` in `package.json`. Both specify a version range for _metadependencies_, the dependencies of your dependencies.

{/* prettier-ignore */}
```json package.json icon="file-json"
{
  "name": "my-app",
  "dependencies": {
    "foo": "^2.0.0"
  },
  "overrides": { // [!code ++]
    "bar": "~4.4.0" // [!code ++]
  } // [!code ++]
}
```

By default, Bun installs the latest version of all dependencies and metadependencies, according to the ranges specified in each package's `package.json`. Say your project has one dependency, `foo`, which in turn depends on `bar`. That makes `bar` a _metadependency_ of your project.

```json package.json icon="file-json"
{
  "name": "my-app",
  "dependencies": {
    "foo": "^2.0.0"
  }
}
```

When you run `bun install`, Bun installs the latest version of each package.

```txt tree layout of node_modules icon="list-tree"
node_modules
├── foo@2.3.4
└── bar@4.5.6
```

If a security vulnerability is introduced in `bar@4.5.6`, you may want to pin `bar` to an older version that doesn't have it. That's what `"overrides"` and `"resolutions"` are for.

---

## `"overrides"`

Add `bar` to the `"overrides"` field in `package.json`. Bun defers to the specified version range when determining which version of `bar` to install, whether it's a dependency or a metadependency.

{/* prettier-ignore */}
```json package.json icon="file-json"
{
  "name": "my-app",
  "dependencies": {
    "foo": "^2.0.0"
  },
  "overrides": { // [!code ++]
    "bar": "~4.4.0" // [!code ++]
  } // [!code ++]
}
```

Bun only reads overrides from the root `package.json`, not from workspace packages. Overrides apply to `peerDependencies` as well.

Every install also checks the lockfile against the overrides whose value is a version, a range, a tarball, or a git or GitHub repository. If the lockfile has a package that such an override does not allow (after a merge, a migration from another package manager, or an install by a version of Bun that did not apply the override), `bun install` resolves that package again, and `bun install --frozen-lockfile` fails and names it. The check leaves these entries as they are:

- a bundled dependency and an optional peer dependency
- a peer or optional dependency that shares its version with a dependency the override does not apply to
- a name that one `package.json` lists in two groups, when the override applies to only one of the two ranges
- a tarball or a repository that a dependency under a version override shares with a dependency the override does not apply to
- a repository that the override also names, whatever commit the lockfile has: the branch or tag of an override is not compared
- an entry that can be the override's package written in another way: a tarball URL next to an override that is a repository or a version, a repository next to an override that is a tarball URL, and a repository on a host other than GitHub, GitLab, Bitbucket and SourceHut whose URL is not the override's

## `"resolutions"`

`"resolutions"` is Yarn's alternative to `"overrides"`, with similar syntax. Bun supports it to help projects migrate from Yarn. When a `package.json` has both fields, Bun uses only `"overrides"` and does not read `"resolutions"`.

{/* prettier-ignore */}
```json package.json icon="file-json"
{
  "name": "my-app",
  "dependencies": {
    "foo": "^2.0.0"
  },
  "resolutions": { // [!code ++]
    "bar": "~4.4.0" // [!code ++]
  } // [!code ++]
}
```

## Values

A value can be any dependency specifier, not only a version range. `npm:` swaps a package for a fork, and `catalog:` (or `catalog:<name>`) keeps the overridden version in sync with a [workspace catalog](/pm/catalogs):

```json package.json icon="file-json"
{
  "name": "my-app",
  "workspaces": {
    "packages": ["packages/*"],
    "catalog": {
      "foo": "^2.0.0"
    }
  },
  "overrides": {
    "quux": "npm:@myorg/quux@^1.0.0",
    "foo": "catalog:"
  }
}
```

Bun warns about a `catalog:` rule whose package is not in the catalog. A dependency that the rule applies to then fails to resolve.

A value of `"$name"` reuses the range you declared for `name` in your own dependencies, so `"bar": "$foo"` pins `bar` to whatever range you declared for `foo`.

A rule replaces a dependency by the name it is declared under, which is the key in `"dependencies"`. That holds for every kind of specifier: a version range, a git repository, a `github:` shorthand, a tarball. For the dependency that a rule replaces, the `"name"` in the `package.json` of a package does not count:

- `"bar": "github:me/bar-fork"` replaces every dependency declared as `bar`, also when the fork's `package.json` names it `@me/bar`. Bun installs the fork as `node_modules/bar`, and does not fetch the package it replaces.
- A dependency declared as `"my-bar": "github:them/bar"` is not replaced by a rule for `bar`. Write the rule for `my-bar`. Bun prints a warning when it fetches such a dependency and a rule for the name in its `package.json` would have replaced it.

`bun update` reads the tarball or repository that a rule names again, as it does for a dependency.

## Nested overrides

You can scope a rule to one parent package, so it only applies to that package's direct dependency. Bun accepts the npm object form, the pnpm `>` form, and a parent with a version range:

```json package.json icon="file-json"
{
  "name": "my-app",
  "overrides": {
    "micromatch": {
      ".": "^4.0.5",
      "picomatch": "^2.3.2"
    },
    "micromatch>picomatch": "^2.3.2",
    "micromatch@^4>picomatch": "^2.3.2"
  }
}
```

`"."` inside an object overrides `micromatch` itself, like a top-level `"micromatch"` rule.

The parent of a nested rule is the package that is installed. Bun matches it by the `"name"` in that package's own `package.json` and by its installed version, as pnpm does. If a rule replaces `micromatch` with a fork whose `package.json` names it `@me/micromatch`, write the rules for the fork's dependencies under `@me/micromatch`:

```json package.json icon="file-json"
{
  "name": "my-app",
  "overrides": {
    "micromatch": "github:me/micromatch-fork",
    "@me/micromatch": {
      "picomatch": "^2.3.2"
    }
  }
}
```

`"resolutions"` accepts Yarn's path form. Bun accepts `**` for compatibility, but either way the rule only affects the parent's direct dependency:

```json package.json icon="file-json"
{
  "name": "my-app",
  "resolutions": {
    "micromatch/picomatch": "^2.3.2",
    "**/micromatch/**/picomatch": "^2.3.2"
  }
}
```

When several rules match, the most specific wins: parent-with-version > parent > top-level.

## Version-scoped overrides

The key can carry a version selector so the rule only applies to dependents whose declared range overlaps it. This is the form `pnpm audit --fix` writes:

```json package.json icon="file-json"
{
  "name": "my-app",
  "overrides": {
    "semver@<7.5.2": "7.5.2",
    "webpack>terser@4": "4.8.1",
    "terser@4": {
      ".": "4.8.1"
    }
  }
}
```

Bun compares the selector with the range each dependent _declares_, not the resolved version. `"semver@<7.5.2"` applies to a dependent that declares `^7.3.0` (which could still pick `7.3.x`) but not to one that declares `^7.5.2`. Dependents using a dist-tag, `workspace:`, git, or URL specifier never match a selector.

`bun add foo` and `bun update --latest` write a range to `package.json`, and the selector is compared with that range. With `"foo@>=2.0.0": "1.2.0"` and `2.0.0` as the latest release, `bun add foo` writes `"foo": "^2.0.0"` and installs `foo@1.2.0`.

Two more selectors match a dependency by how it is declared, like Yarn's `"resolutions"`:

- `"foo@catalog:"` (or `"foo@catalog:name"`) applies to dependents that declare `foo` with that [catalog](/pm/catalogs).
- `"my-foo@npm:foo@^1"` applies to an `npm:` alias named `my-foo` that points at `foo` with an overlapping range. No other rule overrides an alias.

## Limitations

- Bun supports only one parent level. It ignores `a>b>c`, `a/b/c`, and deeper object nesting with a warning.
- Bun does not support pnpm's `"pkg@"` (empty selector) and `"-"` (remove dependency) forms, and skips them with a warning.
- Bun writes a lockfile containing nested or version-scoped rules as `lockfileVersion` 3, which older versions of Bun cannot read.
