title: "Type checking"
description: "Type check a TypeScript project with bun check"
---

`bun check` type checks a TypeScript project. It reads your `tsconfig.json`, reports errors with the codes and messages of `tsc`, and uses every CPU core.

```bash terminal icon="terminal"
bun check
```

```txt
src/index.ts(3,25): error TS2322: Type 'string' is not assignable to type 'number'.
Found 1 error in 1 file, checked 2 files [14ms]
```

`bun check` exits with code `1` when it finds an error and `0` when it finds none. It never writes a file.

```txt
✓ No type errors in 2 files [14ms]
```

## Install TypeScript's library files

The `typescript` package ships the `lib.*.d.ts` files that declare `Array`, `Promise`, and the rest of the language's built-in types. `bun check` reads those files from your project, so your editor and `bun check` see the same declarations.

```bash terminal icon="terminal"
bun add -d typescript @types/bun
```

A project made with [`bun init`](/runtime/templating/init) has both, and a `typecheck` script that runs `bun check`.

Bun looks for `typescript` in these places, in order:

1. `node_modules` in the project directory
2. `node_modules` in each parent directory
3. Packages installed with `bun add -g`

### Bun's own types

[`@types/bun`](/typescript) declares what Bun provides: `console`, `fetch`, `Bun`, and modules such as `bun:test`.

Since TypeScript 6.0, nothing in `node_modules/@types` is included unless `types` asks for it. `bun init` writes that line for you. In an older project, add it yourself:

```json tsconfig.json icon="file-json"
{
  "compilerOptions": {
    "types": ["bun"]
  }
}
```

Your editor reads the same line. Without a `tsconfig.json`, `bun check` includes `@types/bun` if it is installed.

## Choose what to check

Without arguments, `bun check` finds the nearest `tsconfig.json`, starting from the current directory and going up. It checks the files that `files`, `include`, and `exclude` select.

Use `-p` to name a `tsconfig.json` or the directory that holds one.

```bash terminal icon="terminal"
bun check -p packages/server
```

Pass files or directories to check only those and what they import. The compiler options still come from the nearest `tsconfig.json`.

```bash terminal icon="terminal"
bun check src/index.ts
```

Without a `tsconfig.json`, `bun check` uses the compiler options that [`bun init`](/runtime/templating/init) writes, apart from the stricter rules that are a matter of taste (`noUncheckedIndexedAccess`, `noImplicitOverride`, `noFallthroughCasesInSwitch`):

```json
{
  "lib": ["ESNext"],
  "target": "ESNext",
  "module": "Preserve",
  "moduleDetection": "force",
  "jsx": "react-jsx",
  "allowJs": true,
  "moduleResolution": "bundler",
  "allowImportingTsExtensions": true,
  "verbatimModuleSyntax": true,
  "noEmit": true,
  "strict": true,
  "skipLibCheck": true
}
```

### Project references

`bun check` follows `references` in `tsconfig.json`, like `tsc -b`. Each referenced project is checked with its own options, and each file is checked once.

Bun reads a referenced project from its source files. You do not have to build the project first, and Bun does not write `.d.ts` or `.tsbuildinfo` files.

## Check before you run, build, or test

The `--check` flag type checks the entry point and everything it imports. If there is a type error, Bun prints it, exits with code `1`, and does nothing else.

```bash terminal icon="terminal"
bun --check src/index.ts          # run
bun build --check src/index.ts --outdir out
bun test --check
```

```txt
src/index.ts(3,25): error TS2322: Type 'string' is not assignable to type 'number'.
Found 1 error in 1 file, checked 2 files [14ms]
```

With a `package.json` script there is no entry point to start from, so Bun checks the whole project, like `bun check`, before the script runs.

```bash terminal icon="terminal"
bun run --check dev
```

A JavaScript entry point is read for what it imports, whether or not `allowJs` is on. Errors in the JavaScript file itself are only reported with `checkJs`.

## Output

In a terminal, `bun check` shows the source around each error and the declarations the error refers to.

```txt
1 | import { greet } from "./user";
2 |
3 | const message = greet({ id: "1", name: "Ada" });
                            ^
error: TS2322: Type 'string' is not assignable to type 'number'.
    at src/index.ts:3:25

2 |   id: number;
      ^
note: The expected type comes from property 'id' which is declared here on type 'User'
   at src/user.ts:2:3

Found 1 error in 1 file, checked 2 files [14ms]
```

When the output is piped, `bun check` prints one line per error in the format of `tsc --pretty false`. Problem matchers and scripts written for `tsc` keep working. Use `--pretty` or `--no-pretty` to choose a format yourself.

Errors go to stdout. The summary line goes to stderr.

### Many errors

Above 50 errors, the terminal format shows each distinct error once. Under it, `bun check` prints how often the error occurs and in which files. The most frequent error comes first.

```txt
1 | export const v0: number = "0";
                 ^
error: TS2322: Type 'string' is not assignable to type 'number'.
    at m1.ts:1:14
    60 times in 2 files
      30  m1.ts:1
      30  m2.ts:1
```

Use `--all` to show every error. The one-line format always shows every error.

### GitHub Actions

When `GITHUB_ACTIONS` is set, `bun check` also prints a workflow command for each error. GitHub shows those errors as annotations on the pull request diff.

```txt
::error file=src/index.ts,line=3,col=25,endLine=3,endColumn=27,title=TS2322::Type 'string' is not assignable to type 'number'.
```

### AI agents

When `AGENT=1`, `CLAUDECODE=1`, or `REPL_ID=1` is set, `bun check` prints each error as a tagged block with the source lines and no colors.

```txt
<error file="src/index.ts" line="3" column="25" code="TS2322">
Type 'string' is not assignable to type 'number'.
<source>
1 | import { greet } from "./user";
2 |
3 | const message = greet({ id: "1", name: "Ada" });
                            ^^
4 | export default message;
</source>
<related file="src/user.ts" line="2" column="3">The expected type comes from property 'id' which is declared here on type 'User'</related>
</error>
```

## Compiler options as flags

Any compiler option works as a flag, as it does for `tsc`. A flag overrides `tsconfig.json`, including in referenced projects. Use flags to try a stricter option before you commit to it.

```bash terminal icon="terminal"
bun check --noUncheckedIndexedAccess
bun check --strict false
bun check --target es2022
```

Option names are not case-sensitive, and `--target=es2022` is the same as `--target es2022`.

## Differences from `tsc`

`bun check` follows the type checker of TypeScript 7, whichever version of `typescript` your project installs. The installed version only provides the library files.

If `bun check` and `tsc` 7 disagree about an error, that is a bug in Bun. [Open an issue on GitHub](https://github.com/oven-sh/bun/issues) with the code that shows the difference.

These differences are intended:

- The errors do not depend on the order of the files. `tsc` collects the errors of a file right after it checks that file, so it loses an error that a later file raises in an earlier one.
- `bun check` only checks. It does not write JavaScript, `.d.ts`, source map, or `.tsbuildinfo` files, whatever `noEmit`, `declaration`, or `incremental` say. Use [`bun build`](/bundler) to produce JavaScript, and `tsc` to produce declaration files.
- There is no `--watch` mode.
- `bun check` does not load language service plugins from the `plugins` compiler option.
- Of the options that only print information, `listFiles` and `listFilesOnly` work. The others, such as `explainFiles` and `traceResolution`, have no effect.

## CLI usage

```bash
bun check [flags] [...files or directories]
```

| Flag                     | Description                                                         |
| ------------------------ | ------------------------------------------------------------------- |
| `-p`, `--project <path>` | Path to a `tsconfig.json` or its directory                          |
| `--pretty`               | Show source code around each error. Default in a terminal           |
| `--no-pretty`            | One line per error, like `tsc --pretty false`. Default when piped   |
| `--all`                  | Show every error. Without it, identical errors are grouped above 50 |
| `--threads <n>`          | Number of threads. Default: one per CPU core                        |
| `--timing`               | Print how long loading and checking took                            |
| `--cwd <path>`           | Set the working directory                                           |
| `--strict`, `--target`…  | Any compiler option, as for `tsc`. Overrides `tsconfig.json`        |
| `-h`, `--help`           | Print the help menu                                                 |
