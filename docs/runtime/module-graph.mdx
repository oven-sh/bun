---
title: ModuleGraph
description: Run many instances of one app in a single process with Bun.ModuleGraph. Each instance gets fresh module state and its own timers and I/O; compiled code is shared.
---

<Warning>`Bun.ModuleGraph` is experimental.</Warning>

A `Bun.ModuleGraph` loads modules into the current global a second (third, …) time. Each graph has its own module instances, its own `require.cache`, and its own values for the names you pass as `globals`. Parsed code and bytecode are shared between graphs; ES modules share JIT-compiled code too.

```ts host.ts icon="/icons/typescript.svg"
const graph = new Bun.ModuleGraph({
  isolateIO: true,
  globals: { process: tenantProcess }, // free identifiers in the graph's modules
  onError(error, kind) {
    console.error("tenant failed", kind, error);
  },
});

const app = await graph.import("./app.ts");
await graph.run(() => app.handle(request));

graph.dispose();
```

## `isolateIO`

With `isolateIO: true` the graph gets a context of its own for timers and I/O. Everything its code opens belongs to the graph: timers, `Bun.serve` / `Bun.listen` servers, sockets, `fetch()` requests, WebSockets, watchers, child processes (including `Bun.$`), workers, database connections.

`graph.dispose()` closes all of it, and from then on the graph hears nothing, like a worker that was terminated: no `close` handler, `onExit` or `'error'` event is called, a `fetch()` or a connection that was in flight does not reject, and a promise waiting on anything (a request, a child's exit, a file read, compression, `crypto.subtle`, a DNS lookup, `Bun.build`, a stream) never settles. That includes what the host still holds of the graph's: a `Subprocess` the graph spawned is killed, and its `exited` promise stays pending. `FinalizationRegistry` cleanup callbacks are still called. What the graph had already queued as microtasks or `process.nextTick` callbacks still runs, once; whatever that code starts does not start (a connection is not dialed, a UDP socket is not bound, a server does not announce `'listening'`, `child_process.spawn()` spawns nothing) and its promise stays pending rather than rejecting, so code that retries on failure stops there. Closing is not preventing: a process `Bun.spawn` starts is started and then killed, so a very short command can finish first, and synchronous calls (`Bun.spawnSync`, `fs.writeFileSync`) run to completion. `dispose()` releases what a graph holds; it is not a sandbox. Descriptors the graph's `node:fs` streams had opened are closed. A graph made by the graph's own code is disposed with it. (Only a graph with `isolateIO` owns anything: what runs inside a graph without it, another graph it creates included, is the host's.)

The context follows the code asynchronously, like `AsyncLocalStorage`: through `await`, timers, socket handlers and event listeners.

Native addons are shared, but their asynchronous work is the graph's too: a Node-API async work item or thread-safe function completes in the context of the graph whose code created it. After `dispose()` the addon's completion callback still runs, so it can free what it allocated, but it cannot call into JavaScript (`napi_call_function` and the like return `napi_cannot_run_js`, as they do in a worker that is terminating), and a promise it settles for the disposed graph stays pending.

## Disposing

`graph.dispose()` drops the graph's module registry and `require.cache`. Code of the graph that is still referenced keeps working, and its errors still go to `onError`. From then on `graph.import()` and the graph's `require()` fail with `ERR_INVALID_STATE`, as does `import()` from a function of the graph that the host calls; `import()` by the disposed graph's own leftover code stays pending. Modules of the graph that had not run yet never will. An import that was still waiting for a file rejects. One whose module is suspended in a top-level `await` is left alone: it finishes if what the module awaits does.

## Calling into a graph

Code the host calls directly runs in the host's context, even when the function was defined by a graph. Use `run()` to enter the graph's:

```ts
app.start(); // what this opens is the host's
graph.run(() => app.start()); // what this opens is the graph's
```

`Bun.ModuleGraph.current` is the graph whose context the calling code is running in, or `undefined` in the host's. Host functions shared by several graphs (passed in `globals`) can use it to tell their callers apart.

## Errors

Uncaught exceptions and unhandled rejections raised by a graph's module code go to that graph's `onError` instead of the process-wide handlers.

An error belongs to the graph whose code threw it, and stays that graph's through the promises that carry it on. If nobody handles the promise `graph.import()` returned and a module of the graph threw while it was being evaluated (at its top level, after an `await`, or in a dependency), that goes to `onError` too. When none of the graph's code is on the stack (the runtime rejected a promise itself, or the graph's function called what threw as a tail call, as in `() => JSON.parse(text)`), the error goes to the graph whose context is current: a graph with `isolateIO` gets it, and one without has no context to go by. A rejection that reaches an unhandled promise through a `.then()` with no rejection handler, or through an `async` function that returned the promise, currently arrives without a context as well and takes the process-wide path; `await` it, or add a handler, inside the graph.

What the host caused takes the normal process-wide path: a specifier that does not resolve, an `import()` into a disposed graph, and anything `onError` itself throws or rejects while it runs.

## What is shared

The global object, `globalThis` properties, `process` (unless you replace it through `globals`), plugins and native addons are shared by every graph and the host. A graph's listeners on something the host owns (the shared `process`: signals, `process.stdin`, `'exit'`; an emitter the host passed in) are that object's, so they outlive `dispose()`. `ModuleGraph` separates instances of an app you trust from each other; it is not a security sandbox.
