---
title: ModuleGraph
description: Run many instances of one app in a single process with Bun.ModuleGraph. Each instance gets fresh module state and its own timers and I/O; compiled code is shared.
---

<Warning>`Bun.ModuleGraph` is experimental.</Warning>

A `Bun.ModuleGraph` loads modules into the current global a second (third, …) time. Each graph has its own module instances, its own `require.cache`, and its own values for the names you pass as `globals`. Parsed code and bytecode are shared between graphs; ES modules share JIT-compiled code too.

```ts host.ts icon="/icons/typescript.svg"
const graph = new Bun.ModuleGraph({
  isolateIO: true,
  globals: { process: tenantProcess }, // free identifiers in the graph's modules
  onError(error, kind) {
    console.error("tenant failed", kind, error);
  },
});

const app = await graph.import("./app.ts");
await graph.run(() => app.handle(request));

graph.dispose();
```

## `isolateIO`

With `isolateIO: true` the graph gets a context of its own for timers and I/O. Everything its code opens belongs to the graph: timers, `Bun.serve` / `Bun.listen` servers, sockets, `fetch()` requests, WebSockets, watchers, child processes (including `Bun.$`), workers, database connections.

`graph.dispose()` closes all of it. Close handlers (`close`, `onExit`) are still called; other callbacks are not, and promises waiting on them never settle. What the graph had already queued as microtasks or `process.nextTick` callbacks still runs. Whatever a disposed graph opens afterwards is closed at once.

The context follows the code asynchronously, like `AsyncLocalStorage`: through `await`, timers, socket handlers and event listeners.

## Calling into a graph

Code the host calls directly runs in the host's context, even when the function was defined by a graph. Use `run()` to enter the graph's:

```ts
app.start(); // what this opens is the host's
graph.run(() => app.start()); // what this opens is the graph's
```

`Bun.ModuleGraph.current` is the graph whose context the calling code is running in, or `undefined` in the host's. Host functions shared by several graphs (passed in `globals`) can use it to tell their callers apart.

## Errors

Uncaught exceptions and unhandled rejections raised by a graph's module code go to that graph's `onError` instead of the process-wide handlers.

## What is shared

The global object, `globalThis` properties, `process` (unless you replace it through `globals`), plugins and native addons are shared by every graph and the host. `ModuleGraph` separates instances of an app you trust from each other; it is not a security sandbox.
