---
title: ModuleGraph
description: Run many instances of one app in a single process with Bun.ModuleGraph. Each instance gets fresh module state and its own timers and I/O; compiled code is shared.
---

<Warning>`Bun.ModuleGraph` is experimental.</Warning>

A `Bun.ModuleGraph` loads modules into the current global another time. Each graph has its own module instances, its own `require.cache`, and its own values for the names you pass as `globals`. Parsed code and bytecode are shared between graphs; ES modules share JIT-compiled code too. The first module a graph `import()`s is that graph's main module: `import.meta.main` and `require.main === module` are true in it, and in no other module of the graph.

```ts host.ts icon="/icons/typescript.svg"
// A `process` of the tenant's own: its module code sees this one.
const tenantProcess = Object.create(process, { env: { value: { TENANT: "a" }, enumerable: true } });

const graph = new Bun.ModuleGraph({
  globals: { process: tenantProcess }, // free identifiers in the graph's modules
  uncaughtException(error) {
    console.error("tenant failed", error);
    graph.dispose();
  },
  unhandledRejection(reason) {
    console.error("tenant dropped a rejection", reason);
  },
});

const app = await graph.import("./app.ts");
await app.handle(new Request("http://localhost/"));

graph.dispose();
```

## What a graph opens is the graph's

A graph has a context of its own for timers and I/O. Everything its code opens belongs to the graph:

- timers
- `Bun.serve` and `Bun.listen` servers, sockets, `fetch()` requests, WebSockets
- watchers
- child processes, including `Bun.$`
- workers
- database connections
- files opened through `Bun.file().writer()`, `bun:sqlite` and `node:sqlite`
- graphs its code makes

The context follows the code asynchronously, like `AsyncLocalStorage`: through `await`, timers, socket handlers and event listeners.

`graph.dispose()` closes all of it. From then on the graph hears nothing, like a worker that was terminated:

- No `close` handler, `onExit` or `'error'` event is called.
- A `fetch()` or a connection that was in flight does not reject.
- A promise waiting on a request, a child's exit, a file read, compression, `crypto.subtle`, a DNS lookup, `Bun.build` or a stream never settles.
- `FinalizationRegistry` cleanup callbacks are still called.

Microtasks and `process.nextTick` callbacks the graph had already queued still run, once. Whatever that code starts does not start: a connection is not dialed, a UDP socket is not bound, nobody can connect to a server it listens with. Its promise stays pending rather than rejecting, so code that retries on failure stops there.

The host's references to the graph's objects are dead too. Do not use a graph's socket, worker, child process, stream or `Response` after `dispose()`. An operation on one may fail or may never complete: `await worker.terminate()`, `server.close(callback)` or waiting for a child's `'exit'` can wait for ever. From a database the graph had open, the host gets "Database has closed". What was buffered and not yet written is dropped.

`dispose()` releases what a graph holds. It is not a sandbox:

- A process that leftover code starts with `Bun.spawn` or `child_process.spawn()` is started and then killed, so a very short command can finish first.
- Synchronous calls such as `Bun.spawnSync` and `fs.writeFileSync` run to completion.
- A `node:http` or `node:https` request goes through an `Agent`, and what an `Agent` opens belongs to the script that made the `Agent`. A request with no `agent` goes through `http.globalAgent`, which is shared (see [What is shared](#what-is-shared)). Such a request is not the graph's: leftover code's still goes out, one in flight is not cut, and its `'response'` and `'error'` callbacks are still called after `dispose()`. Code whose requests should stop with its graph passes an `Agent` it made itself.
- `node:quic` is not covered yet: an endpoint a graph's code opens stays open after `dispose()`, and its handlers keep running. Code that opens one closes it before its graph is disposed.
- A file descriptor that script holds is the script's to manage: one from `fs.openSync()`, and the one inside a `FileHandle` or a `node:fs` stream. `dispose()` does not close it, as terminating a worker does not. Code that opens one closes it before its graph is disposed. A `FileHandle` that is garbage-collected unclosed is closed then, and reported as it is in any program: Node's `ERR_INVALID_STATE` ("A FileHandle object was closed during garbage collection") as an uncaught exception of the process.

Native addons are shared, but their asynchronous work is the graph's too. A Node-API async work item or thread-safe function completes in the context of the graph whose code created it. After `dispose()` the addon's completion callback still runs, so it can free what it allocated. It cannot call into JavaScript: `napi_call_function` and the like return `napi_cannot_run_js`, as they do in a worker that is terminating. A promise it settles for the disposed graph stays pending. A promise it settles for the host or for another graph is settled.

A thread-safe function keeps the process running only for as long as the graph that created it lives, whichever script asked it to (`napi_ref_threadsafe_function`). A ref taken after that graph was disposed holds until it is released. Its calls always run in the context of the graph that created it. If an addon keeps one thread-safe function for everybody and calls your JavaScript callbacks from it, load the addon in the host first, so that the function is the host's.

## Disposing

A disposed graph is inert. Its code is still JavaScript, so a function of the graph that something still references runs when it is called, and the microtasks and `process.nextTick` callbacks it queues run. Nothing it starts that needs the event loop ever happens: a timer never fires, a request is never sent, a server never listens, an `import()` stays pending, and the promise for any of it never settles. No error says so.

That is one rule for every case. It does not matter when the work was started, before `dispose()` or after it. It does not matter who calls the function: the host, another graph, or an emitter of the host's that the graph left a listener on. A loop that only awaits promises keeps running until it ends, because nothing in it needs the event loop.

Using a graph's code after `dispose()` is not an intended use. `dispose()` is for a graph the host is done with, and nothing reports a call into a disposed graph. A host that may still hold a graph's functions when it disposes the graph, such as a handler in a routing table or a request in flight, removes them first or races what they return against a signal of its own, as shown [below](#calling-into-a-graph).

A graph that a graph's code made is one of the things that graph opened, so it is disposed with it: it is inert from then on too, and its `import()` fails, although nobody called its own `dispose()`. The rule is about the code that starts the work, not about what the work is for: `otherGraph.import()` called by a disposed graph's code never settles, even when `otherGraph` is alive, because a disposed graph's code started it.

`graph.dispose()` also drops the graph's module registry and `require.cache`. An error in what still runs in the graph's context, such as a tick it had queued, still goes to the graph's error handlers. From then on:

- `graph.import()` and the graph's `require()` fail with `ERR_INVALID_STATE`. They are the graph's handle, and using a handle that was disposed is an error.
- Modules of the graph that had not run yet never will.

`dispose()` settles no promise. An `import()` that had not finished may reject or may never settle: what its modules were waiting for, such as a timer or a request, went with the graph. A host that may dispose a graph while importing into it should race the import the same way as a call.

## Calling into a graph

A graph's code runs in the graph's context, whoever calls it. Calling a function the graph exported is enough: a method, a getter, a constructor, a callback handed to `Array.prototype.map` or a listener on an emitter of the host's are the same. A function of one graph that another graph's code calls runs in its own graph's context, and the caller's is back when it returns.

```ts
app.start(); // what this opens is the graph's
```

The host's own code runs in the context it is called in, so it runs in the graph's context when the graph's code calls it. To have the graph own something the host's code opens, hand that code to a function of the graph's:

```ts
// in the graph: export const call = (fn, ...args) => fn(...args);
app.call(() => Bun.serve({ port: 0, fetch: app.fetch })); // the server is the graph's and stops with it
```

Code made with `new Function()` or indirect `eval` is global code: it belongs to no graph, whichever code made it, and runs in its caller's context. So does a CommonJS module compiled with a replaced `Module.wrapper` whose wrapper function is made inside another function.

A promise that a graph's asynchronous function returns is the graph's: if the graph is disposed before it settles, it never does. When the host awaits one and may dispose the graph meanwhile, race it against a promise of its own:

```ts
const disposed = Promise.withResolvers<never>();
const response = await Promise.race([app.handle(request), disposed.promise]);
// elsewhere: graph.dispose(); disposed.reject(new Error("tenant was disposed"));
```

`Bun.ModuleGraph.current` is the graph whose context the calling code is running in, or `undefined` in the host's. Host functions that several graphs share through `globals` can use it to tell their callers apart.

A function run through an `AsyncResource` (`resource.runInAsyncScope(fn)`, `AsyncResource.bind(fn)`) or an `AsyncLocalStorage.snapshot()` runs in the graph context the resource or snapshot was made in, whoever calls it, as it runs in the `AsyncLocalStorage` stores of that moment.

So a host function a graph calls, such as one passed in `globals`, runs in that graph's context. The asynchronous work it starts is the graph's and is dropped with it at `dispose()`. For work that must finish whatever happens to the caller, such as an audit log or billing, leave the graph's context with a snapshot taken in the host:

```ts
import { AsyncLocalStorage } from "node:async_hooks";

const asHost = AsyncLocalStorage.snapshot(); // taken by the host, outside any graph
const graph = new Bun.ModuleGraph({
  globals: { record: (entry: string) => asHost(() => appendToAuditLog(entry)) },
});
```

## Errors

A graph has two error handlers, named after the process events they stand in for:

```ts
new Bun.ModuleGraph({
  uncaughtException(error, origin) {}, // origin: "uncaughtException" | "unhandledRejection"
  unhandledRejection(reason, promise) {},
});
```

With a handler, the error does not reach the process-wide `uncaughtException` / `unhandledRejection` handling. As in Node, an unhandled rejection of a graph that has no `unhandledRejection` is given to its `uncaughtException`, with the origin `"unhandledRejection"`; a graph that wants one handler for everything gives only `uncaughtException`. These two are the only ones: there is no per-graph `rejectionHandled`, `uncaughtExceptionMonitor` or `warning`, and `process` warnings go to the shared `process`.

### Whose error it is

An **uncaught exception** belongs to the graph whose code threw it. A graph's code and everything it starts run in the graph's context, and so does a function of the graph's that the host or another graph calls, so what it throws is the graph's. A host function that the graph's code calls runs in the graph's context too, so what it throws there is the graph's. What a function of the graph's throws goes to its caller, like any call; if the caller does not catch it either, it is still the graph's, whatever it unwound through afterwards.

After an uncaught exception the graph's state is suspect, as a process's is. Disposing the graph is the safe response.

An **unhandled rejection** belongs to the graph whose code made the promise that nobody handled, whoever rejected it:

```ts tenant.ts icon="/icons/typescript.svg"
const load = async () => {
  throw new Error("oops");
};

export function start(signal: AbortSignal) {
  load().then(data => console.log(data)); // no .catch: the engine rejects what .then() returned
  new Promise((resolve, reject) => signal.addEventListener("abort", reject)); // the host's abort() calls reject
}
```

Both are the tenant's: its code made the two promises and handled neither. It does not matter that the host's `abort()` is what called `reject`, or whether the listener is `reject` or `event => reject(event)`. A promise the host made is the host's, even when a graph's code rejects it. The rule follows the promise, not the chain it came from: a graph that calls `.then()` or `.catch()` on another graph's promise has made a new promise, and what becomes of that one is the caller's.

An error that no code threw belongs to whoever opened the thing it happened to. A socket the graph opened that fails with no `error` handler reports to the graph's `uncaughtException`.

`graph.import()` returns its promise to whoever called it. If a module throws while it is evaluated the promise rejects, and if nobody handles that promise it is the caller's unhandled rejection, like a specifier that does not resolve or an `import()` into a disposed graph.

### Where the handlers run

A handler runs in the context the graph was made in: the host's, or the enclosing graph's for a graph that a graph's code made. What it throws, rejects or starts is that context's, so an error the handler lets escape goes on to the host and does not come back to the same handler. That holds for a handler the host wrote. A handler that is a function of some graph runs in that graph's context, like any call of it. A function of the graph's that the handler calls also runs in the graph's context, so an error in what that function starts comes back to the handler.

A graph with no handler for an error hands it to the graph in whose context it was made, and so on up to the host. It was made in a graph's context if that graph's code made it, or a host function that graph's code called did.

## What is shared

The global object, `globalThis` properties, plugins and native addons are shared by every graph and the host. So is `process`, unless you replace it through `globals`. A graph's listeners on something the host owns are that object's, so they are still called after `dispose()`. That includes signal, `process.stdin` and `'exit'` listeners on the shared `process`, and listeners on an emitter the host passed in. They are functions of the graph's, so they run in its context, which is stopped: their synchronous code runs, and the asynchronous work they start never completes. Code that should hear nothing more removes its listeners before its graph is disposed. `ModuleGraph` separates instances of an app you trust from each other. It is not a security sandbox.

`http.globalAgent` and `https.globalAgent` are shared too. A connection belongs to the `Agent` that opened it, and an `Agent` to the script that made it, so a request a graph makes without an `agent` uses a connection that is not the graph's: `dispose()` does not close it, and it keeps the process running like any connection of the host's. Code whose connections should go with its graph passes an `Agent` it made itself.

`mock.module()` in `bun test` is one of the shared things: it applies to what a graph loads afterwards. A graph that already loaded the module keeps the instance it has.
