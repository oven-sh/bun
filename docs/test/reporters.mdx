`bun test` supports different output formats through reporters, both built-in and custom.

## Built-in Reporters

### Default Console Reporter

By default, `bun test` outputs results to the console in a human-readable format:

```sh terminal icon="terminal"
test/package-json-lint.test.ts:
✓ test/package.json [0.88ms]
✓ test/js/third_party/grpc-js/package.json [0.18ms]
✓ test/js/third_party/svelte/package.json [0.21ms]
✓ test/js/third_party/express/package.json [1.05ms]

 4 pass
 0 fail
 4 expect() calls
Ran 4 tests across 1 file. [8.00ms]
```

When a terminal doesn't support colors, the output avoids non-ASCII characters:

```sh terminal icon="terminal"
test/package-json-lint.test.ts:
(pass) test/package.json [0.48ms]
(pass) test/js/third_party/grpc-js/package.json [0.10ms]
(pass) test/js/third_party/svelte/package.json [0.04ms]
(pass) test/js/third_party/express/package.json [0.04ms]

 4 pass
 0 fail
 4 expect() calls
Ran 4 tests across 1 file. [9.00ms]
```

### Dots Reporter

The dots reporter shows `.` for passing tests and prints full error details for failures, useful for large test suites.

```sh terminal icon="terminal"
bun test --dots
bun test --reporter=dots
```

### JUnit XML Reporter

For CI/CD environments, Bun can generate JUnit XML reports. JUnit XML is a widely-adopted test result format that many CI/CD systems can parse, including GitLab and Jenkins.

#### Using the JUnit Reporter

To generate a JUnit XML report, use the `--reporter=junit` flag along with `--reporter-outfile` to specify the output file:

```sh terminal icon="terminal"
bun test --reporter=junit --reporter-outfile=./junit.xml
```

Console output is unchanged; Bun writes the JUnit XML report to the specified path at the end of the test run, and creates the folder if it doesn't exist.

The report omits characters that XML 1.0 doesn't allow, such as most control characters and U+FFFE.

Every test file that ran has a `<testsuite>`, even if it has no tests. Its `timestamp` is the time the file started, in the format of `Date.prototype.toISOString()`.

An uncaught exception or unhandled rejection while a test is running fails that test, and its `<failure>`, `<flakyFailure>` or `<rerunFailure>` has `uncaught="true"`. Examples are an error thrown by a timer and a rejected promise that the test didn't await. The attribute is absent when the test function itself throws, returns a promise that rejects, or calls `done(error)`.

An error outside of any test is reported as a failed `<testcase>` named `(unhandled error)` in that file's `<testsuite>`. Examples are a test file or a preload script that throws while it loads, has a syntax error, or imports a module that doesn't exist.

With `--parallel`, a file whose worker crashed has a failed `<testcase>` named `(worker crashed)`. The files that the crash kept from finishing or from starting have one named `(aborted)`. After `SIGINT` or `SIGTERM`, a file that was running has one named `(interrupted)`, and a file that hadn't started has one named `(aborted)`.

#### Configuring via bunfig.toml

You can also configure the JUnit reporter in `bunfig.toml`:

```toml title="bunfig.toml" icon="settings"
[test.reporter]
junit = "path/to/junit.xml"  # Output path for JUnit XML report
```

#### Describe Blocks in JUnit Reports

By default, each `describe` block becomes a `<testsuite>` nested inside its file's `<testsuite>`. Some tools only read the `<testcase>` elements directly inside a file's `<testsuite>`. For those tools, use `--reporter-junit-suites=flat`:

```sh terminal icon="terminal"
bun test --reporter=junit --reporter-outfile=./junit.xml --reporter-junit-suites=flat
```

```toml title="bunfig.toml" icon="settings"
[test.reporter]
junit = "path/to/junit.xml"
junitSuites = "flat"  # "nested" (default) or "flat"
```

The report then has one `<testsuite>` per file. Each test's name is prefixed with its `describe` block names, and `classname` is the file:

```xml junit.xml icon="file-code"
<testsuite name="math.test.ts" file="math.test.ts" tests="1" ...>
  <testcase name="add &gt; negative numbers &gt; returns the sum" classname="math.test.ts" file="math.test.ts" line="5" ... />
</testsuite>
```

#### Retried tests

A test with [`retry`](/test/writing-tests#retries-and-repeats) is one `<testcase>`, with its final result. The attempts before the last one are in the elements that Maven Surefire uses, which CI tools read to find flaky tests:

```xml junit.xml icon="file-code"
<testcase name="passes on the third attempt" ...>
  <flakyFailure type="Error" message="attempt 1">...</flakyFailure>
  <flakyFailure type="Error" message="attempt 2">...</flakyFailure>
</testcase>
<testcase name="never passes" ...>
  <failure type="Error" message="attempt 3">...</failure>
  <rerunFailure type="Error" message="attempt 1">...</rerunFailure>
  <rerunFailure type="Error" message="attempt 2">...</rerunFailure>
</testcase>
```

#### Environment Variables in JUnit Reports

The JUnit reporter includes environment information as `<properties>` in the XML output, so you can tell which environment and commit a test run was for.

It includes the following environment variables when available:

| Environment Variable                                                    | Property Name | Description            |
| ----------------------------------------------------------------------- | ------------- | ---------------------- |
| `GITHUB_RUN_ID`, `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY`, `CI_JOB_URL` | `ci`          | CI build information   |
| `GITHUB_SHA`, `CI_COMMIT_SHA`, `GIT_SHA`                                | `commit`      | Git commit identifiers |
| System hostname                                                         | `hostname`    | Machine hostname       |

#### Current Limitations

The JUnit reporter does not include:

- `stdout` and `stderr` output from individual tests
- Precise timestamp fields per test case

### GitHub Actions reporter

`bun test` detects when it's running inside GitHub Actions and emits GitHub Actions annotations to the console directly. No configuration is needed beyond installing Bun and running `bun test`.

For an example GitHub Actions workflow, see [CI/CD integration](/pm/cli/install#ci%2Fcd).

## NDJSON Reporter

`--reporter=ndjson` writes each event of the run to `--reporter-outfile` as it happens, one JSON object per line. It's meant for editors and other tools that show test results live: they can read it without running code of their own inside `bun test`. The console reporter still prints.

```bash terminal icon="terminal"
bun test --reporter=ndjson --reporter-outfile=./events.ndjson
```

```toml title="bunfig.toml" icon="settings"
[test.reporter]
ndjson = "./events.ndjson"
```

The events are the same ones a [reporter module](#custom-reporters) gets, with a `type` field that names the event:

```json events.ndjson icon="file-code"
{"type":"runStart","files":["/project/math.test.ts"]}
{"type":"fileStart","file":"/project/math.test.ts"}
{"type":"fileCollected","file":"/project/math.test.ts","tests":[{"type":"describe","name":"math","parentId":null,"line":3,"column":1,"mode":"normal","only":false,"concurrent":false,"id":"d2"},{"type":"test","name":"adds","parentId":"d2","line":4,"column":3,"mode":"normal","only":false,"concurrent":false,"id":"t2"}]}
{"type":"testStart","file":"/project/math.test.ts","id":"t2","attempt":1}
{"type":"testEnd","file":"/project/math.test.ts","id":"t2","name":"adds","fullName":"math > adds","parentId":"d2","status":"fail","duration":0.61,"assertions":1,"attempt":1,"errors":[{"name":"AssertionError","message":"expect(received).toBe(expected)\n\nExpected: 3\nReceived: 2\n","stack":"AssertionError: expect(received).toBe(expected)\n\nExpected: 3\nReceived: 2\n\n      at math.test.ts:5:19\n","expected":"3","actual":"2","uncaught":false}],"earlierAttemptErrors":[]}
{"type":"fileEnd","file":"/project/math.test.ts","duration":13.45,"failedToLoad":false}
{"type":"runEnd","pass":0,"fail":1,"skip":0,"todo":0,"filtered":0,"files":1,"duration":64.05}
```

`--reporter=ndjson` and `--reporter=junit` can't share `--reporter-outfile`. To use both, set one of them in `bunfig.toml`.

## Custom Reporters

Pass the path or package name of a module to `--reporter` to report the run your own way. Its default export is an object with a hook for each event it handles, or a class that `bun test` constructs. The module is loaded from the working directory before any test file runs, and it gets the events in the order they happen:

```ts title="reporter.ts" icon="/icons/typescript.svg"
import type { Reporter } from "bun:test";

export default {
  onTestEnd(event) {
    if (event.status === "fail") {
      for (const error of event.errors) {
        console.log(`${event.fullName} failed at ${event.file}`);
        if (error.expected !== undefined) console.log(`expected ${error.expected}, received ${error.actual}`);
      }
    }
  },
  async onRunEnd(event) {
    await Bun.write("summary.json", JSON.stringify(event));
  },
} satisfies Reporter;
```

```bash terminal icon="terminal"
bun test --reporter=./reporter.ts
```

```toml title="bunfig.toml" icon="settings"
[test.reporter]
modules = ["./reporter.ts"]
```

`--reporter` can be given more than once, so a module can run next to `junit`, `ndjson` or `dots`. The console reporter still prints.

### Events

| Hook               | Event            | When                                                                                                                                                                     |
| ------------------ | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `onRunStart`       | `runStart`       | Before the first file, with the `files` that will run                                                                                                                    |
| `onFileStart`      | `fileStart`      | Before a file loads                                                                                                                                                      |
| `onFileCollected`  | `fileCollected`  | After a file has declared its tests: every `test()` and `describe()`, with its `id`, `parentId`, `line` and `column`. Again for each run of the file with `--rerun-each` |
| `onTestStart`      | `testStart`      | Before each attempt of a test that runs                                                                                                                                  |
| `onTestEnd`        | `testEnd`        | After the last attempt of a test, including skipped and todo tests                                                                                                       |
| `onHookFailure`    | `hookFailure`    | A `beforeAll()` or `afterAll()` hook failed                                                                                                                              |
| `onUnhandledError` | `unhandledError` | An error that no test caught, such as one thrown by a timer between tests                                                                                                |
| `onFileEnd`        | `fileEnd`        | After a file's tests, once even with `--rerun-each`                                                                                                                      |
| `onRunEnd`         | `runEnd`         | After the last file, with the counts of the run                                                                                                                          |

Tests have ids like `"t3"` and `describe()` blocks ids like `"d2"`. An id is unique within its file and the same on every run of the file, so an editor can match the `testEnd` of a test to the place in `fileCollected` where the test is declared. `duration` is in milliseconds.

`testEnd` has a `status` of `"pass"`, `"fail"`, `"skip"` or `"todo"`, and a `reason` when that isn't explained by a thrown error or by `.skip`, such as `"timeout"` or `"filtered"`. Each of its `errors` has the `name`, `message` and `stack` that `bun test` prints. When a matcher such as `toEqual()` compared two values, the error also has them as `expected` and `actual`, formatted as `expect()` prints them, so an editor can show a diff. A test that passed on a retry lists the errors of its failed attempts in `earlierAttemptErrors`.

The `Reporter` and `ReporterEvents` types are exported from `bun:test`.

### Errors and promises

A hook that throws, or a promise of one that rejects, prints the error and fails the run, and the module gets no events after that. A module that can't be loaded stops `bun test` before any test runs.

`bun test` waits for the promises that hooks return at the end of each file and at the end of the run, so `onFileEnd` and `onRunEnd` can write or upload results.

### Limitations

- `--parallel` doesn't support `--reporter=ndjson` or reporter modules yet.
- A test's `console.log()` output isn't part of its events.

### Inspector Protocol

Bun also reports test discovery, start and end to debuggers through its `TestReporter` domain of the WebKit Inspector Protocol, which the VS Code extension uses. A reporter module gets more detail about each test and needs no debugger connection.
