1. The channel between `bun --lint` and the runner
--------------------------------------------------

DECISION: proposal (d). Two environment variables beside the operand form that conformance.md T2.4 specifies:
    BUN_INTERNAL_LINT_OPTIONS   in:  the options of the run, as JSON
    BUN_INTERNAL_LINT_REPORT    out: the path of a file that gets the diagnostics with spans, the related
                                     information and the stand-in log, as JSON
The operands stay the unit files, stderr stays the plain format, the exit code stays 0, 2 or 1, stdout stays
empty. One process checks one program.

K5 does not use this channel. typecheck.md K5 plugs the checker in "through the test importer": that check is a
TypeScript function that the typecheck unit hands to the runner (CH-4). Options, span length, related
information and the stand-in log are fields of its input and output. The channel is what the DEFAULT check of
T2.4 needs, and its list of passing names stays empty until Bun's own parser, the lowering and the checker are
wired together in the binary.

Why (d), from the code:

  criterion                                   (a) 3 vars, TS-1   (b) request file   (c) manifest, stdout   (d) 2 vars
  operands are source files (cli.md C1.3)     yes                yes                no                     yes
  diagnostics on stderr (cli.md C2.2, T2.4)   yes                yes                no: JSON on stdout     yes
  exit code 0 / 2 / 1 (cli.md C1.3)           yes                yes                no: 0 with errors      yes
  programs per process                        1                  1                  up to 256              1
  variables to declare                        3                  1                  1                      2
  the same mechanism is in the tree           the out file       no                 the switch only        the out file

- The review rules of the repository decide for the smallest hook. REVIEW.md:15: "Never add production code
  solely to make a test writable — use `bun:internal-for-testing` or externally observable behavior." All four
  proposals add such code. (c) adds a second driver (a manifest, a loop over programs, state given back between
  programs, a report protocol); (d) adds a reader and a writer and leaves what a user can observe as it is.
  A lint run must not start JavaScriptCore (cli.md C1.1), so the module of that rule cannot serve the command
  line. It is a question for the maintainers all the same: MQ-1.
- conformance.md T2.4 fixes the default check: "the unit files as operands" and "the plain format ... from
  stderr". (a), (b) and (d) add to that one spawn. (c) is a second check beside it, with another operand, another
  stream and other exit codes, and only that second check could ever list an instance.
- The limit of time. One process for one instance ends with the `timeout` and `killSignal` of Bun.spawn. The
  prototype of (c) has to arm a timer again after each line of the report
  (check-contract-default-spawn/top-down/manifest.ts:186 and :215-216, setTimeout), in code that the test file
  runs, where COMMON.md rule 8 and CLAUDE.md ask for no setTimeout.
- The mechanism of (d) exists: a variable that names a file which the binary writes for a test
  (BUN_BYTECODE_DIGEST_OUT, BUN_BYTECODE_ORDER_NAMES_OUT, BUN_BYTECODE_ORDER_OUT: src/bun_core/env_var.rs:45-50,
  read at src/jsc/BytecodeOrderRecorder.rs:67, used by test/bundler/bun-build-compile.test.ts:257). For (c) the
  tree has boolean switches for tests (BUN_INTERNAL_INTERACTIVE_ASSUME_TTY, env_var.rs:295), and no operand that
  changes its meaning and no protocol on stdout.
  One half of (d) has no model: no string variable of env_var.rs holds JSON (they hold paths, addresses, names
  and option strings). If the owners do not want JSON in a variable, the value of BUN_INTERNAL_LINT_OPTIONS is
  the path of a file with the same object; nothing else of CH-3 changes.
- It matches how the cli research plans its own tests: every case a file, all given as operands of one
  `bun --lint`, stderr piped in the plain format (units/cli/rules-comparisons/spec-rules.txt, TESTS).
- The two halves have different owners and different dates. The report needs only what cli.md C2.1 already gives
  a diagnostic (file, start, length, category, code, text, chain, related information): cli can grant it alone.
  The options need the CompilerOptions of typecheck. With (d) each half is granted and detected by itself.
- A lint run of Bun is a process that exits. (c) asks for up to 256 programs in one process: memory given back
  after each program, no state left from the one before, a crash that has to be attributed to an instance and
  the rest sent again. None of that is needed by the product.
- `BUN_INTERNAL_LINT_OPTIONS='{"compilerOptions":{"strict":true}}' bun --lint a.ts` reproduces one instance by
  hand and prints readable diagnostics. The sweep can print that one line for a failing instance.
- (a): the variable _ROOT is not needed for names (the runner maps real names to virtual names itself:
  check-contract-default-spawn/top-down/check.ts:17-28). `error TS-1` is the code of an ad hoc message of the
  reference (internal/diagnostics/diagnostics.go:152-159), used by its harness at
  internal/testutil/harnessutil/harnessutil.go:699 and rejected at internal/testutil/tsbaseline/error_baseline.go:44-48.
- (b) carries the same two payloads in one file and one variable. It was not chosen because a request that is
  ignored and a request that is honoured look the same until the report is read, and because it adds one file
  to write for each instance. If the maintainers want one variable, the payloads of CH-2 and CH-3 move into the
  request file unchanged.

What (d) costs, measured. This is its weak side and the reason why the first edition of the top-down draft
chose (c):
- One process for each instance. Wall time for each instance of 200 (release) and 64 (debug) runs of
  `--revision` on this machine, 16 threads, load average above 600: release 64 ms with 1 process at a time,
  40 ms with 8, 24 ms with 16; debug 270 ms with 1, 57 ms with 8 and with 16. On a lighter machine the earlier
  passes measured 12 ms for a release start, and (td) medians of 2.4 ms to 61 ms release, 272 ms to 351 ms debug.
  The same probes an hour later, load average 570: release 151 ms with 1 at a time and 74 ms with 4, debug
  460 ms with 1. The figures of this machine say how loaded it is more than what a start costs.
- The default libraries are read again by each process. Today's parser, which drops the types, reads the 102
  library files that are no worker or script host library (2,984,246 bytes) in 10 ms in the release build; (td)
  the 15 files of a `target: es2015` program take 6 ms release and 284 ms to 311 ms debug.
  A real checker says what that costs with binding and checking: the command line of typescript-go built from
  source (/tmp/e2e/k4real of the typecheck research), `min.ts --noEmit --skipDefaultLibCheck
  --noErrorTruncation --target es2015`, ten runs: 1.07 s user and 0.31 s system, so about 130 ms of processor
  time for each process; with `--lib es5` (4 files) 29 ms. Three quarters of a process is the default libraries.
- The reference does not pay this: its harness keeps every parsed file for the whole process
  (harnessutil.go:493-530, sourceFileCache), and the typecheck research ran all 12,797 instances in one process
  in 60 s on this machine (/tmp/k4drv/k5/setup3.log).
- A full sweep through (d) pays 12,797 starts and library loads: about 28 minutes of processor time with a
  release build, a few minutes of wall time with 8 to 16 processes at a time; at least two hours of processor
  time with a debug build before any check. A sweep belongs to a release build in both forms.
- conformance.test.ts (budget 10 s in a release build): about 600 to 1,300 listed instances on 8 to 16 cores
  at 130 ms each. In the debug and ASAN lanes (10 to 100 times slower) a list of more than a few dozen names
  needs a fixed sample. That list is empty until the binary checks.
- (c) removes the starts. It removes the library loads only if the checker crate shares parsed and bound library
  files between the programs of one process, which no goal file asks of typecheck. It can be added later without
  a change to the payloads: D of CH-2 and compilerOptions of CH-3 do not depend on what carries them.
The first edition of the top-down draft chose (c) for this cost; its second edition chooses (d) too. What would
justify a batch form later: a list of the default check with more than about a thousand names that has to run
in full in the test file, together with shared libraries in the checker crate.

CH-1. The operand form: what cli.md C2 leaves open
To: cli (src/runtime/cli/lint_command.rs, src/lint/).
Ask. For `bun --lint <files>` when stdout and stderr are no terminal:
 1. stdout stays empty.
 2. stderr holds diagnostics and nothing else, each line ended by LF:
        <path>(<line>,<column>): <category> <code>: <text>      a diagnostic in a file
        <category> <code>: <text>                                a diagnostic without a file
        <two spaces per level><text>                             a line of the message chain, level 1 and up
    line and column 1-based, the column in UTF-16 code units; category one of error, warning, suggestion,
    message; the path relative to the current directory with forward slashes on every platform, or absolute.
    Reference: internal/diagnosticwriter/diagnosticwriter.go:555-566 (head), :342-360 (chain, pre-order),
    internal/diagnostics/diagnostics.go:29-41 (category names). No empty line, no summary, no code frame.
 3. The code is `TS` and a number only for a diagnostic that typescript-go has under that number, with its text.
    Every other code (a rule, a syntax error of Bun without a TypeScript number) is a name:
    [A-Za-z@][A-Za-z0-9@/_-]* and not `TS` and digits. No line `error: <text>` without a code.
    cli's prototype has that already: Code::Ts(u32) prints `TS<n>`, Code::Name prints the name, and the names
    that are no rule are `syntax`, `internal-error`, `cannot-read-file` and `unsupported-extension`
    (lint-prototype.patch, src/lint/diagnostic.rs). The runner reads a name that it was not told to leave out
    as a failure of the instance: a syntax error of Bun in a case without expected errors must not pass.
 4. Exit code 0 with no diagnostic of category error, 2 with one or more, 1 for a refusal with a text on stderr.
    Every other exit code and every signal is read as a crash (a panic ends with SIGABRT on POSIX and with exit
    code 3 on Windows: src/crash_handler/lib.rs:2927-2992).
 5. The operands of one run are the roots of ONE program, in the order given, as for `tsc a.ts b.ts`.
    (td) 1,562 run instances have more than one root. Today cli.md C1.3 reads each operand by itself, and the
    rule tests that cli plans give many cases that do not know of each other as the operands of one run
    (units/cli/rules-comparisons/spec-rules.txt:80-81): with a checker behind the flag those are one program.
 6. Order and duplicates as the reference: sorted with ast.CompareDiagnostics
    (internal/ast/diagnostic.go:458-503: path, start, END of the span, code, category, source, message key,
    arguments, chain, related information), then compactAndMergeRelatedInfos
    (internal/compiler/program.go:1605-1634), which joins diagnostics that differ only in their related
    information. cli.md C2.2 says "file, then position, then code": the end comes before the code. (td) 474
    baselines hold two diagnostics at one start, in 105 their ends differ, in 37 the order by code is the
    reverse of the order by end (first: compiler/TransportStream.ts, compiler/arithmeticOnInvalidTypes.ts).
    cli's prototype has this order (compare_diagnostics in src/lint/diagnostic.rs of lint-prototype.patch). It
    compares the text where the reference compares the message key and then the arguments. No baseline of the
    oracle is decided by that difference: 36 pairs in 22 baselines tie on file, start, end, code and category,
    and all 36 are in ascending order of their text (error-baseline-format/top-down/ties.ts, run again now).
 7. A lint run prints nothing of its own about a bunfig.toml, a package.json or a jsconfig.json in or above the
    current directory, and about a tsconfig.json only what point 8 says. Whatever the run reads, stderr holds
    only lines of point 2. 130 case files have a unit named tsconfig.json (73 run instances) and 242 one named
    package.json (504 run instances), some broken on purpose (19 of the 493 such units are no strict JSON);
    none has a bunfig.toml, a jsconfig.json or a .env file.
 8. Configuration files and operands. The reference refuses operands beside a configuration file: with file
    names on the command line it looks for a tsconfig.json in the current directory and in every directory
    above it, prints TS5112 and checks nothing (internal/execute/tsc.go:180-188, :269-281; measured with
    typescript-go's command line: `error TS5112: tsconfig.json is present but will not be loaded if files are
    specified on commandline. Use '--ignoreConfig' to skip this error.`, exit code 1). The design report of
    this work has `bun --lint` follow that (its row 15, as an earlier finding quotes it; the file is not on
    the disk now). If it does, a conformance run needs the way out: a run with
    BUN_INTERNAL_LINT_OPTIONS set looks for no configuration file and loads none (CH-3 point 1). Without that
    variable the runner can only keep its scratch directory where no directory above holds a tsconfig.json
    (the temporary directory of the system), and the 73 run instances that bring their own cannot run.
 9. The plain form is chosen by "stderr is no terminal" alone: bun_core::output::is_stderr_tty()
    (src/bun_core/output.rs:841), not enable_ansi_colors_stderr() (:2257), which FORCE_COLOR turns on for a
    pipe (:398-438). The runner removes FORCE_COLOR and sets NO_COLOR=1, as bunEnv does.
10. A run whose check reached a stand-in, or recorded an internal diagnostic, says so on stderr with one line
    for each that has a name as its code (`internal-error` is in cli's prototype; one more name for a
    stand-in) and ends with exit code 2: a check that was not complete never looks like a clean run, with or
    without a report. (typecheck gives the data: CH-3 point 4.)
Unlocks: the probe of the default check, three steps of one process each: (1) a file that would leave a mark
if it ran: no mark, exit code 0, nothing printed: "a linter"; (2) a file with a syntax error and
BUN_INTERNAL_LINT_REPORT: exit code 2, one diagnostic on stderr, and a report that holds the same diagnostic
with its start and length: the level "report", else "plain"; (3) BUN_INTERNAL_LINT_OPTIONS with an option name
that does not exist: exit code 1 and the name on stderr: "options are read", else "unsupported: options not
applied". Whether a checker ran is not a matter of the probe: each report says it (`checked`, CH-2).
Alone CH-1 lets no instance be listed: see "Until then" of CH-2.
Until then: the probe refuses the binary and no instance is handed to it. Measured again for this draft: with
BUN_FEATURE_FLAG_EXPERIMENTAL_LINT=1 the release binary (1.4.3-canary.1+367d939d9) and the debug build of the cli
worktree (1.4.3-debug+e3566be88) both run the operand of `bun --lint probe.ts`: the mark is written, exit code 0.

CH-2. The report file
To: cli. One line in src/bun_core/env_var.rs if the declared style is wanted: that file has no owner (RP-5).
Ask.
 1. BUN_INTERNAL_LINT_REPORT, read in lint_command.rs when a lint run starts, after the refusals of C1.4.
    Either `new!(pub BUN_INTERNAL_LINT_REPORT: string, "BUN_INTERNAL_LINT_REPORT", {});` after
    src/bun_core/env_var.rs:181 and `.get_not_empty()` as src/jsc/BytecodeOrderRecorder.rs:67 does, or with no
    edit outside cli's files `bun_core::getenv_z(bun_core::zstr!("BUN_INTERNAL_LINT_REPORT"))` as
    src/runtime/cli/test/ChangedFilesFilter.rs:339 does (clippy.toml:16-17 bans std::env::var only).
    A gate for test hooks exists at src/bundler/bytecode_order.rs:62-71 (debug build, or
    BUN_GARBAGE_COLLECTOR_LEVEL and BUN_FEATURE_FLAG_INTERNAL_FOR_TESTING set). bunEnv has both
    (test/harness.ts:78 and :85) and is the environment of every spawn of the runner, in the test file and in
    sweep.ts, so cli may use that gate.
 2. The value is an absolute path. When the run ends with exit code 0 or 2 the binary writes ONE JSON object
    there (UTF-8, the file created or truncated) and then exits. With exit code 1 no file is written. stdout,
    stderr and the exit code are the same as without the variable.
    bun_core::fmt::write_json_string (src/bun_core/fmt.rs:42) quotes a string; no new dependency.
 3. The object:
        { "checked": true,
          "options": { ... },
          "diagnostics": [ D, ... ],
          "rules": [ R, ... ],
          "standIns": [ "name", ... ],
          "internal": [ "text", ... ] }
        D = { "category": "error" | "warning" | "suggestion" | "message",
              "code": 2322,
              "messageText": "...",
              "next": [ { "messageText": "...", "next": [...] } ],
              "location": { "file": "/tmp/x/0/.src/a.ts", "start": 6, "length": 1, "line": 1, "character": 7 },
              "relatedInformation": [ { "code": 2728, "messageText": "...", "next": [...], "location": {...} } ] }
        R = { "rule": "no-debugger", "category": "...", "messageText": "...", "location": {...} }
    - checked: true when the binder and the checker ran over the whole program. false when the run only parsed,
      or stopped before the check. An instance is listed only with true: a binary that only parses prints
      nothing for the 5,770 instances without expected errors, and none of them may pass that way.
    - options: the value of BUN_INTERNAL_LINT_OPTIONS as the binary read it (CH-3); absent when that variable
      was not set. It is the proof that the options were applied. The value is JSON already: the binary can
      copy its bytes into the report after it has read them without an error.
    - diagnostics: the diagnostics of the run that have a TypeScript number, and only those, in the order of
      CH-1 point 6 (in a harness run: what the harness of the reference collects, CH-3 point 3). The runner
      sorts them again with a stable sort by the virtual path, start, end, code and category, so diagnostics
      that are equal in those keep the order of the report.
    - rules: the diagnostics of lint rules. The runner counts them and leaves them out of the comparison: the
      cases are full of code that the first rules of C3 report (15 case files have a `debugger` statement).
    - next is absent or empty without a chain. location is absent for a diagnostic without a file.
      relatedInformation is always there.
    - file is the real absolute path of a file of the instance, or a default library file: then only its last
      component (lib.<name>.d.ts) is read.
    - start and length count UTF-8 bytes from the first byte of the file; the runner writes every unit as UTF-8
      without a byte order mark. line and character are 1-based, the character in UTF-16 code units. Both
      pairs are given and have to agree. The report and stderr show the same diagnostics: the runner fails a
      run in which one has an entry that the other lacks.
    - standIns: the names of the stand-in log of the run, each once, in the order of the first reach.
    - internal: every other diagnostic of the run, as `<code>: <text>`: a ported panic or assert
      (`internal-error`), a syntax error of Bun that has no TypeScript number (`syntax`), a file that was not
      read (`cannot-read-file`, `unsupported-extension`). Any entry fails the instance.
    - A member that is not named here makes the report unreadable.
    - The runner gives each spawn a path of its own outside the directory of the instance and removes the file
      after it has read it. No file after exit code 0 or 2 means a binary without CH-2: level "plain".
Unlocks. Every listing through the binary. Of the 7,027 E baselines (td) 6,865 need the span length and 1,024 the
related information; the plain format alone rebuilds 143 (own count: 144 baselines have no squiggle line and no
related line, 1,035 have related lines, 14 are in the pretty form).
Until then. A run without a report has the level "plain" and is never listed: no stand-in log, no proof that a
check ran, no spans. On request the sweep compares the first section of the baseline and reports that count apart.

CH-3. The options, and what the checker crate gives
To: typecheck (src/typecheck/), then cli (lint_command.rs hands over).
Ask.
 1. BUN_INTERNAL_LINT_OPTIONS, declared or read as in CH-2 point 1. The value is a JSON object, read with
    bun_parsers::json::parse_utf8 (src/parsers/json.rs:308):
        { "compilerOptions": { "noErrorTruncation": true, "newLine": "crlf", "skipDefaultLibCheck": true,
                               "target": "es2015", "strict": false, "lib": ["es2015", "dom"] },
          "libDirectory": "/repo/test/cli/lint/conformance/corpus/<the directory of LB-2>" }
    - compilerOptions has the form of "compilerOptions" in a tsconfig.json: declared names, booleans, numbers,
      strings, lists of strings, a value of an enumeration as its name in lower case, a file name absolute and
      real. It is the final set: the runner has merged what the harness sets (harnessutil.go:97-104) with the
      directives of the variation. The longest directive text of one case is 424 bytes, so the value stays far
      below the 32,767 characters that Windows allows for one variable.
    - libDirectory is optional and is read only until the libraries are part of the binary.
    - With the variable set the run is a harness run: no configuration file is looked for or loaded (CH-1
      point 8), and the diagnostics are collected as the harness collects them (point 3 below). stderr and the
      report show that one set. BUN_INTERNAL_LINT_REPORT alone changes nothing of a run.
    - An unknown member, an option that the binary does not know and a value that it does not implement are a
      refusal: exit code 1, a text on stderr that names it, no report. Nothing is dropped in silence.
    - Names kept for the program layer. The runner sends one only when cli's API.md says that it is
      implemented; until then such an instance is "unsupported" and no process starts:
      "configFile": "<path>" with "defaultOptions": {...} (73 run instances; the order is the one of
      harnessutil.go:89-109: the options of the configuration file, then defaultOptions where no value is set,
      then compilerOptions; the roots stay the operands);
      "root": "<path>" (175 run instances: a text of the instance names a file by an absolute path such as
      /.lib/react.d.ts, to be found below that real directory);
      "useCaseSensitiveFileNames": false (5 run instances); "captureSuggestions": true (1 run instance,
      harnessutil.go:670-672 and :686-688).
 2. typecheck: an entry that sets one option from its declared name and a JSON value: the port of
    tsoptions.ParseCompilerOptions(key string, value any, allOptions *core.CompilerOptions)
    (internal/tsoptions/parsinghelpers.go:268, the switch from :279; called by the harness at
    internal/testutil/harnessutil/harnessutil.go:301) on core.CompilerOptions
    (internal/core/compileroptions.go:17), with the names of the enumerations
    (internal/tsoptions/commandlineoption.go:86, tsconfigparsing.go:457). It says when it does not know a name.
    (td) the run instances use 90 of the 125 declared names (68 booleans, 11 strings, 6 enumerations, 4 lists,
    1 number); `target` alone covers 5,012 instances, the 12 names used most 10,461, 30 names 12,113.
 3. typecheck: the diagnostics of one program as the harness collects them, not as the command line does:
    configuration file, program, syntactic, semantic and global diagnostics together, the declaration
    diagnostics when the options emit declarations (internal/testutil/harnessutil/harnessutil.go:662-668,
    again after the emit at :676-687), then compiler.SortAndDeduplicateDiagnostics
    (internal/compiler/program.go:1597-1634). The command line collects program and global diagnostics only
    without a syntactic one (program.go:1970) and semantic ones only without any of those (:1979).
    Counted on the programs that the reference built for the 12,797 run instances
    (units/typecheck/drivers-k4-k5/bottom-up/data/manifest.jsonl.gz): 691 have a syntactic diagnostic; in 406
    of them the harness also has a diagnostic that the command line drops at :1970 (in 387 a bind, semantic or
    global one); 61 more have a program or global diagnostic beside a semantic one, dropped at :1979. So the
    command line's rule changes the result of 467 run instances. (By codes alone the two passes had counted
    288 to 293.)
    The emit itself adds nothing: the count before the emit (:673) and after it (:689) is the same in all
    12,797, so no emit has to run. The options are applied as given and none is added: a run that is told
    noEmit reports less (the earlier pass saw TS2441, TS5055 and TS5056 go; 988 run instances set noEmit).
    A run with BUN_INTERNAL_LINT_OPTIONS collects this way (point 1); a run without it may keep the rule of
    the command line.
 4. typecheck: per run, the stand-in log (names, each once, order of the first reach) and the internal log.
    The scratch of the typecheck research has both: Checker.stand_ins: StandInLog with snapshot() ->
    Vec<(&'static str, u32)> and Checker.internal: InternalLog with snapshot() and count()
    (units/typecheck/conventions-scratch/rust/internal.rs:28-81, checker.rs:123-127, :294-297).
 5. typecheck: the default libraries are read from a directory that the caller names (K4 does that), with the
    names of internal/bundled/libs: LB-2.
