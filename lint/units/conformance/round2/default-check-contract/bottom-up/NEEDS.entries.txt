## D-1. cli (its D2): what a pass at the level "first-section" needs of a syntax error

For: cli (`lint_command.rs`, the call of `Parser::parse_for_lint_with_codes`), parser (its table).

The level of expectations.json is "first-section": path, line, column, category, code, text and chain of every
diagnostic of the run are the bytes of the first section of the oracle. With the numbers of D2 an instance passes when
1. every line that the command prints for its files has a `TS` number, with the text that typescript-go has for it;
2. line and column are the reference's (1-based, UTF-16);
3. the command prints as many diagnostics as the oracle holds, in its order.
One `syntax` line beside them fails the instance (cause syntax), error or warning. Bun's parser stops at its first
error where the reference recovers, so an oracle with one diagnostic is what can be met first. Measured by
../../default-check-classification (observed/near.txt): 497 oracles of class E hold a code of the parser's table, 161
only such codes, 121 exactly one diagnostic of the table; for 105 of the 121 Bun reports an error today, for 54
exactly one, at the line and the column of the oracle's. Those 54 are the first names that can enter list E.
Nothing is asked beyond D2 itself. To decide on cli's side: what is printed for a message of the log that has no
number when another message of the same file has one (API.md of cli, "Where the parser has no code for a message").

## D-3. cli: the five names of the command, and a rule reports in a file

For: cli.

The runner leaves a report of a rule out of the comparison and counts it. It takes as a rule a code that is a name, is
none of `syntax`, `cannot-read-file`, `unsupported-extension`, `internal-error`, `internal-stand-in`
(`commandCodes` of `runner/check_bun_lint.ts`) and stands in a file. A name outside the five without a file fails the
instance (cause unknown code).
Ask: a sixth name of the command goes into the table "The codes" of cli's API.md and into `commandCodes` in the same
merge. Until it is there the runner reads such a line in a file as a report of a rule and leaves it out.

## D-7. integrator: the lint path under the leak check

For: integrator, for information.

`conformance.test.ts` starts `bun --lint` six times in every lane (the probe, two units, two instances of the corpus)
and once more for every listed instance, with the environment of the lane. A leak on the lint path ends the child by
a signal or with the exit code 1: the outcome is crash and the test fails. It is to be fixed on the lint path, with no
line in `test/no-validate-leaksan.txt`. With the debug build of 3110ce85c and the settings of CI's leak check the six
runs end clean.
