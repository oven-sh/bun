### RP-6. What the corpus does to the file list of the pull request

To: integrator. For information, no file to change.

- GitHub lists the files of a pull request in the byte order of their paths (read for pull request 44200, 93
  files) and lists 3,000 at most. `scripts/buildkite.ts:435-465` reads 500 at most (10 pages of 50), and
  `.buildkite/ci.ts:1941-1943` stores them for every shard.
- With the corpus the pull request has 22,592 files (today's unit branches together). In that order
  `test/cli/lint/conformance.test.ts` is file 345 and the directory `test/cli/lint/conformance/` is files 346
  to 22,575. Every path that sorts after it is in no list: `test/cli/lint/diagnostics.test.ts`,

  `test/internal/typecheck-ast-generated.test.ts`. This holds as soon as the 9,056 baselines that the unit
  branch has already are merged.
- What the runner does with the list: it runs the changed test files first and outside the parallel bucket
  (`scripts/runner.node.ts:1315-1337`, `:2817-2836`) and marks a new file that fails with "(new)" (`:3018`).
  Those five files lose that. No test is left out: the runner finds its tests on disk (`:728`, `:2683-2684`).
- 339 of the first 500 places are taken by files before `test/`. When the files below `src/` of this work
  grow by 156 more, `conformance.test.ts` itself is past place 500, with or without the corpus.
- The path filters of the workflows are not touched by this. GitHub's documentation says that a filter sees
  the first 300 files of a diff (not measured). This pull request matches the filters of `rust-lints.yml:9-15`
  and `source-lints.yml:38-60` with files below `src/`, which are files 5 to 339.
- `comment-cop.yml:92-94` reads the same list from GitHub, and `src/` sorts before `test/`: it sees every
  file below `src/` as long as the pull request has fewer than 3,000 files before `test/`.

### RP-11. `scripts/runner.node.ts`: the rule by which a file is a test

To: integrator. Optional.

Ask: the functions `isJavaScript`, `isNodeTest`, `isClusterTest`, `isTest`, `isTestStrict`, `isHidden` (lines
2459 to 2498) exported from a module that runs nothing when it is imported, as `scripts/buildkite.ts` exports
`parseJunitFileSuites` for `test/internal/runner-junit.test.ts`.

Why. `getTests` (lines 2500 to 2519) walks all of `test/` and leaves out only a path below `node_modules` or
`node.js` and a name that starts with a dot. So the corpus is walked, and only its names keep it out of a
test run. `conformance.test.ts` cuts these functions out of the source of the runner, holds their text in a
snapshot in every build, and in a release build evaluates them on every name below
`test/cli/lint/conformance` (a tenth of a second; a debug build would take half a minute, because the
functions cost it a millisecond a name).

Until then: a change of one of these functions, or of `getTests`, fails the snapshot of
`conformance.test.ts`, and `bun bd test test/cli/lint/conformance.test.ts -u` takes the new text. A release
build then says whether a name of the corpus is a test by the new rule. With the export, the snapshot goes and
the test imports the functions.

## What only CI can verify

No Windows machine and no macOS machine was available. A green run on Linux says nothing about them.

- Long paths (Windows). The longest path is 191 characters (159 outside this directory), 4 are longer than
  180, and `sync.sh` refuses more than 200. The CI image sets `core.longpaths`
  (`scripts/build/ci-images/spec.ts:1376`); a clone without it needs a root of at most 67 characters.
- Line endings. The image sets `core.autocrlf` false (`spec.ts:1374`), `format.yml:30` sets it true after the
  checkout. `corpus/** -text` of the unit's `.gitattributes` keeps the corpus as it is: on Linux
  `git -c core.autocrlf=true add --renormalize` stages no file of it. It stages the four licence texts beside
  the corpus, which have CR LF and no such line, until that file names them too.
- Time. Against `main` the directory is 22,230 files in 397 directories: that much more in every checkout,
  and in every walk of `test/` by the runner, in each of about 150 jobs of a build. On Linux the walk and the
  rule on all of them take a tenth of a second in a release build. Not measured on Windows.
- That the test ran: `.claude/docs/landing-prs.md:66`. Look for `test/cli/lint/conformance.test.ts` in the
  log of one shard of every platform.
