## The type grammar without lint and with lint (P1)

At `be1ebe5295`. One grammar reads every type: `src/js_parser/parse/parse_skip_typescript.rs`, with the productions
of `internal/parser/parser.go` of typescript-go under their names (`parse_type`, `parse_union_type_or_higher`,
`parse_intersection_type_or_higher`, `parse_type_operator_or_higher`, `parse_postfix_type_or_higher`,
`parse_non_array_type`, `parse_function_or_constructor_type_to_error`, ...), generic over a sink
(`src/js_parser/parse/type_sink.rs`). `TypeSink::CONDITIONAL_FALSE_LEVEL` is gone: every sink reads the type after
the `:` of a conditional type at one level.

| sink | `Out` | `STRICT` | `BUILDS` | `Sub` | used by |
| --- | --- | --- | --- | --- | --- |
| `Discard` | `()` | false | false | `Discard` | every parse: `skip_type_script_type`, `skip_typescript_return_type`, `skip_type_script_type_arguments` |
| `DecoratorMetadata` | `Tag` | false | false | `Discard` | `emitDecoratorMetadata`: `skip_type_script_type_with_metadata`, `skip_typescript_return_type_with_metadata` |
| `Build` | `Option<ts::Type>` | true | true | `Build` | a lint parse only: `build_type_script_type`, `build_typescript_return_type`, `build_type_script_type_arguments`, `build_type_script_type_parameters` |

### How the grammar knows that it is a lint parse

Two switches, and a parse without lint takes neither.

1. At compile time, by the sink: `S::STRICT`, true for `Build` alone. It gates, in `parse_skip_typescript.rs`:
   TS1385 to TS1388 (`parse_function_or_constructor_type_to_error`), `|` or `&` where
   `parseTypeOperatorOrHigher` reads a type (`parse_type_after_leading_operators`), a conditional type after the
   operand of `keyof` and `readonly` where none may follow, a reserved word as an index type (`A[if]`) and as a
   type argument, the word before `{` in `implements class {}`, a missing type (`parse_type_reference`),
   reserved type names (`is_reserved_type_name`), and `typeof #x`.
2. At run time, by the parse: `P::is_lint_parse()`, true when `Parser::parse_for_lint` made the side table. It has
   four readers: `P::type_expected` (`syntax_errors.rs`, on the path of an error: in a lint parse a missing type is
   TS1110 for every sink, also inside an attempt), `pfx_t_open_paren` (`parse_prefix.rs:50`, every `(` that starts
   an expression: a lint parse records the parentheses), `parse_path` (`parse/mod.rs:1993`: `with` on the line
   after a module path starts import attributes), and the statement reader for a declaration whose name is `as`
   or `satisfies` (`parse_stmt.rs:1951`).

The sites that record test `p.starts_for_parse_only.is_some()`, which holds for `parse_only` and for a lint parse,
after the test of the TypeScript token that guarded them before, and call `#[cold]` functions (`lint_*`, `build_*`).

A lint parse reads with `Build`, and so strictly, what it records: annotations, return types and predicates, the
type of a `this` parameter, the types of `as`, `satisfies` and `<T>x`, type arguments after an expression, in JSX
and in heritage entries, and every list of type parameters. It reads with `Discard`, and so as a parse without lint
does but for TS1110, what it does not record: the type of a type alias, the `extends` clause and the members of an
interface, an index signature of a class. Before it builds, it also reads with the loose sinks the type that
decorator metadata is made of (`lint_type_metadata`) and the `<...>` that decides between a cast and an arrow
function.

### The rule for a parse without lint

A parse without lint accepts what it accepted before this work and rejects nothing new. Valid TypeScript means that
tsc as a whole reports nothing: no diagnostic of its parser and no grammar error of its checker. Where the parser
of tsc accepts a text, its checker rejects it, and Bun rejected it before, Bun keeps rejecting it for a sink whose
`STRICT` is false. The case that made the rule: `const a: typeof #a = 1;` stays
`Expected identifier but found "#a"` (`4d06830629`), and only `Build` reads it.

## Memory: what an arena holds

Rule: a value that an arena holds owns no memory of the global heap, because an arena never drops it. Read at
`be1ebe5295` over `src/ast/ts_nodes.rs`, `attached.rs`, `erased.rs`, `generics.rs`, `wrappers.rs` and the `Build`
sink of `type_sink.rs`:

- Every node of `bun_ast::ts` and every record of the four tables is `Copy` (`ts::List<T>` by its own `impl`), so
  none can hold a `Vec`, a `Box` or a `String`. What they point to is in the arena or in the AST stores:
  `StoreRef`, `StoreSlice`, `StoreStr`, `Expr`, `Binding`, `Stmt`.
- `ErasedMemberData::Property` points to a `G::Property` in the arena. It is not `Copy`: it holds
  `ts_decorators: Vec<Expr, AstAlloc>`, whose buffer is in the AST allocation scope, as in every `G::Property` of a
  class that stays, and `ts_metadata`, which holds no heap memory since `be1ebe5295` (`Metadata::MDot` is a
  `StoreSlice<Ref>`).
- The lists themselves are `Vec`s of the global heap: eight in `Attached`, two public and one private in
  `ErasedTables`, two in `Generics`, one in `Wrappers`, three `HashMap`s, and `SyntaxErrors` (an entry holds a
  `Cow<'static, [u8]>`). They are in the `Box` on the parser and are dropped with it, or with the side table when
  `f` returns.
- The `Build` sink gathers the items of a list in a `Vec` on the stack (`b::List`, `b::Set`, the `items` of the
  `build_*` functions, the entries of `lint_class_implements`) and copies them to the arena with
  `ts::List::from_slice`: the `Vec` is dropped where its function returns, also on an error.
