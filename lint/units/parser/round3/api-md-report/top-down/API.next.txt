## The two grammars

Round 1 gave every parse one type grammar that reads what tsc reads. It was measured on release builds against main
(`/workspace/notes/lint/goals/parser3.md`): a parse without lint paid +10.7% and +14.6% instructions in the two groups
of declaration files, and the parser text grew by 269,563 bytes. A parse without `--lint` pays nothing, so there are
two grammars now, one for each job.

### A parse without lint

It runs the type skipper of main with main's behaviour: what it accepts, what it rejects, every error text, every
`emitDecoratorMetadata` value. The text of `parse_skip_typescript.rs` is main's control flow in the form of commit
`2d28b35c01` ("js_parser: make the type grammar generic over a sink"; `parser3.md` names it `6b7ade0f2a`, which this
clone does not have), with one later change: `Metadata::MDot` holds its names as a `StoreSlice<Ref>` in the arena, and
`TypeSink::member` takes the arena (`be1ebe5295`).

```rust
/// What the type grammar keeps of the syntax it reads.
pub(crate) trait TypeSink {
    /// What one type leaves behind.
    type Out: Default;
    /// Binding level of the type after the ":" of a conditional type.
    const CONDITIONAL_FALSE_LEVEL: Level;
    // literal, keyword, function_type, parenthesized, keyof_type, readonly_type, typeof_query, tuple_type,
    // object_type, template_literal_type, reference, member, index_or_array, union_left, union_right,
    // intersection_left, intersection_right, conditional_true, conditional_false
```

### How a site knows which parse it is

By the side table, at run time. `P::starts_for_parse_only` is `None` in `Parser::parse` and `Parser::scan_imports`
and holds the side table in a lint parse. `Parser::parse_only` has a table too, but it is the parser without
TypeScript (`P<'a, false, false>`): in a TypeScript parser the option is set only by a lint parse. A site outside
the type grammar where TypeScript-only syntax is dropped tests that option once, after the token test that guarded
the site on main and inside `if Self::IS_TYPESCRIPT_ENABLED`, and calls a `#[cold]` function of the lint parse when
it is set:

```rust
[[FILL site-shape: one real site, copied from the code. The audit expects this shape (siteaudit2.py, default --pred `(?:p|self)\.lint\(\)`):
if Self::IS_TYPESCRIPT_ENABLED && p.lexer.token == T::TColon {
    if p.lint() {
        return p.lint_type_annotation(owner);
    }
    p.lexer.next()?;
    p.skip_type_script_type(Level::Lowest)?;
}
and the predicate itself, with its doc comment]]
```

That test is the whole cost of the lint parse for a parse without lint: one load and one conditional branch at a
site that only TypeScript syntax reaches. With the option `None` the lines that run are main's. The compile-time
switch of round 1, `TypeSink::STRICT`, is gone: a sink no longer says which parse it serves, because the skipper has
no lint behaviour and the lint grammar has no other sink.

JavaScript pays nothing: the parsers without TypeScript (`P<'a, false, false>` and `P<'a, false, true>`) have no
added test, and their machine code is the one of the reference text.

### What the caller sets up

As for `Parser::parse`: an AST allocation scope is open (the tests use
`bun_ast::ASTMemoryAllocator::borrowing(&arena).enter()`), and `Options::init(jsx, loader)` picks the parser:
`options.ts` (`loader.is_typescript()`) selects `P<'a, true, false>`, otherwise `P<'a, false, false>`, and
`options.jsx.parse` (`loader.is_jsx()`) turns JSX on at run time. The tests also set `features.no_macros` and
`features.dont_bundle_twice`. With a JavaScript loader a type annotation is a syntax error and `a < b > (c)` is two
operators.

### What the entry does, in this order (`Parser::_parse_for_lint`)

1. `is_declaration_file` is `options.ts` and `tspath.IsDeclarationFileName` of `source.path.text`: the base name
   ends in `.d.ts`, `.d.mts` or `.d.cts`, or in `.ts` after a `.d.` (`a.d.css.ts` is one, `a.d.tsx` is none).
2. The parser gets the side table `StartsForParseOnly::for_lint()`: from here `P::starts_for_parse_only` is set and
   `P::is_lint_parse()` is true.
3. A `#!` line is read past. It leaves nothing in the result.
4. The statements of the file are read with `parse_stmts_up_to` in the scope `Module`. In a declaration file they
   are read as after `declare` (`ParseStatementOptions::is_typescript_declare`).
5. The parse fails when the log holds an error that it did not hold before `Parser::init` read its first token,
   also when the parse pass only logged it and went on. `f` is not called, the result is `Err(Error::SyntaxError)`,
   and `errors` gets its entries. A stack overflow is logged as `Maximum call stack size exceeded` at the token the
   lexer is on and is `Err(Error::SyntaxError)` too (`Parser::parse_only` returns `Error::StackOverflow`).
6. Otherwise the lists of `sidecar.attached` are sorted by key and `f` is called. The side table is freed when `f`
   returns. `errors` is left as it was.

### What it does not do

No visit pass: nothing is bound to a symbol by use, folded, lowered, removed or renamed, and no import is scanned.
No `// @bun` shortcut (test `takes_no_shortcut_for_a_bundled_file`). The entry reads and writes no transpiler cache.
No error recovery: a file with a syntax error gives no tree ("No error recovery").

### What `f` gets

- `stmts`: the list that `parse_stmts_up_to` made for the file. The parse pass itself leaves out `;` alone
  (`S::Empty`), the directives `"use strict"` and `"use asm"`, and every statement that TypeScript erases. Another
  directive is an `S::Directive`. A comment that starts with `//!` or `/*!` is an `S::Comment` in the list it
  stands in, before the statement that follows it, and its `loc` is the `loc` of the token after the comment.
- An identifier that is read is an `E::Identifier` whose `Ref` names its text. A declared name has a `Ref` with the
  tag `Symbol`. `name_of` answers for both and for an allocated name. It never panics: a `Ref` that names nothing
  gives an empty name.
- `scopes_in_order` and `symbols` are what the parse pass of `Parser::parse` leaves for the same file. An erased
  statement leaves no scope: the scopes of a declared function, class or namespace are discarded as before, so a
  record can hold statements whose scopes are not in `scopes_in_order`. `ScopeOrder` has no public field and no
  public method: another crate cannot read an entry.
  [[CHECK same-tree: "are what the parse pass of Parser::parse leaves" is P3.1. It was measured once, in research on be1ebe5295 with a relinked binary and a switch that is not in the tree (round2/a3/top-down/results.txt: 3,206 files, 0 differ). State here what was run on the final commit, or that it was not run on it]]
- `import_records`: an erased import or export has no import record. Its path is in its record
  (`erased::ImportDeclaration::module_specifier`, `erased::ExportDeclaration::module_specifier`).
- `is_declaration_file`: in such a file a function, a class, an enum, a namespace, an interface and a type alias
  are records with `ErasedFlags::AMBIENT`. A variable statement without `declare` stays in `stmts` as an `S::Local`
  whose bindings are not declared (each `Ref` names its text). `export default x`, `export = x` and the import and
  export statements that bind values stay as in any file.
- `arena`: the type nodes, the payloads of the records and the lists are in it. Every record and every node is
  `Copy`: a copy may leave `f` and is good as long as the arena and the AST allocation scope are.

`ParsedOnly` has `async_arrow_parameters`, `arrow_expression_body`, `class_element` and `import_path`.
`ParsedForLint` has none of them: the three maps are filled in a lint parse too and are `pub(crate)`, and a path is
`import_records[index].path.text`.

It is one `Box` on the parser (`P::starts_for_parse_only`), made by `Parser::parse_only` (three maps, nothing else)
and by `Parser::parse_for_lint` (`is_lint`). The four tables hold thirteen lists. A record is `Copy`. An offset is a
byte offset in the source (`u32`), `start` of the first byte, `end` after the last. A `Loc` alone names no node
(`a.b.c` is three nodes at one `Loc`), so each kind has its own key:

| table | what | key of a record | how a pass finds it |
| --- | --- | --- | --- |
| `attached` | the TypeScript syntax of a node that stays | `Owner` (a function, an arrow function, a class), or the `loc` of a binding, of a member key, of a class keyword, of a JSX element | the readers `*_of` of `Attached` |
| `wrappers` | `as`, `satisfies`, `!`, `<T>x`, parentheses | `ExprId` of the operand | `Wrapper::wraps(&expr)` |
| `generics` | type arguments after an expression; type parameters of an interface or a type alias | `ExprId` of the operand and `TypeArgumentsOf`; the end of the name of the declaration | `Generics::type_arguments_after(&operand)`, `Generics::type_parameters_of(&name)` |
| `erased` | statements and class members that the tree does not hold | `Place` of a statement; `class_body` and `index` of a member | the place says the list and the index |

`Attached::sort` and the methods that add a record (`optional`, `definite`, `annotation`, `this_parameter`,
`type_parameter_list`, `return_type`, `heritage_clause`, `jsx_type_argument_list`, `keyword`, `type_only_specifier`,

How a later pass finds a record from the node it is at:

| node at hand | call | what is recorded |
| --- | --- | --- |
| `G::Decl` of `var`, `let`, `const`, `using`, also in the head of `for` | `annotation_of(decl.binding.loc)` | the type after `:` |
| `G::Arg` of a function, method, accessor, constructor or arrow function | `annotation_of(arg.binding.loc)` | the type after `:` |
| `Catch::binding` | `annotation_of(binding.loc)` | the type after `:` |
| `G::Property` of a class, kept or erased | `annotation_of(key.loc)` with `key = property.key` | the type of a field. For `[k]: T` the key is the expression in the brackets |
| `G::Fn` | `Owner::function(func.open_parens_loc)`, then `type_parameters_of`, `this_parameter_of`, `return_type_of` | `<T>`, `this: T` with the count of arguments before it, the return type or predicate |
| `E::Arrow` in the `Expr` `e` | `Owner::arrow(e.loc)`, then `type_parameters_of`, `return_type_of` | the same. `e.loc` is at `async`, at `<`, at `(` or at the one parameter |
| `G::Class`, statement or expression, kept or erased | `Owner::class(class.class_keyword.loc)`, then `type_parameters_of`; `heritage_of(class.class_keyword.loc)` | `<T>`; the `extends` clause, then the `implements` clause |
| `E::JSXElement` in the `Expr` `e` | `jsx_type_arguments_of(e.loc)` | `<Foo<T> />` |

A record is made where the parse pass skipped the syntax before, and it is made for erased nodes as well: the
annotations and the return type of an overload signature, of `declare function` and of the members of a declared
class are in these lists under the same keys, and the node is in the record of `erased`.

The `extends` clause holds one `TypeData::ExpressionWithTypeArguments` whose `expression` is `G::Class::extends`.
An entry of `implements` is a `TypeData::TypeReference` where a type reference stands there and `,` or `{` follows
it, otherwise an `ExpressionWithTypeArguments`.

`Annotation::question` and `Annotation::exclamation` are always `None`, and `keywords` and `specifiers` are always
empty: nothing in the parser calls `Attached::optional`, `definite`, `keyword`, `type_only_specifier` or
`specifiers_belong_to`. Every `Annotation` has a `type_node`.

### `wrappers`: what stands around an expression

How to attach: the wrappers of the `Expr` `e` are the records with `wraps(&e)`, that is
`ExprId::of(&record.operand) == ExprId::of(&e)`. `ExprId` is `Hash`: a pass builds one map from it. The payload is
the address of the node for every kind that has a payload in a store (`E::Binary`, `E::Dot`, `E::Call`, ...), and 0
for the kinds that are held inline (`E::Identifier`, `E::Number`, `E::This`, ...), which no other node of the same
kind shares its `loc` with.

`records` is in the order the parse pass finishes the wrappers, so for one operand the list order is from the
inside to the outside: `(x as T)!` gives `As`, `Parenthesized`, `NonNull`, all around `x`; `<T><U>x` gives the
assertion of `U` and then the one of `T`. A parent node holds the bare operand and does not know of the wrappers:
`a + (b)` is an `E::Binary` of `a` and `b`.

What is recorded in a lint parse of TypeScript: `x as T`, `x as const`, `x satisfies T`, `x!` (also in a
decorator), `<T>x`.

How to attach type arguments: by the operand, with `ExprId` as for a wrapper. The operand is the node the tree
holds where the source has `operand<T>`: `E::Call::target` for `f<T>(x)`, for `a?.<T>(x)` and for `@d<T>()`,

an entry of `implements` are in the `ts::HeritageClause` of `attached.heritage`, those of a JSX element in
`attached.jsx_type_arguments`, those of a type reference in its type node.

Where one operand has wrappers and type arguments, the two lists are merged by offset: a `TypeArguments` record
goes directly after the last wrapper of that operand that is no `TypeAssertion` and whose `end` is at or before
the `lt` of the record, and is the innermost where there is none. `(f<T>)` is the parentheses around the
instantiation, `(<A>f)<T>()` is the call of the parentheses, `<A>f<T>` is the assertion of the instantiation. This
rule is read from the order in which the parser makes the records. No test covers a source that mixes the two.

The name of a declared function, class or enum is in its `Stmt`: `parsed.name_of(name.ref_)`. A namespace with a
dotted name is one record for each part: the inner parts have `NESTED`, start at their own name and stand at
`Place::InTree` with the offset of the `.` before them.

How to put an erased statement back between the statements that stay: `place` says the list and the index, and
`index` counts the list as its node holds it (`ParsedForLint::stmts`, `S::Block::stmts`, `G::FnBody::stmts`, ...).
The records of one place are in the order of the source. The offset `scope` of `Place::Scope` is where the parse
pass pushed the scope of the list, which the tree has for every list:

| list | `scope` |
| --- | --- |
| the file | `Place::Module` |
| `S::Block::stmts` | `Stmt::loc` of the block, its `{` |
| `G::FnBody::stmts` of a function, method, accessor, constructor, or of an arrow function with braces | `G::FnBody::loc`, its `{` |
| `S::Try::body` | `Stmt::loc` of the `S::Try`, the word `try` |
| `Catch::body` | `Catch::body_loc` |
| `Finally::stmts` | `Finally::loc`, the word `finally` |
| `G::ClassStaticBlock::stmts` | `G::ClassStaticBlock::loc`, its `{` |
| `S::Namespace::stmts` | `Stmt::loc` of the `S::Namespace`: the keyword, or the `.` before the name of an inner part |
| the body of an erased namespace, module or `global` block | `Place::Erased`: `parent` is the `start` of the `Module` record, the list is its `ModuleDeclaration::body` |
| a `case` clause; the body of `if`, `else`, `for`, `while`, `do`, `with` or a label | no index: the placeholder `S::TypeScript` stays in the tree and the record has `Place::InTree` with its `Stmt::loc` |

`Place::InTree { loc }` means that the tree has a statement with that `Stmt::loc` where the erased statement stood:
an `S::TypeScript`, or with `STAND_IN` the `S::Local` that stands for `export declare var` in a namespace. A list
inside an erased `Declaration` (the body of a function after `declare`) has `Place::Scope` as any list, though its
scope is no longer in `scopes_in_order`.

How to put an erased class member back: the members of the class `c` are the records with
`class_body == c.body_loc`, in list order, each before `c.properties[index]`. `Property` holds the `G::Property`
as the parse pass built it (an overload has an `E::Function` without a body and `NO_BODY`); its annotations and
return type are in `attached`. `IndexSignature` has its range and its flags and nothing else. A member with
`declare` or `abstract` that has a decorator and no value stays in `G::Class::properties` with
`PropertyKind::Declare` or `PropertyKind::Abstract` and has no record.

What is a comment, as the scanner of the reference has it (`internal/scanner/scanner.go`):

- A `//` comment ends before its line break. A `/* */` comment ends after `*/`. A block comment is `JSDoc` when it
  starts with `/**` and the next character is not `/`.
- Comments before the first token, after a `#!` line, between tokens, inside a JSX opening tag and after the last
  token are all in the list, in source order, each once, also where the parser read the source twice.
- Not in the list: the `#!` line; `<!--` and `-->`, which Bun's lexer reads as comments with a warning and the
  reference does not know; a `//` or `/*` inside a string, a template, a regular expression or JSX text.

A comment directive is `@ts-expect-error` or `@ts-ignore` as `processCommentDirective` reads it: in a `//` comment

Its range is the comment for a `//` comment, and the last line of the comment for a block comment.

### Rules that hold for every node

- `start` and `end` are byte offsets in the source (`u32`). `start` is the offset of the first token of the node,
  `end` is the offset after its last token. They are the `getStart()` and the `end` of tsc. `Type::loc()`,
  `Type::range()` and `range(start, end)` give the `Loc` and the `Range` of a diagnostic.
- The `pos` of tsc (the end of the token before the node) is not stored. `full_start(source, comments, start)`
  computes it: it walks back from `start` over the white space of Bun's lexer and over `comments`, which must
  hold every comment of the file in source order. A file that starts with `#!` gives 0 for its first token.
- Every node type is `Copy`. A `Type` or a `Member` is a 20-byte handle: `start`, `end`, and a `TypeData` or
  `MemberData` that holds the kind and a `StoreRef` to the payload. Payloads and lists are in the
  `bun_alloc::Arena` that the caller passes, which is the arena of the lint parse. No node is put in the `Expr` or
  `Stmt` store. The fields of type `Expr`, `Binding` and `StoreSlice<Stmt>` hold what the expression, binding and
  statement parsers made.
- A payload of `TypeData` has no `start` and `end` of its own: they are on the `Type` that holds it. The same holds
  for a payload of `MemberData` and its `Member`.
- `List<T>` derefs to `[T]`. `start` is the end of the token that opens the list (`<`, `(`, `[`, `{`), or the start
  of the first token of the list when no token opens it (the types of a union, of an intersection and of a heritage
  clause, the spans of a template). `end` is the end of the last item or of the comma after it, and `start` when the
  list is empty. A trailing comma: `last.end < list.end`.
- The range of a `Member` takes the `;` or `,` after it.
- A `Name` holds the text without escapes. A private name keeps its `#` and `Name::is_private()` is true.

### How the nodes differ from the reference

- A literal type has no expression node: `LiteralType.literal` is the literal and `negative` stands for the
  `PrefixUnaryExpression` with operator `-`, whose range is the range of the `Type`.
- `TypePredicate.parameter_name` holds the range of the `ThisTypeNode` and no node.
- A modifier list is a `StoreSlice<Modifier>` without a range of its own: it runs from the `start` of its first
  modifier to the `end` of its last.
- `TemplatePiece` keeps the text without escapes. The raw text is the source between `start + 1` and the `${` or
  the closing backtick.
- `Parameter.name` is a `bun_ast::Binding`, which has a `loc` and no end.
- `JSDocOptionalType` and `JSDocVariadicType` have no node: only the JSDoc parser of the reference builds them.
- There is no node for a missing type: the parser stops at its first error.

### No error recovery

The parser stops at its first error as today: error recovery is out of scope. A lint parse that fails returns `Err`
and no tree, no node stands for what is missing, and `f` is not called. The log can hold more than one message,
because some errors are logged and the parse goes on to the end of the statement or of the file before it fails: the
first message of the parse is the error, the others are what followed from it. The reference recovers and reports
more diagnostics for the same file: only its first one can be compared.

### What an entry means

An entry is the diagnostic that the reference has for the condition that Bun's parser found. Bun finds errors with
its own grammar: where the reference decides in another place or has a more specific diagnostic, its first diagnostic
for the same file is another one. The list "Known differences" below names the cases that are known.

| Condition in Bun's parser | Message of Bun | Entry |
| --- | --- | --- |
| a token that the grammar requires is missing (`Lexer::expect`, `expect_contextual_keyword`, `expect_or_insert_semicolon`, `expect_greater_than`) | `Expected "x" but found ...` | TS1005 `'x' expected.` |
| a name is missing and the lexer is on a reserved word | `Expected identifier but found "class"` | TS1359 `Identifier expected. 'class' is a reserved word that cannot be used here.` |
| a name is missing | `Expected identifier but found ...` | TS1003 `Identifier expected.` |
| a string has no closing quote | `Unterminated string literal` | TS1002 `Unterminated string literal.` |
| a template has no closing backtick | `Unterminated string literal` | TS1160 `Unterminated template literal.` |
| a comment has no `*/` | `Expected "*/" to terminate multi-line comment` | TS1010 `'*/' expected.` |
| the token starts no expression (the last arm of `parse_prefix`) | `Unexpected x` | TS1109 `Expression expected.` |
| the same at the first token of a statement of a block, of a function body or of the file, unless the token is a binary operator | `Unexpected x` | TS1128 `Declaration or statement expected.` |
| the same for `default` at the top of the file | `Unexpected default` | TS1005 `'export' expected.` |
| the same for `catch` and `finally` | `Unexpected catch` | TS1005 `'try' expected.` |
| the token starts no type (the lint grammar) | `Unexpected x` | TS1110 `Type expected.` |
| a function or constructor type is an operand of `\|` or `&` (the lint grammar) | the text of the entry | TS1385, TS1386, TS1387, TS1388 |

### What a lint parse rejects that a parse without lint accepts

How the parser knows that it is a lint parse: "How a site knows which parse it is". The checks below are in the lint
grammar, which only a lint parse runs, or on a path that only an error takes. A parse without lint accepts, rejects
and logs what main does.

- A type that is missing inside an attempt. The skipper of main turns the log of the lexer off in an attempt and
  goes on as if the type stood, so a parse without lint takes `let x: (a: ) => void`, `f<A | >(x)`, `f<,>;` and
  `new A<B | >()`. The lint grammar records TS1110 for the missing type. If the attempt goes back, the message goes
  with it. If the attempt stays, the parse fails, as the reference fails when it keeps type arguments that it read
  with an error.
- `typeHasArrowFunctionBlockingParseError`: inside an attempt, a return type that is missing before `=>` ends the
  attempt, so `(a): => a` is no arrow function and the `:` is the error (TS1005 at the `:`).
- `parseFunctionOrConstructorTypeToError`: `A | () => void`, `| new () => A`, `A & <T>() => T`,

- `|` or `&` where `parseTypeOperatorOrHigher` reads a type is TS1110: `A & | B`, `| | A`, `& | A`, `keyof | A`.
  The skipper of main takes any run of these operators.
- `isListElement` of `PCTypeMembers` (type literals and what follows the mapping of a mapped type): a token that
  starts no member is TS1131 at that token, so `{ a A }` fails at `a` as in the reference, and not at `A`.

### How the table follows the log

The parser drops and restores messages of the log while it backtracks. A record holds the index of its message and
the address and the length of the text of the message. When the parse ends, a record counts only if the message at
its index still has that text, and the last such record of a message wins. So no backtracking site has to know the
table. A site that logs past the lexer inside an attempt must be one whose attempt truncates the log when it goes
back. [[FILL log-truncation: the attempts of the lint grammar that truncate the log, by name. At b882bfc32f: `restore_parser_snapshot`, the lexer backtrackers, `set_aside_failed_read`, `build_in_type`, and `lexer_backtracker_kept` only in a parse that has a side table (parse_skip_typescript.rs:3396-3428, `rewind_lint_attempt`). R1 puts the backtrackers of the skipper back to main's text]]

### Why the test binary needs stand-ins

A test binary of `bun_js_parser` links none of the C and C++ objects of bun. With one test that parses, the linker
reported 46 undefined symbols at `e3566be889` (`measure/base/cargo-test-undefined-symbols.txt`). A binary without
such a test links, because nothing in it reaches them. Miri is no way around the linker: a parse reads the stack
pointer with inline assembly (`bun_core::StackCheck`), which Miri does not run. `src/parsers` has a file of the
same name for its own tests.

`native_test_shims.rs` defines 57 symbols in Rust, each `#[unsafe(no_mangle)]`: the 46, and the others of the two
families that a change of the parser reaches first (the scans of `bun_highway`, the entry points of mimalloc).

| symbols | what the stand-in does |
| --- | --- |
| `Bun__StackCheck__getMaxStack` | a bound 1 MiB below the first call of the thread, and the same bound at every later call |
| `WTF__parseDouble` | the longest decimal prefix as fast_float reads it, parsed by `str::parse::<f64>` |
| 17 scans `highway_*` of bytes and substrings | scalar loops with the predicate of each kernel of `highway_strings.cpp` |
| 6 of `simdutf__*` | `validate_ascii`, `validate_utf8`, the two UTF-8 lengths of UTF-16, UTF-16 to UTF-8 with errors, base64 encode |
| 24 of `mi_*` | blocks of the allocator of the test binary, kept in a table by address: a heap is a number, and `mi_heap_destroy` frees the blocks of its heap |
| `__bun_macro_context_get_remap` | no path is one of a macro |
| `bun_cpu_features`, `getRSS`, `getPeakRSS`, `compress2`, `is_executable_file`, `bun_restore_stdio`, `on_before_reload_process_posix`, `mi_process_info` | what the crash reporter and a reload of the process link to: they report nothing, or fail |

What does not link: the visit pass. At the base a test of another crate that ran `Parser::parse` on TypeScript

`Bun__JSC__operationMathPow`). A test stays on `Parser::init`, `P::init`, `Parser::parse_only`,
`Parser::parse_for_lint` and what the parse pass calls. Where a later change makes the linker report a symbol, its
stand-in goes into that file. The 57 stand-ins are enough for every test of the crate at b882bfc32f.

## Memory: what an arena holds

Rule: a value that an arena holds owns no memory of the global heap, because an arena never drops it.

- Every node of `bun_ast::ts` and every record of the four tables is `Copy` (`ts::List<T>` by its own `impl`), so
  none can hold a `Vec`, a `Box` or a `String`. What they point to is in the arena or in the AST stores:
  `StoreRef`, `StoreSlice`, `StoreStr`, `Expr`, `Binding`, `Stmt`.
- `ErasedMemberData::Property` points to a `G::Property` in the arena. It is not `Copy`: it holds
  `ts_decorators: Vec<Expr, AstAlloc>`, whose buffer is in the AST allocation scope, as in every `G::Property` of a
  class that stays, and `ts_metadata`, which holds no heap memory since `be1ebe5295` (`Metadata::MDot` is a
  `StoreSlice<Ref>`).
- The lists themselves are `Vec`s of the global heap: eight in `Attached`, two public and one private in
  `ErasedTables`, two in `Generics`, one in `Wrappers`, three `HashMap`s, and `SyntaxErrors` (an entry holds a
  `Cow<'static, [u8]>`). They are in the `Box` on the parser and are dropped with it, or with the side table when
  `f` returns. [[CHECK memory-comments: after R5 (B1) add the lists of the comments, of the comment directives and of the pragmas]]
- The lint grammar gathers the items of a list in a `Vec` on the stack and copies them to the arena with
  `ts::List::from_slice`: the `Vec` is dropped where its function returns, also on an error.
