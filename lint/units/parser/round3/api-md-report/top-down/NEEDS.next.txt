## N3. No JavaScript reaches a lint parse in this worktree (`src/runtime`, owner: cli)

For: the test files `test/bundler/transpiler/lint-parse*.test.ts` that parser.md allows, and every check of the
lint parse that is to run with `bun bd test`.

Everything that JavaScript or a command line can call is in `src/runtime`, and nothing there calls
`Parser::parse_for_lint`. `Bun.Transpiler` and the one parser hook of `bun:internal-for-testing`
(`bytecodeOrderNames`, which ends in `Parser::parse_only`) run a parse without lint. So no test that `bun bd test`
runs can reach the lint grammar, `Parser::parse_for_lint`, the side table or a backtracking point of a lint parse,
and no file `lint-parse*.test.ts` exists.

The route is the command of the cli unit, `BUN_FEATURE_FLAG_EXPERIMENTAL_LINT=1 bun --lint <file>`
(`src/runtime/cli/lint_command.rs`): once it holds the call of N2, a test spawns it and reads what it prints. The
rows for that test are ready: `round3/tests-known-differences/bottom-up/lint-command-rows.json` and
`lint-parse-grammar.test.ts.draft` (the 366 cases of the four removed test files through the command; its
expectations are predictions until the command exists).

No binding of `bun:internal-for-testing` is asked for. One that printed the side table would need a printer of
every table in `src/runtime`, or a `pub` one in the parser that only that binding calls.

### Workaround on our side, in place now

The tests of the lint parse are `#[test]`s inside `bun_js_parser`, which see what is `pub(crate)`, and they run in
this worktree with `cargo test -p bun_js_parser --lib`: [[FILL tests-total: "<n> passed" at the final commit]]. The
366 cases that round 1 asserted through `Bun.Transpiler` are the rows of `src/js_parser/parse/grammar_rows_tests.rs`.
The test binary links because `src/js_parser/native_test_shims.rs` defines, in Rust and under `#[cfg(test)]`, the C
and C++ symbols that it links to. `API.md`, "How the tests of the parser run", has the commands and what the
stand-ins do.

## N4. No job of CI runs the tests of `bun_js_parser` (`.github/workflows/rust-lints.yml`, no unit owns it)

For the integrator. CI runs the `#[test]`s of a crate only in the job `cargo miri test`, for the crates of
`MIRI_CRATES` in `scripts/rust-miri.ts`. `bun_js_parser` cannot join that list: a parse calls
`bun_core::StackCheck::is_safe_to_recurse`, which reads the stack pointer with inline assembly (`frame_address` in
`src/bun_core/util.rs`), and Miri runs no inline assembly. The job `cargo clippy` type-checks the tests
(`cargo check --workspace --all-targets`) and runs none. Since round 3 this matters more: the 366 cases of the four
removed `bun:test` files, which CI ran, are `#[test]`s of this crate now, which CI does not run.

Needed: one step in the job `clippy`, after the step `cargo check --all-targets`:

```yaml
      - name: cargo test -p bun_js_parser
        env:
          BUN_CODEGEN_DIR: ${{ github.workspace }}/build/debug/codegen
        run: cargo test -p bun_js_parser --lib
```

The setup of that job builds the targets `codegen`, `clone-lolhtml` and `clone-rust-argon2` and installs clang and
lld, which is what the step needs: the test binary links no object of C or C++. The step was not run in CI.

### Workaround on our side, in place now

The same command in the worktree, after one `bun bd --version`.
