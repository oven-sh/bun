## What changed for a caller in round 3

Round 3 put a parse without lint back to the parser of main and gave the lint parse its own grammar. The shape of
`ParsedForLint`, of the four tables of the side table and of the type nodes is the one of round 1, with these
differences. Each is described in its section.

- A parse without lint is main again, byte for byte: what it accepts, what it rejects, every error text, every
  `emitDecoratorMetadata` value. The 366 cases that round 1 asserted for it are tests of the lint parse now, and what
  main does with them is listed in "Known differences of a parse without lint".
- `EXPECTED_VERSION` of the runtime transpiler cache is 33 again: the output of the transpiler does not change.
- `TypeSink::STRICT` is gone, with `BUILDS`, `Sub` and `K`. A site asks the side table, not the sink ("How a site
  knows which parse it is").
- [[PICK parens: the decision on parentheses records. Check: the case of a `.js` source in wrappers::tests::records_are_those_of_the_known_sources, and `grep -n "starts_for_parse_only\|fn lint" src/js_parser/parse/parse_prefix.rs` around pfx_t_open_paren]]
  Parentheses: a lint parse of TypeScript records every pair of parentheses around an expression, as before. A lint
  parse of JavaScript records none: `wrappers.records` is empty for a `.js`, `.jsx`, `.mjs` or `.cjs` file. A pass
  that needs the parentheses of a JavaScript file reads the tokens between two nodes.
  [[OR]]
  Parentheses: no parse records them. `WrapperData::Parenthesized` is never made, in TypeScript and in JavaScript: the
  site is the `(` that starts any expression, which every parse runs. A pass that needs parentheses reads the tokens
  between two nodes.
  [[END]]
- A lint parse of JavaScript fills none of the four tables ("What a lint parse of JavaScript records").

  Some valid TypeScript that round 1 read is read by a lint parse as main reads it, because its site is one that
  JavaScript reaches: "Known differences of the lint grammar" lists the sources.
