== 6. THE SMALL PORT FOR ParseIsolatedEntityName (jsx.go:1435-1447, parser.go:282-289) ==
Callers: getJsxNamespace (compilerOptions.JsxFactory, the @jsxfrag pragma argument), getLocalJsxNamespace (the @jsx pragma argument), getJsxFragmentFactoryEntity (pragma, compilerOptions.JsxFragmentFactory). The result is used for: the first identifier's text (the namespace name that TS2874 and TS2879 look up), the whole tree in c.resolveEntityName(factory, Value, ignoreErrors, false, node) and entityNameToString(factory) inside checkApplicableSignatureForJsxCallLikeElement (TS6229), and the emit resolver. So a real name tree is needed, not only the first name.
Upstream: a fresh parser state over the string with ScriptKindJS (context flags = NodeFlagsJavaScriptFile, JSX language variant), nextToken(), parseEntityName(allowReservedWords = true, allowPrivateName = false, no message), and the result counts only when the current token is EndOfFile AND no diagnostic was produced (scanner errors are routed into the same list). Then markAsSynthetic sets Loc = (-1, -1) on every node of the tree.
Port (in checker/jsx.rs, about 40 lines, with the K1 scanner): set the text; tok = scan(); name(): if tok >= Kind::Identifier (identifiers and every keyword) take token_value (the unescaped text), scan, create an Identifier; otherwise fail. entity = name(); while tok == Dot { scan; if tok == LessThan break; if tok is a private identifier fail; right = name(); entity = QualifiedName(entity, right) }. Result = entity when tok == EndOfFile and the scanner reported no error and nothing failed, else none. Nodes go into the checker's node overlay with kind, parent links, text, Loc (-1, -1) and NodeFlagsJavaScriptFile. Comments and white space are trivia (`React /*x*/ . createElement` is valid); `a.` , `a b`, `a.<`, `a.#b`, `1a`, an unterminated comment are invalid. The upstream rule `identifier after a line break followed by another identifier on the same line` only fires when more tokens follow, which is invalid anyway, so it needs no code. The keyword-with-escape check of nextToken cannot fire on this path (identifier names are consumed with nextTokenWithoutCheck).
On an invalid string the callers fall back: c._jsxNamespace stays "React" and c._jsxFactoryEntity becomes the synthetic React.createElement (jsx.go:1383: NewQualifiedName(NewIdentifier, NewIdentifier), not marked synthetic). Verified: jsxFactory `h.create` removes the TS2874 errors; jsxFactory `h create` gives the same output as no factory plus TS17016.

== 7. JAVASCRIPT AND JSDOC SCOPE ==
The reference reparses JSDoc into ordinary nodes in its PARSER (parser/reparser.go, 748 lines): type annotations, type parameters, modifiers, optional markers and overload signatures appear as normal nodes with NodeFlagsReparsed, @typedef and @callback as KindJSTypeAliasDeclaration, `@import` as KindJSImportDeclaration. At this commit there is no KindJSExportAssignment and no KindCommonJSExport; module.exports and exports.x are binary expressions bound with SymbolFlagsModuleExports and assignment declaration kinds. The checker therefore has no JavaScript layer: 148 functions of the package carry JavaScript or JSDoc branches (data/js-sites.tsv), 42 of them in the 20 layers. They are ported with their functions; nothing is left out.
What these layers do for JavaScript and JSDoc:
 - checkSourceElementWorker: EagerJSDoc and {@link} resolution (any file); the two JS declaration kinds; the JSDoc type kinds.
 - D-JSDOC: checkJSDocTypeIsInJsFile (errors only in TypeScript files); checkUnmatchedJSDocParameters (TS8024 error in JavaScript, suggestion in TypeScript; TS8029 and TS8032 JavaScript only), getAllJSDocTags.
 - D-FUNC: FunctionLikeData.FullSignature (a reparsed `@type {function}`) with TS8030; duplicate function implementations are not reported in JavaScript (3438); reparsed overloads are exempt from the adjacency rule (3642).
 - D-CLASS: checkJSDocAugmentsTagMatchesExtends (TS8023); the JSDoc wording of the override messages (4801-4850).
 - D-IMPEXP: import and export context messages differ in JavaScript; checkAliasSymbol 6841-6872 (TS18042, TS18043 with related TS18044); checkExternalModuleExports ignores repeated exports.x assignments; `require` variable declarations are aliases (5976).
 - D-UNUSED and G-GRAMMAR: JSTypeAliasDeclaration and JSImportDeclaration in the kind lists; reparsed modifiers skip the order errors; a reparsed `?` token means a bracketed @param name (grammar 711).
 - T-JSDECL: section 4.
 - Driver level, outside the unit: whether a JavaScript file is checked at all, the plain JavaScript code filter, the JSDoc diagnostics.
In TypeScript files the JSDoc is parsed lazily: only comments containing @see or @link are parsed at parse time (they feed the unused check), the rest on the first node.JSDoc(file) call (deprecation suggestions, the @param name suggestion). Error output of a TypeScript file depends on JSDoc in exactly two ways in these layers: a {@link} reference silences TS6133 and TS6196 under noUnusedLocals (verified on unused.ts), and JSDoc type syntax in a type position (`?T`, `T!`, `*`) gives TS17020, TS17019, TS8020 (verified on jsdoc_ts.ts), which needs the JSDoc type node kinds in the tree.
For the importer this means: a TypeScript 6.0.2 tree of a JavaScript file is NOT the reference's tree (ts-dump-and-test-importer measured 512 of 1,276 JavaScript units different). JavaScript instances stay provisional until the importer or the lowering reproduces the reparser; the checker code is the same either way.
