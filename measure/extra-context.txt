Design picked before the code was written: filereader-onread-arm (FileReader's read completion calls a registered JS callback through the event loop; child stdout/stderr get no pull promise and no push inside _read()), because it is the only candidate that prevents the unwanted operation (a user 'data' listener running under NativeReadable's pull reaction or under flow() driven by a pulling _read()) and the only one whose per-chunk cost is below main's. Why not the minimal patch: a catch around the pull reaction or an own `emit` compensates instead of preventing; it keeps the promise, adds a frame per event, stops a manual emit('data') or read() from throwing to its caller, and guards one of two emit sites. A process.nextTick push loses chunks for a listener that re-attaches from a promise job and emits 'end' before an async listener's continuation. An fd-backed net.Socket (requested on #36316) costs +18 syscalls per spawn, loads node:net, and is POSIX only.

Requirements the diff must keep (each has a test or fixture):
R1. No 'uncaughtException' handler: the throw is fatal (exit code 1), the listener is called once, and neither 'end' nor the child's 'close' follows (a wrapper that does child.on('close', code => process.exit(code)) must not exit 0).
R2. A listener that removes itself and comes back from a promise job loses no chunk.
R3. 'end' does not come before an async listener's continuation.
R4. Readable.fromWeb over a fetch body keeps the unhandledRejection channel (only child stdio opts in to the callback).
R5. No extra tick or promise per chunk.

Where the diff departs from the design plan, on purpose. Check these hardest:
(a) Process lifetime is kept as on main, not as in Node. The source reads from spawn on (as Node does), but the reader is unref'd until the stream's first _read(), and what it reads before that waits in a JS list (kUnread in native-readable.ts), not in the Readable's buffer. Reason: pushing into the Readable before anything reads makes Readable call _read() itself (maybeReadMore), so _read() would stop being the signal that something reads the stream. Measured with an unref'd `sleep 2` child: untouched pipes: Node 2 s, main 0 s, this diff 0 s; 'data' / 'readable' / pause(): 2 s on all three. The repo rule is .claude/docs/landing-prs.md 'Never silently break existing users' and 'Never let user-visible behavior change as a side effect of unrelated work'.
(b) After a read callback throws, the source does not ask whether the report 'ends the run'. It pauses its reader, and a task queued with EventLoop::enqueue_task_after_yield starts it again on the loop's next turn (FileReader::wait_for_next_turn, waits_for_next_turn). An end or a read error that arrives on the turn of the throw is held and reported by that task. So a run that ends at the error (bun run, bun -e) calls no listener again, and a run that goes on (--hot, an immediate, a pending top-level await, bun test, the REPL) loses nothing. An earlier version of this branch added VirtualMachine::uncaught_exception_ends_run plus state in VirtualMachine.rs, repl.rs and Task.rs to predict this; that is removed.
(c) Known residual, unchanged from main: a listener attached in the child's 'exit' gets what was read before it from flow() inside a tick. A fatal throw there is followed by 'end' and 'close' on main and with this diff, because ticks run on after a fatal report in every such case in Bun. Node ends the process at the throw. A test that pinned Node's result there was removed as out of scope.
