### What happens

One install removes an `npm:` alias and adds a package that depends on the same name. The package that the new dependency gets depends on the lockfile format. `bun install` exits 0 and prints no warning.

```
# package.json at the first install
{ "name": "app", "version": "1.0.0", "dependencies": { "kept": "npm:short@1.0.0" } }

# package.json at the second install
{ "name": "app", "version": "1.0.0", "dependencies": { "new-dependency": "1.0.0" } }
```

The registry has `kept@1.0.0`, `short@1.0.0` and `new-dependency@1.0.0`. `new-dependency` depends on `kept@^1.0.0`.

| Lockfile from the first install | `node_modules/kept` after the second install | Manifests that the second install requests |
| --- | --- | --- |
| `bun.lock` | `kept@1.0.0` | `/kept`, `/new-dependency` |
| `bun.lockb` | `short@1.0.0` | `/new-dependency`, `/short` |
| `package-lock.json` (npm 11.16 wrote it, bun migrates it) | `short@1.0.0` | `/new-dependency`, `/short` |
| none | `kept@1.0.0` | `/kept`, `/new-dependency` |

- The results are the same when a registry package holds the alias (`has-alias@1.0.0` depends on `"kept": "npm:short@1.0.0"`) and the second install replaces `has-alias` with `new-dependency`.
- bun saves the result. `bun install --frozen-lockfile` then reports no changes.
- npm 11.16 with its own `package-lock.json` keeps `short@1.0.0` in `node_modules/kept` in both cases. It requests only `/new-dependency`.
- `yarn.lock` is not in the table. `bun install` fails for a `yarn.lock` that has no entry for a dependency of package.json (`error: new-dependency@1.0.0 failed to resolve`), with or without an alias.

Seen on bun 1.4.3-canary.1 (367d939d9) and on main at a4f1429148. #44294 does not change these results.

### Cause

`PackageManager::known_npm_aliases` maps a dependency name to the last `npm:` alias that bun read under that name. `enqueue_dependency_with_main_and_success_fn` (`src/install/PackageManager/PackageManagerEnqueue.rs`) sends a plain dependency of that name to the alias target when the alias version is in the range of the dependency.

- The loader of `bun.lockb` (`buffers::load` in `src/install/lockfile/Buffers.rs`) and the migration of `package-lock.json` register the alias of each dependency row. The loader of `bun.lock` registers no dependency row.
- Nothing removes an entry when the install drops the row that held the alias. The new dependency resolves while the entry is still there.
- #44294 moves the registration out of the loaders into `Lockfile::record_dependency_row_aliases`, which bun calls when it keeps a `bun.lockb` or a migrated lockfile. It keeps the difference between the formats.

### Decision needed

Which package does bun want in `node_modules/kept`?

1. The alias target, for every lockfile format. npm gives this result: it keeps the package that the lockfile has under that name when its version is in the range. The loader of `bun.lock` must then register its dependency rows, which changes the first row of the table.
2. The registry package, for every lockfile format. `bun.lock` and an install with no lockfile give this result. There are two ways to get it:
   - No lockfile row registers an alias. A new dependency then also does not follow an alias that a locked registry package still holds. `bun.lock` behaves like this today. After #44294 this is the removal of `Lockfile::record_dependency_row_aliases` and its two calls.
   - Only the rows that package.json still reaches register an alias. This needs a walk over the lockfile before the first resolve.
3. Keep the difference between the formats.

Related work:

- Draft #36476 removes the alias map and asks for a decision on the same question (its note "Name-blind binding").
- #43375 builds the map again from the rows that the install reaches, but only after the first resolve.

### Workaround

Make the edit in two installs. Remove the alias and run `bun install`. Then add the new dependency and run `bun install`. With `bun.lockb`, the second install then puts `kept@1.0.0` in `node_modules/kept`.
