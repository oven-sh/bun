### What happens

A command that resolves a dependency row again, right after bun migrated yarn.lock, can request a wrong package name. The row is an `npm:` alias that a package of yarn.lock declares, and the target name is over 8 bytes.

```
# package.json
{ "name": "app", "dependencies": { "has-aliases": "1.0.0" } }

# yarn.lock (yarn v1)
"dependency-of-some-other-package@npm:some-other-package@1.0.0":
  version "1.0.0"
  resolved "<registry>/some-other-package/-/some-other-package-1.0.0.tgz#<sha1>"
  integrity <sha512>

has-aliases@1.0.0:
  version "1.0.0"
  resolved "<registry>/has-aliases/-/has-aliases-1.0.0.tgz#<sha1>"
  integrity <sha512>
  dependencies:
    dependency-of-some-other-package "npm:some-other-package@1.0.0"
```

```
$ bun update dependency-of-some-other-package
migrated lockfile from yarn.lock
error: GET <registry>/:%2f%2flocalhost:PORT - 404
error: dependency-of-some-other-package@npm:some-other-package@1.0.0 failed to resolve
```

- With a target name of 8 bytes or less (`npm:short@1.0.0`), the same command exits 0.
- `bun install` and `bun update` with no name exit 0 in this project. They keep the package that yarn.lock binds to the row.
- With the alias in the root package.json, the command exits 0. bun reads that row from package.json.

Seen on bun 1.4.3-canary.1 (367d939d9) and on main at a4f1429148. #44294 does not change this result.

### Cause

The yarn.lock migration parses a dependency row with the version literal as its own string buffer: `SlicedString::init(literal, literal)` in `src/install/yarn.rs` (lines 1635, 1707, 1759, 1811 and 1863 on main, and line 573 in `process_deps`).

`Dependency::parse` stores a string over 8 bytes as an offset into the buffer it gets (`sliced.sub(...)` in `src/install/dependency.rs`). The offset is then relative to the literal, and not to `lockfile.buffers.string_bytes`. The migration sets `version.literal` again after the parse, so the literal is right and the name of the alias target is not. A reader slices that name from `string_bytes` and gets other bytes. In the output above they are a part of the registry URL.

Other rows parse against the lockfile buffer: `version_string.sliced(this.buffers.string_bytes.as_slice())` at `yarn.rs:1175`, and `npm_lock.rs:679` for package-lock.json.

From a read of `Dependency::parse`, the same holds for each string that it slices from such a row: a git or GitHub reference, a tarball URL, a folder path, a dist-tag over 8 bytes. I ran only the alias case.

### Possible fix

Append the literal, then parse it with `literal.sliced(this.buffers.string_bytes.as_slice())`. The assignment to `version.literal` after the parse is then not necessary.

### Workaround

Run `bun install` first. It saves bun.lock, and later commands read the rows from bun.lock. `bun update dependency-of-some-other-package` then exits 0 and requests `/some-other-package`.
