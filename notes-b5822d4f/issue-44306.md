### What happens

`bun update --latest` moves a package past the version of its catalog entry when only an override refers to that entry. The catalog entry keeps the old version in package.json and in bun.lock.

```json
{
  "name": "app",
  "version": "1.0.0",
  "workspaces": { "packages": [], "catalog": { "kept": "1.0.0" } },
  "dependencies": { "parent": "1.0.0" },
  "overrides": { "kept": "catalog:" }
}
```

The registry has `kept@1.0.0`, `kept@1.1.0` and `parent@1.0.0`. `parent` depends on `kept@^1.0.0`.

```
$ bun install
$ bun update --latest
^ kept 1.0.0 -> 1.1.0

1 package installed
```

After the update:

- package.json still has `"catalog": { "kept": "1.0.0" }`.
- bun.lock has `"catalog": { "kept": "1.0.0" }`, `"overrides": { "kept": "catalog:" }` and the row `"kept": ["kept@1.1.0", ...]`.
- `bun install --frozen-lockfile` reports no changes.

`docs/pm/overrides.mdx` says that `catalog:` "keeps the overridden version in sync with a workspace catalog".

When a dependency also refers to the entry (`"dependencies": { "kept": "catalog:" }`), the same command writes `1.1.0` to the catalog entry in package.json and in bun.lock. The entry and the row then agree.

The result is the same with `resolutions` and with a named catalog (`catalog:g`). Seen on bun 1.4.3-canary.1 (367d939d9) and on main at a4f1429148, with bun.lock and bun.lockb.

### The alias form

With `"catalog": { "kept": "npm:short@1.0.0" }`, main and 1.4.3-canary.1 print `(no changes)` and keep `short@1.0.0`. That is not a rule of `update --latest`: the loader of the lockfile registers the alias of the catalog entry, and the row follows that alias before bun reads the override.

#44294 removes that registration. With it, the alias form gives the same result as the plain form: `^ short 1.0.0 -> 1.1.0`, and the catalog entry stays `npm:short@1.0.0`. A change for this issue needs a test for the alias form too.

### Cause

For `--latest`, `PackageJSONEditor::edit_catalogs_before_update` (`src/install/PackageManager/PackageJSONEditor.rs:683`) writes `latest` to each catalog entry in memory. After the install, `edit_catalogs_after_update` (line 755) writes the new version to each entry, and gives an entry that it cannot resolve its first text back.

`resolve_catalog_literals` (line 860) reads only the dependency rows whose own version is `catalog:` (line 880). A row that gets the entry through an override is not one of them. So the row resolves with the temporary `latest`, and the entry gets its first text back.

### Expected

One of these two:

1. The catalog entry gets the new version, as it does when a dependency refers to it.
2. The row stays at the version of the catalog entry.

### Workaround

After the update, write the new version to the catalog entry by hand.
