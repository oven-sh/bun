# `bun fmt`

A formatter for JavaScript, JSX, TypeScript, JSON, CSS, Less, SCSS, GraphQL, YAML, Markdown and MDX whose output is byte for byte that of Prettier. The target is the released **3.9.9**: its source, its snapshots, and the npm package as an oracle.

**The one exception: what is written means what the file means.** Where the output of Prettier or oxfmt is another program, template or document, the printer here prints the right thing, in every flavor: what the tool would have to print, formatted like what is around it, or, where nothing is clearly right, the smallest node around the place as it is written. Nothing is parsed again to find that out: the rule is in the printer, next to the code that it corrects, with a comment that says what the tool prints. It applies to nothing but the inputs that the tool damages, so no fixture of theirs moves. A row in `test/cli/format/format.test.ts` has the input, what is printed, and what the tool prints.

**Formatting the result again changes nothing, where that is a matter of one decision.** An object type that is broken in the source stays broken, so one that breaks because it does not fit `will_break()` the next time. Prettier and oxfmt ask that of the return type to lay out the only parameter of a function, and print `m(⏎a: string,⏎): {` first and `m(a: string): {` from then on (prettier#19968). What is printed here is the second: `write_parameters_and_return_type` in `js/print/function.rs`. Where the tools print the same both times, so does `bun fmt`. See "Variants that are tried" below.

- **The specification is Prettier**: `src/language-js/**`, `src/document/**`, `src/main/comments/**`, and its snapshot tests, `tests/format/{js,jsx,typescript}/**/__snapshots__/format.test.js.snap`.
- **The code is a port of oxc's formatter** (`crates/oxc_formatter_core`, `crates/oxc_formatter`), which is a port of Biome's, which is modelled on Prettier. Where oxc deviates from Prettier, Prettier wins. Both are MIT licensed. See the crate docs in `lib.rs`.
- **There is no AST of its own**. It prints straight from the type checker's HIR through the handles of `bun_lint::ast` (`src/lint/CLAUDE.md` has the table ESTree → handles).

Not there: Astro, Babel-only proposals, plugins. CSS, GraphQL, Markdown and HTML in templates are formatted: `css/embed.rs`, `graphql/embed.rs`, `markdown/embed.rs`, `html/in_js.rs`, and `js/quick_guests/` for the quick way.

**Flow.** A file is Flow if `--parser flow` or `babel-flow` says so, if a comment before its code has `@flow` or `@noflow`, or if it is called `.js.flow` (`bun_lint::linter::is_flow_file`). The caller picks the dialect: `Dialect::flow_parser` for Prettier's `flow`, `Dialect::flow` for `babel-flow`, for which `flow::uncommented` first makes code of `/*:: */` and `/*: */`. The HIR has no node of its own for Flow: `src/sema/parser/parser/flow.rs` has the table of what stands for what, `src/lint/ast/flow.rs` tells the nodes apart, `js/print/flow.rs` has all that is printed differently. The functions for the nodes of TypeScript call it behind `f.file().is_flow()`, after the dispatch on the kind of node: a file that is not Flow pays one load where a hook is. `<T extends A>` and `<T: A>` stay as they are written with either parser: with Babel's, Prettier prints `<T: A>` for both. Tests: `--languages=flow`.

## The pipeline

```
File (HIR + binder tables)                     bun_lint::ast. The parser has recorded the nodes around each comment
  └─ js::comments::for_file   → FileComments    which node owns each comment: js/attach/
  └─ js::format_file         → [FormatElement] the document (IR): ir/element.rs
       └─ ir::document::Tracker                told about each element as it is written: a group with a forced line
                                               break in it is broken, every other group is measured
  └─ ir::printer::print    → bytes           decides which groups fit on the line
```

`range.rs` has the entry point, `format_with_cursor(file, &options, &mut scratch, &mut out, parse)`. `Scratch` (`ir/run.rs`) holds every buffer, so that formatting the next file allocates nothing.

**Most scripts never get there.** The driver first asks the quick way, which goes from text to text on its own: see "JavaScript: the quick way" below.

**No walk finds the parents.** The instance of the parser that the formatter uses (`Parser::CLAIMS`) reports each expression, statement and type to `bun_sema::bind::Claims` where it adds the node. There the kind of the node is known at compile time, so a node "claims" its children with a few stores, where a walk over the finished lists mispredicts a branch per node. `try_bind_for_format_with` adds what the records say (functions, classes, members, declarations) and hands the lists to the binder's tables. The parents of types go to `File::set_type_parents`. A file that another instance has parsed (Flow, a syntax error) is walked: `fill` in `src/sema/bind/parents.rs`, `Parents::new` in `src/lint/ast/node.rs`. **Whoever adds a kind of node, or a child to one, changes the walk and `claims.rs`.** A debug build compares the two for every file.

What a caller does with a file, in this order, is `format_for_tests` in `src/lint/driver/fmt/mod.rs`: JSON, style sheets, GraphQL, YAML and Markdown by `options.parser` or the name of the file (`json::format`, `css::format`, `graphql::format`, `yaml::format`, `markdown::format`: they take text), `pragma::before_parsing`, parse as a module and, if that fails, as a script, `sort_imports::sorted_text`, `range::format_with_cursor`.

**Import sorting** (`js/sort_imports/`, option `FormatOptions::sort_imports`, compiled once per run from `sort_imports::Settings`) has five flavours. `@trivago`/`@ianvs` `importOrder*` and prettier-plugin-organize-imports are text → text preprocessors in Prettier, so they are here too: `sort_imports::sorted_text(file, how)` gives the text that has to be parsed and formatted instead of the file, byte for byte the plugin's (`babel.rs`: @babel/parser's comment attachment over the HIR, `generator.rs`: @babel/generator's printer for imports, `trivago.rs`/`ianvs.rs`: the plugins, `organize.rs`: TypeScript's organizeImports and textChanges), or `None` if formatting the file as it is gives the same (`layout.rs`): only a file whose imports move is parsed twice. oxfmt's `sortImports` (`oxfmt/`) happens inside `format`: `FormatStatements` tells an `ImportRun` what it is about to write, a run of imports is captured and written as `Interned` sub-ranges, one per line, in sorted order. `sortImports` from bunfig.toml or `--sort-imports` (`How::Native`) runs oxfmt's sorter with two additions. Side-effect imports act as barriers, and `native.rs` sorts the names inside braces and merges imports from the same module. `native.rs` is a text → text pass too, so both `sorted_text` and `format` do part of the work. oxfmt moves every comment directly above the first import along with it. Here those that are about the file by their text (a pragma, a directive for a linter, a license: `bun_lint::fix::is_file_level_comment`, which `--fix` goes by too), and all comments above them, stay on top, as they do with the three plugins. The driver checks the result with `SortImports::keeps_imports`. Tests: `test/cli/format/sort-imports`, made by `test/cli/format/oracle/sort-imports/`, and `test/cli/format/sort-imports.test.ts`, which has no oracle.

## Style sheets, YAML, Markdown: the other printer

These three are ports of Prettier's own printers, which count on what `printDocToString` does step by step (two line breaks in a row are an empty line, `dedentToRoot`, how a `fill` measures), so they do not print with `ir/`. `css/doc.rs` has `Elements`, the parts of a document one after the other in one list, and `printDocToString`, `fits` and `fill` on it. `Doc` is the tree, for who takes documents apart (Markdown, embedded code). `doc::print` writes it to `Elements`. There is one printer.

The printer for style sheets returns no documents. It writes operations (text, lines, start and end of a group, indentation, items of a `fill`) to `css/sink.rs`. **There is one implementation of every rule, and two ways to take what it writes.** At first the sink writes straight to the output: outside of groups a line is a line break, inside everything is on one line. That is what Prettier prints if the line fits as a whole. If it does not, or a group has something in it that is more than its content on one line (a forced break, a line suffix), `Sink::end_unit` says so, what has been written of the statement is taken back, and the printer writes the statement again, to `Elements`. So writing a statement must have no effect but what it writes.

`css/memo.rs` keeps, per thread and up to 1 MB, what a declaration was printed as on one line, and writes that again for the same declaration. Half of the declarations of a style sheet are repeats. A mistake here makes the output of a file depend on the files that the thread has formatted before, which no fixture shows. Therefore:

- **The key has to hold everything that the printed line depends on**: the text of the declaration, all of it (`Printer::memo_text`), and `Printer::memo_context`: the syntax, `singleQuote`, `trailingComma`, the flavor, the name of the at-rule around it, and whether it is in an ICSS rule, a Less variable, a nested property of SCSS. **Whoever makes the printing of a declaration look at one more thing (an option, an ancestor, a sibling, text outside of it) adds that to the key, or keeps such declarations out of the memo.** The width is not in the key: a hit is measured at the end of its line like everything else.
- Nothing is kept of a declaration with a comment, a line break or a block, of one that failed, or of a style sheet that is written as a document. The style sheets of a file of HTML have a memo of their own, for that file.

**`css/quick/` prints most statements while the parser reads them.** Before `postcss.rs` asks for the tokens of a statement, `Parser::read_known_statements` looks at its text. Most of a style sheet is written in a few small languages: `value.rs` (words, numbers, strings, calls, lists, maps), `selector.rs`, and the heads of at-rules in `mod.rs`. For a statement in one of them, one scan finds where it ends and what is printed for it. `layout.rs` has the line breaks of a value that does not fit: what `value_groups.rs` and `doc.rs` do together, in closed form. Everything else is refused and goes the long way (tokens, nodes, `parse.rs`, the printer), so the long way stays the one description of what is printed. What is known takes one of two forms:

- A **run** (`Kind::Run`): statements in a row are one node and one text in `Tree::extra`, which the printer copies. A block that is closed and has nothing in it but a run becomes part of the run around it. Only what is printed the same whatever is next to it is in a run: `Parser::is_alone` (no comment on its line, no `@else`, no stray `;`), not after `prettier-ignore`.
- A **node with `Node::printed`**: the fields that `postcss` gives it, all of them, and the text. `Shape` says when the text holds. The printer takes it then, and prints the node the long way otherwise.

`Parser::read_standing_lines` is a shorter way to the same runs: for lines that are in the source as they are printed, indentation and all, and are of the simplest kinds. Each `end_of_simple_*` takes a part of what the scanner next to it takes.

- It is off with `--no-short-cuts`, which also turns off the memo, in the oxfmt flavor, with front matter, with `sortTailwindcss`, and for a style sheet that is written as a document. In a file of HTML, `layout.rs` is not asked. If the printer finds a run where it cannot copy it, `Quick::is_refused` is set and the file is formatted again without.
- To skip tokens, the tokenizer has to be where it would be: nothing handed back, no `url` or unclosed parenthesis that it has looked ahead for. `read_known_statements` asks.
- **Whoever changes how something is printed asks whether `quick/` takes it.** The languages are closed, so a new rule for what they refuse needs nothing. A rule for what they take is written twice, or what it is about is refused from then on. What the printing of a statement depends on outside of the statement is in `Block` (the at-rule around it by name, a declaration around it) and in `Quick::start` (the options).
- `test/cli/format/short-cuts.test.ts` has what was printed in another way once. What finds such things is a fuzzer that formats with and without `--no-short-cuts`: windows of real style sheets with damage, made-up statements, the output of the long way with damage, all with extreme options.

## YAML: plain lines are printed while they are read

With `proseWrap: "preserve"` nothing in a block mapping or sequence of one-line scalars depends on the width. What is printed is the text, line by line, with regular indentation, one space where there were several, the preferred quotes, at most one empty line. `yaml/direct.rs` does that without tokens, tree or document: one scan over the lines with a stack of the open collections (the column of their items in the source and in the output). Stretches of the source that stay are copied as a whole: a text that is formatted is one copy. `yaml::format` tries it first, so it also serves front matter and code blocks in Markdown and HTML. `yaml::document` (front matter of style sheets and Handlebars) does not.

- **Whatever is not certain is refused**, and the whole text goes through parser, tree and printer: explicit keys, tabs, directives, `...`, odd indentation, every syntax error, `# prettier-ignore`, the flavor of oxfmt, other values of `proseWrap`, and each place where a comment changes how its owner is printed. `print_comments` has the rules of `attach_comment` and `take_end_comments` for comments on lines of their own. **Whoever changes what `ast.rs` or `printer.rs` do with comments, empty lines or scalars changes `direct.rs` too**, or makes it refuse.
- **An item whose value is something else goes the long way by itself** (`delegate`): a scalar over several lines, a flow collection that does not fit, properties. `key: value` with the lines below it that are indented further is parsed as a document of its own, and `Printer::print_only_item` prints it at the column of the key. Not with a comment on a line of its own or a block scalar in it.
- **`plain_lines` is the loop for the most common lines.** It does what the loop of `run` does and nothing else. It reads no bytes in a loop: `bun_highway::YamlMarks` has one bit per byte for control characters, spaces, `:`/`#` and quotes, found by one kernel call per text, and a line is judged from 57 bits of each.
- Only three things are measured, and only for ASCII: a flow collection on one line, `key: |`, and the key of `key: # comment`.
- `FormatOptions::no_short_cuts` turns it off. `test/cli/format/short-cuts.test.ts` compares the two ways. Fixtures and real files find little here. What found the mistakes: damaged files, stretches of files and made-up documents with comments in every column, formatted both ways in one process, some million cases per minute.

## JSON: what is written is compared with the source

`json/writer.rs` writes a document without comments from the tree. Before it copies anything it looks whether the source goes on with the same bytes (`Writer::goes_on_with`, `put_source`), and only moves the end of the stretch that is still to be copied. A document that is formatted is copied once, at the end. One that is indented differently costs two copies per line. `no_short_cuts` makes every comparison fail.

## GraphQL

```
text ─ parser.rs ─→ Tree ─ comments.rs ─→ who owns each comment ─ printer.rs ─→ the document of ir/        the long way, and templates
text ─ tokens.rs ─→ [Token] ─ direct.rs ─→ bytes                                                           a file
```

The tokens of a text are printed in their order, nearly all as they are written, and what is between two of them follows from the grammar. So `direct.rs` has the grammar and the rules of the printer in one: it looks at a token, decides what goes before it, and writes both. **It is a second implementation of `parser.rs` and `printer.rs`: whoever changes a rule there changes it here, or makes `direct.rs` refuse.** It accepts nothing that `parser.rs` refuses. `--no-short-cuts` turns it off, `test/cli/format/short-cuts.test.ts` compares.

- **Three ways to write**, and what one is not sure about goes to the next. Straight to the output with every group on one line. If that does not fit, or a line break is forced in a group: a list in brackets is written on lines (whatever follows the group, it breaks), anything else is a `unit` that is read again and written to the `Elements` of `css/doc.rs`. A definition with anything else in it (a comment that is not between two items, a syntax error, a string that is not printed as Prettier prints it) is parsed by `parser::parse_definition` and printed from its tree. `# prettier-ignore`, what is nested more than 64 deep and every error of the long way give up the text.
- **Nothing is copied token by token.** As long as the text between two tokens is what would be written there, they join a run of the source, which is copied in one piece. A formatted file is one run.
- **No token waits for another.** `tokens::scan` finds all tokens first, from the bitmaps of `bun_highway::ScannerStops`. Reading a token where the last one ends is a chain of loads that took 40 % of the time.
- **Comments** between two items of a block, of a list in brackets that is on lines, and between definitions are written where `comments::attach` and `Builder::print` put them: `Direct::end_item`. A token that is taken with a comment before it refuses the definition, so an item that goes on behind a comment is never taken for two.

## Handlebars: a template is printed while it is read

```
text ─ lexer.rs ─→ [Token] ─ parser.rs ─→ [Statement] ─ tokenizer.rs ─→ Tree ─ printer.rs ─→ the Elements of css/doc.rs        the long way
text ─ direct.rs ─→ bytes                                                                                                      a template, but for the parts that are refused
```

Most of a template is written in a small part of the language: elements with plain attributes, words, mustaches and blocks with paths, strings and numbers, comments. For that part `direct.rs` has the grammar, the rules of `printer.rs`, and what `css/doc.rs` makes of the document, in one scan. The indentation is the number of elements, blocks and groups that are open. **It is a second implementation of `printer.rs`: whoever changes a rule there changes it here, or makes `direct.rs` refuse.** `--no-short-cuts` turns it off, `test/cli/format/short-cuts.test.ts` compares.

- **A group is written on one line first** (`Mode::Flat`), which ends where the line is full. If it does not fit, together with what follows it up to the next possible line break (`Rest`), what has been written is taken back, and the group is written with its line breaks (`Mode::Free`), in which the groups in it decide for themselves. If the source has a line break where the group has its first one, it is the other way round, and `Direct::flat` tells how wide the group would have been: what is formatted is read once.
- **The rest of the document is in broken groups**, so the first `line` of any kind ends it: all white space, what is behind the name of a start tag or a block, what is behind the path of a mustache with parameters. `nodes_fit` reads that far and no further.
- **The children of an element, a block or the template are a group too**, but only the white space between two nodes depends on it: what is in a group that fits decides to be on one line by itself. So nothing is decided before the first such white space (`free_list`), and nothing at all if it has a line feed in it.
- **What is not certain is refused, and goes the long way by itself** (`delegate`). Nodes with white space in front of them and behind them, among nodes that are on several lines, are printed between two line breaks. They are parsed as a template of their own, and printed at their indentation. Where they end is found roughly (`end_of_nodes`): a text that parses is a list of whole nodes. If they have no white space around them, what is around them is refused, up to the template. A start tag or a `{{#a}}` with a line feed behind it goes alone (`delegate_head`), so that one odd attribute does not take all of an element along.
- **What a part depends on outside of itself, or the other way round, gives up the template**: `{{! prettier-ignore }}` is about the next node but one, which has to be in the part, with the white space at its end if it is a text. White space between two words is not between two nodes. After an escaped mustache, the lexer makes a text of their own of the backslashes in front of the next one. A string ends at a quote with a backslash in front of it only if no other one follows, however far away. After `<script />`, a `<` starts no tag. What loses text (`Tree::has_lost_text`) leaves all of the template as it is.
- **"It does not fit on one line" has to be as certain as a text that is written**: the white space in front of it has been printed by then, whatever is refused later. A line feed is no line break in a component that is printed as `<A />`, or in a block with nothing else in it, so both are found out first. A node that was too wide as far as it was read, and is refused further on, may be printed as it is written, which can be narrower: then the list is refused with it (`read_to`).
- **White space is a blank, a tab or a line feed.** Next to a form feed or a carriage return, which the printer counts too, nothing is split.
- **What is written is compared with the source** (`copy`, `put`, `new_line`) and joins the run that is still to be copied. A template that is formatted is copied once, at the end.
- **Runs of bytes are not read one by one.** One kernel call finds where names, blanks and plain text end (`bun_highway::ScannerStops`), so the end of a name, a word, a value or an indentation is a load and a bit scan, with no loop to leave.
- It is off for `htmlWhitespaceSensitivity: "ignore"`, with front matter, a range, `sortTailwindcss`, another end of line than `\n`, and in Markdown. What is nested more than 128 deep goes the long way, which says what is nested too deeply.
- What found the mistakes: templates made up from a grammar with odd things in it, the output of the long way with damage, and every construct next to every neighbor in every place at every width, each formatted both ways in one process, also at the widths at which a line of the text or of the output just fits. What none of them found: what has been printed by the time that something is refused, and rests on how that was read.

## Markdown and MDX: what isn't parsed

With `proseWrap: "preserve"` most of a text is printed as it's written, or nearly so. `markdown/as_written.rs` reads such text once and makes no nodes of what is in it. The long way (parser, tree, `Doc`, printer) takes 40 cycles per byte, the `Reader` 6.

- **Blocks below the root** (`Reader::lines_at`): paragraphs, headings, fenced code, lists, block quotes, tables, HTML, Liquid, thematic breaks, for MDX comments and JSX that can't be parsed. `bun_md` asks at every line where a block can start outside of all containers (`Extensions::lines`) and skips what the `Reader` takes. A run of such blocks is one node, `Kind::AsWritten`, whose neighbors see the kinds of its first and last block (`Node::first_kind`, `last_kind`). A text that's read from start to end never meets the parser: `parse::tree_without_parser`.
- **What is in a paragraph or a heading that the parser has found**, in a list or a quote (`Reader::content_of`, asked by `Builder::leaf_source`): the parser doesn't read it, and it's one `AsWritten` in that node.
- **Code in a language that has a formatter** is found the same way (`What::Code`), and gets the node that the parser would have made. JavaScript and TypeScript that would be printed as it is written is like code without a formatter: part of the run.
- **What has to be certain is the output, not the tree.** `[a]` is printed the same whether or not `a` is defined, and so is `**` whether or not it's strong emphasis. What has to be excluded is that the parser finds something in the bytes that's printed in another way. Every byte that can start or end something is looked at and has to be explained. Whatever isn't is refused: the block goes to the parser.
- **What the printer writes from a value, or looks for in the source by itself, is not "as it's written"**: the label of `[a][b]` (decoded, a space for white space), the text of an image (`bracket_content` counts brackets, those in code too), a word with a `*` in strong emphasis (written anew, so white space that isn't ASCII next to `**` is refused), an address without angle brackets (it goes on to the next white space, whatever is in between).
- **What starts first comes first.** A link or a reference that starts before `{{` and is complete takes it (`[a]({{ "b")`, `[a][{%] %}`), and what the `Reader` jumps over can hide the start of something that the parser looks for everywhere (`[[` in `<http://a[[b>`).
- **Whether a label is defined isn't known, so both readings have to print the same.** The label in `[a][b]` is read as it's written if it's defined, so no code, HTML or Liquid starts in it. `[a][b](c)` is a reference and text, or text and a link. A paragraph that starts with `[` is a definition if the first `]`, be it in code, has a `:` behind it.
- **A check for "it's printed like this already" compares with what is printed**: columns aren't bytes, and "no colon" isn't "a dash".
- **Small differences are written, not refused**: the padding of a table, `*` for `-`, `*a*` for `_a_`, two spaces in a row, the empty lines between two blocks. `Reader::replace` copies the run to `Tree::rewritten` from the first difference on. A run without one is a range of the text.
- **What depends on a neighbor that the `Reader` doesn't see is checked in the tree**: a list that follows a list gets another marker, and a block after `<!-- prettier-ignore -->` stays as it is. `Preprocessor::is_wrong_as_written` says so, and the text is parsed once more without the `Reader`.
- **A line that ends a paragraph is read in another way than one that follows an empty line** (`>2. a` is no list there). So a paragraph that's ended by a line which the `Reader` then refuses goes to the parser together with that line.
- **MDX has its own rules** (`Reader::mdx_content`): a tokenizer of remark-parse 8 looks for its end in the text as it's written, code included, and text with a `*` or a `_` is written anew.
- **JSX in MDX isn't handed to JavaScript where the result is certain** (`Reader::jsx`): half an element (`<Tabs>`, `</Tab>`: an empty line ends a block) can't be parsed and stays as it is, and one element with strings for attributes and words in it is compared with the layout of `printJsxElement` (`is_jsx_as_printed`). If it isn't laid out like that, the layout is written (`write_jsx_words`): what is printed depends on the words and the small elements, on nothing about the white space between two words, and next to an element on whether there is any. What starts with a closing tag isn't handed over either (`print_embedded`).
- **What isn't handed to a guest has to ask every option that the guest asks.** There are two such texts: JSX, and a code block of JavaScript or TypeScript that is formatted already, about which the quick way is asked (`js::quick::block_stands`, whose `options_for` names every option too). Other code blocks, front matter, `import` and `export` always go to their formatter, by the same `parser_for` as on the long way. Formatted input isn't the output if classes are sorted, so `is_jsx_as_printed` takes `FormatOptions` apart field by field, without `..`: a new option doesn't compile until someone has said what it means there.
- **Nothing is looked for ahead again and again.** What is searched beyond the line (two spaces, an empty line, `w.`) is a `Next`, which goes on from where it was. The end of a line is kept (`known_line`), and so is how far every `_` of MDX is harmless, or where the first one isn't. "Markdown takes linear time" in `format.test.ts` has the shapes.
- **What is below the root is printed as soon as it has a document** (`Printer::print_to`): nothing there is in a group or indented. A part that's only texts and forced line breaks isn't measured (`write_lines`).
- **Code that a guest has formatted is one text there** (`Printer::is_one_text`): the guest appends to a vector that starts with the fence and what follows it on its line, and the fence goes behind it. A line break in a text is a forced line break where nothing is indented, unless a blank is in front of it, which only one of the two takes away, or the guest has marked it with a `\r`. The fence is the one that the code needs as it's written. If the formatted code needs a longer one, the document is made the long way.
- **A guest costs what it does before its first byte and after its last**, and a text has many small ones. Their options are made once for a text (`options_of_guests`), their memory is kept from one to the next (`Guests`), and nothing is copied but into the output.
- All of it is off with `no_short_cuts`, for another `proseWrap`, for oxfmt's flavor, in a template and in a code block. `test/cli/format/short-cuts.test.ts` has the shapes that a fuzzer found to differ.

## JavaScript: the quick way

```
text ─ quick/ (lexer, parser, tree, comments, printers, document, layout; a reader that takes whole statements from the bytes) ─→ bytes        or `Refused`
```

`quick/` is the crate `bun_format_quick`. It depends on `bun_core` alone and knows nothing of the HIR, of `ir/` or of `FormatOptions`. The driver's `format_script` asks it after `pragma::before_parsing` and the decision about Flow, before anything is parsed. Hosts ask it too: see "as a guest" below.

- **What it prints is byte for byte what the long way prints, and `Refused` is always a valid answer.** The driver then goes on as if it had not asked: the long way prints the file, or says what is wrong with it. So the quick way reports no error, and refuses every text that the long way rejects.
- **`js/quick.rs` is the door.** `options_for` takes `FormatOptions` apart field by field, without `..`: a new option does not compile until someone has said what it means there. Not asked at all: `no_short_cuts`, `--debug-check`, `experimentalTernaries`, a range or a cursor, `insertPragma`, the oxfmt flavor, sorted imports or classes, `jsdoc`, `--debug-comments`, a `parser` other than the one that the name of the file stands for, a `filepath` that is not the path that is parsed (a text without a name has the name ""), comment types of Flow. `endOfLine: "auto"` is resolved there.
- **As a guest it is still text to text, and the host says what a file does not have.** The crate's options for that:
  - `indentation`: by how many levels the host indents the code. The layout starts with that indentation and the reader's lists start at that depth, so every line of the result but the first has all of its indentation, a line that starts in a template or a comment has none, and the host writes the result as one text (`Writer::lines`). **The width of the line is never made narrower instead**: `isLoneShortArgument` and its like ask for a share of `printWidth`, and what follows a line break in a template has all of the line.
  - `is_in_markdown`: a program that is nothing but an element of JSX gets no semicolon. The door sets it only if the code has a `<`: with it, lines are not joined.
  - `marks_line_breaks_in_texts`: see `FormatOptions::is_in_markdown`. Only for a code block that Markdown indents. One below the root says `FormatOptions::is_at_margin`, gets no marks and is read like a file.
  - `is_mdx_es_syntax`: whatever is no `import` or `export` is refused, and so is `export * as a from`.
- **Code blocks in Markdown and MDX**: the driver's `format_block_in` asks before it makes anything for the long way. **Code that is formatted already is no guest at all**: Markdown's `Reader` asks `js::quick::block_stands` (the crate's `stands`, `stands.rs`), which goes through the lines with the functions of the reader and makes nothing. Such a block is part of the text around it. After some refusals in a row most blocks are not asked about (`Scratch::credit`), which changes what a run costs and nothing else.
- **Scripts in HTML and Vue**: `html/embed.rs::write_script_quickly`, in front of the long way in `text_to_doc`. Only where what is printed depends on nothing around the script but the indentation: the level is known, there is no parent parser, the script starts a line and ends one (`short_cuts.mode` is off where `</script` shares its last line). `js::quick::format_script` refuses what a host reads in another way than a file: `<!--`, `-->`, `@flow`, a byte order mark, `import` and `export` in what is known to be no module. `type="module"` goes the long way: what only a script can have is an error there. A template that may be in another language is refused (no guests are lent to that `Quick`): the long way numbers its placeholders and escapes `</script` there. Svelte's scripts go the long way (`babel-ts`).
- **Expressions of Vue** (`:a`, `v-a`, `@a`, `{{ }}`): `write_attribute_quickly`, `write_interpolation_quickly`, the crate's `format_expression`. The text is read as the program `(` expression `)`, as on the long way, and printed below a `JsExpressionRoot`, between the name of the attribute with `="` and the closing quote, wrapped as `formatAttributeValue` wraps it. **The line is known**: the start tag is on one line with all that is in it, or the attribute starts a line at the indentation of the attributes. So a result on one line is right either way. A result on several lines is right if the tag cannot be on one line, which holds if `<`, the name of the element and a blank are at least as wide as a level of indentation. Between braces only a result on one line is taken. Refused: comments, `quoteProps: "consistent"`, in an attribute `"`, `&quot;`, `&apos;` and a backslash, between braces `{`. Of `v-for` the right side goes this way if the left side is nothing but names, which are text in front of it: its parentheses are broken only where the first line has no room, and then it is refused. Slots and `generic` go the long way.
- **JSX of MDX** (`is_mdx_jsx`) is an expression too: `<$>`, the text and `</$>` below a `JsExpressionRoot`, of which `print/jsx.rs` prints what is between the two (`is_mdx_block`).
- **Its own guests.** A template in another language is formatted by that language's formatter in this crate, whose document is written into the quick way's (`js/quick_guests/`).
- **It is a second implementation of the parser's rejections, of `js/attach/` and of `js/print/`.** Whoever changes what one of those rejects or prints changes it in `quick/` too, or makes `quick/` refuse.
- `--no-short-cuts` turns it off, which makes the long way the oracle: `test/cli/format/short-cuts.test.ts`, and every fuzzer that formats both ways. `--bench` says how many scripts and bytes went which way, and why the others were refused (`quick::Reason`).
- Its scratch (`quick::Scratch`: in the driver's `Scratches` for files and for code blocks, in `html::Scratch`, in the memory of Markdown's `Reader`) lives from file to file, one for each thread. Nothing in it changes what the next file is printed as.

## JavaScript: expressions that do not fit on their line

`js/flat/` writes what starts a line straight from the tree to text (its `mod.rs` has the contract). An expression that is too wide is written there too, with its line breaks, where those are certain. `js/flat/breaks.rs` has the rules, and they are the part to read before adding a layout.

- **`Line::fits_or_breaks` is what the printer does with a group in a group that is broken**: on one line if that fits together with what follows up to the next possible line break (`Line::tail`), else once more with `Line::breaks`. An attempt ends where the line is full, so each costs no more than a line.
- **Which layout applies is asked of `print/` and `utils/`**, not decided again: `AssignmentLike::layout_of`, `arguments_layout`, `MemberChain::new`, `BinaryLikeExpression::layout`, `can_break_between_parameters`. **Whoever changes what one of those printers writes for a layout changes it in `flat/` too**: `assignments.rs`, `expressions.rs` (arguments), `chains.rs`, `binary.rs`, `conditionals.rs`, `arrows.rs`, `suffixes.rs`, `forced.rs`.
- **What is not known goes the long way by itself**: an argument, an operand, a branch or a right side on a line of its own is a hole (`Part::Expr`, `Part::Aligned`) that `print/` fills. After one, the width of the line is not known, and nothing more is decided on it.
- **A line that is too wide has been measured in bytes, up to where it was full.** So all of it has to be plain and free of comments, holes included (`Line::has_measured`), and a choice among variants (a chain on one line or not, an argument hugged or not) needs to know where the first forced line break is.
- The elements of an array and the properties of an object that are certain to break are items like statements: `write_array_element`, `write_property`. Not where line breaks are taken out again or the content is printed apart: `Formatter::capture_without_short_cuts`.
- What found the mistakes: every `printWidth` from 20 to 120 over real files and the fixtures of Prettier and oxfmt, with and without `--no-short-cuts`, and real files with damage (names made longer, lines joined and split, comments, parentheses) under random options. `test/cli/format/short-cuts.test.ts` has one input for each kind of mistake.

## Syntax errors

`[error] a.css: SyntaxError: Unclosed string (3:6)`, and under it the lines around the place as Prettier shows them. `syntax_error.rs`:

- A parser **notes** why it refuses, `refusal.note(Message::UnclosedString, offset)`, which is `#[cold]`, and returns `Refused`, which has no size. An `Err` that carried the eight bytes itself changed what hot functions return, and cost style sheets 0.9 % of their instructions.
- At the top it is `FormatError::SyntaxErrorAt(refusal.reason())`. The offset is a byte of the text as the file has it, not counting a byte order mark: what has parsed the result of `normalize_end_of_line` maps it back with `before_normalizing_end_of_line`.
- `Message` is one enum for all languages. A text says what is wrong at the place that the offset points to, in our words: for something that is not closed, the place is where it was opened.
- A parser that knows where it stands when it gives up needs no more than that: JSON's keeps its unit error, and the message is made from the state afterwards. The exception is a token that is fine in itself but comes where a comma, a colon or the end was needed. The text at that place can't tell, so the reader notes what it expected: `Reader::expects`.
- Words that are made at run time do not fit: TOML's are those of Bun's own parser, which the driver asks a second time (`toml::syntax_error`), only for a file that has been refused.
- Line and column (UTF-16 code units) are the driver's: `Problem::at` in `src/lint/driver/fmt/mod.rs`. It prints the error the way Bun prints every error.
- `FormatError::SyntaxError`, without a place, is for scripts: the driver has the parser's diagnostics.
- `format.test.ts` has a row for each language and kind of refusal.

## How deep, how long

**There is no number for how deep something can be nested, how long it can be, or how many steps something may take.** Prettier and oxfmt have none (but `serde_json`'s 128, past which oxfmt doesn't sort a `package.json`), and every one that was here refused or, worse, silently misprinted what they print.

- **Whatever calls itself for what is nested asks the stack first**, in every stage: parser, what walks the tree, printer, document, `--debug-check`. `stack.rs`: `Stack::has_room()`. One that is told no goes on with anything, and whoever started the work asks `Stack::ran_out()` at the end: `FormatError::NestedTooDeeply`, "RangeError: The code is nested too deeply.", and the file stays as it is. Never an answer like "it does not match" or "as it is written". For JavaScript: `f.context_mut().has_stack_left()`.
- **In `js/` the doors ask**: `write!(f, child)` for an `Expr`, a `Stmt`, a `TypeNode`, and `write_expression`. What writes something that is nested in itself in any other way (a `Format` of its own that makes another of itself, a function that is handed a child) asks for itself, with a comment that says "not by way of `Expr`". One that does not is not seen by a test: another one beside it asks, so the file is refused with the right words, until it is a little deeper and the stack ends. To see it, tell the checks of this crate that the stack ends 200 KB below them, let the parser keep the real one, and watch the memory behind that end.
- **How deep is a matter of bytes per level, and only an LTO build shows them.** LTO inlines whole printers into `write_declaration`, `write_type` and `write_less_common_expression`, and a function takes the stack for everything that is inlined into it, used or not. So a printer that needs much of it is `#[inline(never)]`, one that only runs for a node with comments is `#[cold]` too, and one that writes its child first (`a.b`, `a as b`) does the rest in a function of its own. `objdump` shows what a function takes: the `push`es and the `sub $.., %rsp` at its start.
- **Find the stage that gives up before changing a frame.** `--debug-comments` parses and attaches and does not print, so it has the same limit if the parser is the one. A file that the fast variant of the parser refuses is parsed again by the general one (`Parser<true, ..>`), so the limit is the larger of the two. A breakpoint at `Parser::refuse` and the stack pointer of each frame above it show the functions that call each other and what each takes.
- **What builds a tree** that is walked afterwards, and the first that calls itself for a tree that a loop has built, takes `Stack::for_tree()` or `check_for_tree()`, which leaves room for what comes afterwards.
- **A document has nothing in it twice.** A document of Prettier can have the same object in both branches of an `ifBreak`. A copy of it here doubles with each level: `Alignment::IfBreak` is there for the one place that needs it.
- **A question with a yes or a no** (is there a line break in it, is it empty) is a loop over a list of what has not been looked at.
- **Trees are vectors of nodes with indices.** The one that owns what is in it, `css/doc.rs::Doc`, has a `Drop` that is a loop: what the compiler derives calls itself for each level, and cannot ask. So a `Doc` is taken apart through `&mut` and `take()`, not by moving out of it.
- **A loop that could go on for ever** gets a condition that makes it end, not a count: the selector parser refuses where `postcss-selector-parser` goes round in circles.
- **What is nested `n` deep is indented by `n * n` blanks.** `is_too_long` (`lib.rs`) is the longest string of JavaScript, where Prettier ends with "RangeError: Invalid string length": `FormatError::TooLong`. Each printer asks where it starts a line, and indents nothing from there on.
- A crash by the stack lives in a window of depths: shallower fits, deeper is refused early. So it is looked for at every size in steps of 3 % around each change of answer, on a release build: a debug build keeps more stack free.

## HTML

```
text ─ lexer.rs ─→ tokens ─ parser.rs, parse.rs ─→ Tree (ast.rs) ─ preprocess.rs ─→ what white space counts ─ printer.rs, tag.rs ─→ the document of ir/
```

- **The lexer and the parser take turns** (`TreeBuilder::fill`): a step of the lexer is a tag with its attributes, a text, a comment. So the lexer can be told what the parser has made of everything in front of its cursor.
- **Runs** (`runs.rs`): a child with a line break in front of it and behind it is printed between two forced line breaks, so what is printed for it depends on its text, the indentation and the options alone. At the start of a line the lexer asks `Runs::scan`, which reads children from the bytes for as long as it can tell what is printed for them, and writes that down: no tokens, no nodes, no document. They become one node, `Kind::Ready`. What it cannot tell ends the run: that child and the elements that are open there go the long way, the children in front of it on each level are runs of their own. **Whoever changes how an element, an attribute, a text or a comment is printed looks at `runs.rs` too.** Only in a file of HTML or Vue (the indentation is the number of open elements, which `print_ready` checks: if it is wrong, the text is formatted again without short cuts). What is written is compared with the source as it is written (`Sink`), and is copied only from where the two differ: for a text that is formatted already, a `Kind::Ready` is a range of the source. The start tag of an open element with a run in it is kept too (`Flags::HAS_READY_START_TAG`). A text of HTML that is one run from start to end has no tree and no document (`Runs::whole`, asked by `format_with`); if it is not, what has been found goes to the lexer. **No look ahead that is repeated for each child goes further than the line or the next `<`**: `format.test.ts` has a text with something unclosed on every line for each. **What is printed for a child also depends on what is around the run**, which the bytes of the run do not show: `parent_of_run` refuses what is in a `<foreignObject>`, however deep, and what is in an element behind `<!-- display: .. -->`. **What is measured is measured as the printer measures it**: it skips a text without width together with the blank in front of it, so a word of nothing but combining marks is refused. Nothing is read deeper than 128 levels, so that the printer says what is nested too deeply. `test/cli/format/short-cuts.test.ts` has the forms that once went wrong.
- **A file with a tree costs more than what is in the tree**: lexer, parser, `preprocess`, printer and `ir/` are some 150 KB of code that is cold for every small file. What goes the long way takes 100 cycles a byte, a run 15. So what pays is a text that is one run. Behind front matter, or with code in it, it has a document and no tree (`print_front_matter_and_run`).
- **What a run looks for, it finds in bitmaps** (`bun_highway::HtmlMarks`, one kernel call per text): the end of a name, of a plain value, of white space, of plain words is a count of zeros in 57 bits, not a loop with a branch that is mispredicted at its end.
- **Children that share lines** (`read_pieces`, `put_pieces`): words and elements with nothing but words in them, between two line breaks that are forced, or all that is in an element. The layout is that of `printChildren` in closed form: the words of a text are a `fill`, an element is `group([line, group([element, line])])`, and a group fits if it does together with what follows it up to the next possible line break. A blank in front of a line break takes no room. **Where such lines end is a matter of the neighbors**: a line break is forced next to a node with a line break on both sides, which the last child of an element without an end tag, the first child of the text and the last one without a line break behind it do not have. `mergeSimpleElementIntoText` makes one word of `a<b>c</b>d`. What is refused: an element that has to break in itself, two elements or a word between two elements without white space, `<br>`, and in Vue `{{ }}` next to a line break, which is a node of its own there.
- **An only child that is an element** and does not stay on the line of its parent is read like a child on lines of its own (`element_with_only_child`): `ends_line` takes the end tag of the parent for the end of the line.
- **A text is read as the lexer reads it**: in `{{ }}` there are no references, a backslash and `//` take the next character with them whatever it is, quotes hide `}}` (`interpolation_end`). A `<` that starts no tag is text.
- **Code in a run** (`Code`): a `<script>` or a `<style>` that names no language does not end the run. What is printed has a NUL and where the code is in its place, and `print_lines_and_code` hands it to its formatter. If that fails, the text is formatted again without short cuts.
- **The blocks of a Vue file** (`Scanner::block`): at the root of a Vue file a run reads a `<template>` without attributes whose children are on lines of their own, and a `<script>` and a `<style>` whose attributes have no value, but for `lang`. Anything else there ends the run. A file that is one run is written as text, without a document (`write_lines_and_code`): its lines are copied, a script is what the quick way for JavaScript makes of it, a style sheet what `css::format` does. Where one of them refuses, or the lines of a style sheet have to be indented, there is a document and no tree, as for HTML. **Whoever asks the tree about the blocks of a file asks the runs too**: whether the expressions of a template are TypeScript is a matter of a `<script>` that a run may have read (`Tree::has_typescript_script_in_run`).
- **It prints with `ir/`**, because scripts and expressions are written to the same document by `js/`, and HTML in a template of JavaScript is part of that file's document. `writer.rs` has Prettier's builders. The printer of `ir/` writes no line break on an empty line, Prettier's does, so the `Writer` keeps track of whether the line is empty and asks for an empty line where Prettier gets one from two line breaks in a row. **Everything goes through the `Writer`**, or through `Writer::foreign` for what another formatter writes.
- **Scripts and expressions** (`js.rs`, `embed.rs`, `vue.rs`): this crate cannot parse JavaScript, so the caller does: `FormatOptions::parse_javascript`, or the closure that `html::format_with` is given, which keeps its interner. `Formatter::write_embedded` lends the document to a formatter for the other text. An expression is the file `(` expression `)` whose name starts with a NUL. Its `ast_parent()` is `AstNodes::Program`, which stands for Prettier's `JsExpressionRoot` and `NGRoot`. `f.options().in_html` says what Prettier's `__` options and its parsers for expressions say. A hook in `js/` is a named function next to its use. A name, a path of names and their negation are written without being parsed (`write_path`). In Vue, so is all that `canonical.rs` knows to be printed as it is written if it fits on its line: a small part of JavaScript in the one spelling that the printer gives it. It is asked where the line is known: an attribute is either in a start tag on one line or on a line of its own, an expression between `{{` and `}}` likewise. **What the printer of JavaScript prints differently one day has to go from `canonical.rs`**, and so has what an option changes that is formatted already: with `sortTailwindcss`, a string of several words. **A line is known only if nothing else is printed on it**: what is in a `<pre>` follows its last attribute, and `</script` follows the code where the next sibling prints its `>`, so neither takes a short cut.
- **Imports and JSDoc comments in scripts**: `html::options_of_host` says which of `sort_imports` and `jsdoc` is for the code in a text, by its parser: oxfmt's are for a Vue file only, the plugins of Prettier sort everywhere. `js.rs::with_file` applies them to `Piece::Script`, never to an expression. In a Vue file the plugins work on the text before it is parsed: `with_sorted_scripts`. `test/cli/format/sort-imports/hosts.json` has what the tools print.
- **The flavor of oxfmt**: oxfmt hands HTML, Vue, Angular and MJML to the Prettier that it brings along, so all of it is `Flavor::Prettier` (`options_of_host`), style sheets and expressions too. Its plugin takes over the parsers `babel`, `babel-ts` and `typescript`, in a Vue file only: `Options::script_flavor`. There a script is parsed one way, `Syntax::Ts`, or `Syntax::Tsx` if a script of the file says `lang="tsx"`, and a native `on*` attribute is a script like another, which Prettier hugs.
- **Angular** (`angular.rs`, `angular/`): a port of Angular's own lexer and parser says what is an error, and rewrites the expression as TypeScript that our parser reads into the same tree: `a | b: c` is `a | b(c)`, and in Angular every `|` is a pipe.
- **Other languages**: YAML, Markdown, JSON, GraphQL, Handlebars and the style sheets of a file of HTML are printed to text at the width that is left (`Writer::printed_text`). Where that width is not known (in a template of JavaScript, in Markdown), and for a `style` attribute, a style sheet comes as a `Doc` (`css::document`) that `css/embed.rs::write_document` writes to the document. Prettier calls `cleanDoc` with the document of what is embedded: `Sink::is_cleaned`.
- `in_js.rs`, `map_strings.rs`: HTML in the templates of JavaScript, Prettier's `embed/html.js`.
- `verify.rs`: `--debug-check`. The same elements, attributes, comments and blocks in each other the same way, text that is more than white space in the same places between them, and the same letters as often in all that is text, in whatever language.
- `cursor.rs`: `cursorOffset`. A range is all of the text in Vue and nothing elsewhere, as in Prettier.

## How the code differs from oxc's

### The IR

`FormatElement` is 16 bytes and `Copy`. There is no arena and there are no lifetimes in it: text is a range of the source (`SourceText`), a range of `Storage::text` (`OwnedText`), or up to 14 bytes inline (`Token`). Interned content is a range of `Storage::pool`.

There is no pass over a finished document. `Formatter::write_element` tells `document::Tracker` about every element, and when a group or captured content ends, what the printer has to know about it is written into its start tag or its `Skip`: whether something in it forces a line break (Prettier's `propagateBreaks`), and `Flat`: how wide it is on one line. So **every element has to go through `f.write_element` or a builder**, never `f.storage.pool.push`, and `f.elements_from(start).will_break()`, `memoized.inspect(f).will_break()` cost nothing. A document that is written without a `Formatter` (JSON) calls `document::propagate_expand` once, which replays it to a `Tracker`.

The printer decides on a measured group from its width and a look at what follows it up to the next possible line break, and prints a group that fits with `print_flat`, a loop that only writes texts. A group is not measured if what it is on one line depends on the printer: content that depends on another group by id, a line suffix, a variant with a forced line break. Those are measured element by element, as in Prettier.

Three frequent shapes are one element each, which the builders write by themselves: `if_group_breaks(&",")` (`TokenIfBreaks`), the `indent` + line break of `soft_block_indent`, `block_indent`, .. (`StartIndentWithLine`, `EndIndentWithLine`), and `group(&indent(&soft_line_break_or_space())).with_group_id(id)` (`IndentedLineGroup`).

**Each frequent kind of element has a function that writes it.** `f.write_element` takes an element of any kind. The builders call the function for their kind in `ir/formatter.rs` (`write_short_token`, `write_source_token`, `write_space`, `write_line_break`, `start_group`, `end_group`, ..). Thousands of places inline these, so they are short: what they usually do is a push within the capacity of the pool and the notes of the `Tracker` for that kind. What is rarer (the pool is full, the text is the first one in a group) is a second function, which is not inlined and gets what the element is made of, not the element. A string literal in `write!` or `format_args!` is a `Literal`, whose token is made at compile time.

### Variants that are tried

`group(..).should_expand(is_broken_in_the_source).stays_expanded(true)` is `GroupMode::StaysExpanded`: a group like another, of which the printer knows that it is written to break the next time if it breaks now. `best_fitting!(a, b).with_fallback(Fallback::FlattestIfStable)` is for two variants of which `will_break()` picks `b`. If `a` does not fit on one line, the printer prints it expanded (`Printer::try_expanded`). If such a group breaks in it, the printer goes back to where it was and prints `b`, in which that group and those around it break, as they do the next time. Nothing is tried twice: a try that ends early also decides on the variants of this kind that were being printed in it.

### `Formatter` is concrete

No `dyn Buffer`, no generic context. `f: &mut Formatter<'a>`, where `'a` is the lifetime of the file.

### Nodes

oxc: `impl FormatWrite for AstNode<'a, IfStatement<'a>> { fn write(&self, f) }`. Here: a free function that gets the handle and its parts, `write_if_statement(statement, test, consequent, alternate, f)`, called from the `match` in `format.rs`.

`AstNode<'a, T>` with its `parent` pointer does not exist. Handles are `Copy` and know their file. **`AstNodes<'a>`** (`js/ast_nodes.rs`) is a view with oxc's variant names, made on demand:

```rust

node.parent(), node.span(), node.ancestors()
matches!(e.ast_parent(), AstNodes::ExpressionStatement(s) if s.is_arrow_function_body())
```

### Optional chains

`a?.b.c` is two nodes in ESTree, a `ChainExpression` and the member expression in it, and one `Expr` here.

- `e.as_ast_nodes()` is ESTree's `Expression`: `ChainExpression(e)` if `e` is the whole of a chain (`e.is_chain_root()`).
- `e.as_chain_element()` is the member access, the call or the `!` itself. Its `parent()` is the `ChainExpression`.

So oxc's `matches!(callee, Expression::StaticMemberExpression(_))`, which is false for `(a?.b)()`, is `matches!(callee.as_ast_nodes(), AstNodes::StaticMemberExpression(_))`, not `matches!(callee.kind(), ExprKind::Dot { .. })`.

### One lifetime

`File<'a>` is invariant in `'a`. A function that takes two handles, or a handle and the formatter, needs **one** lifetime for them: `fn f<'a>(a: Expr<'a>, b: List<'a, Expr<'a>>, f: &Formatter<'a>)`. With `'_` twice it does not compile ("lifetime may not live long enough"). The same for closures: annotate `|e: Expr<'a>|`, or make it a nested `fn`.

## Comments

The algorithm is Prettier's, not oxc's. Before printing starts, every comment is attached to exactly one node, as a leading, trailing or dangling comment. A printer prints the comments that a node owns. It never decides who owns a comment.

### One record per comment

`hir::Comment` (`src/sema/hir.rs`) is the only representation of a comment. Its index in `File::comments` is the comment's id.

| who writes it | what                                                                                                                                                        |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| the lexer     | the span, where the previous token ends and the next token starts, line or block, whether it spans lines, whether there is a line break before and after it |
| the parser    | the enclosing, preceding and following node                                                                                                                 |

- The parser finds the three nodes while it parses (`src/sema/parser/parser/comments.rs`). Each time a node is finished, its range is compared with the closest comments that are still pending. Nothing walks the tree afterwards.
- This only happens with `Options::attach_comments`, which only the formatter sets. The hooks are behind the parameter `COMMENTS` of the `Parser`, so `bun lint` and `bun check` run a parser that is compiled without them. One comparison per node was 0.1% of the instructions of `bun check` on vscode.
- `bun_lint::ast::comments::Comment<'a>` is the handle to the record, `Copy` like `Expr<'a>`.
- The formatter stores only what it decides itself, by comment id (`js/comments.rs`): placement and marker, the table from a node to its comment ids (`js/owners.rs`), and one "printed" bit.
- `hir::File::detached_semicolons` lists each `;` that ends a statement but does not directly follow the previous token. `File::without_semicolon(span)` uses it to give Prettier's `locEnd` without looking at the text. It is recorded with `attach_comments` too.

**Do not scan the source text** to find a token, or to skip whitespace and comments. If a position is missing, have the lexer or the parser record it.

### Attaching: `js/attach/`

1. `surrounding_nodes.rs` converts the three recorded nodes to `AstNodes`, and adjusts them where ESTree's tree is not the HIR's. For example, ESTree has a node for the closing tag of a JSX element.
2. `rules.rs` is Prettier's `handle-comments.js`, with the same function names. `rules/oxfmt.rs` has the rules of the oxfmt flavor: where oxfmt prints a comment somewhere else than Prettier, the comment has another owner.
3. A comment that no rule handles is attached by its position in the line (`attach_by_text_position`, `break_ties` in `mod.rs`): on its own line it leads the following node, at the end of a line it trails the preceding node.

An owner is an `AstNodes`, a name (an identifier or a literal key is a token here and a node in ESTree, so it is identified by its start offset), or the parentheses after a `/** @type {T} */` cast.

**Nothing here may walk a list for each comment**: not the comments of the gap, not the elements of the array, not the parents up to the root. A file can have 40,000 comments between two tokens, or one in each of 40,000 elements. `AttachContext::comments_between_same_tokens` has what the rules ask about all the comments between two tokens, found once. Elements are in source order, so search them by halves. The test "JavaScript with many comments takes time in proportion to its size" has the shapes that once took quadratic time. Add yours.

### Printing

```rust
let owned = f.comments().of_node(node);   // leading, trailing, dangling: CommentList<'a>, and is_ignored
f.comments().of_name(start_offset)
leading_comments(node)  trailing_comments(node)  dangling_comments(node).with_block_indent()   // impl Format
```

- **Leading and trailing comments are printed by the wrappers**: `write!(f, expr)`, `write!(f, statement)`, `write!(f, ty)`, `format_node(node, f, |f| ..)` and `format_name(span, f, |f| ..)` in `js/format.rs`. This is Prettier's `printComments`.
- **Dangling comments are printed by the function that writes the node**, like Prettier's `printDanglingComments`. If a node prints its dangling comments in several places, `f.comments().attachment(comment)` has Prettier's `comment.marker` to tell them apart.
- **`// prettier-ignore`**, and `// oxfmt-ignore` in that flavor: the same wrappers copy the node's source text (`write_ignored_node`). `f.comments().is_ignored(node)` is Prettier's `hasNodeIgnoreComment`.
- **`FormatNodeWithoutTrailingComments(&child)`** leaves the child's trailing comments to the caller, which prints them with `trailing_comments(child_node)`.
- **Prettier's `willPrintOwnComments`**: a few nodes print their own leading and trailing comments (a JSX element inside parentheses, the members of a union). The wrappers skip those.
- **Every comment is printed exactly once.** `Comments::mark_printed` returns false for a comment that has been printed.
- **A comment that is left over does not cost the file.** Prettier throws (`ensureAllCommentsPrinted`). Here the file is formatted once more, and the statement or the class member around the comment writes it after itself (`ir/run.rs`, `write_comments_without_printer`). The comment moves, so it is still a bug: the owner has no printer. `--debug-unprinted-comments` lists what the first pass left over, and the tests want nothing there. Code in a template has no second pass and stays as written.
- **A comment that waits for the end of the line** (`line_suffix`) is written at the next line break, wherever that is. `Comment::fmt` puts a `line_suffix_boundary` before a block comment that it writes with line breaks of its own (`/**⏎ * a⏎ */`), so that it is not inside that comment.
- **Formatting something only to look at it**: `f.speculate_will_break(&content)` forgets which comments were printed meanwhile. The result of `memoized().inspect(f)` or `f.intern` has to be used, not thrown away.
- **Questions by offset are for layout only**: `has_comment_in_span`, `comments_in_span`, `has_comment_before(token_start)`, `comments_directly_before(token_start)`. Their answers do not depend on what has been printed. Never use them to pick the comments to print.
- `/** @type {T} */ (e)`: `utils/typecast.rs` keeps the parentheses.

### `f.is_quiet()`

Most nodes have no comment anywhere near them. `f.is_quiet()` is true while a node is written that has no comment inside its span, and no node inside it that owns a comment from elsewhere. The wrappers in `format.rs` then skip everything above. Use it to skip work that is only about comments:

```rust
if !f.is_quiet() && !f.comments().of_node(node).dangling.is_empty() { .. }
```

A node's own leading and trailing comments are outside its span, so ask for those before entering the node. Calling the `Comments` methods without the check is always correct: `of_node` tests one bit for a node that owns nothing.

**Enter only what the attach step takes for a node.** "From elsewhere" means that the owner is not the node that was recorded before, after or around the comment. A plain leading comment is expected in the scope of the parent, directly before its node. So `format_node(X, ..)` around something that `can_attach_comment` leaves out puts a scope between the two: in `interface A { a⏎// comment⏎: B }` the comment leads `B` for Prettier, the `: B` starts behind the comment, and inside it nothing looks for comments. The second pass then hides the mistake. `conformance.test.ts` checks that no comment of `own/cases` is left to it, in both flavors.

### Debugging

In builds that have the test runner (debug and canary):

```sh

bun bd fmt --debug-comments-oxfmt out a.ts       # the same in the oxfmt flavor
```

## JavaScript: where lines are written without a document

`js/flat/mod.rs` has the contract of the short cut. This is about where it applies: `ShortCuts::for_code` is the list of what turns it off for a file (`experimentalTernaries`, a cursor or a range, sorted imports or classes, JSX of MDX, HTML in a template, a `\r` that is not part of `\r\n`).

- **Hosts.** This is about the code that the quick way has refused. Code in Markdown and MDX is a file of its own, with its own width. A script in HTML or Vue is written into the document of the host: `html::format_with` says that it formats again, the long way, if the printer finds a wrong guess (`ShortCuts::for_host`), `text_to_doc` says that a script follows and how deep it is indented, if that is known (`start_script_at`), and `js.rs::with_file` makes the state of the script from that (`for_script`). A host that does not say so (Svelte, Angular, an attribute) gets none. What is printed to a text of its own (`print_to_text`) is `LongWay`: nobody formats it again.
- **Templates.** Whether a template has the label `embed` is known once its language's parser has read it (`has_embed_label`), which costs as much as a third of formatting it. What only has to refuse asks `css::embed::may_be_in_another_language`, which looks at what is around the template and parses nothing.
- **Flow** (`flat/flow.rs`): the nodes of TypeScript stand for something else, so what only Flow has is refused node by node: `check_flow_statement` at the top of `Line::statement`, `check_flow_member`, `check_flow_new`, `only_in_typescript`. Every type goes to `flow_type`, which knows few. **Who adds a kind of node to `flat/` asks what it stands for in Flow** (the table in `src/sema/parser/parser/flow.rs`).
- **The oxfmt flavor** is on. A line is the same in both flavors, what differs is where something breaks: who writes a line break in `flat/` looks at the hooks of the flavor in the printer that it stands for (a union that is too wide has no line of its own for oxfmt, a line with only a comma on it is an empty line between two arguments).
- **Types in JavaScript** that is not Flow are an error that is printed like Flow: `Line::is_typescript` is what the writers of types ask.
- **Without semicolons**: `Line::semicolon()` is the `;` that the printers write as `OptionalSemicolon`. `semicolon_before` is the one that a statement starts with.
- **What follows on the line** is given as at least and at most: `write_line(span, (least, most), ..)`. It fits only with the most, it is too wide only with the least, and in between it is refused.
- **Text that is not plain ASCII**: the first attempt counts bytes. If `check_source_up_to` meets a block of the source that is not plain, or the line is too wide and its source is not plain, there is a careful attempt: `source`, `long_bytes` and `string` measure every text (`Line::measure`), `Line::extra` is what the line has more bytes than columns. **A decision to break must not rest on bytes**: whoever finds "too wide" in the middle of an attempt and goes on with a hole asks `is_plain_source` for all that the hole hides.
- **Block comments on the line of an item** count for its width, or move its start. `ShortCuts::has_block_comment_in_line` says whether the file has any, from the comment records, and only then is the source around an item looked at.
- **JSX** (`flat/jsx.rs`): an element is one line, or its tags end lines. `print/jsx/child_list.rs` asks for each child that has a line of its own (`write_jsx_child`), also in an element that the printers write. What is between the tags is written by the printers, in a group: a fill is printed differently after a forced line break until a group starts. So a child is a group here if and only if the printers write one for it, which they do for all but `<a />`.

## The quick way: templates in other languages

```
quick/print/embed.rs ─ which template, its text with placeholders, what is around it ─→ Quick::embed() ─→ Guests::format(guest, text, &mut Sink)
js/quick_guests/mod.rs ─ QuickGuests ─→ css: Doc ─ from_doc.rs ─→ Sink      graphql: ir ─ from_ir.rs ─→ Sink      html: writer.rs (ToQuick) ─→ Sink
```

The crate `quick/` knows JavaScript only. `js/quick.rs` lends it `QuickGuests` (`quick/guest.rs`: `Guests`, `Sink`), which turn the text of a template into a document by the functions that the long way uses, and write it into the document of the file, where the printer of the template stands. Nothing is printed to text and read again. The document of `quick/` is Prettier's, command for command, so what is written is what Prettier's builders say.

- **Three answers**: `Written`, `NotRead` (a syntax error: what has been written is taken back, the template is printed as it is), `Refused` (the file goes the long way). **Whatever is not certain to be printed as the long way prints it is `Refused`.**
- **What Prettier does with `mapDoc()` happens while the guest writes**: the printer of the template sets a filter (`quick/holes.rs`), and every text goes through it: substitutions for placeholders, escapes, `&quot;` in the value of an attribute (`Sink::quote_entities_open`). It sees one text at a time, Prettier sees two texts in a row as one: a text that ends in `$` in front of one that starts with `{` refuses the file.
- **Markup does not go through `ir/`.** `html/writer.rs` has Prettier's builders, and two places to write to. For `ir/` it works out where Prettier gets an empty line or a blank that the printer of `ir/` would skip. For `ToQuick` every builder is written as it is. **Who needs something of the document that the `Writer` has no method for adds a method with both**, as `two_lines`, `style_sheet`, `start_attribute_value` are.
- **What another formatter writes with `ir` elements** (`Writer::foreign`: expressions and scripts, by the long way for JavaScript; GraphQL) goes to a `Formatter` of which nothing is kept, and `from_ir.rs` translates it. The two printers differ where white space meets white space: `Last` keeps track of what is on the line, line breaks in a row that are certain to be printed become one, and what depends on whether a group breaks is refused. Between two texts nothing is ever refused. `Fallback::FlattestIfStable`, a cursor and a short cut's text have no translation.
- **`from_doc.rs` is one to one**, and refuses what `css/embed.rs` and `markdown/embed.rs` cannot say in `ir/` or say differently: a forced line break without `breakParent`, line breaks in a row other than the pairs that `css/embed.rs` knows, a line break in a string in a group.
- **The long way is the oracle, also where it isn't Prettier.** `test/cli/format/short-cuts.test.ts`, "templates in another language", has a row for each such place. They are refused: Markdown that `ir/` has no words for (a block quote), that may be on one line with its backticks, with a table under `proseWrap: "never"` or a line break in inline code. Front matter in a style sheet. A query of nothing but a line continuation. Markup that is blank once its escapes are read. A text without width.
- **What the template's printer asks the guest**: the number of top-level nodes of markup (`Sink::set_top_level_count`), how many placeholders were replaced (the filter counts). The label `embed` is that of the finished document, which is kept under the node, so nothing is parsed twice. **What the guest asks**: `Sink::hole_count`, and `Sink::indentation_of_template`, for the width that is left for what markup prints to text.
- `Quick` cannot hold a borrow, so the guests are a `'static` box that lives with it, and `QuickGuests::start_file` copies the options of each file.
- What found the mistakes: windows of real texts and fixtures in each language, with damage, with `${}` in every place, in every kind of template in every kind of expression, under random options, each formatted both ways in one process.

## Performance rules

The goal is to be faster per core than oxfmt and Biome.

- **Measure on an LTO build, and measure time too.** Without LTO, what is inlined changes with unrelated code, which is worth 0.2% either way, and what pays can be the opposite: `#[inline(never)]` on the functions that write elements makes a build without LTO 2 to 4% faster and an LTO build 1 to 3% slower. A count of instructions does not see a large `memmove`: it is one instruction. Cycles differ by 10% with what the other thread of the core does, so compare instructions, mispredicted branches and misses of the instruction cache too.

- **What is rare stays out of the common path.** The printers that a file goes through are some 250 KB of code and the first cache for instructions has 32 KB. What is rare where it stands (comments, type casts, a cursor, a layout for few inputs) is a function of its own, `#[cold]` if it is very rare, behind a check that is inlined. What wraps a closure and does not depend on it takes `&mut dyn FnMut` (`format_node_with_comments_by`).
- No heap allocation per node. `SmallVec` for lists that are small in practice, `f.take_vec()` for element buffers.
- No `String`, no `format!`, no `to_vec()` on the path of ordinary code. Text is `&[u8]`.
- `format_with` closures and `format_args!` are static dispatch and cost nothing. `&dyn Format` only where oxc needs it (`best_fitting!`).
- `as_ast_nodes()`, `ast_parent()` are cheap but not free (a table lookup and a `match`). Ask once, keep the result in a `let`.
- `memoized()`/`intern`/`capture` move nothing: the elements stay where they are written, behind a `FormatElement::Skip(len)`, and an `Interned` is a range of the one vector. What is formatted and thrown away stays there too.
- Decide from the syntax first, look at the source text or the comments last.
- Sort with `crate::sort` (`bun_collections::index_sort`), not with `slice::sort*`: each `sort_by` with a closure of its own is 4 to 30 KB of code in the binary. The standard sorts are for a sort that a profile shows to be hot, and only by a key that is `Ord`: they may panic on a comparison that is not a total order, which `crate::sort::sort_by` takes.

## The command line: `src/lint/driver/fmt`

A run over a few files is over in milliseconds, so what is around the formatter counts: system calls, threads, memory.

- **How many threads**: `Pool::threads_for(nanoseconds)`, five times the cube root of the milliseconds of work, which `files::time_to_format` estimates from the sizes of the files, and no more than finish the other files while one formats the largest. A thread takes 0.1 ms to start, one after the other whoever starts them, and what it touches (4 MB on large files) is given back page by page when the process ends. `--threads` is taken as it is. `Pool::threads()` is still what oxfmt's summary names.
- **`bun_sema_driver::StandingThreads`** are started when the arguments are known (`Pool::call_up`), and more of them as a search finds more. They wait for one region after the other, and one call wakes all of them. The main thread looks at arguments and directories with them (`Meanwhile::Helps`), and puts the files in order while they format (`Meanwhile::Does`). It formats nothing: its stack is smaller.
- **No lock that all threads take at the same time, or for each file.** `bun_threading::Mutex` does not spin: threads that meet at one are let through one by one, 50 µs each. So a thread has a `Worker` with its buffers, its results and the options it has resolved, its caches stay with it, and a search shares a directory only with a thread that has nothing to do.
- **The order of files is the order of messages, nothing else.** `files::Expansion` keeps what a search has found as it was found. `Expansion::order` is asked for while the files are formatted, `Expansion::sort` before that by what prints a list. Whatever is collected file by file and printed (names of plugins, of packages) is collected in order: see the loop in `format_files`.
- **Options are resolved once for the files that share them**: `Configs::options_for_one_of_many`. **`OptionsKey` has to hold everything that the options of a file depend on**, but for `filepath`: the scope (directories with nothing of their own share their parent's), which overrides and which sections of `.editorconfig` match, and whether it is a `package.json`. Whoever makes `options_of` look at one more thing about the path adds it to the key, sets `Resolved::depends_on_directory`, or makes `options_key` return `None`.
- **A file is four system calls**: `lstat` or `fstatat` when it is found, then `open`, `read`, `close`. A read that asks for more than the size and gets the size has all of it (`fs::read_file_of_size`). Anything else goes the long way.
- **Directories are listed for what is looked for in them.** With `--no-config --no-editorconfig` none is. Those above files that are named are listed on all threads (`Configs::list_ahead`), and what is found in them is read in the order of the arguments.
- Nothing is freed at the end (`ManuallyDrop` in `format_files`). To give memory back from all threads at once takes as long as the end of the process does: each call interrupts every other thread.
- `bun fmt --timing` has the phases. `--bench=<rounds>` (canary, debug) is the formatter alone.

## Conventions

Those of `src/CLAUDE.md` and `src/lint/CLAUDE.md`: no `unsafe`, nothing that can panic on any input (`.get()`, `let .. else`, `saturating_sub`), byte searches through `bun_core::strings`, no `std::fs`/`println!`, `pub(crate)`, no warnings. Comments say what the reader cannot see, in the present tense, and never narrate the port. Naming Prettier's function that something corresponds to is good: ``/// Prettier's `shouldHugTheOnlyFunctionParameter`.``

A node that is not ported yet is written as it is in the source: `write!(f, FormatSuppressedNode(span))`.

## Features beyond Prettier's options

`sortImports`, `sortTailwindcss`, `sortPackageJson`, `jsdoc`, `svelte`, `insertFinalNewline` and TOML all come from oxfmt, but none of them needs oxfmt's flavor. Each one except TOML has a flag and a `[fmt]` key in bunfig.toml. They work with any config file or none, and everything else keeps Prettier's defaults. TOML has no switch. It's formatted wherever no Prettier config applies (`Configs::formats_toml`).

- **Where the keys live**: `FEATURES` in `src/lint/driver/bunfig.rs` lists the keys that take `true`, `false` or a table, with each table's options. They end up in `Options::format` (`src/lint/driver/fmt/cli.rs`) under the same names that `settings` in `fmt/config.rs` uses for an `.oxfmtrc.json`. In a `.prettierrc` these names are still unknown options, unless a flag or `[fmt]` sets them too (`Configs::options_for`).
- **`[[fmt.overrides]]`** has the shape of `overrides` in a `.prettierrc`. Its globs follow oxfmt's rules and are relative to the bunfig.toml (`Configs::directory_of_bunfig`). Overrides behave like flags that only apply to some files.
- **Defaults can differ from oxfmt's** when nearly everybody would set the same value. Example: `functions` of `sortTailwindcss` (`FUNCTIONS` in `fmt/tailwind.rs`).
- **TOML layout**: without an oxfmt config, arrays and inline tables get Bun's own layout. The header of `toml/printer.rs` lists the rules. The TOML snippets in `docs/lint/rules` follow it (`src/codegen/lint-rule-options.ts`), and `test/cli/lint/rule-docs.test.ts` checks that. Tests: `test/cli/format/toml-layout.test.ts`.
- **Generated files**: without a Prettier or oxfmt config, minified code and lock files are skipped unless they're named on the command line (`files::is_generated`).
- **`.gitignore`**: without a Prettier or oxfmt config, every `.gitignore` counts, from the root of the repository down, as for Git and for `bun lint` (`Ignored::git_ignores_in`). Outside of a repository, from the working directory down. With a Prettier config it's only the one in the working directory, because that's all Prettier reads.
- **`--debug-check`** is Prettier's flag: nothing is written, every file that passes is named, and one whose formatted text says something else is an error. Without it nothing is compared.
- **Adding a feature** that another tool's config file turns on? Give it a flag and a key, and test it in `test/cli/format/bunfig.test.ts`.

## `sortTailwindcss`

oxfmt's option, which is made of `prettier-plugin-tailwindcss`: the classes of Tailwind CSS in a text are put in the order of their rules.

- **One function**: `tailwind.rs::Tailwind::sorted_between` is `sortClasses` and `sortClassList` of `prettier-plugin-tailwindcss`, which everything in oxfmt ends in. A language only says where a text with classes is, and what is at its ends (`Ends`).
- **The order** is known to the Tailwind of the project alone, which is JavaScript. The formatter asks `Orders` for the ranks of a list of classes. The driver implements it (`src/lint/driver/fmt/tailwind.rs`): a class that is not known is noted, the text stays as it is, and `Tailwind::has_missed` says that what has been printed is of no use. The driver puts such a file aside, asks once for all classes (`tailwind.js`, run by `evaluate.rs`), and formats those files again. Where Tailwind 3 and 4 put a class does not depend on what else they are asked about (27,345 real lists: no pair in another order), only the numbers that they answer with do, so all classes are asked about at once. So the formatter is what collects the classes, and nothing is run for files without any. What is sorted is not sorted again further down: that would ask for a list that only the second pass knows of.
- **Without the package** classes stay as they are and that is no error: a shared config turns the option on for projects that have no Tailwind. The option is off for the files of such a directory (`for_file`), for `bun/format` and `prettier/prettier` too, and only `--doctor` says so (`Classes::note`). A Tailwind that is there and cannot be asked is an error, and its files are left as they are: it cannot be loaded, `stylesheet` or `config` names no file or is for the other major version.
- **JavaScript**: `js/utils/tailwindcss.rs`, a port of oxc's, with its stack of contexts (`JsFormatContext::tailwind_context`) and what follows from it: no context for the arguments of a call that is written as a member chain, a text of a template is sorted in a call of another function and a string is not.
- **Style sheets**: `@apply`, in `print_at_rule_up_to_block`.
- **Handlebars**: the plugin changes the tree, and so does `handlebars/tailwind.rs`.
- **HTML, Vue and Angular**: the plugin rewrites the values of attributes in the tree, so `html/tailwind.rs` rewrites the text before it is parsed. Of the code in HTML the plugin takes over programs and `__js_expression`, nothing else: `js.rs::with_file`.
- **`--debug-check`** knows that words change places and that one that is there twice is there once: `verify/tree.rs::has_same_words`. HTML is compared without the option: `html::has_same_content`.
- **`prettier-plugin-tailwindcss` in a Prettier config** turns it on too, with the plugin's options and defaults (`SetBy::Plugin` in `fmt/tailwind.rs`): `Tailwind::follows_plugin`. Where oxfmt has rules of its own, the plugin's count then. In JavaScript that is its `transformJavaScript`: the stack has one context, and a string or a template walks up its ancestors to see whether it is sorted (`collapse_by_plugin`). `collapse_among` is its `canCollapseWhitespaceIn`, for JavaScript, Vue and Angular. What the plugin sees depends on the parser: Babel, TypeScript, or `@prettier/plugin-oxc` (`Oxc`). Where it takes away the blank that keeps two classes apart, the blank stays. If the project has no `tailwindcss`, or an option is for the other major version, the order is read off the plugin's own `createSorter` (`loadBundled` in `tailwind.js`).
- **Not there**: with `preserveWhitespace`, a line break in a list does not break the groups around it in oxfmt. oxfmt does not sort in the cells of a `test.each` table. Without the package oxfmt takes a Tailwind that the plugin brings along, also for `config` with version 4 installed. There is no order built in here.
- **Tests**: `test/cli/format/tailwind`, with a stand-in for the package. `test/cli/format/oracle/tailwind/make-fixtures.ts` makes what is expected with the real tools.

## Sorting `package.json`

`json/sort_package_json.rs`. There are two orders and one way to apply them:

- `sortPackageJson`, which is oxfmt's option: the order of the Rust crate `sort-package-json` (`sort_package_json/oxfmt.rs`).
- `prettier-plugin-packagejson` in a Prettier config: the order of the npm package `sort-package-json`, which is a different one (`sort_package_json/npm.rs`). `sortPackageJson` from a flag or `[fmt]`, whether `true` or `false`, wins over the plugin.

Each order is a table of the known keys with what to do with the value of each (`FIELDS`, `Over`). `npm.rs` also has code for `scripts`, `exports`, dependencies and `pnpm.overrides`.

- **Sorting only moves members.** Both tools parse the text into values and write those back, which rewrites numbers and strings and drops duplicate keys. Here `json::format` parses the text as always, `sort` reorders the nodes of the tree, and the writer prints every name and value from its source text. The headers of the three files list what differs from the tools.
- **Only with the `json-stringify` parser**, which is what a `package.json` gets unless `parser` says otherwise. There a comment is a syntax error, so no comment ever has to move with a member, and a container's width doesn't matter, so removing a duplicate from `keywords` needs no new measurements.
- The driver only says which order applies, and whether the working directory has a lock file of Yarn or pnpm (`Configs::options_of`).
- Tests: "prettier-plugin-packagejson" in `test/cli/format/format.test.ts` and "sortPackageJson" in `bunfig.test.ts`. `test/cli/format/oracle/packagejson/fuzz.mjs` compares `bun fmt` with the real plugin on random files and on real ones, and knows which differences are deliberate.

## Svelte

`src/format/svelte`: a port of `prettier-plugin-svelte` 4.1.1, which oxfmt calls too, and of the parser of Svelte 5.57 (`phases/1-parse`).

- **The steps are the plugin's, but for the first.** The plugin takes what is in `<script>` and `<style>` out of the text before Svelte parses it, with two regular expressions that know nothing of comments, strings and attributes, leaves a mark in its place, and looks for the mark to put it back. Whole scripts are lost that way, and the mark is written to files. Here nothing is taken out: the parser reads a script up to its end tag and a style sheet up to the `</style` between two rules (`end_of_css`: not the one in a string, a comment or `url()`), as Svelte does, unless Svelte throws there or what the end tag is in is not closed where CSS wants it closed, on its line: then it is the first end tag, and the style sheet stays as it is, with a warning, and the tree says where what is in it is (`Kind::Script`, `Kind::StyleSheet`, the text in an element). `parser.rs` makes the tree of `parse(text, { modern: true })`, as far as the plugin looks at it (`ast.rs`). `print.rs` makes the plugin's documents of it, as a tree (`doc.rs`): the plugin takes documents apart again (`trim`, the last child of a list), so they cannot be written as they are made. `doc::write` writes them through `html/writer.rs`, and lets go of each as it is written. `code.rs` writes JavaScript and style sheets where `embed` does.
- **JavaScript in the markup** has no end that could be found without parsing it. `trait Js` (`parser.rs`) asks for one expression, declaration or type at a place in the text. `js.rs` answers with `FormatOptions::parse_parts`, which the driver implements on `bun_sema_parser::Parts`: it is made for one text, so what the scanner finds out about the whole text is found out once, not for every expression. That says where a part ends. The file that is looked at is parsed from the part alone, so that what a `File` looks for in its text (backslashes, `<!--`) is not looked for in the whole component for every expression. There is no scanner of JavaScript here, and there must not be one. The parser reads TypeScript in every file. In a component that is JavaScript to Svelte, what only TypeScript has is an error (`File::first_typescript_syntax_in_javascript`), but `as`, `satisfies` and `!`, before which acorn stops: `{#each a as b}`. What has been parsed as TypeScript is printed as TypeScript. Which of the two it is has to be known before the first script is parsed, so it is `regex_lang_attribute` of Svelte that says so (`is_typescript` in `parser.rs`), with both of its alternatives: the letters `lang=` anywhere before the first `>` of a `<script`, or a `lang` behind attributes with values, in which there can be a `>`, as in `generics="T extends A<B>"`. The first script with a `lang` counts.
- **Nothing is parsed or looked for again and again.** Svelte finds the end of the expression of `{#each a as { b = c }}` by hiding what is from the last `as` on and parsing again, as often as it takes. Here what is before the error is parsed once more, by the parser that makes up what is missing, and the expression ends at the last place with an `as` behind it where something ends that is in nothing else (`Js::ends_of_expressions`): three times at most. What is looked for ahead (the next `>`) is remembered for as long as it holds (`Next`), what is asked of the stack is kept with it (`Parser::is_in`), and the places of many warnings are found in one pass (`BeforeNormalizing`, `Places` in the driver), which shows a line once.
- **Hooks in the printer of JavaScript**: `HtmlRoot::{SvelteExpression, SvelteStatement}`, `InHtml::{has_single_quotes, has_babel_tree}`, `Formatter::write_with_lines_removed` (Prettier's `removeLines`, which keeps conditional groups).
- **When** (`Configs::formats_svelte` in `src/lint/driver/fmt`): `--svelte`, `--no-svelte` and `svelte` in `[fmt]` turn it on or off, and `[[fmt.overrides]]` can do that for some files. Like every option, they override a config file unless `--config-precedence` says otherwise. The options are `svelte.sortOrder` and so on in `[fmt]` and for oxfmt, and `svelteSortOrder` and so on for Prettier. If none of those are set, it depends on the config. Without a Prettier or oxfmt config, Svelte is on. With oxfmt, it's on if the config has `svelte`, which an override can turn on and off for some files, including Markdown files with Svelte blocks. With Prettier, it's on if the config lists the plugin for the file, whichever version of it is installed: components never go to the project's Prettier. Other versions print some components differently (4.1.0: 19 of 7,047 real ones). The values of the plugin's options are only read where components are formatted.
- **Ranges and cursors**: to Prettier, nothing in a component is a source element, so with `rangeStart` or `rangeEnd` the file is left unchanged, like HTML. Prettier then prints the text that the plugin parsed, with `✂prettier:content✂` in place of each script's content. It also looks up `cursorOffset` in that text. Bun finds the cursor by comparing the component with its formatted text (`cursor_in_formatted_text`).
- **What the plugin damages** is a long list, and each has its rule in `print.rs`, `pattern.rs` or `code.rs`, with a comment that says what the plugin prints, and a row in the tests. A rule is about what is wrong, not about an input. White space: it is text before an inline element whatever is before the text, between two texts that a script was between, everywhere in `<pre>` and `<textarea>` (in an element with nothing else in it, in a block), next to a comment that goes elsewhere with its script, and a no-break space is never white space, but at the end of the component, where Svelte has `trimEnd()`. Where sorting puts one there, it is written as `&nbsp;`, and U+FEFF at the start of the file as `&#xFEFF;`. What is as it is written (under `<!-- prettier-ignore -->`, a `<tr>` in a `<tr>`) has no white space at its ends, which is printed around it. What follows a comment that is at the end of its line is on the next line, in a tag of Svelte and in a start tag. What is printed behind a `{` does not start like a tag of Svelte (`{(/a/.test(b))}`). Where Svelte takes no comment, none is printed: behind a declaration (`{const a = (b /* c */)}`), behind the expression of an `{#each}` without `as`, behind the name of a snippet. Code that would end with one once it is formatted stays as it is written (`can_end_with_comment` in `code.rs`), and so does the expression of an `{#each}` without `as` that would end with an `as` (`{#each () => (a as B)}`). Who prints something else in the place of an expression looks for comments first (`has_comments`, not `has_comments_around`): `a={/* b */ a}` is not `{a}`, `this={/* b */ "a"}` is not `this="a"`, and a `{:then a /* b */}` with nothing in it stays. The head of a snippet stays as it is written where a comment would be printed behind its `)`: the only parameter is hugged (`should_hug_function_parameters`), and the comment is not between the brackets of the pattern or of the default, or the braces of a type, where a line ends behind it. So it does where Prettier itself moves a comment each time: one behind the `=` of a default that starts with a parenthesis (`a = // b\n(c as D).e`, in a `.ts` file too). With `svelteAllowShorthand: false` a name is written out only if it can be a variable: not `class:a-b`, `style:--a`, `class:if`. A script without a `lang` is code only if its `type` says so (`has_type_of_code`: none, `module`, a name of JavaScript or TypeScript, `text/partytown`, whatever the case and whatever is behind a `;`), or JSON. Any other stays as it is written, byte for byte and without a warning, whether it can be read as JavaScript or not: the plugin reads all of them as JavaScript, so `x^2 + y^2` in a `math/tex` becomes `x ^ (2 + y) ^ 2;` and `<p>{{a}}</p>` in a `text/template` is JSX. Nothing that is written is left out: modifiers, the parts of `this="h{a}"`, a `{:catch}` with nothing in it, without which Svelte throws the error again. Also: `prop='"'` becomes `prop="""`, `this={'a"b'}` becomes `this={"a"b"}` and `this={ "a\\b" }` becomes `this="a\\b"` (a string is made a text only if it is letters, digits and `-_:.`), the head of `{#snippet a(b /* () */)}` ends in the comment, the comment in `{#each a as b: /* c */ D}` is lost, a comment around an expression is lost (`{a /* b */}`, `{#if a /* b */}`, `on:a={b /* c */}`), so is one in a pattern or in `{@debug}`, what follows a `//` comes before it (`{@const a = b} // c`), `{ b: c = 1 }` loses its key, `<keygen>` gets an end tag that Svelte refuses, and so does a `<tr>` that another `<tr>` has ended a cell in. So have what is in a script under `<!-- prettier-ignore -->`, a `literalline` at an end of the markup, and the parts of a component with `svelteSortOrder: "none"`.
- **Syntax errors** are where Svelte throws. One in a `<script>` or a `<style>` is a warning, as it is for the plugin: what is in the tag stays as it is, `Scratch::unformatted` has the message and the place, and the driver prints it (`Scratches::warnings`).
- **`--debug-check`**: `verify.rs`, on the reader of `html/verify.rs`. Its header says what is compared: among it the words of the markup in their order, the white space that is text, every byte in `<pre>` and in the value of an attribute, the tokens of the code in the markup in their order (`File::tokens`), and the number of comments. What a token is comes from the tree where that matters: a string that is a value is no name and a word like `static` that is one is no modifier (`exprs_of_kind`), never from the tokens next to it, which change, a template is free to change if `verify::is_in_another_language` says so. It compares tokens, not trees, and neither parentheses nor commas: `(a + b) * c` is `a + b * c` to it. `verify::compare` would tell them apart, and takes a `Program`, which only the driver can make. Scripts are compared by their letters, as in HTML. `bun fmt --debug-check-svelte <before> <after> ..`, in debug and canary builds, is the check for two texts: the tests give it what the plugin prints.
- **Tailwind**: `tailwind.rs`, the plugin's `transformSvelte`.
- **Tests**: `test/cli/format/svelte`. `cases.json` has what the real plugin and the real oxfmt print, and is made by `test/cli/format/oracle/svelte/make-fixtures.ts`. An oracle has to repair two things after every file: see there.

## Languages that only a plugin of Prettier reads

`.astro`, `.php` and the like: languages that Bun can't parse. In Prettier's flavor, a file whose language comes from a plugin in the config is handed to the project's Prettier. A file that Bun can parse never is, and that includes `.svelte` and `package.json`.

- **Where**: `src/lint/driver/fmt/prettier.rs`, which talks to the host of the JS plugins of `bun lint`: `src/lint/js_plugin/prettier.rs` and `worker/prettier.js`.
- **When**: `prettier` and every package that the configuration names as a plugin are installed. Prettier loads all of them, also those that are built in here. Else the files are named and left as they are.
- **Options**: Prettier resolves them, from the configuration file that the driver has found. The flags are merged as `--config-precedence` says.
- **Tests**: "a language that only a plugin of Prettier reads" in `test/cli/format/format.test.ts`, with a plugin of a few lines.

## Pitfalls

- oxc tracks an older release of Prettier (3.8). Where they differ, the snapshot of 3.9.9 is right.
- `Expr::span()` is without parentheses, like in ESTree. `e.outer_span()` has them.
- A backtick string without substitutions is `ExprKind::Template`. JSX text is `ExprKind::String` with `e.is_jsx_text()`.
- `a, b, c` is `Binary { op: Comma }`, left-nested. `e.sequence()` are the operands. `BinaryLikeExpression::new(e)` is `None` for it. `#a in b` is a binary-like expression (`AstNodes::PrivateInExpression` tells it apart).
- Patterns in declarations are `Pat`. In assignments they are expressions: `e.is_assignment_target()`, and `as_ast_nodes()` says `ArrayAssignmentTarget`, ..
- `export` is a modifier of the declaration. `stmt.as_ast_nodes()` is the `ExportNamedDeclaration`, `FormatDeclaration(stmt)` the declaration in it, `stmt.span_without_export()` its span.
- Methods: `member.func()` / `prop.func()` is the function, whose span starts at the parameters in ESTree.
- Elements of `implements` and of the `extends` of an interface are `TypeKind::Ref`, or `TypeKind::Heritage` if they are not names.
- `x!!` is one `ExprKind::NonNull(x)`. `FormatNonNullMarks(e)` writes every `!`.
