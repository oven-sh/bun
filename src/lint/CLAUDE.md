# `bun lint`

A linter that is compatible with ESLint and typescript-eslint: the same rule names, options, messages, report locations, fixes and `eslint-disable` comments. Rules are written in Rust against the HIR and binder output that `bun check` already produces. **Nothing is converted to ESTree**, and no rule or helper may build or query an ESTree tree or esquery selectors: that is for a later JavaScript plugin API. Design goals, in order: correct (matches ESLint), fast, pleasant to write rules in.

## Add a rule: the checklist

A rule is done when all four are done. CI fails if 2, 3 or 4 is missing.

### 1. Write it

One file, `src/lint/<crate>/rules/<name_in_snake_case>.rs`. See [Writing a rule](#writing-a-rule). Pick the crate by where the rule comes from:

| The rule is                       | Crate                                 | `Meta`                                          |
| --------------------------------- | ------------------------------------- | ----------------------------------------------- |
| An ESLint core rule               | `eslint`                              | `Meta::eslint("no-foo", kind)`                  |
| A typescript-eslint rule          | `typescript`                          | `Meta::typescript("no-foo", kind)`              |
| A port of an ESLint plugin's rule | `plugins`, `react`                    | `Meta::plugin(Plugin::Import, "no-foo", kind)`  |
| A port of an oxlint rule          | `unicorn`, `react`, `jest`, `plugins` | `Meta::oxlint(Plugin::Unicorn, "no-foo", kind)` |
| Bun's own                         | `plugins`, file `bun_no_foo.rs`       | `Meta::plugin(Plugin::Bun, "no-foo", kind)`     |

`kind` decides the default severity: `Kind::Problem` is for code that misbehaves, `Kind::Suggestion` for code that could be better.

### 2. Register it

- Add `module::Struct,` to the `bun_lint::rules! { .. }` list in the crate's `lib.rs`, in alphabetical order. That is the only list. `--rules`, name lookup, aliases, config validation and the docs URL all come from `META`.
- **Options**: the JSON schema is data, not code.
  - Bun's own rule: add `"bun/no-foo": [<schema of each option>]` to `src/lint/linter/schema/own.json`. `[]` means no options.
  - A port: the schema comes from upstream. See the header of `src/lint/linter/schema/generate-schemas.mjs`.
  - Then regenerate `schemas.txt` and `data.rs` with that script.
- **On by default?** Almost never. `.recommended()` / `.presets(..)` mirror what upstream's presets turn on. What is on with no config file is `BUILT_IN` in `src/lint/driver/configs.rs`.

### 3. Document it

Every rule has a page: `docs/lint/rules/<plugin>/<rule>.mdx`. It shows up on the website, in `bun lint --explain <rule>` and in editors. Copy a good one: `eslint/eqeqeq.mdx` (options), `eslint/no-var.mdx` (short), `typescript/no-floating-promises.mdx` (types), `bun-test/no-focused-tests.mdx`.

````mdx
---
title: "bun/no-foo"
description: "Disallow `foo()` outside of tests"
---

What goes wrong without the rule, concretely. One short paragraph.

## Examples

Reported:

{/* bad */}

```js
foo();
```

Not reported:

{/* good */}

```js
bar();
```

## Options
````

- You write `title` (the ID as reports print it), `description` (one line, at most 110 characters, no full stop) and the text. The rest of the frontmatter, the `## Configure` section and `index.mdx` are generated:
  ```sh
  bun src/codegen/lint-rule-docs.ts --write --bun=./build/debug/bun-debug
  ```
- **Every example is run.** Each `js` / `jsx` / `ts` / `tsx` block needs a marker on the line before it:

  | Marker                                                          | Meaning                                                                                                |
  | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
  | `{/* bad */}`                                                   | The rule reports this code                                                                             |
  | `{/* good */}`                                                  | The rule reports nothing here, and the code parses                                                     |
  | `{/* bad {"options": ["smart"]} */}`                            | With these options                                                                                     |
  | `{/* bad {"count": 2} */}`                                      | Exactly two reports                                                                                    |
  | `{/* good {"filename": "a.test.ts"} */}`                        | The file has this name                                                                                 |
  | `{/* file "other.js" */}`                                       | Another file next to the next example                                                                  |
  | `{/* bad {"root": true} */}`                                    | The example is its own project and working directory. For options that are paths, like `src/client/**` |
  | `{/* bad {"root": true, "packages": {"prettier": "3.9.9"}} */}` | These packages are installed next to it                                                                |
  | `{/* bad {"config": "oxlint", "settings": {..}} */}`            | Run next to an `.oxlintrc.json`. For a rule that only reports there                                    |
  | `{/* skip */}`                                                  | Not run. For a fragment that cannot stand alone                                                        |
  | `{/* never reports */}`                                         | On its own line: the rule reports nothing, so the page needs no `bad` example. Say why in the text     |

- Prettier skips `docs/lint/rules` (`.prettierignore`): it would reformat the examples, and many rules are about exactly that.
- Say the problem, not "This rule enforces ..". Use normal programmer English. Be succinct. Small realistic examples (`user`, `items`, `save()`, not `foo`). The good example shows how to fix the bad one.
- Every claim is shown by an example or read in the source. Do not write what you remember about the rule from another linter, and do not copy another tool's docs.
- An options table (`Option | Default | What it does`) plus an example for each option that is not obvious.
- **`## Configure` is generated. Don't edit it.** It sits between two marker comments, before `## Examples`. It shows how to turn the rule on in `bunfig.toml`, then every option set to its default. A deprecated rule and a rule that never reports don't get one. Names, types and enum values come from the rule's schema. For an oxlint port, which has no schema, they come from the options table and the `options` of the examples. A default comes from upstream's `defaultOptions`, then from `default` in the schema, then from what you write under `## Options`:

  | You write                                                    | The snippet has                                                |
  | ------------------------------------------------------------ | -------------------------------------------------------------- |
  | `` `20` `` in the `Default` column: JSON in backticks        | `max = 20,`                                                    |
  | Anything else in that column, such as "none"                 | `# max = <number>,`                                            |
  | ``the value of `fn` if you set it, otherwise `"it"` `` in it | `withinDescribe = "it",`                                       |
  | `` `"always"` (default) `` or ``The default is `"always"` `` | `"always"`, for an option that is a plain value, not an object |

  The test lints every example on the page twice, with the rule only turned on and with that snippet. If the reports differ, a default is wrong.

### 4. Test it

| The rule is | Where its tests are                                                                                                                            |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| A port      | Upstream's own cases, in `test/cli/lint/conformance/bundle.zst`, with what the real tool reports. See [Testing](#testing) and the README there |
| Bun's own   | A table in `test/cli/lint/bun-rules.test.ts`: `«` and `»` mark what is reported, a plain string without them is a case with no report          |

```sh
bun bd test test/cli/lint/bun-rules.test.ts -t no-foo
bun bd test test/cli/lint/rule-docs.test.ts   # a page for every rule, generated parts up to date, every example and snippet runs
bun bd test test/cli/lint/conformance.test.ts
```

Test what the rule must NOT report as hard as what it must: a false positive costs more trust than a miss. If the message alone leaves a reader puzzled, add a hint (see `test/cli/lint/hints.test.ts`).

## Writing a rule

Read `rule.rs` (module docs) first, then `ast/mod.rs`. `eslint/rules/{no_debugger,eqeqeq,no_labels,max_classes_per_file,no_cond_assign}.rs` are the examples to imitate.

- File `no_foo_bar.rs`, struct `NoFooBar`, `Meta::eslint("no-foo-bar", ..)` / `Meta::typescript(..)`. `use bun_lint::prelude::*;`
- The struct holds the parsed options and nothing else. It is shared by all threads. Per-file state is `type State<'a>`, returned by `start`, reached as `cx.state`. `no_state!();` writes both for a rule that keeps nothing and is for every file.
- One `const NAME: Message = Message::new("messageId", "Text with {{placeholders}}.")` per upstream message, with upstream's `messageId` and text verbatim.
- A message that does not tell what is wrong and what to do gets a hint: `.hint("One sentence.")` or `.hint_with(|| ..)` on the report, `.hints()` on `Meta`, and a case in `test/cli/lint/hints.test.ts`. `pretty` and `agent` print it under the message, no other format does, and never with a configuration of oxlint. It is Bun's own text: one line, about 90 characters, plain words. All work for it is in the closure, which runs only for a report that is shown.
- `Meta` mirrors upstream `meta`: `kind`, `.fixable(..)`, `.has_suggestions()`, `.recommended()` / `.presets(..)`, `.requires_types()`, `.deprecated()`, `.extends_base_rule(..)`.
- Options: apply upstream's `defaultOptions` / schema defaults by hand in `new`. `options.object(0)` is empty when missing, so every lookup falls back to the default.
- The doc comment on the struct is upstream's `meta.docs.description`.
- Port the behaviour of the upstream JavaScript/TypeScript rule, not oxc's. oxc's Rust port of the same rule is useful for ideas, but it deviates from ESLint in places and its AST is different.

### Listeners, and why they look the way they do

A listener is a method of `Rule`. `const ON: On` names those that are called, and for which kinds: `On::new().exprs(&[ExprTag::Call, ExprTag::New]).binaries(&[BinOp::EqEq]).funcs().finish()`. It is a constant, so which code runs for a rule is known when it is compiled: there is no table of callbacks and no call through a pointer. The HIR keeps the nodes of a file in one vector per sort. So:

- `.exprs(&[ExprTag::Call])` + `fn expr`, `.stmts(..)` + `fn stmt`, `.types(..)` + `fn ty`, `.pats(..)` + `fn pat`, `.funcs()` + `fn func`, `.classes()`, `.members()`, `.props()`, `.params()`, `.var_decls()`, `.cases()`, `.symbols()`, ..: the method runs in a tight loop over exactly those nodes, **in no particular order**. No tree walk. **This is the default. Use it unless the rule cannot work without order.** Several kinds of one sort with different work: one method with a `match` on `tag()`.
- `.enter(tags)` + `fn enter` / `.exit(tags)` + `fn exit`: source order, around the children. The nodes of the listened kinds are collected and sorted by span, so it costs in proportion to how many there are: fine for functions, classes, loops and blocks, wasteful for identifiers. Use it for rules that are inherently about nesting order. `tags` is a constant: `NodeTags::new().exprs(&[..]).stmts(&[..]).union(NodeTags::FUNC)`.
- `.binaries(&[BinOp::EqEq, BinOp::NotEq])` + `fn binary`, `.unaries(&[UnOp::Typeof])` + `fn unary`: the `Binary` / `Unary` expressions with these operators only. `.optional_chains()` + `fn optional_chain`: the `Dot`, `Index` and `Call` that are part of an optional chain. A rule about `==` is not called with the other operators, and not at all in a file without a `==`.
- `.method_calls(&["then", "catch"])` (`a.then()`), `.function_calls(&["require"])` (`require()`), `.calls_named(&[..])` (both), `.members_named(&["length"])` (`a.length`) + `fn expr`, in place of `.exprs(&[ExprTag::Call])` / `.exprs(&[ExprTag::Dot])`: for a rule that does nothing with a call or a member of another name. It is called with those, in the order in which it would be called with all, and with every one whose name takes more than a look to find: `a["b"]()`, `a.#b()`, `a.b!()`, `(a.b as T)()`, `a()()`, `super()`. **It still compares the name**: the calls are grouped by a class of names, so a few of other names come too. They add up with each other and with other kinds. `new a.b()`, ``a.b`c` `` and `import()` are no `Call`s. In a file that mentions none of the names and has none of the odd ones the rule is not started: up to 12 names fit in `ON`, a rule with more has a guard in `start`. Names that only the options know: `ON` has all calls, and `narrow` names them one by one (`on.method_call(name)`, `.function_call(..)`, `.member_named(..)`). From `start` or `finish`, without `fn expr`: `file.calls_on(&Self::ON)`.
- The sorts run in the order in which `Rule` has the methods, the kinds of a sort in the order of their `enum`.
- `fn narrow(&self, file) -> On`: what of `ON` the rule listens to with its options, under this flavour, in this file, built with the same builders. Write it wherever an option decides about a listener or a kind: not an early return at the head of a method, which is a call per node, and never `enter` / `exit` for nothing, which make the linter put nodes in order. What is not in `ON` does not count. A rule whose kinds only its options know (selectors) names all in `ON`.
- `fn start(&self, file) -> Option<State>`: once per file, after `narrow`, and only if the file has a node of a kind that is listened to. `None`: not this file. `finish`, `enter` / `exit`, `symbols`, the literals and `nodes` count as "every file has it": a rule with those says in `start` whether the file has a candidate.
- A rule about a **name** (`eval`, `require`, `hasOwnProperty`, `Promise`, ..) has `file.mentions("eval").then_some(..)` in `start` (`file.mentions_any(&[..])`): a filter that the parser fills, which costs a few instructions. Not in a listener: there it is asked once per node. `false` is certain, however the name is spelled. It is sound only where the name has to be an identifier, a key, a name in a type, a string or a piece of a template of the file: helpers that evaluate constants (`get_string_if_constant`, `get_static_value`, the properties that `ReferenceTracker` follows) can make `"eval"` of `"ev" + "al"`. Not for private names.
- Reachability needs no listener: `stmt.is_reachable()`, `case.is_end_reachable()`, `func.is_end_reachable()`, `file.has_unreachable_statements()`, `stmt.is_repeating_loop()`. A rule that needs ESLint's segments analyzes the few functions that are candidates itself (`func.code_path_steps(enter, exit)`, `code_path::steps_of_code_path(..)`: see `constructor_super.rs`, `no_useless_return.rs`). There are no listeners for code paths.
- `.string_literals()` + `fn string_literal` / `.number_literals()` + `fn number_literal`: every ESTree `Literal` that is a string / a number, as a `Literal` (`span()`, `text()`, `owner()`). Only some are expressions here: the others are keys, literal types, module specifiers, names in quotes of imports and exports. Use these instead of listing the places by hand.
- In `start` and `narrow`, `file.has_exprs(..)`, `file.has_stmts(..)`, `file.exprs_of_kind(tag)`, `file.stmts_of_kind(tag)`, `file.funcs()` tell whether there is anything to listen for.
- `.finish()` + `fn finish(&self, cx: &mut Cx<'_, Self>)`: once at the end. Collect in `cx.state` from unordered listeners, decide here.
- ESLint rules often keep a stack only to know "which function/class/loop am I in". Do not port the stack: ask the node (`node.enclosing_function()`, `node.ancestors()`, `func.enclosing()`, `func.returns()`, `func.yields()`).
- Reports are sorted by where they start. ESLint leaves what **starts at one place** in the order in which it was reported, which is the order of its traversal: every listener on entering a node before every listener on leaving one, the outer node first on entering and last on leaving, and what is reported when the program ends after all that. That order is printed, and it decides which fix wins. Here the end stands in for the node: the longer first. A rule says where that is wrong: `Meta::reports_on_exit()` (upstream reports in `:exit` listeners or at the end of a function's code path: after what is reported on entering, the shorter first), `Meta::reports_at_the_end()` (only in `Program:exit`: after all that, rule by rule), `Report::on_exit(bool)` where only some listeners are such, `Report::shorter_first()`.
- **Two reports of one rule with the same span** stay in the order in which they were made. A rule in which two listeners (or two kinds, or two nodes of one kind) can report at one place listens by `enter` / `exit` for those kinds (right for a rule with types, or with few nodes), or collects the candidates and reports in `finish`, sorted by the start of the listened node, the longer first: see `no_unsafe_assignment.rs`. `--run-eslint-tests .. --in-order` fails a case whose messages come in another order than they were recorded.

### When the rule itself fails

A JavaScript rule that can't do its job throws: a file named in its options is missing, or isn't JSON. A report can't say that, because a report has the severity the rule is set to, and a comment can disable it.

| The JavaScript rule                              | Here                                                                                      |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| throws in `create` because of its options alone  | `fn validate(options) -> Result<(), Vec<u8>>`. Checked once per config. It ends the run   |
| throws anywhere else: `throw new Error(message)` | `cx.throw(node, "Error", message)`, then `return`. `node` is the node the listener is at  |
| `JSON.parse(text)`                               | `bun_lint::linter::json_parse(text)`: V8's error messages, and no limit on nesting either |
| `fs.readFileSync(path)`, `fs.existsSync(path)`   | `file.modules()?.read(path)`, `.exists(path)`                                             |

What `cx.throw` does is what the real tool does with a rule that throws, whatever severity the rule has:

- **oxlint config**: the file gets one error, `Error running JS plugin.`, with the path and `Error: message`. It has no rule name, no comment disables it, `--quiet` keeps it, and the exit code is 1. The file keeps what the rules that oxlint has itself report, and loses what every other rule reports: this rule, the JavaScript plugins, and the other native rules that oxlint doesn't have. That's what oxlint does when a rule of a JS plugin throws. A comment that disabled one of the lost reports then counts as unused. The next file is linted as usual.
- **ESLint config, or none**: the run ends with exit code 2 and `message`, `Occurred while linting <file>:<line>`, `Rule: "<id>"`.

Only one throw per file counts, so calling it from a listener that runs for every node prints one error. `start` has no `cx`: keep the problem in the state and throw from `finish` or the first listener. See `test/cli/lint/rule-throws.test.ts`.

### Performance rules

- Decide from the syntax first. Touch tokens, comments, line/column, references, scopes and types only when the cheap checks have passed: each of these is computed lazily for the whole file on first use.
- Nothing is declared or resolved before a rule asks. `pat.symbol()`, `symbol.declarations()`, `node.scope()`, `scope.symbols()/get/resolve` compute the scopes and variables of the file on first use; `expr.symbol()`, `symbol.references()`, `expr.reference()`, `file.unresolved_references()` also the references. Together that costs a third of what parsing the file costs. After that each is a load or two.
- `skip_trivia_back` takes a token that ends in `*/`, like the regex `/a*/`, for a comment. Where that can be, use `file.token_before(..)`.
- `skip_trivia(text, end_of_node)` finds the next token after a node without scanning the file. `expr.operator_span()`, `func.open_paren()`, `func.arrow_span()`, `func.body_span()`, `class.body_span()`, `call.close_paren()` are positions the HIR already has or finds locally.
- No allocation on the path that reports nothing. No `format!`, `to_vec`, `collect` before you know there is a report.
- Compare `Name`s with each other (`a == b` is an integer compare), or with text by `name.is("x")` / `name.is_any(&[..])` / `match name.bytes() { b"x" => .. }`, which look the text up. In a listener that is called with many nodes, compare with a `Name` that `start` has made once (`file.name_of("x")`, kept in the state).
- A rule that asks the same of every identifier (a pattern, a length, a prefix) keeps the answers in a `bun_lint::source::ByName<T>` in its state: `cx.state.known.get_or_insert_with(name, || ..)` is a load after the first time, and a file has ten times as many identifiers as names. See `id_match.rs`.
- A rule with hundreds of names that are not constants of the program computes `mention_bit(text)` once in `new` and asks `file.mentions_bit(bit)`.
- `narrow` and `start` run for every file that has a node of a kind in `ON`, and most repositories are made of small files: no allocation, no search of the whole text and no shared data (scopes, tokens, lines) in them unless the file has a candidate.
- The cheapest and most selective test first: the operator, the number of arguments, `tag()` of a child, a byte of the text, before anything that walks (`parent()`, `ancestors()`, `scope()`), allocates or searches. Compute nothing up front that only the path that reports needs. `e.tag()`, `as_ident()`, `as_call()`, `as_fn()`, `chain()` are loads, `kind()` is a call.
- `symbol.has_reads()`, `has_writes()`, `has_modifying_references()` are one load: ask before walking `symbol.references()`.
- `ast_utils::equal_tokens(a, b)` decides plain text without tokens. `file.position(..)` and `file.line_of(..)` count line breaks while few are asked for. `file.comments()` is a list the parser made. A question about tokens still scans the whole file.
- The budget: on 10,000 files (143 MB, 7.8 M expressions) a rule should cost 0.5 to 3 ms of CPU where it reports nothing.
- `.fix(|fixer| ..)` and `.suggest(..)` closures only run when fixes are wanted. Put all fix computation inside them.

### Code conventions (Bun-wide, enforced by CI)

- No `unsafe`. No `.unwrap()`/`.expect()`/indexing that user input can make panic: use `let .. else`, `?`, `.get()`.
- Text is `&[u8]`. Searching goes through `bun_core::strings` (`index_of`, `index_of_char_usize`, `index_of_any`, `contains`, `contains_char`, `last_index_of_char`, `split`, ..): `str::find/rfind/contains/split*/replace*/matches`, `slice::windows`, `.iter().position(|b| *b == b'x')`, `.contains(&b'x')` are denied by lints. `==`, `starts_with`, `ends_with`, `trim_ascii`, `eq_ignore_ascii_case` are fine. What JavaScript does to a string (`trim`, `\s`, line breaks, `length`, `<`, `localeCompare`, `Number(s)`, `toFixed`) is written once, in `bun_core::strings` and `bun_core::fmt`: the table at the head of `utils/text.rs` says which function is which. Do not write a private helper for text in a rule.
- No `std::fs`, `std::path`, `std::env`, `println!`.
- Every warning is an error: no unused imports, variables, `mut`, dead code. `pub` only for what another crate uses, otherwise `pub(crate)` or private. (The rule struct and a struct used as its `State<'a>` have to be `pub`.)
- The clippy lints in `[workspace.lints.clippy]` are denied too. The ones that bite: `derive_partial_eq_without_eq`, `or_fun_call` (`.or_else(|| f())`, not `.or(f())`), `needless_pass_by_value`, `redundant_clone`, `trivially_copy_pass_by_ref`, `needless_collect`.
- Comments: only what the next reader could not work out quickly. Never narrate the port, never reference ESLint line numbers. Naming the upstream helper a function corresponds to (`` /// ESLint's `isLoop` ``) is good.
- Let-chains (`if let Some(x) = a && let Some(y) = b`) are available and preferred over nesting.

## ESTree → this API

ESLint's rules, docs and tests speak ESTree (TSESTree for TypeScript). The mapping:

| ESTree                                                                                                                                                                                                                                                                                                             | Here                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Program`                                                                                                                                                                                                                                                                                                          | `&File`, `Node::File`. `file.body()`                                                                                                                                                                                                           |
| `Identifier` (a reference)                                                                                                                                                                                                                                                                                         | `ExprKind::Ident(name)`                                                                                                                                                                                                                        |
| `Identifier` (a binding)                                                                                                                                                                                                                                                                                           | `PatKind::Ident(name)`                                                                                                                                                                                                                         |

### Report locations must match ESLint's

The fixtures compare `line`, `column`, `endLine`, `endColumn`. `.span()` equals the ESTree range for most nodes. Known differences, which you must handle when upstream reports such a node:

- An exported declaration: see `ExportNamedDeclaration` above.
- A method's function: `func.span_from_params()`.
- `Identifier` with a type annotation (`a: T` in a declarator or a parameter): typescript-estree's range of the identifier includes `?` and the annotation. `pat.span()` does not: `param.binding_span()`, `var_decl.binding_span()`.
- A parameter: ESTree has no parameter node. `a = 1` is an `AssignmentPattern` (`param.span_without_modifiers()`), `...a` a `RestElement`, otherwise it is the pattern.
- JSDoc casts in `.js` (`/** @type {T} */ (e)`) are invisible: there is no `As` node, the parentheses belong to the operand.
- `fn expr` for `ExprTag::Dot` is also called with JSX tag names (`<a.b />`, `expr.is_jsx_tag_name()`) and with the operand of a `typeof a.b` type, which are not `MemberExpression`s for ESLint. Conversely `extends a.b` of an interface and `implements a.b` are `TypeKind::Ref` here and `MemberExpression`s there.
- `MemberKind::Constructor` also covers `static constructor() {}`, which ESLint calls a method.
- A `Member`'s span includes its `;`, like ESTree's `PropertyDefinition`, and for interface members the `,` or `;`, like `TSPropertySignature`.
- A `VariableDeclaration` in the head of a `for` has no `;`.

If the API lacks something you need (a position, a flag, a helper several rules want), do not work around it in the rule by re-scanning text in an ad-hoc way. Say so in your final report, naming the accessor you wanted, and write the rule as if it existed.

## Testing

```sh
cargo build --release -p bun_sema_standalone                         # bun-sema
zstd -dc test/cli/lint/conformance/bundle.zst > /tmp/bundle.txt         # the test cases
bun bd lint --run-eslint-tests /tmp/bundle.txt --rule=eqeqeq --verbose
bun bd lint --run-eslint-tests /tmp/bundle.txt --report=/tmp/report
target/release/bun-sema hir file.ts --print                          # the HIR of a file
bun bd test test/cli/lint/conformance.test.ts                        # the test cases on `bun lint` itself, those with types too
```

Each fixture `<plugin>/<rule>.json` has upstream's `meta` (messages, schema, default options) and, per case, `code`, `options`, `languageOptions`, and the `messages` and `output` that real ESLint produces.
