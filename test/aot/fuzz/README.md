# Fuzzing the ahead-of-time compiler

`run.ts` makes small programs without end. It runs each one twice, once with `bun <file>` and once as an executable built by `bun build --compile --aot`, and keeps every program for which the
two runs differ. Nothing in this folder runs in CI, except the tests of the fuzzer itself (`../the-fuzzer-*.test.ts`). Run it by hand after a change to the compiler, for as long as you can
spare a machine.

## Run it

```sh
bun test/aot/fuzz/run.ts --seconds 3600 --jobs 16 --out /tmp/fuzz
```

`bun` is a Bun built from this tree: `bun run build:release` leaves it at `build/release/bun`. The Bun that runs the script is the Bun under test; `--bun <path>` names another one. A released
Bun that does not know `--aot` fails at the first build. Start it from the root of the repository. It needs no network and no reference build. Two sources start `python3` and
draw nothing where it is missing, and `--written-again` reads programs with the `typescript` package, which `bun install` at the root brings. The comment at the top of `run.ts` lists every
option.

How long to run it:

| for                                         | run                                                                                                       |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| a smoke test that the fuzzer itself works   | `--seconds 120 --jobs 4`: a few hundred programs                                                          |
| a change to one part of the compiler        | ten minutes to an hour of the sources that aim at that part: `--sources <a>,<b> --seconds 3600`           |
| a release, or a change to the flow analysis | every source overnight on a large machine: `--rounds --seconds 3600 --jobs 32`, until `<out>/STOP` exists |

A build takes about a second of one core, so sixteen jobs judge some tens of thousands of programs an hour. Most finds come in the first hour behind a change; a source that has been quiet for a
night has little left to say about that compiler.

One run looks at one way to build. Several runs side by side, each with other options, find more than one wide run:

```sh
.. --modes default,every-function-hot,every-function-cold     # how hot a function is decides how it is compiled
.. --modes counts-as-very-large,cold-and-very-large           # what only a very large application gets
.. --validate                                                 # the executable checks at run time what the compiler took for proven
.. --modes moved-loads-checked,claims-checked                 # the same for loads that were moved and for what the back end is told
.. --collector-stress 1,2,3,5,7,11 --compiled-run-seconds 60  # a collection at every n-th allocation
.. --fail-predictions 1,2,7                                   # the general road is taken though the fast one would have done
.. --lowered-limits                                           # one limit of the compiler at 0, 1 or 2: a small program meets what only a large one does
.. --written-again                                            # each program also written again so that it prints the same and the compiler knows less about it
```

`burst.ts` starts such runs side by side, shares the cores of the machine among them, and lists what they found in one file, `<out>/NEW.tsv`:

```sh
bun test/aot/fuzz/burst.ts --minutes 60 --out /tmp/burst
```

Four of its lanes run `fuzzilli/lane.ts` in place of `run.ts`. That driver draws from scenes of ordinary code as well as from the sources here, puts from one to four hundred programs into one
executable, and holds each against `bun run`:

```sh
.. --kind few       # one to eight programs to a build: the compiler proves of a small program what it cannot prove beside many others
.. --kind many      # four hundred to a build, thirty-two to an entry point: four times as many programs in the same time
.. --kind packages  # each program split into files and packages
.. --kind external  # beside a package that is marked as external, so code that the build has not seen may run
```

On Linux every program, plain and compiled, runs with process numbers of its own and a process group of its own (`unshare --user --pid`, `setsid`), where the kernel lets anybody have them: whatever it signals, it reaches nothing but itself. Elsewhere,
and beside that, a program that names `kill` is not run at all (`accepted-differences.tsv`).

## What it draws from

A source turns a number, the seed, into a program. `--sources a,b:8` picks sources and weights them; without the option all are drawn. There are three kinds.

- **Generators.** Most files of this folder export `generate(random)`, which writes a program about one subject at random: any seed gives a program. `sources.ts` names them.
- **Tables.** A few files count their programs and export `programOf(index)`: every start of a loop crossed with every kind of typed array, say. The seed picks the row.
- **Lists**, in `sources/`. Where a subject is a cross of places, things and options, and some members need a flag, an environment variable or further entry points, a file of `sources/`
  writes the members down (`family.ts`). The seed picks the member. A list may go on without an end: member n is made when seed n is drawn (`endless`).

The table at the end of this file says what each source is about.

Every second program is also drawn in several files, under the name `<source>-in-several-files`: its declarations lie in up to four further files, some of them JavaScript, some with
declaration files that say too little or are not valid, some published as packages. `--one-file-only` turns that off.

## What a find looks like

`<out>/findings.tsv` gets a line for each find: when, how it was built, what kind of failure it is, `<source>:<seed>`, a name, and the two lines that differ. `<out>/findings/<name>/` holds

- `reduced.*`, the program cut down as far as the failure lets it (a folder if it has several files), and `original.*`;
- `plain.txt` and `compiled.txt`, what the two runs printed;
- `finding.json`: seed, source, mode, flags, and the pass or the result of the flow analysis without which the failure goes away.

`<out>/as-tests/<name>.<ext>`, or `<name>/main.<ext>` with its other files, is the reduced program once more, as a file of `../parallel`: its flags, entry points and exit code stand in its first lines.

The kinds: `different output`, `different exit code`, `crash` and `hang` of the executable; `internal compiler error`, `build crash`, `build hang` and `build error` of the build;
`validation failure`, where the executable caught a false proof. A death by a signal or a failed assertion is always a bug. A time limit that ran out on a busy machine is not a verdict.

`bun test/aot/fuzz/run.ts --replay <source>:<seed>` makes the same program again and prints it with its verdicts; `--print-only` only prints it.

A difference that is meant (docs/compiler/compatibility.mdx says which are) gets a line in `accepted-differences.tsv` with the reason, and is counted and not kept from then on.

## From a find to a test

1. Replay it on a fresh build, alone, to see that it is still there.
2. Take its file under `<out>/as-tests/` and cut it further by hand until every line is needed. `bun test/aot/run-parallel.ts --root=<out>/as-tests <file>` runs it as CI will.
3. Fix the compiler.
4. The small program lands with the fix, as `test/aot/parallel/<topic>/<what-it-does>.<ext>`, or as a folder with `main.<ext>` if it has several files. If it takes flags, its first lines say so:
   `// Flags: --aot-validate`, `// Env: TZ=America/New_York`, `// Entry points: ./child.cjs` (`../run-parallel.ts` lists them all). A fault of one pass is better pinned by a test in the compiler's
   own language under `test/aot/engine-tests/`.
5. Nothing else is committed: no seeds, no lists of programs that were once wrong, no output of a generator. The generator can make them again.

## Add a source

Write `<subject>.ts` with `export function generate(random: Random): string`, add its name to the list for TypeScript or for JavaScript at the end of `sources.ts`, and add a row to the table
below. Every program must print what it computes, must print the same in every run, and must end by itself within a second or two.

A finding is a folder `findings/<kind and what is guilty>/` with `reduced.*`, `original.*`, both outputs and `finding.json`. The small program goes to `../parallel` with the fix.

A failure that shows only while other programs share the build is kept as `findings/<kind> only together <..>/`: `p0.*` is the program, the other `p*` are the companions it needs, `main.js` imports the one its argument names, and `commands.txt` builds and runs it.

A typed program whose build stops at a type error is asked of TypeScript itself, under the options of the tsconfig.json that lay beside it and with Bun's typings at hand. What TypeScript refuses too is a fault of the source or a mutant that does not type-check: `status.txt` counts it as skipped, `type error TSn, as in TypeScript`. What TypeScript accepts, and plain Bun runs, is a finding of the kind `build refused`, one for each message.

A run ends its batches behind its clock. There up to four failures are still confirmed; from the last call on (a third of the run behind its end, five minutes at most) nothing is built again: what ended by a signal or stopped the compiler is stored as it was drawn (`<kind> not tried again <..>`, with the programs that shared its build), the rest is listed in `not-confirmed.tsv`. `../the-fuzzer-judges-as-it-says.test.ts` holds the driver to this and to the paragraph above.

After ten findings of a group no more of that group are stored, so move a finding out of `findings/` once it has been looked at.

A finding whose name says `no switch` goes away with no pass and no result of the flow analysis switched off. Most of these are no fault of the compiler: the program prints what differs by design.
What plain Bun prints differently each time it runs is dropped and listed in `unstable.tsv`; a kind that comes again gets a line in `accepted-differences.tsv`.

What is never meant (a build that runs out of its clock or stops with an internal error, anything that ends by a signal, a run that never ends) is not set aside by a line that looks at the text of a program alone, and is kept when it is a program of `../parallel` that fails by itself. One that ends by a signal, or stops the compiler, and does not do so at the next try is stored whole under `.. not at the next try ..`. A failure that is drawn behind the clock of a run is confirmed and stored as it is, without a reduction.

## Values that reach a place their type excludes (`unsound-types`)

`generators/unsound-types.ts` puts each program together from a hole of TypeScript's type system, a type, the value that arrives, the place where the reference is held, the kind of function that uses it, the time and the uses. A program is clean under `strict` and has no cast, no `any` and no `!`: `type-check.ts` asks TypeScript itself, and what it refuses is listed in `refused-by-typescript.tsv` and not run. That is a bug of the generator.

- A program is about one hole, which is its group: `groups.tsv` counts programs, runs and failures by hole, and two holes that fail with the same words are two findings.
- It has up to four cases, each with its own declarations. A finding is cut down to the case that fails by itself before it is reduced.
- The table `filed` at the top of the generator lists the holes, forms and uses that run into a bug that is filed already. They are not drawn. Take a line out when its fix is in. `AOT_FUZZ_UNSOUND_HOLES=a,b` draws from those holes only, filed or not.

```sh
bun test/aot/fuzz/run.ts --sources unsound-types:8,grammar --validate --out /tmp/fuzz    # eight programs of it for one of the grammar
bun test/aot/fuzz/run.ts --sources unsound-types --count-only --out /tmp/census          # which holes fail, and how: nothing is reduced
bun test/aot/fuzz/generators/unsound-types.ts /tmp/programs --count=1000 && bun test/aot/fuzz/type-check.ts /tmp/programs
```

## Texts parsed under generated types (`texts-for-generated-types.ts`)

A tool of its own, beside `run.ts`. It draws TypeScript types, writes one program that parses texts under each of them (`JSON.parse(text) as T`, a variable of type `T`,
`(await request.json()) as T`), builds it, and lets it run. The program makes its own texts for as long as it is given: texts that are a `T`, nearly a `T`, JSON of another shape, nearly JSON,
spelled and held in many ways. It needs no second run to compare with: nothing is checked and the value may be anything, so every call gives what a parser written in the program, one character
at a time, and `JSON.parse(text)` give. For every type it also holds a function that reads each member through the type and a twin with the same body whose parameter is `any`; both print the same.

```sh
bun test/aot/fuzz/texts-for-generated-types.ts --seconds 3600 --jobs 16 --out /tmp/texts                     # the Bun that runs this is the Bun under test
.. --flags ";--aot-validate;--aot-heat=everything-is-hot;--aot-heat=everything-is-cold"                      # each program is built with one of the sets, in turn
.. --stress 1,2,3,5,7,11        # a collection at every n-th allocation that leaves the fast path
.. --full-heap                  # what is parsed is kept until no more fits into a small heap, again and again
.. --workers                    # the program runs in Workers that are ended after a few milliseconds
.. --growth                     # texts that grow sixteenfold may take sixteen times as long, not their square
```

`<out>/findings/<seed>/` holds the program and what it printed. `./program --seed <seed> --seconds 20 --only T7 --trace` prints each text before it is asked.

## The builds that matter

A run has one Bun under test. One program against several builds of Bun at once is not among the options: start a run for each build, with `--bun <path>` and the same `--seed`.

| Form                             | What it is                                              | What only it has found                                                                            |
| -------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| as Bun ships                     | link-time optimization and the symbol order file        | registers that unwinding did not restore: whether that crashes depends on register allocation     |
| AddressSanitizer with assertions | `--profile=release-local --asan=true --assertions=true` | an assertion that had been false for two days, behind which an ordinary object lost its prototype |
| validated                        | any build, with `--validate`                            |                                                                                                   |
| release                          |                                                         |                                                                                                   |

A Bun that was built with `--asan=true` against a WebKit built beside it sees no allocation of WTF (strings, vectors, hash tables, objects from the fast allocator) unless `Malloc=1` is in
the environment of every process. `../a-matcher-asks-a-compiled-object-for-a-name-nothing-else-has.test.ts` once told the two apart: silent without it, a use after free with it.
